- Твоя задача — **доводить любую задачу до полного, готового к использованию результата**. Не «накидал и спросил», а «сделал, проверил, показал работающее».

- Видишь неоднозначность → выбираешь **наилучший вариант** под Юлдаш (см. эталоны: Яндекс Такси, inDrive, Uber, Maxim — но красивее) и реализуешь без колебаний.
- **Единственное исключение** — критическая угроза безопасности (утечка ключа в git) или явное разрушение проекта (снести рабочий экран, переписать `mobile/`): тогда **один короткий вопрос**, только если без него совсем нельзя.

**«Готово» в Юлдаше = всё сразу, иначе не готово:**
1. Любая надпись — **на двух языках** через `appText(ru, ba)`. Никогда односторонне. Черновой башкирский → в `docs/tasks.md` на проверку Александру.
2. UI в **едином стиле**: цвета `Canon*`, формы `CanonCardShape/CanonItemShape`. Новых сущностей не плодить.
3. **Анимации в коде** (Compose): плавные появления, нажатия, смена экранов/вкладок. Уровень iPhone — дорого, плавно, лаконично.
4. Новый экран → `enum Screen` + ветка в `when` внутри `YuldashApp()`.
5. Собралось: `gradlew :app:assembleDebug` зелёный (команда — в разделе 5).
6. **Второй мозг обновлён**: `architecture.md` / `decisions.md` / `lessons.md` / `tasks.md`.

**Автопилот-цикл каждой задачи:** прочитал мозг (`docs/`) → сделал целиком → собрал → обновил мозг → коротко отчитался Александру (вывод + что работает). Без пауз на «можно ли продолжать».

> Автономность ≠ «прячу что сделал». Для крупного/рискованного покажи **diff** — это **информировать**, не просить разрешения. Правила ниже (два языка, единый стиль, не помечать «готово» без сборки, не трогать `mobile/` и чужой код) остаются в силе — они и есть твой стандарт качества.

### Отчёт о сделанной работе — тоже «как школьнику»

Правило простого языка действует **не только в обычном разговоре**. Оно обязательно и в
**отчёте о проделанной работе**, и в **любом вопросе/уточнении** к Александру. Отчёт, который
он не понял, — это не отчёт.

- **Сначала — что это меняет для человека**, потом уже как сделано. Не «добавил `imePadding`»,
  а «кнопка «Подтвердить» пряталась за клавиатурой — теперь видна; в коде это `imePadding`».
- **Никаких имён файлов, функций и классов в начале фразы.** Они уместны в конце, как справка
  («это в `LoginScreen.kt`»), а не как объяснение.
- **Каждый технический термин — сразу расшифровка** простыми словами: контраст, тач-цель,
  миграция, токен, флаг, сборка. Если расшифровать не получается — значит, эту деталь Александру
  знать и не нужно, убери её.
- **Объясняй через ситуацию, а не через код:** «женщина с ребёнком не могла сверить номер
  машины в тёмной теме», а не «контраст пары CanonTaxiInk/CanonTaxiBg равнялся 1.05».
  Цифру можно оставить рядом — но после человеческого объяснения, а не вместо него.
- **Вопрос задавай так, чтобы на него можно было ответить, не зная кода.** Варианты — словами,
  с последствиями каждого («если так — быстрее, но релиз какое-то время несёт непроверенное»).
- **Не прячь плохие новости за терминами.** «Сборка сломана» лучше, чем «`compileDebugKotlin`
  завершился с ненулевым кодом».
- Длинный отчёт — таблицей или короткими пунктами. Сплошную стену текста Александр читать
  не должен.

## 4.5 🧩 Стандарты UI-качества (на каждом экране)

- **Все состояния, не только «успех»:** загрузка (скелетон/спиннер), пусто (дружелюбная заглушка + действие), ошибка / нет сети (понятный текст + кнопка «Повторить»). Всё — на двух языках.
- **Адаптив:** корректно на узких и широких экранах; челка/вырез и системные бары через `WindowInsets` (`systemBarsPadding()` / `safeDrawing`). Контент не лезет под статус-бар и навигацию. Длинный текст (башкирский часто длиннее русского) не ломает вёрстку.
- **Тёмная тема:** поддерживаем. Цвета — только из `Canon*` со светлым/тёмным вариантом; не хардкодь `Color(0xFF…)` в экранах. Нет dark-палитры — заведи в одном месте, не размазывай по экранам.
- **Доступность:** контраст текста ≥ 4.5:1, тач-цель ≥ 48dp, текст в `sp` (уважать системный размер шрифта), у иконок-кнопок — `contentDescription` на двух языках.
- **Плавность 60fps:** списки — `LazyColumn/LazyRow` с `key`; тяжёлое кешируй (`remember`), никаких лагов на прокрутке и анимациях.

## 6. 🧱 Принципы кода

- **Простота.** Минимум кода, минимум изменений. Трогай только то, что нужно для задачи.

## 12. 🧩 Оркестрация: несколько агентов одновременно

**Зачем:** ускорить — пустить агентов параллельно.
**Главная опасность — конфликты.** Весь UI Юлдаша в одном файле `MainActivity.kt`. Если два агента правят его разом, последний затирает правки первого (уже ловили вживую: файл «уехал» на 350 строк за минуту, сборка краснеет, эмулятор уходит в ANR).

### 🥇 Золотое правило
**Один файл — один агент в один момент.** Параллелить можно только то, что НЕ пересекается по файлам и общим ресурсам (эмулятор, сборка).

### A. Зоны ответственности (lanes)
Делим проект на непересекающиеся зоны. Один агент = одна зона → их файлы не пересекаются → конфликтов нет.

| Зона | Файлы | Можно параллельно? |
|---|---|---|
| 🎨 **UI** | `android/.../MainActivity.kt` | да, но **только ОДИН UI-агент** |
| 🔌 Backend | `backend/` | да |
| 🖼 Ресурсы | `android/.../res/`, иконки, ассеты | да |
| 🧠 Мозг | `docs/` | да, но **один писатель на файл** |
| ⚙️ Конфиг/сборка | `*.gradle.kts`, `AndroidManifest.xml`, `local.properties` | **ни с кем** (влияет на всех) |

→ UI-зону держит **один** агент. Backend / ресурсы / доки можно вести параллельно с UI — это разные файлы.

### B. Общие ресурсы — строго по очереди
- **Эмулятор один.** `install` / `launch` / `screencap` / `uiautomator` / тапы делает **только UI-агент**. Два агента на одном эмуляторе = ANR и мусорные касания.
- **Сборка одна.** `gradlew assembleDebug` пишет в общий `app/build/` → две сборки разом ломают друг друга. Собирает один агент за раз.

### C. Правильная изоляция — git worktree
По-настоящему без конфликтов — когда у каждого агента своя копия репозитория (worktree): правки не пересекаются, в конце сводим (merge).
- **Предусловие:** проект — git-репозиторий. ✓ Сделано: ветка `main`, первый коммит, `.gitignore` без секретов (`local.properties`, `*.jks`, backend `.env`/`.db`/`.venv`) и без QA-артефактов. Worktree-изоляция теперь доступна.
- Внутри одной сессии Claude Code: запускай субагентов с изоляцией `worktree` (инструменты Agent / Workflow). Каждый получает свою копию, лид сводит результат. Это **родной механизм Claude Code — предпочитай его «двум окнам вручную».**

### D. Если worktree пока нет (две сессии руками) — протокол «замок»
Минимум, чтобы не затирать:
1. В `docs/tasks.md` завести раздел **«🔒 Замки»**.
2. Перед работой агент пишет строку-замок: `🔒 MainActivity.kt — занят, <кто>, <время>`.
3. Другой агент видит замок → этот файл НЕ трогает, берёт свободную зону.
4. Закончил → снимает замок + пишет в «Ревью».
5. **Перед стартом всегда:** перечитать `tasks.md` (свежие замки) и перегрепнуть свой файл — если номера строк «уезжают», кто-то пишет параллельно, остановись.

### E. Роли
- **Лид (оркестратор):** режет задачу на непересекающиеся куски, раздаёт зоны, следит за замками, в конце сводит и собирает **один раз**. Сам в большой файл не лезет, пока заняты воркеры.
- **Воркеры:** строго своя зона, за границы не выходят, эмулятор не трогают без права, отчитываются лиду.

### F. Долгий план (чтобы параллелить стало легко)
`MainActivity.kt` слишком большой для параллели. Постепенно резать на файлы (`ui/screens/…`, `data/…`, `maps/…`) — тогда разные экраны = разные файлы = разные агенты без конфликтов. Резать по одному экрану за раз, не ломая сборку (см. §6).

### ⚡ Быстрый старт для Александра
Хочешь параллельно — давай каждой сессии **одну зону одной строкой**:
- Сессия 1: «только `MainActivity.kt` (UI), эмулятор твой».
- Сессия 2: «только `backend/`, эмулятор не трогай».
- Сессия 3: «только `docs/` и иконки».

Если зоны пересекаются хоть в одном файле — не запускай разом, делай по очереди.

### G. ruflo (MCP-оркестрация) — есть, но опционально, не «волшебная кнопка»
- Подключён MCP-сервер **`ruflo`** (`mcp__ruflo__*`): swarm, hive-mind, agent_spawn, память, code-analysis — 16 областей. Это тяжёлый фреймворк координации/консенсуса/общей памяти между агентами.
- **По умолчанию — НАТИВНЫЕ инструменты Claude Code, не ruflo:** `Agent` (сабагент, поддерживает `isolation: "worktree"`) и `Workflow` (детерминированный фан-аут). Они реально правят файлы и собирают. ruflo — слой поверх; для обычной работы по Юлдашу не нужен.
- **Когда вообще брать ruflo:** только если задача правда требует роя с консенсусом/общей памятью между многими агентами. Иначе — лишняя сложность.
- **ruflo НЕ отменяет золотое правило.** Рой из 10 агентов в одном `MainActivity.kt` всё равно затирает сам себя. Топология роя не меняет физику: один файл — один писатель.

### H. Как реально ускорить разработку (приоритет сверху вниз)
1. **Резать `MainActivity.kt` на модули** (`ui/screens/…`, `ui/components/…`) — это РАЗБЛОКИРУЕТ весь параллелизм (разные экраны → разные файлы → разные агенты). Один экран за раз, сборка зелёная после каждого (§6, §12.F). Это главный рычаг — всё остальное вторично.
2. Пока файл цельный — параллелить только непересекающиеся зоны (UI ↔ `backend/` ↔ `docs/` ↔ `res/`), каждую своему сабагенту с `isolation: "worktree"`.
3. Лид сводит (merge) и собирает/тестит **один раз** в конце — сборка и эмулятор общие, их нельзя делить.
4. Тяжёлый ресёрч/аудит (не правка файлов) — в фоновые сабагенты, чтобы основной контекст был чистым.
