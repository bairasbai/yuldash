## ГРАФ СТАТУСОВ ЗАКАЗА

`InstantOrderStatus` (`backend/app/models.py:644-655`):
`scheduled | created | searching | offered | accepted | arriving | onboard | done | cancelled | expired`

Таблица разрешённых переходов водителя — `backend/app/instant_service.py:47-59`
(`ALLOWED`, `TERMINAL`, `PASSENGER_CANCELLABLE`, `DRIVER_CANCELLABLE`).

### Нормальный поток

| Из | В | Кто | Где в коде |
|---|---|---|---|
| — | `created` | пассажир (`POST /instant/orders`) | `routers/instant.py:321-338` |
| — | `scheduled` | пассажир (`POST /instant/schedule`) | `routers/instant.py:387-403` |
| `scheduled` | `searching` | пассажир (`POST .../activate`, ленивая при `GET /instant/scheduled`) **или** воркер | `instant_service.py:990-1013`, `taxi_worker.py:58-78`, `routers/instant.py:412-445` |
| `created` | `searching` | сервер, сразу после создания | `instant_service.py:1016-1025` |
| `searching` | `offered` | matcher (сервер) | `instant_service.py:959-987` |
| `searching` | `expired` | matcher: нет Redis / нет кандидатов / `search_round ≥ instant_max_offers` | `instant_service.py:936-956` |
| `offered` | `accepted` | ТОЛЬКО `current_offer_driver_id`, оффер не протух, CAS `WHERE status=offered` | `instant_service.py:678-730`, `routers/instant.py:517-542` |
| `offered` | `searching` | отказ водителя / протухший оффер (ленивый `reconcile_offer` или воркер) | `instant_service.py:1028-1036`, `1039-1044`, `1047-1063`, `taxi_worker.py:214-240` |
| `accepted` | `arriving` | назначенный водитель (`POST .../arrived`) | `routers/instant.py:581-611` |
| `arriving` | `onboard` | назначенный водитель | `routers/instant.py:614-618` |
| `onboard` | `done` | назначенный водитель (+ начисление комиссии) | `routers/instant.py:621-634` |
| `scheduled/created/searching/offered/accepted/arriving` | `cancelled` | пассажир | `instant_service.py:733-783` (`PASSENGER_CANCELLABLE`) |
| `accepted/arriving/onboard` | `cancelled` | водитель (в т.ч. `reason=no_show`) | `instant_service.py:733-783` (`DRIVER_CANCELLABLE`) |
| `searching/offered/accepted/arriving/onboard` | `cancelled` (есть водитель) / `expired` (нет) | воркер, `order_stuck_hours=6` | `taxi_worker.py:82-128` |
| `expired`/`searching` (+`wait_until` в будущем) | `searching` | воркер, очередь «подожду» | `taxi_worker.py:132-172` |
| `expired`/`searching` (+`wait_until` истёк) | `expired` (окончательно) | воркер | `taxi_worker.py:175-210` |

### Что важно про граф

* `done` / `cancelled` выхода не имеют (в `ALLOWED` ключей `(done, …)`/`(cancelled, …)` нет).
* `expired` **терминален только на словах**: очередь «подожду» гоняет его обратно в `searching`
  (`taxi_worker.py:143`). Именно на этом висят дыры P1-1 и P1-2 ниже.
* Пропустить ступень нельзя: `ALLOWED` — строгая цепочка `offered→accepted→arriving→onboard→done`.
  «Завершить не начав» отбивается (проверено: `POST /done` на `accepted` → 409).
* Пассажир двигать статусы не может вообще: `transition()` зовётся только с `Actor.driver`,
  а в `ALLOWED` нет ни одного ключа с `Actor.passenger`.
* Права на каждый переход: `accept` — `_guard_actor` (`instant_service.py:666-675`) требует
  `current_offer_driver_id == user.id` и непротухший оффер; остальные — `_guard_owns`
  (`instant_service.py:658-663`) требует `driver_id == user.id` / `passenger_id == user.id`.

## ПОДТВЕРЖДЁННЫЕ ДЫРЫ

### [P0] `/instant/orders/{id}/arrived` — оракул точки подачи чужого заказа

- **Файл:строка**: `backend/app/routers/instant.py:581-610` (гео-проверка на 592-609,
  проверка владельца — только внутри `transition` на 610)
- **Что не так**: гео-проверка «ты на месте?» выполняется **до** проверки, что заказ вообще
  твой. Ответ отличается в зависимости от того, попал ли атакующий в радиус 500 м от точки
  подачи. Получается работающий оракул: любой залогиненный пользователь перебором координат
  находит адрес подачи ЛЮБОГО заказа с точностью до 500 м. Точка подачи такси = как правило
  дом человека. Это ровно то, что CLAUDE.md §8 запрещает.
- **Сценарий поломки**:
  1. Атакующий регистрируется обычным способом (телефон), берёт токен.
  2. Перебирает `order_id` (последовательные int) и шлёт `POST /instant/orders/{id}/arrived`
     с сеткой координат по району.
  3. Далеко → `409 «Ты ещё не на месте подачи…»`. Близко → `403 «Ты не водитель этого заказа»`
     (если заказ принят) либо `409 «Нельзя перейти searching→arriving»` (если ещё ищется).
     Тексты РАЗНЫЕ → сигнал однозначный.
  4. Бинарный поиск / сетка 500 м по посёлку → адрес подачи. Лимит 300 запросов/мин на IP
     (`config.py:404`) этому не мешает.
- **Доказательство** (реальный прогон, `verify_oracle.py`, заказ пассажира в Баймаке):
  ```
  Уфа (300 км)          -> HTTP 409 · Ты ещё не на месте подачи — ожидание начнётся, когда подъе…
  Сибай (25 км)         -> HTTP 409 · Ты ещё не на месте подачи — …
  Баймак центр (~1 км)  -> HTTP 409 · Ты ещё не на месте подачи — …
  в 300 м от подачи     -> HTTP 403 · Ты не водитель этого заказа
  ```
  Работает и на заказе БЕЗ водителя (`searching`): далеко → 409 «не на месте»,
  близко → 409 «Нельзя перейти searching→arriving».
  Для сравнения, `/receipt` и `/onboard` посторонним отдают 403/409 сразу, без утечки.
  Код:
  ```python
  order = session.get(InstantOrder, order_id)
  if not order:
      raise herr(404, "Заказ не найден", "Заказ табылманы")
  # ... ни одной проверки прав ...
  if lat is not None and lng is not None and order.from_lat and order.from_lng:
      if haversine_km(lat, lng, order.from_lat, order.from_lng) > _ARRIVED_RADIUS_KM:
          raise herr(409, "Ты ещё не на месте подачи — ...")
  order = isv.transition(session, order_id, isv.Actor.driver, S.arriving, user.id)  # тут наконец права
  ```
- **Как чинить**: поднять проверку владельца в начало ручки —
  `if order.driver_id != user.id: raise herr(403, ...)` сразу после `if not order`.
  Тогда посторонний получает 403 при любых координатах.

### [P1] Заказ в очереди «подожду машину» отменить НЕВОЗМОЖНО — водителя всё равно пришлют

- **Файл:строка**: `backend/app/instant_service.py:748-749` (ранний выход `cancel_order`),
  `backend/app/routers/instant.py:684-708` (`/wait` не трогает статус),
  `backend/app/taxi_worker.py:132-172` (`retry_waiting_orders`)
- **Что не так**: «подожду машину» оставляет заказ в статусе `expired` и просто ставит
  `wait_until`. `cancel_order` считает `expired` терминальным и **молча возвращает заказ как
  есть, отдавая HTTP 200**. `wait_until` при этом не очищается ни здесь, ни где-либо ещё.
  Воркер продолжает искать и назначает водителя человеку, который нажал «Отмена» и получил «ок».
- **Сценарий поломки**:
  1. Ночь в райцентре, машин нет → заказ `expired`, пассажир жмёт «Подожду машину».
  2. Через 3 минуты передумал → жмёт отмену. Сервер: **200 OK**, статус в ответе `expired`.
  3. Ещё через 2 минуты воркер находит освободившегося водителя → `offered` → водитель едет.
  4. Человека нет на месте. Водитель ждёт, жмёт «пассажир не вышел» → пассажиру страйк и
     пауза такси на 24 ч (`instant_service.py:635-645`), водителю — пустой пробег.
- **Доказательство** (`verify_http.py`, реальные HTTP-вызовы):
  ```
  /wait   -> 200 wait_until: 2026-08-07T09:45:29
  /cancel -> 200 СТАТУС ПОСЛЕ ОТМЕНЫ: expired  wait_until: 2026-08-07T09:45:29   ← не изменилось
  воркер перезапустил: [1] → ИТОГОВЫЙ СТАТУС: offered  водителю предложено: 2
  ```
  Код `cancel_order`:
  ```python
  if order.status in TERMINAL:
      return order   # уже терминальный — idempotent
  ```
  `TERMINAL = (S.done, S.cancelled, S.expired)` — `instant_service.py:47`.
- **Как чинить**: в `cancel_order` до раннего выхода обработать случай
  `status == expired and wait_until is not None` — снять `wait_until` и перевести в `cancelled`
  (или как минимум снять `wait_until` и вернуть честный ответ). Плюс очищать `wait_until` в
  любой отмене/завершении. Ещё лучше — не держать очередь в `expired`, а завести отдельный
  статус (или оставлять `searching` с `wait_until`), тогда терминальность снова станет честной.

### [P1] «Заказать заново» из очереди ожидания даёт ДВА живых заказа и двух водителей на одного человека

- **Файл:строка**: `backend/app/routers/instant.py:308-315` (проверка «уже есть активный»
  не включает `expired`), `backend/app/taxi_worker.py:132-172`,
  клиент — `android/.../InstantOrderScreen.kt:930` (`onRetry = { order = null }` — на сервер
  ничего не шлёт)
- **Что не так**: анти-дубль на создании заказа смотрит статусы
  `created/searching/offered/accepted/arriving/onboard`. Заказ в очереди «подожду» лежит в
  `expired` и в этот список не попадает. Кнопка «Заказать заново» в UI просто обнуляет экран,
  старый заказ остаётся в очереди у воркера. Итог — два параллельных заказа одного пассажира,
  и матчер назначает на них ДВУХ РАЗНЫХ водителей.
- **Сценарий поломки**:
  1. Машин нет → заказ A `expired` → «Подожду машину» (`wait_until` +20 мин).
  2. Человек не дожидается, жмёт «Заказать заново» → создаётся заказ B (сервер не видит A).
  3. Освобождаются два водителя. Воркер/матчер назначают одного на A, другого на B.
  4. К подъезду приезжают две машины. Одну человек берёт, вторая либо отменяет принятый заказ
     (водителю копится страйк, `driver_cancel_times`, `instant_service.py:595-613` → пауза
     офферов), либо жмёт «пассажир не вышел» (страйк пассажиру + пауза такси на 24 ч).
     Наказаны обе невиновные стороны.
- **Доказательство** (`verify_dup.py`):
  ```
  заказ A: 1 expired
  A поставлен в очередь до 2026-08-07T09:50:32
  заказ B: 2 expired — тот же заказ? False
    заказ #1: status=offered offer_to=2
    заказ #2: status=offered offer_to=3
  ИТОГ: у одного пассажира одновременно живых заказов: 2
  ```
- **Как чинить**: добавить в проверку `existing` условие «`status == expired` И
  `wait_until > now`» (заказ в очереди — живой), либо при создании нового заказа гасить
  очередь старого (`wait_until = None`). Оба варианта одной строкой.

### [P1] `start_matching` / `advance_after_no_accept` пишут статус БЕЗ CAS — воскрешают отменённые и завершённые заказы

- **Файл:строка**: `backend/app/instant_service.py:1019-1022` (`start_matching`),
  `backend/app/instant_service.py:1030-1033` (`advance_after_no_accept`)
- **Что не так**: весь остальной файл двигает статус атомарно
  (`UPDATE … WHERE id=? AND status=<ожидаемый>` — `transition`, `cancel_order`). Эти две
  функции делают безусловный `UPDATE … WHERE id=?`. Их зовут фоновые задачи, которые сначала
  выбирают ПАЧКУ до 200-500 строк, а потом обрабатывают их по одной (Redis geosearch + пуш на
  каждую) — окно между выборкой и записью измеряется секундами. Всё, что успело стать
  `cancelled`/`accepted`/`done` за это время, откатывается назад в `searching`.
- **Сценарий поломки**:
  1. Воркер (`taxi_worker.py:221-227`, `advance_stale_offers`) выбирает пачку протухших офферов.
  2. Пока он обрабатывает первые строки пачки, пассажир заказа #57 нажимает «Отмена» → `cancelled`,
     пуш водителю «заказ отменён», промокод возвращён.
  3. Очередь доходит до #57 → безусловный UPDATE → статус снова `searching` → матчер шлёт оффер
     новому водителю. Водитель едет к человеку, который отменил заказ.
  То же самое через `retry_waiting_orders` (`taxi_worker.py:156`) и через ленивый
  `reconcile_offer` при обычном `GET /instant/orders/{id}` (`routers/instant.py:512`).
- **Доказательство** (`verify_zombie.py`, оба случая реально воспроизведены):
  ```
  B. пачка advance_stale_offers: [(2, 'offered')]
     после отмены пассажиром: cancelled
     ПОСЛЕ advance_after_no_accept: expired      ← отменённый заказ переписан
  C. заказ вручную доведён до: done
     ПОСЛЕ advance_after_no_accept: expired      ← ЗАВЕРШЁННЫЙ заказ переписан
  ```
  (в тесте нет свободных водителей, поэтому итог `expired`; с водителем рядом это `offered`)
  Код:
  ```python
  def advance_after_no_accept(session, order, notify=True):
      session.execute(
          update(InstantOrder).where(InstantOrder.id == order.id)     # ← нет AND status = ...
          .values(status=S.searching, current_offer_driver_id=None, offer_expires_at=None)
      )
  ```
  Ср. `finish_expired_waits` (`taxi_worker.py:191-195`) и `close_stuck_orders`
  (`taxi_worker.py:102-106`) — там перечитывание под `with_for_update()` и повторная проверка
  статуса есть. То есть авторы знали про этот паттерн, но в двух местах его пропустили.
- **Побочный эффект на деньги**: у воскрешённого `done`-заказа `CommissionDebt` уже начислен
  (`debt.py:308`), и обратно он не снимается — заказ может уйти в `cancelled`, а долг останется.
- **Как чинить**: добавить условие статуса в оба UPDATE и проверять `rowcount`:
  `.where(InstantOrder.id == order.id, InstantOrder.status.in_((S.offered,)))` для
  `advance_after_no_accept` и `.in_((S.created, S.expired, S.searching, S.scheduled))`
  для `start_matching`; `rowcount == 0` → выйти, ничего не делая.

### [P1] Гео-проверка «Я на месте» в проде НЕ РАБОТАЕТ (опечатка в ключе Redis + клиент не шлёт координаты)

- **Файл:строка**: `backend/app/routers/instant.py:600` — `livepos.livepos_get("instant", order_id)`;
  пишет позицию `backend/app/routers/location.py:223` — `livepos_set("order", order_id, …)`;
  клиент `android/.../data/ApiClient.kt:2307` — `call("POST", "/instant/orders/$id/arrived", JSONObject(), …)`
- **Что не так**: проверку добавляли специально, чтобы водитель не мог нажать «Я на месте»
  из дома (с этой кнопки идёт платное ожидание, а через 8 минут открывается «пассажир не
  вышел» со штрафом и страйком). На деле она не срабатывает никогда:
  * Android шлёт **пустое тело** — `lat`/`lng` всегда `None`;
  * фолбэк читает из Redis ключ `livepos:instant:{id}`, а WS-трек пишет `livepos:order:{id}` —
    ключи разные, значение всегда `None`;
  * оба `None` → проверка пропускается, `transition` в `arriving` проходит откуда угодно.
- **Сценарий поломки**: недобросовестный водитель принимает заказ, не выезжая, жмёт
  «Я на месте» → у пассажира тикает платное ожидание (`wait_fee_rub_per_min` после
  `wait_free_minutes=5`) → через `5+3` минуты водитель жмёт «пассажир не вышел» → пассажиру
  фиксируется штраф-подача, страйк, и после 3 таких — пауза такси на 24 часа. Человек при
  этом стоял у подъезда.
- **Доказательство**:
  ```
  ключ записи (location.py): livepos:order:42
  ключ чтения (/arrived)   : livepos:instant:42
  ```
  Тест `backend/tests/test_taxi_gaps.py:95` (`test_arrived_without_coords_still_works`)
  проверяет только, что без координат ручка отвечает 200 — фолбэк не покрыт ничем.
  Тест `test_arrived_rejects_faraway_driver` (строка 82) передаёт координаты в теле явно,
  поэтому опечатку не ловит.
- **Как чинить**: (1) поправить ключ на `"order"`; (2) научить Android класть последнюю
  известную позицию в тело `arrived` (у него она есть — он же шлёт её в WS-трек).
  Пока не сделано (2), фикс (1) закрывает случай «WS-трек включён», а это основной живой сценарий.

### [P2] Заказ, застрявший в `created`, не закрывает никто — и навсегда блокирует пассажиру такси

- **Файл:строка**: `backend/app/taxi_worker.py:48` (`_ALIVE` без `S.created`),
  `backend/app/routers/instant.py:308-315`
- **Что не так**: воркер закрывает зависшие заказы только в статусах
  `searching/offered/accepted/arriving/onboard`. Статус `created` живёт ровно между `INSERT`
  и `start_matching` в `create_order` (`routers/instant.py:337-345`) — но если между ними
  что-то упало (исключение в `promo_ride.consume` / `_cache_client()` / обрыв запроса),
  заказ остаётся в `created` навсегда. А `create_order` считает `created` активным и на каждый
  новый заказ возвращает этот мёртвый.
- **Сценарий поломки**: у пассажира один раз сорвалось создание заказа → он больше НИКОГДА
  не может вызвать такси: каждый «Заказать» возвращает тот же зависший заказ. Спасает только
  ручная отмена (она разрешена: `created ∈ PASSENGER_CANCELLABLE`), если клиент вообще
  показывает кнопку отмены в этом состоянии.
- **Доказательство** (`verify_http.py`, заказ в `created` возрастом 30 дней):
  ```
  run_once: {}                                   ← воркер его не увидел
  статус зависшего в created через 30 дней: created
  новый заказ этого пассажира -> 200 вернулся id: 2  ← вернулся тот самый зависший
  ```
- **Как чинить**: добавить `S.created` в `_ALIVE` (и, для полноты, продумать протухание
  `S.scheduled` — его тоже не закрывает никто, если воркер выключен).

### [P2] `search_round` не сбрасывается — очередь «подожду 20 минут» умирает после 8 офферов, молча

- **Файл:строка**: `backend/app/instant_service.py:964-965` (`search_round >= instant_max_offers`),
  `backend/app/instant_service.py:1016-1025` (`start_matching` счётчик не трогает)
- **Что не так**: `instant_max_offers = 8` (`config.py:300`) — предохранитель на число офферов
  по заказу. Счётчик растёт при каждом оффере и **никогда не обнуляется**, в том числе при

  пассажир нажал «Подожду». Воркер каждые 2 минуты перезапускает поиск, водители отказываются

  после перезапуска: статус = expired | предложено водителю = None | search_round = 8

  отдельный потолок ретраев (`retry_count` уже есть и не используется как ограничитель).

### [P2] Онлайн-оплата после отметки «получил наличные» забирает деньги у пассажира и никому их не отдаёт

## ПРОВЕРЕНО И ЧИСТО

* **Гонка двух accept на один заказ.** Row-lock + условный `UPDATE … WHERE status=offered`,
  `idempotent=False` (`instant_service.py:678-730`). Принять может только
  `current_offer_driver_id`, протухший оффер отбивается 409. Покрыто тестами
  `test_instant.py:265` и `test_instant.py:277` (в т.ч. настоящими потоками).
* **Двойное «завершить».** Комиссия не задваивается: `accrue_for_order` проверяет существующий
  долг и опирается на `UniqueConstraint("order_id")` (`models.py:946`, `debt.py:308-354`),
  `IntegrityError` ловится. Тест `test_stale_screen_taxi.py:77`.
* **Комиссия после отмены.** Долг начисляется только на переходе `onboard→done`, а из `done`
  штатных выходов нет (`cancel_order` возвращает терминальный заказ как есть). Онлайн-оплата
  гасит долг Модели А (`ledger.py:271` → `debt.void_debt_for_order`) — двойной комиссии нет.
  Ставка комиссии фиксируется на `created_at` одинаково в оффере, витрине и долге
  (`debt.py:324`, `ledger.py:260`, `instant_service.py:1096`) — обойти через границу тарифной
  ступени нельзя.
* **Клиент не диктует цену.** В `EstimateIn`/`OrderIn` полей цены нет намеренно
  (`routers/instant.py:85`), сервер считает сам, суммарный коэффициент ограничен
  `surge_max_k` (`instant_service.py:410-417`).
* **Двойная отмена.** `cancel_order` идемпотентна (ранний выход на терминальном статусе) +
  условный UPDATE, `rowcount == 0` → 409. Отмена ровно в момент принятия сериализуется
  row-lock'ом на строке заказа.
* **Пропуск ступеней.** `ALLOWED` — строгая цепочка; «завершить не начав», «сесть до приезда»,
  «отменить принятый заказ пассажиром после посадки» — всё отбивается 409 (тесты
  `test_instant.py:240/255`, `test_stale_screen_taxi.py:119`).
* **Гейт водителя на приёме заказа.** `_guard_taxi_driver` стоит на `POST .../accept`
  (`routers/instant.py:524`) и на `presence`: флаг/город такси, `ensure_active` (пауза
  «Справедливости»), approved-заявка, долг по комиссии, `guard_pretrip` (580-ФЗ, на сегодня),
  `guard_taxi_rested` (8 ч/день + 56 ч/неделю), `guard_taxi_quality`. Проверка стоит именно
  на сервере, а не только на экране. Активные заказы (`arrived/onboard/done`) намеренно
  через гейт не ходят — так и задумано.
* **`eligible()` не проверяет approved-заявку**, но это не дыра: попасть в Redis-presence можно
  только пройдя `_guard_taxi_driver`, а финальный барьер стоит на `accept`. Максимум — оффер,
  который отобьётся 403.
* **Приватность до accept.** Телефоны/имя/машина/госномер закрыты, точка подачи водителю
  округляется до ~1 км (`instant_service.py:1263-1265`). WS-трек `/ws/instant/{id}/location`
  пускает только пассажира и НАЗНАЧЕННОГО водителя и только в `accepted/arriving/onboard`,
  с перепроверкой раз в 15 кадров (`routers/location.py:173-217`). Тест
  `test_instant.py:358`. (Единственный обход — оракул P0 выше.)
* **Воркер без Redis.** `_expire_no_drivers` отрабатывает мягко, запрос не падает
  (`test_instant.py:391`). Но: **без Redis такси не работает вообще** — presence живёт только
  в Redis, значит каждый заказ мгновенно уходит в `expired`. Это осознанная деградация, а не баг.
* **Воркер реально запущен на проде**: `deploy/yuldash-taxi-worker.timer` — `OnCalendar=*:0/1`
  (раз в минуту), `taxi_worker_enabled=true` по умолчанию.
* **Предзаказы (вопрос 6).** Время прошло → активирует воркер (`activate_due_scheduled`,
  раз в минуту) либо ленивая активация на `GET /instant/scheduled`. Никто не взял → обычный
  `expired` + пуш «рядом никого». Цена и сурж пересчитываются на момент активации, промо
  ужимается вниз (`promo_ride.reclamp`) — обойти потолок кампании через предзаказ нельзя.
  Предзаказ не блокирует создание обычного заказа (в `existing` его нет) — это корректно.
* **Торг о цене (вопрос 7) в режиме ТАКСИ отсутствует** — цена фиксированная, считает сервер.
  Торг живёт только у попуток (`routers/requests.py:504-783`, это чужой срез). Бегло проверил
  там: ходы чередуются (`last_offer_by`), свою же цену принять нельзя (`requests.py:779-781`),
  лимит ходов есть, гонка двух accept закрыта `with_for_update()` на `RideRequest`
  (`requests.py:713-719`) — два водителя не создадут две брони. Единственная мелочь: у
  встречной цены нет нижнего порога (`CounterIn.price: ge=0`), можно предложить 0 ₽.
* **Приватность справочника клиник** (`routers/medical.py`): список поездок к клинике требует
  входа, публичен только справочник — сделано осознанно и правильно.
* **`driver_schedule.py`, `pickup.py`** — дыр не нашёл (владелец проверяется, валидация дней/
  времени строгая, публичная витрина без персональных данных).

## НЕ ДОКАЗАНО

* **Обход комиссии через «не жать done».** Водитель, который довёз человека и не завершил
  заказ, комиссию не платит: через `order_stuck_hours=6` воркер закроет заказ как `cancelled`
  и денег не тронет (`taxi_worker.py:82-128`, прямо так и написано в докстринге). Это осознанное
  решение Модели А «на доверии», а не баг, — но экономически это открытая дверь, и стоит
  хотя бы считать метрику «принял → не завершил» рядом с `contact_then_cancel`.
* **Гонка `reconcile_offer` при обычном поллинге** (тот же корень, что P1-4, но через HTTP,
  а не через воркер): доказал только на уровне сервисных функций, живой HTTP-race с двух
  клиентов не воспроизводил. Ширина окна — время коммита `cancel_order`.
* **Сколько заказов реально висит в `created` на проде** — не проверял (в прод не ходил).
  Механика подтверждена, частота неизвестна.
* **Доставка пуша об оффере на реальном устройстве** — вне возможностей этого прогона.
* **`_order_base_fee_kop` берёт `Tariff.base` в момент отмены**, а не зафиксированный при
  создании (`instant_service.py:541-544`). Если админ поправит тариф в БД, штрафы по старым
  заказам поедут. Реальность сценария не проверял — тарифы правятся руками и редко.
* **Поведение на Postgres.** Всё воспроизводил на SQLite (как и штатные тесты). CAS-логика от
  этого не зависит (проигравший гонку получает `rowcount 0` на обеих БД), но окна гонок на
  Postgres с `FOR UPDATE` могут отличаться по ширине.
