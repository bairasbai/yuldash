## ГРАФ СТАТУСОВ ДОСТАВКИ

Поле `ParcelDelivery.status` (`models.py:1384`), значения:
`created | accepted | in_transit | delivered | canceled | returning | returned`.

```
                    POST /parcels            (parcels.py:529)
                    POST /courier/orders     (courier.py:854)
                              │
                              ▼
        ┌──────────────── created ─────────────────────────────┐
        │                     │                                │
        │  accept             │  cancel (отправитель) 638      │  ночная чистка >30д
        │  parcels.py:777     │  admin cancel 1265             │  cleanup.py:361
        │                     │  admin close 1339              │  → canceled
        ▼                     ▼                                ▼
    accepted ──────────► in_transit ────────────► delivered  (terminal*)
        │  status:819        │   status:836 (+code)
        │                    │   attempt-failed 998 (счётчик, статус НЕ меняется)
        │                    │
        │   release 920 ─────┤   release 920  ⚠ ДЫРА №2 (коробка уже у курьера)
        │   admin release    │   admin release 1289
        │   worker 298       │   → обратно в created
        │                    │
        │   worker 304 ──────┤   → canceled  (in_transit, 72ч без движения)
        │                    │
        └── return-start ────┴──► returning ──► returned  (terminal*)
                 1035                 │  1071
                 │                    │
                 │                    ⚠ ДЫРА №6b: returning → delivered (status:836)
                 │                    ⚠ ДЫРА №11: у returning НЕТ авто-выхода
                 ▼
        ⚠ ДЫРА №6a: accepted → delivered напрямую, минуя in_transit

  ⚠ ДЫРА №1:  returned ──(status:836 + code)──► delivered   (закрытая доставка воскресает)
  admin close (1339) может перевести ЛЮБОЙ статус в любой из delivered|canceled|returned,
  включая уже финальный (проверки «уже закрыто» нет) — это осознанная админ-власть.
```

`* terminal` — с оговоркой: `delivered` и `returned` **не терминальны** из-за дыры №1
(`parcels.py:813` знает только `("delivered", "canceled")`, хотя рядом в файле лежит корректный
`_FINAL_STATUSES = ("delivered", "canceled", "returned")` — `parcels.py:65`).

Кто имеет право двигать:
| переход | кто | чем проверено |
|---|---|---|
| → accepted | любой авторизованный (poputka) / одобренный курьер (courier, buy_bring) | `parcels.py:748,750,757,765,771-776` |
| accepted→in_transit→delivered | только `courier_id == me` | `parcels.py:808` (иначе 404) |
| release / return-start / return-done / attempt-failed | только `courier_id == me` | `parcels.py:900,1031,1065,992` |
| cancel | только `sender_id == me` | `parcels.py:619` |
| goods-cost | только `courier_id == me` | `courier.py:892` |
| admin cancel/close/release-courier | `role == admin` | `parcels.py:1175` |

## ПОДТВЕРЖДЁННЫЕ ДЫРЫ

### [P1] №1. `returned → delivered`: закрытая возвратом доставка «воскресает», комиссия списывается как оплаченная
- **Файл:строка** — `backend/app/routers/parcels.py:813` (проверка финала), `:836` (переход),
  `:1073-1074` (что делает return-done), `backend/app/routers/courier.py:276-289` (finalize).
- **Что не так** — гвард в `parcel_status` перечисляет только два финальных статуса из трёх.
  `returned` через него проходит. А `return-done` перед этим уже поставил
  `commission_kop = 0; commission_paid = True` — и `commission_paid` при «воскрешении» никто не
  сбрасывает, тогда как `finalize_commission_kop` заново проставляет полную комиссию.
- **Сценарий поломки** — курьер не застал получателя, привёз коробку обратно отправителю, нажал
  «вернул» (заказ закрыт, комиссию мы честно не берём). Через час он жмёт «доставлено» и вводит
  код, который отправитель когда-то диктовал получателю (или просто просит код у отправителя
  «для отчёта»). Итог: заказ снова `delivered`, курьеру +1 доставка и +заработок в
  `/courier/earnings`, платформе начислено 225 ₽ комиссии **и сразу помечено «оплачено»**.
  В отчёте админа эти 225 ₽ попадают в `collected_fee_kop` — строку «деньги дошли». Это ровно
  тот класс выдуманной выручки, который убирал аудит 2026-07-26. Отправитель, у которого посылка
  уже дома, получает пуш «Посылка доставлена ✅».
- **Доказательство** (прогон):
  ```
  RETURNED->DELIVERED: 200 delivered
  после воскрешения: status= delivered commission_kop= 22502 commission_paid= True
                     returned_at= 2026-08-07 09:25:36
  кабинет курьера: {'delivered_count': 1, 'commission_earned_kop': 22502,
                    'commission_owed_kop': 0, 'commission_paid_kop': 22502, ...}
  ```
  Код:
  ```python
  # parcels.py:813
  if parcel.status in ("delivered", "canceled"):
      raise herr(409, "Посылка уже завершена", ...)
  # parcels.py:65 — правильный список лежит тут же и не используется
  _FINAL_STATUSES = ("delivered", "canceled", "returned")
  ```
- **Как чинить** — в `parcel_status` сверяться с `_FINAL_STATUSES` (одна константа на файл), и в
  ту же ветку добавить `returning`: из «везу обратно» в «вручил» переход должен идти через явную
  отмену возврата, а не молча. Отдельно — сбрасывать `commission_paid = False` везде, где
  `commission_kop` пересчитывается вверх.

### [P1] №2. Курьер снимается с заказа, физически увезя посылку; след «кто вёз» стирается
- **Файл:строка** — `backend/app/routers/parcels.py:63` (`_COURIER_HOLDS`), `:902` (гвард release),
  `:920-921` (`courier_id = None; status = "created"`).
- **Что не так** — снятие разрешено из `in_transit`, то есть после того, как курьер забрал
  коробку. Заявка возвращается в открытую ленту, `courier_id` обнуляется. Ровно этот случай
  фоновый воркер обрабатывает по-другому и объясняет почему:
  ```python
  # taxi_worker.py:267-269
  # • `in_transit` (коробка уехала с ним) → возвращать в список нечего, закрываем разбор
  #   как «отменена»... courier_id НЕ обнуляем: след «кто вёз» — единственное, по чему
  #   потом можно открыть спор и найти посылку.
  ```
  Ручной эндпоинт делает прямо противоположное.
- **Сценарий поломки** — курьер забрал лекарство у бабушки, отъехал, передумал, нажал «не смогу
  везти». Лекарство у него в машине. Заявка снова в ленте, её берёт другой курьер и едет по
  адресу отправителя за посылкой, которой там нет. Отправитель не может открыть спор:
  `parcel_dispute` требует назначенного курьера и отвечает 409 «Курьер ещё не назначен — спорить
  не с кем» (`parcels.py:1148-1151`). Чат тоже закрыт: статус `created` не входит в
  `PARCEL_CHAT_READABLE` (`chat.py:51-53`) — переписка с тем, у кого коробка, недоступна обеим
  сторонам. Единственный след — запись в Центре уведомлений типа `courier_release`.
- **Доказательство** (прогон):
  ```
  release из in_transit: 200 created courier_id= None
  в открытой ленте: True | return_reason наружу: сломался
  бывший курьер-1 читает чат: 403
  ```
- **Как чинить** — из `in_transit` разрешать только `return-start` (везу обратно) или спор.
  Если снятие из `in_transit` всё-таки нужно — не обнулять `courier_id`, не возвращать в ленту,
  а переводить в отдельное «посылка у курьера, разбор» с уведомлением админа.

### [P1] №3. Новый курьер читает всю переписку отправителя с прежним курьером
- **Файл:строка** — `backend/app/routers/chat.py:571-580` (выборка), `:148` (проверка доступа).
- **Что не так** — доступ к чату даётся по **текущему** `courier_id`, а сообщения выбираются по
  `parcel_id` без отсечки по времени/курьеру:
  ```python
  # chat.py:148
  is_courier = parcel.courier_id is not None and user_id == parcel.courier_id
  # chat.py:579
  select(Message).where(Message.parcel_id == parcel_id).order_by(Message.id.desc()).limit(limit)
  ```
- **Сценарий поломки** — отправитель пишет курьеру №1 то, чего нет ни в одном поле формы: номер
  квартиры, где лежит ключ, что получатель — пожилая женщина, живёт одна, приходить после шести.
  Курьер №1 снимается (или его снимает админ / воркер). Курьер №2 берёт заявку и одним запросом
  получает всю эту переписку. Это шире, чем то, что мы вообще собирались отдавать курьеру.
- **Доказательство** (прогон): курьер-2 получил `200` и текст `«Код скажу лично, дом 5 кв 3,
  соседка Гульнара»`, написанный до его появления; бывший курьер-1 при этом получил `403`.
- **Как чинить** — отдавать сообщения с `Message.created_at >= parcel.accepted_at` для роли
  курьера (у отправителя история остаётся полной), либо привязать сообщения к «сессии курьера».

### [P2] №5. Комиссия курьера считается в отчёте админа дважды
- **Файл:строка** — `backend/app/routers/courier.py:288`, `backend/app/routers/parcels.py:1219-1222`.
- **Что не так** — при вручении финализатор пишет комиссию в ДВА поля:
  ```python
  # courier.py:287-288
  parcel.commission_kop = commission
  parcel.fee_kop = commission           # fee_kop = доход платформы (statement в /admin/parcels)
  ```
  а строка `unbilled_fee_kop` суммирует `fee_kop` по всем доставленным без фильтра по типу:
  ```python
  # parcels.py:1219-1221
  unbilled = session.exec(select(func.coalesce(func.sum(ParcelDelivery.fee_kop), 0))
      .where(ParcelDelivery.status == "delivered")).one()
  ```
  Хотя докстрока обещает: «unbilled_fee_kop — сбор по «по пути»: начислен тарифом, но никому не
  выставлен».
- **Сценарий поломки** — одна и та же комиссия курьера попадает и в `owed_commission_kop`
  («начислено, ждём»), и в `unbilled_fee_kop` («выставить некому»). Александр смотрит отчёт и
  видит вдвое больше денег, чем есть. Существующий тест не ловит, потому что строит строки в БД
  руками, а не проходит реальный путь заказ → вручение.
- **Доказательство** (прогон, честный путь через API):
  ```
  commission_kop= 22502 fee_kop= 22502 type= courier
  delta owed: 22502   delta unbilled: 22502
  ```
- **Как чинить** — в запросе `unbilled` добавить `ParcelDelivery.delivery_type == "poputka"`
  (или `.notin_(_BILLABLE_TYPES)`). Заодно решить, нужно ли вообще дублировать комиссию в
  `fee_kop` — два имени у одной суммы и породили расхождение.

### [P2] №6. «Доставлено» в обход «забрал» (и из «везу обратно»)
- **Файл:строка** — `backend/app/routers/parcels.py:816` (in_transit требует accepted), `:827`
  (ветка delivered не требует ничего).
- **Что не так** — переход в `in_transit` проверяет предыдущий статус, переход в `delivered` — нет.
- **Сценарий поломки** — (а) `accepted → delivered`: курьер закрывает доставку, ни разу не отметив
  «забрал». Фото «взял целой» снимается именно на переходе `accepted → in_transit`
  (`parcels.py:820-826`), значит первой границы ответственности не существует, и спор «оно уже
  было битым» опирается только на слово. (б) `returning → delivered`: курьер, объявивший возврат,
  всё равно закрывает заказ как вручённый — статус `returning` в ветке delivered не проверяется.
- **Доказательство** (прогон): `ACCEPTED->DELIVERED: 200`, `RETURNING->DELIVERED: 200`.
- **Как чинить** — в ветке `delivered` требовать `parcel.status == "in_transit"` (а для
  «вручил после начатого возврата» завести явную отмену возврата `returning → in_transit`).

### [P2] №7. Стоимость покупки можно вписать в закрытый возвратом заказ

### [P2] №8. Одна копейка «за товар» сразу после принятия запирает и отправителя, и курьера
- **Файл:строка** — `backend/app/routers/courier.py:898-904` (нет ни нижней границы смысла, ни
  проверки, что курьер вообще доехал), `backend/app/routers/parcels.py:631-634` (запрет отмены),
  `:914-917` (запрет снятия).
- **Что не так** — `goods_actual_kop > 0` работает как необратимый замок на заказе, а поставить
  его можно в ту же секунду, что и принять заказ.
- **Сценарий поломки** — курьер берёт «купи и привези» и сразу отправляет `actual_kop = 1`.
  С этого момента отправитель не может отменить («Курьер уже купил товар — отмена только через
  спор»), а курьер не может сняться. Выход — только спор или админ. Для недобросовестного курьера
  это способ держать заказ; для добросовестного, случайно нажавшего, — тупик на ровном месте.
- **Доказательство** (прогон):
  ```
  goods-cost сразу после accept: 200
  cancel отправителем: 409 | release курьером: 409
  ```
- **Как чинить** — принимать фактическую стоимость только из `in_transit` (курьер физически
  съездил), и/или ввести окно отмены ввода самим курьером до перехода «еду вручать».

### [P2] №9. Админ снимает курьера с «купи и привези» — деньги за товар остаются в заказе следующего

### [P2] №10. Фоновый воркер закрывает ЖИВУЮ доставку
- **Файл:строка** — `backend/app/taxi_worker.py:252-258` (`_last_parcel_move_at`), `:272`, `:304`.
- **Что не так** — «последнее движение» = `accepted_at or created_at`. Ни отметки «не застал»
  (`delivery_attempts`), ни срока `deliver_by` (до 30 дней вперёд, `parcels.py:76`) воркер не

- **Сценарий поломки** — отправитель ставит срок «через 10 дней» (система это разрешает), курьер
  берёт заказ, честно ездит, дважды отмечает «получателя нет дома» — и на четвёртые сутки воркер
  переводит заказ в `canceled`. Обе стороны получают «долго не было связи, доставку закрыли
  автоматически», хотя связь была сегодня. Если это `buy_bring` с закупленным товаром — деньги
  курьера уходят вместе с заказом, без записи.
- **Доказательство** (прогон): `worker обработал: True | статус после воркера: canceled |
  попыток: 2 | срок: 2026-08-17`.
- **Как чинить** — считать «последнее движение» по максимуму из `accepted_at`, времени последней
  попытки и последнего сообщения в чате; не закрывать раньше `deliver_by`.

### [P2] №11. `returning` — статус-тупик: авто-выхода нет, отправитель заперт
- **Файл:строка** — `backend/app/taxi_worker.py:247` (`returning` исключён намеренно),
  `backend/app/cleanup.py:348-365` (чистка трогает только `created`),
  `backend/app/routers/parcels.py:627-628` (отправителю 409).
- **Что не так** — из `returning` выйти может только курьер (`return-done`) или админ. Если курьер
  исчез, заказ висит вечно; отправитель отменить не может, воркер по замыслу не трогает.
- **Сценарий поломки** — курьер нажал «везу обратно» и пропал (сломался телефон, уехал из
  района). Через 90 дней заказ всё ещё `returning`, занимает место в потолке «на руках» у курьера
  (`_CARRYING_STATUSES`, `parcels.py:60`) и в потолке «в работе» у отправителя
  (`parcels.py:432`). Отправитель звонит в поддержку — и только человек может это закрыть.
- **Доказательство** (прогон): `returning спустя 90 дней: returning | отмена отправителем: 409
  «Курьер уже везёт посылку обратно»`.
- **Как чинить** — отдельный таймаут возврата (например 7 дней от `return-start`) → авто-`returned`
  с уведомлением обеих сторон и сигналом админу; либо разрешить отправителю подтвердить «получил
  обратно» самому.

### [P2] №12. Публичная трекинг-ссылка после возврата показывает «Ищем курьера…» и продолжает отдавать точки А и Б
- **Файл:строка** — `backend/app/routers/share.py:168-176` (`_parcel_state`), `:63`
  (`_PARCEL_STATUS_PHASE` без `returning`/`returned`).
- **Что не так** — финальными считаются только `delivered` и `canceled`; неизвестный статус
  падает в фолбэк `"searching"`, и страница остаётся «живой» вместе с координатами отправления
  и назначения на все 72 часа TTL ссылки.
- **Сценарий поломки** — посылку вернули отправителю. Получатель (у которого ссылка из SMS,
  и это может быть человек, которому ссылка ушла по ошибочному номеру) видит «Ищем курьера…»
  и карту с двумя точками, включая дом отправителя. `family.py:222` при этом запрещает выдавать
  новую ссылку только для `delivered`/`canceled` — для `returned` ссылку всё ещё выпишут.
- **Доказательство** (прогон):
  `публичная страница после возврата: searching {'ru': 'Ищем курьера…'} | from: {52.7, 58.6} |
  to: {54.7, 55.9}`
- **Как чинить** — в `_parcel_state` и в `family.parcel_track_link` использовать общий список
  финальных статусов (`returned` туда входит), фолбэк неизвестного статуса делать `finished`,
  а не `searching`.

### [P2] №13. Причина отказа курьера уходит в открытую ленту и не модерируется
- **Файл:строка** — `backend/app/routers/parcels.py:924` (`parcel.return_reason = reason`),

- **Сценарий поломки** — курьер снимается с текстом «отправитель хамит, живёт в доме с
  наркоманами» — и это читает каждый курьер района на карточке заявки; отправитель ни удалить,

- **Как чинить** — не показывать `return_reason` в `_parcel_available` (оставить сторонам и

### [P2] №14. `parcel_status` — единственный денежный переход без блокировки строки
- **Файл:строка** — `backend/app/routers/parcels.py:807` (`session.get`), против
  `:616-618` (cancel), `:897-899` (release), `:989-991` (attempt-failed), `:1028-1030`
  (return-start), `:1062-1064` (return-done) — там везде `.with_for_update()`.
- **Что не так** — проверка «в каком статусе» и запись «новый статус» разнесены и ничем не
  сериализованы, а `UPDATE` идёт по `id` без условия на прежний статус.
- **Сценарий поломки** — отправитель жмёт «отменить» ровно в тот момент, когда курьер жмёт
  «доставлено». Отмена берёт лок, пишет `canceled` и фиксирует компенсацию 100 ₽; запрос курьера,
  прочитавший строку до этого, дожидается лока и перезаписывает статус на `delivered`. Итог:
  заказ одновременно «доставлен» и с записанной компенсацией за отмену; отправителю сказали одно,
  курьеру — другое, комиссия начислена.
- **Доказательство** — воспроизвести гонку в однопоточных тестах на SQLite нельзя; вывод сделан
  по коду: в `parcel_status` нет `with_for_update`, тогда как во всех соседних мутирующих
  эндпоинтах он есть. **Не воспроизведено, доказано чтением.**
- **Как чинить** — тот же `select(...).with_for_update()` в начале `parcel_status` (и в
  `courier_goods_cost`, `courier.py:891`).

### [P2] №16. Нет счётчика неверных кодов вручения

## НЕ ДОКАЗАНО

1. **Гонка cancel ⟷ deliver (дыра №14).** Механизм выведен из кода (единственный мутирующий
   эндпоинт без `with_for_update`), но не воспроизведён: нужны параллельные соединения к
   Postgres. На SQLite в тестах гонок нет по определению.
2. **Превышение потолка «15 на руках» при параллельных accept.** Потолок считается запросом без
   лока (`parcels.py:765`), лок держится на строке ДРУГОЙ посылки — теоретически 20 одновременных
   accept'ов на 20 разных заявок могут пройти. Не воспроизведено.
3. **Поведение при `PARCEL_FEE_ENABLED=true` целиком.** Доказан только двойной счёт в отчёте
   (дыра №5). Остальное (кому и как выставлять сбор попутчику) — продуктовый вопрос, а не дефект
   кода: пути оплаты у сбора нет по замыслу, и это честно задокументировано в `config.py:238-244`.
4. **Перебор кода вручения как реальная атака.** Отсутствие счётчика доказано (дыра №16),
   но осуществимость перебора 32^6 под общим IP-лимитером я не считал и не проверял.
5. **Приватность `receiver_name` в открытой ленте.** Полное имя получателя видно всем курьерам
   до принятия. Это может быть осознанным решением (в докстроке модели прямо написано «публично
   курьеру», `models.py:1381`) — как дыру не засчитываю, но флажок для роли security ставлю.
6. **Утечка `parcel_id` в SOS/зимнем протоколе.** Номер доставки и маршрут кладутся в текст
   события (`safety.py:783-793`) — беглый просмотр показал, что телефонов и координат там нет,
   но целиком ветку `safety.py` я в этом срезе не проходил.
