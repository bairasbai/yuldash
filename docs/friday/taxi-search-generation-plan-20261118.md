# Поиск такси: план устранения ABA

Статус: план и воспроизводимая граница существующего исправления, не реализованная защита. База `8abe8b7`, дерево опубликованного `746499c`. Runtime, схема, тарифы и API в этом пакете не меняются.

## Доказанный остаточный риск

Текущий writer сравнивает `(searching_at, search_round, offer_token)`. При полностью совпавшем повторном запуске поиска старый lookup всё равно может завершить новый поиск. Два теста вызывают настоящий `start_matching` в другой Session при замороженном времени и останавливают новый lookup после commit: старый результат записывает offered либо expired.

`test_taxi_search_aba_known_gap.py` содержит два strict XFAIL с `raises=KnownSearchABA`. Ошибка подготовки, неожиданный exception или несоблюдение равенства снимка не маскируются этим XFAIL. С `--runxfail` получены именно два отказа по старой записи offered/expired. Обычный адресный прогон: 16 passed, 2 xfailed; это **не** означает, что ABA устранено. Реальное время имеет микросекундную точность, не искусственно объявляется секундным. Замороженное время проверяет отсутствие зависимости гарантии от уникальности часов.

## Предпочтительное решение: монотонная ревизия строки

Предлагается отдельный nullable `search_revision BIGINT`, не `offer_token`. Каждый успешный новый/повторный поиск атомарно выполняет `COALESCE(search_revision, 0) + 1` в том же UPDATE/транзакции, что переход и критерии. Не вычислять increment из stale ORM, не сбрасывать при expiry/cancel/reassign, не переиспользовать уже опубликованную revision при application retry. Откат ещё не опубликованной транзакции не создаёт нового видимого поколения; lookup не должен начинаться до успешного commit. Переполнение должно быть fail-closed без нового поиска и без сброса счётчика.

Это выбор для строгого различения поколений одного существующего order_id без зависимости от часов и вероятности UUID-коллизии. Альтернатива UUID4 String32 проще согласуется с offer_token, но имеет вероятностную уникальность. Она допустима только при честно ограниченной гарантии; здесь предпочтительна ревизия. Удаление и повторное создание того же order_id, ручные откаты/восстановления значений и действия старых writers не покрываются одним счётчиком.

Миграция аддитивная, nullable, после актуальной единственной Alembic head. Не выполнять её на реальной БД в рамках разработки. Исторические terminal/scheduled строки могут оставаться NULL; массовая backfill сама по себе не делает старые процессы безопасными.

## Обязательные writers и потребители

| Место | Требование |
|---|---|
| `start_matching` | Increment при каждом успешном начале, включая searching→searching |
| `_reassign_after_driver_cancel` | Increment вместе с новым поиском после отмены |
| `advance_after_no_accept` | Increment вместе с offered→searching; не сбрасывать search_round; сохранить CAS оффера |
| `add_fallback_category` | Increment при фактической смене критериев, включая already-searching и отсутствие снижения цены; новый владелец обязан продолжить подбор |
| `apply_destination` / соответствующие router-входы | Increment при смене маршрута до принятия; атомарное инвалидирование старого оффера и затем новый подбор |
| `apply_waypoints` / соответствующие router-входы | Аналогичная обработка поисковых/предложенных заказов и актуальности предложения |
| `try_offer_next`, `_expire_no_drivers` | Снять scalar revision до lookup, сравнить `id + searching + expected revision` в обоих UPDATE; существующие ограничения оставить |

Создание, scheduled activation, retry worker, decline/timeout/lazy reconcile должны проходить эти точки. Любой новый writer координат, category/fallback_categories, options, women_only или иных критериев поиска должен участвовать в том же протоколе.

Исторические active searching с NULL: короткая свежая блокировка строки, повторный status check, атомарное назначение первой revision и свежий снимок до lookup. Нельзя считать NULL==NULL полной защитой поколения. Два инициализатора должны сериализоваться/проигрывать CAS, не переписывать друг друга.

## Критический prerequisite: порядок смены маршрута

Inventory исправлен после прямой сверки кода: `can_change_destination` разрешает created/searching/offered, а не только принятую поездку. В текущем offered destination router сначала вызывает `advance_after_no_accept` (включая новый matching/push по старому адресу), затем `apply_destination`. `set_waypoints` также допускает pre-accept и не отзывает offered явно. Это статически обнаруженный отдельный риск порядка операций, не подтверждённый HTTP-регрессией в этом пакете и не исправленный им.

Один increment в advance не устранит публикацию старых критериев. Требуется отдельный проверенный пакет:
1. Свежая строка и status guard под row-lock.
2. Новые маршрут/остановки/цена и revision в одной транзакции, без изменения денежных формул.
3. При offered одновременно отозвать старый оффер и установить searching, без промежуточного matching.
4. После commit продолжить matching по новому committed состоянию; для already-searching также явно назначить продолжение.
5. Проверить все helper-входы, включая destination/accept. Принятая поездка сохраняет свои правила согласования водителя.

До этого нельзя заявлять полную защиту обновления критериев. Redis/геопозиции/eligibility тоже могут измениться без revision заказа; гарантируется поколение решения по строке, не неизменность мира во время lookup.

## Границы Redis и уведомлений

Проигравший CAS не меняет tried-set и не пушит. Победитель записывает tried до commit под DB row lock: перенос после commit открывает окно decline раньше tried. При этом Redis side effect с последующим неудачным DB commit остаётся отдельной проблемой.

`_expire_no_drivers` очищает tried по order_id после commit: новый поиск может уже начаться. Нельзя механически перейти на ключ по revision, потому что tried должен переживать advance/reassign и иметь собственный lifecycle. Нужны отдельный план namespace/условной очистки и тесты. Post-commit push тоже может устареть; revision не заменяет outbox и не даёт end-to-end линейризуемости.

## Порядок реализации и критерии приёмки

1. Совместимая схема/model, локальные upgrade/idempotence/downgrade и одна head. Никакой реальной миграции.
2. Writers + оба CAS, atomic increment, NULL-init, overflow fail-closed. Удалить строгие XFAIL только после превращения исходных сценариев в PASS.
3. Отдельные регрессии смены destination/waypoints/fallback в searching/offered с проверкой порядка publish. Сохранить pricing/reclamp и водительские согласования.
4. Два concurrent matcher, rollback, NULL legacy, совпавшее время/round/offer_token, все entry writers, отсутствие effects проигравшего, контроль неизменённого успешного пути. Отдельно настоящая PostgreSQL-конкурентность.
5. Scoped, независимая приёмка, полный backend gate на зафиксированном кандидате. Только затем отдельная GitHub-ветка. Main/production требуют отдельного разрешения.

## Rollout и откат: не выполнялись

Аддитивная схема совместима со старым кодом, но гарантия несовместима со старым writer. В mixed fleet старый процесс может оставить прежнюю non-NULL revision, а старый matcher вообще игнорирует CAS. До подтверждения обновления всех API/worker/manual runners и завершения старых in-flight работ полная гарантия не действует. При rollback старого writer её нужно явно снять. Если нужна непрерывная гарантия во время mixed rollout, потребуется отдельная DB-enforced схема и запрет обхода старым CAS, это не минимальный пакет.
