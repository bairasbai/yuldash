## 1. Proposed exact contract

A successful authoritative accepted/final-closure operation clears matching_resume_revision, matching_resume_next_at and matching_resume_attempts to NULL in the SAME owner UPDATE/flush. Do not validate pending before clearing: complete, partial, negative or mismatched tuples all terminate. All-NULL baseline stays absent. No new pending CAS or pending-validation refusal may block the actual business transition. Preserve existing status/actor/ownership predicates, money, promo, effect ordering and commit boundaries. An existing CAS loser or idempotent early return does not repair pending.

This differs intentionally from transfer: a successful clear supersedes caller-dirty pending values. It must not discard unrelated dirty fields, introduce a full refresh/expire, or resurrect a deleted ORM object. Pending disposal cannot later be undone by the caller's stale identity-map flush.

## 3. Core vs ORM authoritative dirty-field semantics

Core transition/cancel/old-queue UPDATE executes under session.no_autoflush, synchronize_session=False, so pending dirty values cannot flush between successful clear and sync. Preserve existing preceding query behavior, not promise that no earlier caller flush occurred. Capture success via rowcount or fully consumed returned IDs as appropriate. For ONLY matched persistent same-session, nondeleted identity-map objects (also exclude session.deleted), synchronize pending3 as committed NULL using SQLAlchemy attributes.set_committed_value. This deliberately clears semantic history for pending3; does not touch other attributes/histories and does not load absent objects. Exact matched IDs are needed for bulk old-queue operation. Owner status/other fields must retain previous synchronization semantics: implementation must explicitly retain existing fetch synchronization or equivalently sync its known changed owner fields; do not turn off owner synchronization without a tested replacement. This is a review item, not permission to weaken it.

Alternative narrow ordering: retain existing synchronize_session='fetch'/auto for owner UPDATE within no_autoflush, then explicitly set committed pending3 NULL for successful matched objects before later flush. Use this if it best preserves current owner behavior; independent tests must prove dirty pending is not rewritten during synchronization. Do NOT selective-refresh all pending before deleting histories: refresh could read from wrong late transaction or hide the intended authority. No full refresh, expire_all, implicit target load, commit or rollback in sync helper.

For ORM finish/worker paths simply assign pending3=None alongside status before existing flush. No preflush set_committed_value: it would suppress the necessary SQL update. After a successful ORM flush histories become clean normally. Failure keeps existing rollback semantics; no post-error repair write.

Winner tests must show unrelated dirty price/comment/etc histories and persisted values follow prior caller behavior. Loser/early-return tests show pending values and dirty histories unchanged. If an ORM object is scheduled for deletion, never reload/reinsert it to synchronize; preserve existing deletion semantics without claiming the clear establishes a new terminal row.

## 4. Episode semantics and explicit exclusions

- accepted ends matching obligation, not the entire ride. A later driver cancellation may start a new search episode; after clear, reassign must not silently recreate old pending. Producer for that new episode remains separate.
- cancel has multiple commits. Crash after first cancellation commit but before reassign leaves all-NULL cancelled owner; this slice does NOT provide durable recovery of that gap. Do not preserve old obligation or manufacture a new one without reviewed policy.
- _expire_no_drivers3482+ preserves wait_until, writes expired in exact generation CAS and commits. retry_waiting_orders173+ restarts expired/searching with future wait. Therefore blanket expired clear conflicts with continued queue admission. Leave this helper unchanged in first slice. Journal must choose attempt-level clear+future new producer versus retain during active wait; no decision is made here.
- Scheduled raw cleanup expiry and /wait concurrent semantics similarly remain unresolved. Expired with no future wait might be final today but future /wait can reactivate it; do not claim universally terminal from enum alone.
- finish_expired_waits explicitly removes wait, stuck closure removes wait, and user orders again explicitly removes old wait: those are selected final queue exits, not a new broader expiration policy.
- Old+1 pending mismatch collision from transfer is not solved generally: a live owner can still acquire accidental equality. Terminal clear removes it only on selected successful closure. Consumer activation blocked by provenance/episode validity, not rescued by equality.
