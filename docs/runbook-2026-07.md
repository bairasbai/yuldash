## 🔥 1. Приложение не работает у всех

### Шаг 1. Понять, жив ли сервер (30 секунд)

На сервере (`ssh root@85.239.52.55`):

```sh
curl -s http://127.0.0.1:8000/health
```

- Ответ `{"status":"ok","db":"ok",...}` → **бэкенд жив**. Проблема, скорее всего, в сети/операторе
  у пользователей или в самом приложении на телефоне. Проверь ещё снаружи: `curl -s https://yulbash.ru/health`
  (тоже с сервера — с ноута curl часто режет ТСПУ, это нормально).
- Ответа нет / ошибка / `db` не `ok` → идём на шаг 2.

Подсказка: если сервис падал, тебе уже должен был прийти алерт в **Telegram** от бота
`@yuldash_sms_bot` («🔴 Юлдаш ПРОД УПАЛ»). Мониторинг проверяет /health каждую минуту.

### Шаг 2. Посмотреть, что говорит сервис

```sh
systemctl status yuldash-api
```

(выход из просмотра — клавиша `q`). Строка `Active: active (running)` = работает,
`failed` или `activating` = упал/перезапускается.

Последние ошибки в логе:

```sh
journalctl -u yuldash-api -n 100 --no-pager
```

Смотреть живьём (обновляется само): `journalctl -u yuldash-api -f` (выход — `Ctrl+C`).
Ищи строки `[ERR]`, `Traceback`, `Error`.

### Шаг 3. Перезапустить

```sh
systemctl restart yuldash-api
sleep 5
curl -s http://127.0.0.1:8000/health
```

Сервис настроен на автоперезапуск при падении (`Restart=always` в systemd), поэтому
если он «лежит» долго — значит падает **снова и снова** при старте. Тогда читай лог
(шаг 2): чаще всего виновата свежая выкатка (→ раздел «Откат» ниже) или база.

### Шаг 4. Если дело в базе (в /health `db` не `ok`)

```sh
systemctl status postgresql
systemctl restart postgresql
systemctl restart yuldash-api
```

### Шаг 5. Если ничего не помогло — проверь диск и память

```sh
df -h        # диск. Если Use% = 100% — кончилось место, это частая причина «всё умерло»
free -h      # память
```

Диск забит → почисти старое: `du -sh /opt/yuldash/backups /var/log/journal` покажет, кто ест место.
Старые бэкапы чистятся сами (14 дней), журнал можно ужать: `journalctl --vacuum-size=500M`.

## 🗄 2. База данных: бэкап и восстановление

### 2.1 Снять бэкап руками (перед любым рискованным действием!)

Одной строкой с ноута:

```powershell
ssh root@85.239.52.55 "/opt/yuldash/backup-db.sh"
```

Скрипт сам: снимет дамп → сожмёт → положит в `/opt/yuldash/backups/` → зальёт копию в облако (S3).
Проверить, что файл появился и он свежий:

```powershell
ssh root@85.239.52.55 "ls -lth /opt/yuldash/backups/ | head -5"
```

### 2.2 Восстановить из бэкапа (пошагово)

> ⚠️ Восстановление **затирает текущие данные** базы тем, что было в бэкапе.
> Делай это только если данные реально испорчены/потеряны. Сначала — п.2.1 (снять
> бэкап текущего состояния, даже испорченного: вдруг понадобится).

На сервере:

```sh
# 1) Найти нужный файл (обычно самый свежий сверху):
ls -lt /opt/yuldash/backups/yuldash-*.sql.gz | head

# 2) Остановить API, чтобы никто не писал в базу во время восстановления:
systemctl stop yuldash-api

# 3) Пересоздать базу и залить дамп (подставь ИМЯ-ФАЙЛА из шага 1):
sudo -u postgres psql -c "DROP DATABASE yuldash;"
sudo -u postgres psql -c "CREATE DATABASE yuldash OWNER yuldash;"
gunzip -c /opt/yuldash/backups/ИМЯ-ФАЙЛА.sql.gz | sudo -u postgres psql yuldash

# 4) Запустить API обратно:
systemctl start yuldash-api

# 5) ПРОВЕРКА — это обязательный шаг, не пропускай:
curl -s http://127.0.0.1:8000/health
sudo -u postgres psql -d yuldash -c 'SELECT count(*) FROM "user";'
sudo -u postgres psql -d yuldash -c 'SELECT count(*) FROM ride;'
sudo -u postgres psql -d yuldash -c 'SELECT count(*) FROM booking;'
```

`/health` = ok и счётчики выглядят правдоподобно (не нули) → восстановление удалось.

### 2.3 Сервер умер совсем — бэкап из облака

Локальные бэкапы умерли вместе с сервером, но копия каждого лежит в облаке
(Timeweb S3, бакет `yuldash-backups`). С любой машины, где есть aws-cli и ключи
(ключи — в панели Timeweb → Хранилище S3, там же можно перевыпустить):

```sh
aws --endpoint-url https://s3.twcstorage.ru s3 ls s3://yuldash-backups/
aws --endpoint-url https://s3.twcstorage.ru s3 cp s3://yuldash-backups/ИМЯ-ФАЙЛА.sql.gz .
```

Дальше — поднять новый сервер по инструкции `backend/ops/README.md`, раздел 5
(«Сервер умер — как поднять сервис»). Ориентир: 1–3 часа, потеря данных — максимум сутки
(бэкап снимается раз в день в 04:00).

### 2.4 Автобэкап — что уже настроено

- ✅ **Cron ежедневно в 04:00** запускает `/opt/yuldash/backup-db.sh`, лог — `/opt/yuldash/backups/backup.log`.
- ✅ **Копия в облако S3** (Timeweb, бакет `yuldash-backups`) — уходит после каждого бэкапа.
- ✅ Локально хранятся **последние 14 дней**, старое удаляется само.

Быстрая проверка, что автобэкап жив (одной строкой с ноута):

```powershell
ssh root@85.239.52.55 "ls -lt /opt/yuldash/backups/yuldash-*.sql.gz | head -3 && tail -5 /opt/yuldash/backups/backup.log"
```

Верхний файл должен быть **сегодняшний или вчерашний**. Если ему больше двух дней — бэкап сломался, разберись сейчас, а не при аварии.

### 2.5 ⚠️ Настроить: еженедельная авто-репетиция восстановления

Бэкап, который ни разу не разворачивали — это надежда, а не бэкап. В репозитории уже есть
готовый скрипт `backend/ops/restore-verify.sh`: он берёт свежий дамп, разворачивает его во
**временную** базу (боевую не трогает), проверяет таблицы и строки, пишет `OK`/`FAIL` и убирает за собой.

Рецепт (на сервере, один раз):

```sh
# 1) Убедиться, что свежие ops-скрипты лежат на сервере (если каталога нет — скопировать с ноута:
#    scp -r backend/ops root@85.239.52.55:/opt/yuldash/backend/ops)
ls /opt/yuldash/backend/ops/

# 2) Открыть расписание:
crontab -e

# 3) Добавить строку (репетиция каждое воскресенье в 05:00) и сохранить:
0 5 * * 0  /opt/yuldash/backend/ops/restore-verify.sh >> /opt/yuldash/backups/restore-verify.log 2>&1

# 4) Проверить, что встало:
crontab -l

# 5) Прогнать один раз руками прямо сейчас — в конце должно быть "OK":
/opt/yuldash/backend/ops/restore-verify.sh
```

Раз в неделю поглядывай хвост лога: `tail -20 /opt/yuldash/backups/restore-verify.log` — там `OK` или `FAIL`.

## 🚀 3. Деплой и откат

### 3.1 Как выкатить новую версию бэкенда

Обычно это делает Claude. Главные правила:

- **Истина = ветка `main`** — бэкенд деплоится из неё, не из рабочих веток `claude/*`.
- Перед выкаткой — **бэкап** (п.2.1). Это твоя страховка на 30 секунд.

Безопасный способ — скрипт `backend/ops/deploy.sh` (он сам: подтянет код → зависимости →
миграции → рестарт → **проверит /health** и, если сервис не поднялся, **сам откатится**
на прошлую версию и пришлёт алерт в Telegram). На сервере:

```sh
APP_DIR=/opt/yuldash SERVICE=yuldash-api HEALTH_URL=http://127.0.0.1:8000/health BRANCH=main \
  bash /opt/yuldash/backend/ops/deploy.sh
```

> Скрипт по умолчанию настроен на staging — прод трогает **только** с явными переменными, как выше.
> Это защита от случайного запуска.

Точечный ручной деплой одного файла (как делалось раньше, тоже рабочий путь):

```powershell
scp backend/app/ФАЙЛ.py root@85.239.52.55:/opt/yuldash/app/
ssh root@85.239.52.55 "chown -R yuldash:yuldash /opt/yuldash && systemctl restart yuldash-api && sleep 5 && curl -s http://127.0.0.1:8000/health"
```

После любого деплоя — проверка: `/health` = ok и нет свежих `[ERR]` в `journalctl -u yuldash-api -n 50`.

### 3.2 Как откатиться, если после выкатки всё сломалось

Если катил через `deploy.sh` — он уже откатился сам (смотри его вывод/алерт). Если руками:

```sh
# На сервере, в каталоге приложения:
cd /opt/yuldash
git log --oneline -5           # найти прошлый коммит (второй сверху)
git reset --hard ХЭШ_ПРОШЛОГО_КОММИТА
chown -R yuldash:yuldash /opt/yuldash
systemctl restart yuldash-api
curl -s http://127.0.0.1:8000/health
```

### 3.3 Про `alembic downgrade` (откат миграций базы) — когда можно, а когда НЕЛЬЗЯ

Простыми словами: **код откатывать безопасно, базу — почти никогда не нужно.**

- Наши миграции **аддитивные** — они только добавляют колонки/таблицы, старый код спокойно
  работает с новой схемой. Поэтому при откате кода базу **не трогаем** — это план по умолчанию,
  и `deploy.sh` ведёт себя так же (`ROLLBACK_DB=0`).
- `alembic downgrade` **НЕЛЬЗЯ**, если после миграции в новые колонки/таблицы уже записались
  реальные данные пользователей — downgrade их **удалит безвозвратно**.
- Единственный случай «можно»: миграция накатилась и тут же всё сломала, реальных данных в новых
  структурах ещё нет, и ты понимаешь, что делаешь. Тогда, сняв бэкап (п.2.1):

```sh
cd /opt/yuldash && sudo -u yuldash ./.venv/bin/alembic downgrade -1   # откат ровно на один шаг
```

Сомневаешься — не делай downgrade. Восстановление из бэкапа (п.2.2) — более предсказуемый путь.

## 🔑 5. Секреты (ключи, пароли)

**Где лежат:**
- `/opt/yuldash/.env` — главный файл секретов бэкенда (jwt_secret, ключи SMS/Telegram/YooKassa,
  DATABASE_URL). Только на сервере, в git его **нет**.
- `/opt/yuldash/.backup-s3.env` — ключи облака для бэкапов (права 600).
- `/opt/yuldash/.monitor.env` — chat_id для алертов.
- На ноуте: `android/local.properties` (ключ карт, DSN) — тоже не в git.

**Никогда не коммитить:** `.env`, `local.properties`, файлы `*.jks` (подпись приложения),
любые строки вида `api_id=`, `token=`, пароли — ни в код, ни в `docs/`, ни в чат.

**⚠️ Обязательно сделать один раз:** сохранить **резервную копию `/opt/yuldash/.env`** в надёжном
месте вне сервера (менеджер паролей). Умрёт сервер — без этого файла новый не запустить:

```powershell
scp root@85.239.52.55:/opt/yuldash/.env $HOME\yuldash-env-backup.txt
# → положить содержимое в менеджер паролей, файл с диска удалить
```

**Если ключ утёк** (попал в git/чат/скриншот) — считай его чужим, действуй сразу:
1. **Выпустить новый ключ** там, где он выдан: Telegram-бот → `@BotFather` → `/revoke`;
   sms.ru → личный кабинет; S3 → панель Timeweb → Хранилище S3 → перевыпуск; ключ карт →
   кабинет Яндекса; `jwt_secret` → просто придумать новый длинный случайный (после смены все
   пользователи должны будут войти заново — это нормально и ожидаемо).
2. **Вписать новый** в `/opt/yuldash/.env` на сервере → `systemctl restart yuldash-api`.
3. **Старый отозвать/удалить** (не «оставить на всякий случай»).
4. Если утёк в git — сказать Claude вычистить из истории; просто удалить файл новым коммитом недостаточно.

## ✅ 6. Чек-лист «раз в неделю» (5 минут, можно в воскресенье)

Всё — одной ssh-сессией: `ssh root@85.239.52.55`, дальше по порядку:

```sh
# 1) Бэкап жив? Верхний файл — сегодня/вчера, размер не нулевой:
ls -lt /opt/yuldash/backups/yuldash-*.sql.gz | head -3

# 2) Копия в облаке уходит? В хвосте лога должно быть "s3 upload ok" (или "s3 ok"):
tail -5 /opt/yuldash/backups/backup.log

# 3) Репетиция восстановления прошла? (после настройки п.2.5) Ищем "OK":
tail -5 /opt/yuldash/backups/restore-verify.log

# 4) Место на диске (Use% меньше 80% — хорошо):
df -h /

# 5) Сервис здоров:
curl -s http://127.0.0.1:8000/health

# 6) Были ли ошибки за неделю:
journalctl -u yuldash-api --since "7 days ago" | grep -c "\[ERR\]"
```

Плюс глазами: Telegram — не было ли 🔴-алертов; Sentry (когда настроишь) — новые ошибки.

| Что | Норма | Если не норма |
|---|---|---|
| Свежий бэкап | сегодня/вчера | смотри `backup.log`, запусти `/opt/yuldash/backup-db.sh` руками |
| S3-копия | `s3 upload ok` в логе | проверь ключи в `.backup-s3.env` / панель Timeweb |
| restore-verify | `OK` | `FAIL` = бэкап негоден — разбираться СЕГОДНЯ |
| Диск | < 80% | `journalctl --vacuum-size=500M`, чистка старья |
| /health | `status:ok, db:ok` | раздел 🔥 1 этого файла |
| [ERR] за неделю | 0 или единицы | `journalctl -u yuldash-api | grep "\[ERR\]" | tail` и к Claude |

**Рецепт ротации cron-логов** (на сервере, один раз — logrotate уже установлен в Ubuntu):

```sh
cat > /etc/logrotate.d/yuldash <<'EOF'
/opt/yuldash/monitor.log /opt/yuldash/backups/backup.log /opt/yuldash/backups/restore-verify.log {
    monthly
    rotate 6
    compress
    missingok
    notifempty
    copytruncate

EOF
```
