# 🍏 iOS для Юлдаша через Compose Multiplatform — план и честная оценка

> Задача: «писать Android и iOS одновременно». Выбран путь **Compose Multiplatform (CMP)** — потому что
> Юлдаш уже на Kotlin/Compose, и CMP переиспользует существующий код, а не заставляет переписывать всё
> на другом языке (как React Native/Expo). Ниже — как это делать, где блокеры и что уже сделано.

Дата: 2026-07-20. Роль: Android-архитектор + техлид.

---

## Вывод (коротко)

- ✅ **CMP — правильный выбор.** Наша вёрстка на Compose, токены `Canon*`, двуязычие `appText` и анимации
  переезжают в общий код (`commonMain`) **почти без изменений**. Это доказано пробником (см. ниже).
- ⚠️ **Два жёстких блокера**, о них честно:
  1. **iOS нельзя собрать без Mac.** Это правило Apple, не CMP. Windows не компилирует iOS. Нужен Mac
     (или облачный Mac / macOS-раннер в CI).
  2. **Карта (Яндекс) — самый большой кусок.** У Яндекс MapKit **нет** общей версии: на Android один SDK,
     на iPhone — отдельный нативный. Карту придётся делать по-платформенно (общая логика, платформенный рендер).
- ⏱ **Это не «кнопка», а проект на несколько недель** фокусной работы + обязательный Mac. Делаем поэтапно,
  Android рабочий не ломаем ни на одном шаге.

---

## Почему CMP, а не React Native / Expo

| | Compose Multiplatform | React Native / Expo |
|---|---|---|
| Язык | **Kotlin** (наш) | JavaScript/TypeScript (чужой) |
| Наш текущий код | **переиспользуется** | выбрасывается, пишем заново |
| UI | наш Compose как есть | переписать на JSX-компоненты |
| Дизайн `Canon*`, `appText` | **едет 1:1** | заново |
| Риск для проекта | низкий (наращиваем) | высокий (переписывание с нуля) |

Раз фундамент уже на Compose — глупо его сносить. CMP наращивает поверх, а не начинает заново.

## Что переезжает как есть, а что надо портировать

**Едет в `commonMain` почти без правок (главный выигрыш):**
- Вся Compose-вёрстка экранов (кроме той, что рисует карту-View).
- Дизайн-токены `Canon*`, `appText`/двуязычие RU-BA, формы, анимации. ← **доказано пробником**.
- Доменные модели (`Domain.kt`), чистая логика, форматтеры, слой состояния (ViewModel на Kotlin).
- Навигация (`enum Screen` + `when`).

**Надо портировать (у каждого — платформенная реализация через `expect/actual`):**

| Сейчас (Android) | Зачем | На iOS |
|---|---|---|
| Яндекс MapKit `maps.mobile:4.39.0-full` | карта, маршрут, маркеры | **отдельный нативный Яндекс iOS SDK** (CocoaPods) через UIViewController-interop |
| OkHttp (WebSocket) + HttpURLConnection (REST) | сеть, realtime-чат/гео | **Ktor client** (мультиплатформенный: OkHttp-движок на Android, Darwin — на iOS) |
| Firebase Messaging + Analytics | пуши, метрики | **Firebase iOS SDK + APNs** (Apple Push) |
| `androidx.security:security-crypto` | шифрованное хранилище JWT | **iOS Keychain** |
| Coil 2.7.0 | показ удалённых фото | **Coil 3** (мультиплатформенный) |
| ZXing core | QR оплаты СБП | мультиплатформенная QR-либа (напр. `qrose`) |
| `TripLocationService` (foreground GPS) | фон-трекинг поездки | **CoreLocation** background updates |
| `BuildConfig` (ключи, URL) | конфиг | плагин **BuildKonfig** или `expect/actual` |
| runtime-права | гео и пр. | платформенные API |

> Вывод из таблицы: **UI переезжает легко, платформа (карта/сеть/пуш/гео/хранилище) — это работа.**
> Карта — самый большой и рискованный пункт.

## Поэтапный план (Android рабочий не ломаем ни на шаге)

- **Фаза 0 — каркас (пробник).** Доказать, что общий Compose + `Canon` + `appText` едут на iOS.
  → **Сделано** в `experiments/cmp-ios-poc/` (см. ниже; в облаке не собрано — нет SDK/Mac).
- **Фаза 1 — вынести «чистое» в `commonMain`.** `Domain.kt`, `appText`, `Canon*`, форматтеры, состояние.
  Сеть → Ktor, хранилище → `expect/actual`. Первая сборка на Mac. Делаем по кусочку, Android зелёный.
- **Фаза 2 — «тупые» экраны без карты** → `commonMain`: профиль, списки поездок/заявок, чат, формы,
  онбординг. **По одному экрану за раз**, сборка зелёная после каждого (правило проекта §6/§12.F).
- **Фаза 3 — карта (самое тяжёлое).** `expect/actual` «MapView»: Android — Яндекс MapKit как есть,
  iOS — Яндекс iOS SDK нативно. Логика маршрута/ETA — общая, рендер — платформенный.
- **Фаза 4 — платформенное:** пуши (FCM/APNs), фон-гео (foreground service / CoreLocation), платежи,
  подпись iOS, TestFlight.

**Реалистичная оценка:** несколько недель фокусной работы + Mac. Порядок сложности: Фаза 3 (карта) ≈
половина всех усилий.

## Что сделано в этой сессии

`experiments/cmp-ios-poc/` — изолированный проба-проект (рабочий `android/` **не тронут**). В нём один
общий экран на Kotlin/Compose рисуется и на Android, и на iPhone: карточка «Юлдаш», приветствие,
кнопка смены языка RU ⇄ BA, анимация — всё в фирменном `Canon`-стиле. `Canon.kt` и `AppText.kt`
портированы 1:1 из рабочего кода → показывают, что стиль и двуязычие переезжают без изменений.

**⚠️ Не проверено сборкой.** Облачная среда — Linux **без Android SDK** и **без macOS**, компилировать
нечего. Код написан по известным-совместимым версиям (AGP 8.13.2 / Kotlin 2.3.0 / CMP 1.11.0), но
собрать его нужно на машине с Android SDK (Android-часть) и на Mac (iOS-часть). Поэтому статус —
**«написано, ждёт сборки на твоей машине»**, а не «готово».

## Практический совет (ты на Windows)

Чтобы вообще собирать/публиковать iOS без покупки Mac:
- **Облачный Mac** (аренда) или **macOS-раннер в CI** (GitHub Actions `macos-latest`) собирает `.ipa`.
- Для установки на свой iPhone и публикации всё равно нужен **Apple Developer** (~$99/год) и подпись.
- Для повседневной отладки iOS удобнее живой Mac.

Это не блокер «прямо сейчас»: Фазы 0–2 (вынос кода в общий модуль) делаются и без Mac — Mac нужен,
когда впервые собираем именно iOS-приложение.
