## 0. Честный контекст (читать первым)
- Бэкенд = **сервер + база данных + хостинг + SMS** = это **деньги** (хостинг, SMS) и **поддержка** (кто-то чинит, когда падает).
- Это слабое место Александра по его же словам → тут ведёт **спец по серверам/безопасности** из команды.
- **Стартуем дёшево:** бесплатные тарифы (Supabase free / VPS за ~300–500 ₽/мес) хватит на пилот в Баймаке.
- **152-ФЗ:** телефон и геолокация — персональные данные. Нужны согласие, политика, хранение в РФ (для РФ-аудитории). Заложить с первого дня.

## 1. Роли
- **Пассажир** — ищет поездки, создаёт заявки, бронирует.
- **Водитель** — публикует поездки, откликается на заявки, проходит проверку. Кабинет: статус «на линии», маршруты, места, цена, история, рейтинг, документы.
- **Админ/диспетчер** — модерация водителей и жалоб, города/маршруты, реклама, спорные поездки, «диспетчерская» (оформить заявку за пожилого по звонку).

## 2. Авторизация
- Вход по **телефону + SMS-код** (OTP). Сессия — JWT (токен доступа + refresh).
- **Телефон скрыт** до подтверждения поездки (отдаём маскированный `+7 *** ** 12`, реальный — только подтверждённым участникам).
- Согласие на обработку перс.данных при регистрации (галка + версия оферты).

### Выключатели способов входа

`GET /admin/switches` возвращает карту `switches`. `POST /admin/switches/{key}` принимает `value`, необязательные `confirm` и `note`, возвращает обновлённую настройку. `stored=null` означает значение по умолчанию. Доступность канала определяется `effective` и `blockers`. История содержит до 50 последних решений, включая автора и время.

Для обоих маршрутов нужны роль администратора и действующая Telegram-сессия. Запись повторно проверяет сессию под замком пользователя, блокирует строки настроек по ключу и сохраняет историю вместе со значением. Повтор сохранённого значения не создаёт запись. Telegram сохраняет вход владельца. Если отключение SMS оставляет аккаунты без способа входа, сервер запрашивает явное подтверждение и возвращает число `affected`.

Общий `external.paid` и индивидуальный `external.sms_notices` видит и меняет настроенный Telegram-владелец. Для записи живого `login.sms` действует та же проверка. Остальные администраторы видят его с `editable=false`. Оба внешних ключа по умолчанию выключены. Для кода нужны готовность SMS.ru, сохранённый `login.sms` и общий допуск. Для уведомлений нужны `SMS_NOTIFY_ENABLED`, настроенный отправитель и оба внешних ключа. Готовую отдельную настройку можно сохранить на паузе. Общая пауза сохраняет её значение и закрывает новые допуски после фиксации. Сверка статусов и проверка ранее выданных кодов при включённом `login.sms` продолжаются. Пауза, которая убирает активный SMS-вход, применяет ту же проверку последнего способа и подтверждение с числом затронутых аккаунтов.

Ответ внешних ключей содержит `revision`. Изменение этих ключей требует `expected_revision` из прочитанного состояния. Повтор уже сохранённого значения не создаёт запись. Устаревший запрос другого значения получает `409 switch_revision_conflict`. Клиенты перечитывают состояние и сохраняют исходную ревизию при подтверждении.

Миграция `cq_paid_external_switches` добавляет исходные значения. Откат сбрасывает внешние переключатели и фиксирует паузу в журнале. Прежние запросы включения после повторного обновления устаревают. Перед откатом к серверу без общего выключателя выключи индивидуальные настройки живого SMS и проверь готовность Telegram. SMS-уведомления отправляются через общий канал сайта и Android. Код банкинга попутки остаётся за границей [RS-08](plans/rideshare/RS-08-card-payment-switch.md).

Ключ `rideshare_card_payments` видит Telegram-владелец. Эффективное состояние выключено. В ответ входят ревизия, история и двуязычная причина `bank_project_unaccepted`. Включение возвращает 409. Выключение требует прочитанную ревизию и сохраняется вместе с записью истории. Миграция `cs_card_payment_switch` вводит два поля карточного согласия водителя и исходное состояние ключа. При откате ключ остаётся выключенным, история сохраняется, поля согласия удаляются. Ответы по поездке, деталям и квитанции возвращают `card_payment:false`. Карточный и банковский СБП-запрос по брони остаются закрыты сервером RS-01.

`/config/login-methods` кешируется до 10 секунд. Допуск выдачи кода читает БД под тем же замком. Новая выдача после отключения закрыта. Прежняя проверка уже выданного кода может завершиться, если прочитала настройку до отключения. Платный SMS-вход допускается после одобрения подключения и явного включения владельцем.

Миграция `cn_admin_telegram_cutover` отзывает прежние входы администраторов. При выкладке нужно согласовать остановку старых процессов авторизации, обновление схемы и новый вход владельца. Откат ревизии сохраняет отзыв прежних сессий. При откате приложения на сборку без выключателей платный провайдер должен оставаться отключённым конфигурацией.

### Настройка сверки карточной оплаты попутки

`RIDESHARE_BANK_READ_ENABLED=false` по умолчанию. Для отдельного контура сверки используются `RIDESHARE_BANK_SHOP_ID`, `RIDESHARE_BANK_SECRET` и постоянный `RIDESHARE_BANK_FERNET_KEY`. Пустая или некорректная конфигурация закрывает доступ к банковскому контуру. Участникам остаётся доступна сохранённая история. Ключи такси отделены от настроек попутки. Адрес возврата формируется сервером на `https://app.yulbash.ru/receipt/{booking_id}`, без ключей и токенов. [Авторизация API ЮKassa](https://yookassa.ru/developers/using-api/interaction-format#auth-http-basic)

Миграция `cy_rideshare_bank_account_binding` сохраняет `provider_account_id` у новых попыток. Старые записи без привязки доступны в истории. Внешняя сверка и выдача ссылки требуют текущего аккаунта и того же окружения. Поменять секрет при сохранении того же аккаунта можно без пересоздания брони. Откат миграции с сохранённой привязкой останавливается, чтобы не потерять связь с магазином.

Серверный допуск новых операций закрыт и при старых включённых флагах. Это ограничение действует перед внешними POST, в том числе при повторе подготовленной операции. Команда `python -m app.rideshare_bank_worker` читает допущенные операции своего магазина. При выключенной или неполной настройке она завершается без запросов к БД или банку. Для запуска по минутному расписанию подготовлены `yuldash-rideshare-bank-worker.service` и `yuldash-rideshare-bank-worker.timer`. [План RS-08](plans/rideshare/RS-08-bank-payment.md)

Входящее уведомление доступно по `POST /payments/rideshare-bank/webhook`. По умолчанию маршрут отвечает 404. Для него нужны настроенный контур чтения и отдельный `RIDESHARE_BANK_WEBHOOK_PROXY_TOKEN`. Шаблон `backend/deploy/nginx-rideshare-bank-webhook.conf.example` ограничивает сети источника и подключает локальный секретный файл, который перезаписывает одноимённый входящий заголовок. При подключении проверить актуальность сетей, отсутствие прямого внешнего доступа к приложению и поведение HTTPS-прокси. URL с `/api/v1` закрыт. [Проверка подлинности уведомлений](https://yookassa.ru/developers/using-api/webhooks)

Маршрут берёт ту же аренду чтения, что и планировщик. Сумму, статус и связи перепроверяет по GET. Занятое чтение и временная ошибка дают 503, чтобы банк повторил уведомление. Терминальный дубль, неподдерживаемое, чужое событие и подтверждённое несовпадение принимаются без проводки. Тело ограничено 64 КиБ и тремя секундами. Одновременно допускаются до четырёх проверок на процесс. Пятисекундный таймаут GET применяется к ожиданию порции ответа.

### Реквизит водителя для выплаты попутки

Водитель читает свой статус по `GET /driver/bank-recipient` и начинает подключение по `POST /driver/bank-recipient/setup` с текущей версией реквизита. `POST /driver/bank-recipient/setup/{id}/confirm` принимает явное согласие и синтетический токен на локальном стенде. Попытка действует десять минут. Она связана с входом водителя, магазином, окружением, версией реквизита и версиями обоих выключателей.

После успешной записи квитанцию можно прочитать в том же входе по `GET /driver/bank-recipient/setup/{id}`. Android и PWA используют `GET /driver/bank-recipient/setup/{id}/receipt`, где поле `confirmation` содержит квитанцию либо `null`. Квитанция и точный повтор подтверждения доступны сутки, в том числе на паузе. У ответа нет токена, номера карты или временной ссылки. `POST /driver/bank-recipient/revoke` принимает текущую версию и удаляет собственный токен даже на паузе. Старая запись без зашифрованной привязки, повреждённый реквизит или смена магазина требуют нового согласия. Уже допущенная выплата использует сохранённый снимок запроса.

Тестовая запись закрыта в рабочем окружении. В кабинетах Android и PWA тестовые действия появляются только при доступном синтетическом контуре. Клиент сохраняет для восстановления идентификатор попытки и исходную версию в рамках одной авторизованной сессии. Выход удаляет эту запись. Подключение реального реквизита через банковский виджет остаётся отдельным этапом. Миграция `cz_rideshare_recipient_setup` хранит согласие и квитанцию без исходного токена. Ночная чистка удаляет незавершённые попытки спустя сутки после истечения и завершённые попытки спустя сутки после подтверждения. Квитанция сохраняется, пока её версия используется текущим реквизитом или сохранённой банковской попыткой. [Виджет выплат ЮKassa](https://yookassa.ru/developers/payouts/making-payouts/bank-card/using-payout-widget/implementing-widget)

### Допуск и учёт SMS-входа

`POST /auth/request-code` принимает российский мобильный номер, `lang=ru|ba` и `channel=sms`. Язык и канал можно опустить. Для допуска нужны свободные лимиты номера, IP, устройства и сервиса. Повтор для номера доступен через 60 секунд. На номер разрешено до 5 выдач в UTC-час и 10 в UTC-сутки, на IP до 40 в час, на устройство до 5 в час. `SMS_DAILY_CAP` задаёт общий потолок сервиса в UTC-сутки, по умолчанию 300. Если идентификатор устройства отсутствует, применяется отдельный лимит устройства на IP. Сервер берёт адрес запроса из ASGI. Перед включением платного входа требуется подтвердить настройку доверенных прокси.

Сервер записывает все резервы одной транзакцией до вызова провайдера. Переключение SMS прекращает новые допуски. Ответ выключателя содержит `in_flight` для свежих попыток, допущенных до отключения и ещё ожидающих результата. Код хранится как HMAC, а стабильный `SMS_BUDGET_HMAC_KEY` отделён от ключа сессий. Для локального провайдера `mock` доступен встроенный тестовый ключ. На настоящем подключении нужен отдельный одинаковый ключ у всех процессов. Его смена меняет идентификаторы счётчиков и делает выданные коды недействительными. Правило смены ключа для рабочего подключения следует согласовать вместе с включением провайдера.

Подтверждённый отказ до приёма сообщения гасит код и однократно возвращает только общий резерв. Неизвестный результат сохраняет резерв, а полученный код можно ввести до истечения срока. Если процесс остановился до записи ответа, при проверке кода свежая попытка остаётся `reserved`. Через 30 секунд проверка переводит её в `unknown` и позволяет сверить HMAC до истечения срока. Автоматическая повторная отправка отсутствует.

Ревизия `co_sms_budget` гасит и очищает прежние открытые SMS-коды с сохранением истории попыток. Откат также гасит выданные новым кодом подтверждения и удаляет таблицы бюджета. Код живёт `OTP_TTL_SEC` секунд, по умолчанию 300. Ночная уборка хранит историю кодов сутки, попытки отправки 30 дней, счётчики и отметки оповещения 48 часов после конца окна. Счётчик задержки повтора живёт 48 часов от обновления. Уборка истёкших окон не возвращает расход.

### Подключение SMS.ru

Адаптер отправляет по HTTPS форму POST с русским или башкирским шаблоном. Последняя строка содержит домен `app.yulbash.ru` и код для автоподстановки. Ключ, номер и код передаются в теле запроса. Из ответа SMS.ru в записи попытки остаются только идентификатор сообщения и числовой статус. Транспорт проверяется на синтетических ответах в памяти. [Отправка SMS.ru](https://sms.ru/docs/api/api_group_sms/send) · [Шаблоны](https://sms.ru/docs/templates/auth_templates)

До договора и согласования имени и шаблонов `SMS_RU_LOGIN_READY=false`. Для рабочего подключения нужны `SMS_PROVIDER=smsru`, `SMS_RU_API_ID`, одобренное имя `SMS_FROM`, отдельный `SMS_BUDGET_HMAC_KEY` и подтверждённая готовность. При выполнении условий владелец явно включает `login.sms` на экране «Выключатели» в PWA. `SMS_NOTIFY_ENABLED=false` по умолчанию отвечает отдельно за уведомления близким. Текущая приёмка охватывает синтетический серверный контур, а условия подключения, утверждение текстов и доставку на телефон проверяют при подключении.

На согласованной среде `python -m app.sms_reconcile --limit 100` запрашивает статусы известных ID. Команда атомарно отмечает запрос перед HTTP, поэтому одновременные процессы не сверяют один ID повторно в минутном окне. Разрешённую ранее отправку можно сверить при выключенном входе. Поздняя недоставка, неизвестный статус и отсутствие сообщения у провайдера сохраняют резерв. Если идентификатор потерян с ответом, SMS.ru не даёт сверить эту попытку по внутреннему UUID Юлдаша. [Статус SMS.ru](https://sms.ru/docs/api/api_group_sms/status)

Ревизия `cp_smsru_receipts` добавляет два поля и уникальный индекс идентификатора. Откат удаляет поля квитанции, сохраняя историю резерва и кода. При рабочем откате сохранность квитанций учитывается отдельно.

### Способы оплаты в попутке

Водитель читает и меняет свой список через `GET /driver/pay-settings` и `PUT /driver/pay-settings`. Разрешены наличные и ручной перевод по СБП. Пустой список разрешает договориться о любом из этих способов. Изменяющий запрос передаёт `expected_updated_at` из ответа чтения. Повтор того же списка сохраняет старую ревизию. Два разных изменения по одной ревизии дают одно сохранение и один отказ `pay_settings_changed` с актуальными данными.

В поездках и деталях брони список приходит как `driver_pay_methods`. Перед бронированием и сменой способа пассажиром сервер проверяет его в свежем запросе. `pay_method_not_accepted` при бронировании сохраняется как окончательный результат команды. Для нового выбора нужна новая команда. Водитель сохраняет договорённость по уже открытой брони, а участники могут записать сумму по прежним правилам. Суммы попутки передаются в целых рублях. Пассажир платит напрямую водителю.

## 3. Модель данных (таблицы)
> Имена ниже — ориентир исходного проекта. Денежные единицы определяет [§8 AGENTS.md](../AGENTS.md): такси, доставка и банковский учёт — копейки; узкое исключение D7 для попутки (`Ride.price`, `Booking.price`, `pay_amount`, цены остановок) — целые рубли, см. ## 4. Матчинг (киллер-фича против такси)
Не «вызвать машину», а **найти совпадение**:
- ранжируем `rides` под `request` по: совпадение маршрута (from/to и попутные точки) → близость по времени → категория (больница/посылка/обычная) → места ≥ нужного → дети/багаж разрешены → рейтинг водителя → платное поднятие (внутри релевантных) → время создания.
- и наоборот: водителю показываем подходящие `requests` на его маршруте.
- На сервере — простой SQL/гео-фильтр (радиус городов), позже — настоящий гео-поиск.

### События подписок на попутки

`da_route_watch_dispatch` добавляет `routewatchevent` и `routewatchnotice`. История прежних сообщений с подтверждённой ссылкой на рейс защищает от повтора для действующих подписок получателя. Хранение записи о рейсе отделено от записи центра уведомлений. Уборка удаляет завершённые события через 30 дней, а записи о показе рейса через 180 дней после создания при условии, что рейс уже вышел из окна ленты.

Для согласованной выкладки сначала остановить процессы API со старой схемой рассылки, затем накатить миграцию и запустить новую версию API. По тому же окружению установить новые `yuldash-route-watch-worker.service` и `yuldash-route-watch-worker.timer` из `backend/deploy` и включить таймер. Он проверяет записанные события каждую минуту. Перед откатом дождаться обработки накопившихся событий, затем остановить новый API и таймер. Миграция запрещает откат при наличии необработанных событий.

Проверки очереди выполняются с синтетическими данными и заглушкой канала. Включение таймера на рабочем сервере относится к выкладке.

### Публикация попуток на выбранные даты

Серверный кандидат `POST /rides/series` принимает общий черновик и до десяти дат. Он приводит даты к минутам UTC, убирает повторы и фиксирует общую часть серии в существующем реестре команд. Каждая дата получает отдельный ключ, квитанцию и собственную транзакцию. Рейс и событие подписок фиксируются вместе с квитанцией. Ответ сообщает сохранённый исход каждой даты.

При потере ответа клиент повторяет исходный набор или одну неизвестную дату с прежним базовым ключом и прежним черновиком. Сервер сверяет квитанцию перед новой публикацией. Завершённые квитанции после окна прямого повтора читаются по ключу даты. Закрытие неизвестной даты использует общий API намерений и отпечаток этой даты.

### 5.2 Правила сделки попутки (аудит 2026-08-07, изменения контракта)
- **`POST /bookings`** — «только для своих» (`only_trusted`) теперь закрывает и бронь: не-«свой» (уровень < L3) получает **403** `{ru: "Поездка только для своих", ba: "Сәфәр тик үҙ кешеләр өсөн"}`. Раньше фильтр стоял только на выдачах (лента, карта, карточка, отклик), и закрытую поездку бронировали по прямому id — обещание «круга своих» ломалось на самом важном шаге.
- **`POST /bookings/{id}/driver-status {"status":"done"}`** — завершить можно только НАЧАВШУЮСЯ поездку: раньше времени выезда (допуск 30 минут на неточные часы) → **409** `{ru: "Поездка ещё не началась — завершить можно после времени выезда"}`. Повторный вызов по уже завершённой/отменённой броне по-прежнему отвечает «ок» (идемпотентность не тронута). Причина: цикл «опубликовал на 2030 год → забронировал вторым аккаунтом → завершил» из трёх запросов рисовал бейдж «N поездок» и открывал оценку.
- **`POST /requests/{id}/cancel`** — принимает заявку не только в `active`, но и в `matched` (раньше 400). Из `matched` не вело ни одной двери: ни отмены, ни правки, ни ночной чистки. Бронь и поездку отмена заявки не трогает.
- **`RideOut.driver_trips`** («N поездок») — считаются только СОСТОЯВШИЕСЯ поездки (уже выехавшие) и не больше `TRIPS_PAIR_CAP` (8) поездок с одним и тем же попутчиком за 30 дней. Тот же приём, что защищает средний балл от накрутки парой аккаунтов.
- **Локи под гонку** (`cancel_booking`, `no-show`, принятие отклика) читают строку ЗАНОВО: `with_for_update().execution_options(populate_existing=True)`. Без этого SQLAlchemy возвращал уже загруженный объект со старыми полями — лок брался, а перепроверка статуса смотрела в прошлое (овербукинг мест, две поездки на одну заявку).

## 8.5 🗄 Миграции БД — Alembic (с 2026-06-27)

Схема БД управляется **Alembic** — последовательностью версий схемы. Состояние применённых миграций на рабочем сервере здесь не подтверждено. Историческая июньская запись указывала baseline `75accea6f8bd`; она не подтверждает нынешнюю ревизию.

**Как готовить изменение схемы:**
1. Изменить модель и подготовить файл миграции в своей ветке на отдельной тестовой базе.
2. Проверить изменения схемы, одну конечную ревизию и применимый прогон миграций; успешная сборка не доказывает применение на сервере.
3. Использовать [руководство миграций](deploy-migrations.md) и [границы применимости выпускной инструкции](release-runbook.md). Создание миграций на рабочей базе и общий `downgrade -1` не являются текущим рабочим порядком.
4. Выкладка, изменение рабочей базы и её восстановление — только после отдельного «да» Александра по §8. Сначала нужен применимый к выбранной версии сценарий и подтверждённая резервная копия.

- Файлы: `backend/alembic/` (env.py, versions/) + `backend/alembic.ini`.
- `alembic upgrade head` идемпотентен (если уже на head — ничего не делает).
- Старые ручные `migrate_*.sql` — историч., больше не нужны (но в репо остались).
- ⚠️ `init_db` ещё зовёт `create_all` (создаёт отсутствующие ТАБЛИЦЫ как раньше). Для новых КОЛОНОК — только Alembic (create_all колонки не добавляет). Со временем — убрать create_all, перейти полностью на `alembic upgrade` в деплое.
