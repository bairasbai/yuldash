# 🏗️ Бэкенд Юлдаш — архитектура (блюпринт)

> Это план настоящего сервиса. Сейчас вся логика локальная и пропадает при перезапуске ([architecture.md](architecture.md)). Здесь — что строим, в каком порядке, по какой схеме. Документ не зависит от выбора технологии: модель данных и API одинаковы для любого стека.

## ✅ Статус (2026-06-22)
- **Фаза 1 бэкенда РЕАЛИЗОВАНА** в папке `backend/` (FastAPI + SQLModel + JWT). Эндпоинты: вход по SMS-коду (OTP, пока мок), поездки, заявки, брони, матчинг, статус водителя.
- **Проверено локально:** `backend/smoke.py` → `SMOKE OK` (логин → поездка → поиск → заявка → матчинг → бронь → подтверждение).
- **Фаза 2 РЕАЛИЗОВАНА** (там же): чат (сообщения по брони), семейный контроль (доверенные контакты, шаринг поездки, статусы «сел/доехал»), безопасность (SOS, жалобы, блокировки). Проверено: `smoke.py` → `SMOKE OK`.
- **Сервер куплен** Александром. Разворот — позже отдельным шагом. Для деплоя нужен SSH-доступ по ключу (НЕ присылать пароли в чат) + IP/ОС сервера. Инструкция деплоя — `backend/README.md`.
- **Дальше:** подключить реальный SMS-провайдер; написать `ApiRepository` в Android (пакет `data/`) поверх этих эндпоинтов и переключить экраны с моков по фазам.

## 0. Честный контекст (читать первым)
- Бэкенд = **сервер + база данных + хостинг + SMS** = это **деньги** (хостинг, SMS) и **поддержка** (кто-то чинит, когда падает).
- Это слабое место Александра по его же словам → тут ведёт **спец по серверам/безопасности** из команды.
- **Стартуем дёшево:** бесплатные тарифы (Supabase free / VPS за ~300–500 ₽/мес) хватит на пилот в Баймаке.
- **152-ФЗ:** телефон и геолокация — персональные данные. Нужны согласие, политика, хранение в РФ (для РФ-аудитории). Заложить с первого дня.

## 1. Роли
- **Пассажир** — ищет поездки, создаёт заявки, бронирует.
- **Водитель** — публикует поездки, откликается на заявки, проходит проверку. Кабинет: статус «на линии», маршруты, места, цена, история, рейтинг, документы.
- **Админ/диспетчер** — модерация водителей и жалоб, города/маршруты, реклама, спорные поездки, «диспетчерская» (оформить заявку за пожилого по звонку).

## 2. Авторизация
- Вход по **телефону + SMS-код** (OTP). Сессия — JWT (токен доступа + refresh).
- **Телефон скрыт** до подтверждения поездки (отдаём маскированный `+7 *** ** 12`, реальный — только подтверждённым участникам).
- Согласие на обработку перс.данных при регистрации (галка + версия оферты).

## 3. Модель данных (таблицы)
> Имена — ориентир. Деньги храним в копейках (int). Все даты — UTC.

- **users**: id, phone, name, role, language(ru/ba), verified, created_at, consent_version.
- **driver_profiles**: user_id, status(online/offline), rating, trips_count, about, badges[].
- **vehicles**: id, driver_id, make, model, color, plate, photo_url, seats.
- **driver_documents**: id, driver_id, type(license/sts/photo), file_url, status(pending/approved/rejected), reviewed_by.
- **rides** (предложение водителя): id, driver_id, from, to, waypoints[], depart_at, seats_total, seats_left, price, category(обычная/больница/посылка), comment, status(active/done/cancelled), boosted_until.
- **requests** (нужда пассажира): id, passenger_id, from, to, desired_at, seats, max_price, category, with_kids, baggage, comment, status, for_relative_of (семейный заказ).
- **bookings/matches**: id, ride_id, request_id?, passenger_id, driver_id, seats, price, status(pending/confirmed/onboard/done/cancelled), boarding_code, confirmed_at.
- **boarding_codes**: код посадки (4 цифры) на booking, проверяется при встрече.
- **messages**: id, thread_id(booking/request), sender_id, text, voice_url, transcript, created_at, read_at.
- **trusted_contacts**: id, user_id, name, relation, phone, notify_by_default.
- **trip_shares**: booking_id, contact_id, status_updates(sat/arrived) — семейный контроль.
- **ratings**: from_user, to_user, booking_id, stars, text.
- **badges**: проверен, ездит в больницу, можно с детьми, помогает с сумками, женщина-водитель, рекомендуют соседи.
- **reports / blocks**: жалобы и чёрный список.
- **partners / ads**: рекламодатель, erid, город, маршрут, категория, размещения, бюджет, статус, impressions, clicks (модель уже есть в приложении — переносим на сервер).
- **payments**: booking_id, amount, method(cash/transfer/card later), status(pending/paid/failed/refunded), provider_id.
- **audit_log**: кто что изменил (для админки и споров).

## 4. Матчинг (киллер-фича против такси)
Не «вызвать машину», а **найти совпадение**:
- ранжируем `rides` под `request` по: совпадение маршрута (from/to и попутные точки) → близость по времени → категория (больница/посылка/обычная) → места ≥ нужного → дети/багаж разрешены → рейтинг водителя → платное поднятие (внутри релевантных) → время создания.
- и наоборот: водителю показываем подходящие `requests` на его маршруте.
- На сервере — простой SQL/гео-фильтр (радиус городов), позже — настоящий гео-поиск.

## 5. API (REST, по фазам)

Плюс реальные: `/rides/near`, `/feed`, `/bookings/{id}/rate`, премиум-фильтры в `GET /rides`.

**Заявки:** `POST /requests`, `GET /requests/mine`, `GET /requests/feed` (для водителя по маршруту).
**Матчинг/брони:** `GET /match?request_id` / `?ride_id`, `POST /bookings`, `POST /bookings/{id}/confirm`, `POST /bookings/{id}/boarding` (код), `POST /bookings/{id}/status`.
**Водитель:** `POST /driver/online`, `POST /driver/documents`, `GET /driver/dashboard`.
**Чат:** `GET /threads/{id}/messages`, `POST /threads/{id}/messages` (текст/голос+транскрипт). Реалтайм — websocket/подписка.
**Семья:** `POST /trusted-contacts`, `POST /bookings/{id}/share`, статусы «сел/доехал».
**Безопасность:** `POST /sos`, `POST /reports`, `POST /blocks`.
**Админ:** `GET /admin/drivers?status`, `POST /admin/drivers/{id}/approve`, `GET /admin/reports`, `GET /admin/ads`...
**Платежи:** `POST /payments`, `GET /payments/mine`.

## 5.1 🆕 Эндпоинты (2026-06-28, большая сессия — всё на проде)
- **Поток заявок (замкнут):** `GET /requests/feed` (водитель видит заявки), `POST /requests/{id}/respond` (отклик + push пассажиру; нет устройства → Telegram админу), `GET /requests/{id}/responses`, `POST /responses/{id}/accept` (создаёт Ride+Booking). Таблица `RequestResponse`. `/responses` и `/accept` пускают admin (принять ЗА юзера).
- **Профиль:** `POST /me/update` (имя и/или `avatar_url`, оба опц.). `User.avatar_url` (миграция `migrate_avatar.sql`). `conversations`/`RideOut`/отклики отдают аватары.
- **Админ:** `POST /admin/request-for-phone` (создать юзера+заявку по телефону), `GET /admin/drivers/pending` (модерация), `GET /admin/reports` (жалобы). Все `role==admin`.
- **Чёрный список/жалобы:** `GET /blocks`, `DELETE /blocks/{id}`, `GET /reportable-users` (попутчики из поездок).
- **Прочее:** `POST /callback` (звонок оператору → Telegram админу), `GET /bookings/{id}/boarding-code` (код посадки участникам), `POST /driver/online` + `online` в `/driver/status` + `RideOut.driver_online`.
- **Автоадмин (auth.py `_maybe_promote_admin`):** роль admin при входе если совпал `telegram_id`==`ADMIN_TELEGRAM_CHAT_ID` ИЛИ `phone` в `ADMIN_PHONES`.
- **Уведомления админу (`services.notify_admin_telegram`):** запрос звонка, отклик на админ-заявку, срочная/«помощь»-заявка (`POST /requests` с `assisted=true` или category urgent) — в Telegram владельцу.

### 5.2 Правила сделки попутки (аудит 2026-08-07, изменения контракта)
- **`POST /bookings`** — «только для своих» (`only_trusted`) теперь закрывает и бронь: не-«свой» (уровень < L3) получает **403** `{ru: "Поездка только для своих", ba: "Сәфәр тик үҙ кешеләр өсөн"}`. Раньше фильтр стоял только на выдачах (лента, карта, карточка, отклик), и закрытую поездку бронировали по прямому id — обещание «круга своих» ломалось на самом важном шаге.
- **`POST /bookings/{id}/driver-status {"status":"done"}`** — завершить можно только НАЧАВШУЮСЯ поездку: раньше времени выезда (допуск 30 минут на неточные часы) → **409** `{ru: "Поездка ещё не началась — завершить можно после времени выезда"}`. Повторный вызов по уже завершённой/отменённой броне по-прежнему отвечает «ок» (идемпотентность не тронута). Причина: цикл «опубликовал на 2030 год → забронировал вторым аккаунтом → завершил» из трёх запросов рисовал бейдж «N поездок» и открывал оценку.
- **`POST /requests/{id}/cancel`** — принимает заявку не только в `active`, но и в `matched` (раньше 400). Из `matched` не вело ни одной двери: ни отмены, ни правки, ни ночной чистки. Бронь и поездку отмена заявки не трогает.
- **`RideOut.driver_trips`** («N поездок») — считаются только СОСТОЯВШИЕСЯ поездки (уже выехавшие) и не больше `TRIPS_PAIR_CAP` (8) поездок с одним и тем же попутчиком за 30 дней. Тот же приём, что защищает средний балл от накрутки парой аккаунтов.
- **Локи под гонку** (`cancel_booking`, `no-show`, принятие отклика) читают строку ЗАНОВО: `with_for_update().execution_options(populate_existing=True)`. Без этого SQLAlchemy возвращал уже загруженный объект со старыми полями — лок брался, а перепроверка статуса смотрела в прошлое (овербукинг мест, две поездки на одну заявку).

## 6. Безопасность уровня продукта
Проверка документов водителя (модерация в админке) · фото машины + госномер · код посадки · скрытый номер · SOS · доверенные контакты · жалобы/блокировки · аудит-лог. Чувствительное (точные координаты, телефон) — не логировать, отдавать только по праву.

## 7. Офлайн / плохой интернет (важно для районов)
- Черновик заявки и «повтор последнего маршрута» — локально на телефоне, синк при сети.
- Звонок водителю / SMS-сценарии как запасной канал.
- Минимальный трафик: лёгкие JSON, без тяжёлых картинок без нужды.

## 8. Диспетчерская (локальная киллер-фича)
Кнопка «Мне сложно, позвоните» → заявка в админку → оператор/доверенный помощник оформляет поездку за пожилого. Технологии Яндекса не побьём, **человеческим сервисом — можем**.

## 8.5 🗄 Миграции БД — Alembic (с 2026-06-27)

Схема БД управляется **Alembic** (история изменений + откат, «git для базы»). Прод проштампован baseline-ревизией `75accea6f8bd` (все текущие таблицы).

**Как изменить схему (новое поле/таблица):**
1. Поменял модель в `app/models.py`.
2. Сгенерить миграцию (на сервере, там deps+БД):
   `ssh root@85.239.52.55 "cd /opt/yuldash && ./.venv/bin/alembic revision --autogenerate -m 'что изменил'"`
3. Глянуть сгенерированный файл в `alembic/versions/`, забрать в репо (scp).
4. Накатить на прод: `./.venv/bin/alembic upgrade head`.
5. Откат при ошибке: `alembic downgrade -1`.

- Файлы: `backend/alembic/` (env.py, versions/) + `backend/alembic.ini`.
- `alembic upgrade head` идемпотентен (если уже на head — ничего не делает).
- Старые ручные `migrate_*.sql` — историч., больше не нужны (но в репо остались).
- ⚠️ `init_db` ещё зовёт `create_all` (создаёт отсутствующие ТАБЛИЦЫ как раньше). Для новых КОЛОНОК — только Alembic (create_all колонки не добавляет). Со временем — убрать create_all, перейти полностью на `alembic upgrade` в деплое.

## 9. Порядок миграции (мок → реальное)
Совпадает с порядком Александра:
1. **Auth** (SMS) + профиль/роль. Заменить фейковый логин.
2. **Водительский кабинет** (статус, документы, машина).
3. **Реальные поездки + заявки + матчинг** (заменить `demoRides`/локальные заявки).
4. **Чат + голос** (сообщения на сервере, голос→файл+транскрипт, сценарий «нажал→сказал→заявка»).
5. **Семейный контроль** (доверенные, шаринг статуса, уведомления).
6. **Безопасность** (модерация документов, SOS, жалобы).
7. **Админка**.
8. **Платежи** (сначала наличные/перевод, отметка вручную; карта — позже).
9. **Партнёры маршрута** (реклама на сервере + «партнёр маршрута»: кафе/аптека/СТО/больница по пути).

## 10. Как готовим приложение (не ломая текущее)
- Ввести тонкий слой данных: интерфейс `Repository` (например `RidesRepository`) с двумя реализациями — `MockRepository` (что есть сейчас) и `ApiRepository` (реальный сервер). Экраны зовут интерфейс, не моки напрямую.
- Тогда переключение «моки → сервер» = одна строка, по фазам, без переписывания экранов.
- Это «состояние вверх / почва под бэкенд» из `CLAUDE.md` (раздел 7).

## Открытые решения (за Александром + спецом по серверам)
- **Стек:** managed (Supabase — Postgres+auth+realtime, free tier, мало серверного кода) vs свой сервер (FastAPI/Ktor на VPS).
- **SMS-провайдер** для OTP (стоит денег; для РФ — напр. SMS-провайдеры с поддержкой РФ-номеров).
- **Хостинг** и кто поддерживает (Александр vs спец по серверам).
- **Хранение данных в РФ** (152-ФЗ) для российской аудитории.
