# Единый реестр проверки Юлдаш

Создан 20.09.2026. Этот документ — очередь оставшейся работы и единственное место для текущих статусов блоков. Старые отчёты остаются доказательствами, их не переписываем. Инвентаризация файлов не означает, что их поведение проверено.

## Основной проход пользователей — фиксированный список от 24.09.2026

По просьбе пользователя приоритет изменён: сначала связать основные пользовательские шаги, затем вернуться к редким гонкам. Это уточнение очереди B01–B11, а не новый параллельный аудит. Состав — **13 контекстов** из [карты ролей](audit-role-journeys.md); это не 13 независимых ролей БД и не 13 тестов. Один совместный путь может дать доказательства сразу двум строкам. Новые варианты не увеличивают этот список молча: добавление требует записанной причины. Необязательные варианты (торг, регулярный рейс, поездка для родственника и т.п.) остаются отдельными критериями своих блоков, не скрываются за основным проходом.

Путь принимается только при доказанной связке его шагов, зафиксированных клиенте/среде/версии, отсутствии необъяснённого сбоя и явном остатке внешних интеграций. API-тест не заменяет нажатие в Android; управляемый HTTP не доказывает работу настоящего сервера; PWA не заменяет Android. У каждого пути отдельно: основной успех, обычный отказ/повтор, внешняя проверка. Историческое доказательство не повторяем, пока не обнаружена изменённая зависимость; при неизвестной актуальности честно отмечаем необходимость сверки, а не объявляем его свежим.

## Что считаем кодом

Полный список, единственный блок-владелец каждого файла и SHA256 (отпечаток содержимого) находятся в [audit-code-inventory.json](audit-code-inventory.json). Алгоритм явно записан в `hash_algorithm`: текстовые переводы строк CRLF/CR нормализуются в LF перед SHA256, остальные байты сохраняются. Это исключает ложное изменение от checkout Windows/Linux. Бинарные материалы исключены, их отпечатки не рассчитываются. Снимок строит [tools/audit_inventory.py](../tools/audit_inventory.py) из tracked и неигнорируемых untracked файлов текущей рабочей копии. Он включает незакоммиченные правки. Время и номер коммита намеренно не входят в детерминированный снимок: доказательства привязываем к содержимому файлов, а не к одному HEAD грязной рабочей копии.

На первом снимке: **128 Android + 103 backend/app + 268 PWA = 499 основных исходников**. Дополнительно: **792 файла тестов/их поддержки, 294 файла инфраструктуры/конфигурации/текстовых ресурсов, 89 файлов публичного сайта/промоматериалов**. Всего **499 + 792 + 294 + 89 = 1674 файла**. Это разные категории, не количество тестов. Актуальные числа после изменений всегда брать из `counts_by_kind` JSON, а не переносить эти числа в новые отчёты вручную.

В область входят не только три приложения: найден отдельный публичный сайт `web/`, отличный от PWA `webapp/`, и код `promo/`. Они получили B11. XML/SVG, миграции БД, CI, манифесты, зависимости и скрипты входят отдельно. Конфигурация относится к B10, тест может принадлежать пользовательскому блоку.

Исключены: старый Flutter `mobile/` (не трогаем), эксперимент `experiments/`, документация, результаты тестов, приватные анкеты, бинарные картинки/видео/шрифты, зависимости и сгенерированные файлы. Секреты и локальные настройки не читаются. Список исключённых видимых git файлов с причиной есть в `excluded`; игнорируемые git локальные файлы вообще не обходятся. Инвентаризация не доказывает безопасность исключённых файлов или всех двоичных материалов.

Распределение по именам/путям — правило владения, не утверждение, что файл содержит только одну функцию. Например, `BookingActiveTripScreen.kt` принадлежит B02, хотя содержит чат; `ApiClient.kt` и общие модели — B09; общий протокол офлайн-хранилища и очередь — B01, а доставка сообщения — B05. Для `TripPass.kt` явно задан B01, поскольку в этом же файле есть Outbox: изменение должно попадать на рассмотрение и брони, и чата. При обнаружении смешанной ответственности не делим файл между двумя писателями: один владелец исправляет его по запросу другого блока. Правила распределения меняются в скрипте, а не вручную в JSON.

## Статусы и правила закрытия

- **Не проверено:** нет прикреплённого достаточного результата для этого пункта. Это не заявление об отсутствии любых исторических тестов.
- **Частично:** есть доказательства отдельных проверок, но остаются обязательные пункты.
- **Проверено локально:** все перечисленные локальные критерии пункта выполнены на зафиксированных отпечатках файлов.
- **Подтверждено устройством:** дополнительно пройден точно указанный сценарий на названном эмуляторе/телефоне. Эмулятор не подменяет физический телефон.
- **Блокировано доступом:** указан конкретный недоступный сервис/устройство/настройка и что нужно для продолжения. Такой пункт не считается пройденным.

Статус всего блока не повышаем по одному удачному тесту. «Закрыт для пробного выпуска» допустимо только после выполнения его обязательного списка, отсутствия известных блокирующих ошибок и сохранения доказательств. Остаточные ограничения перечисляются явно; общие проценты строк не являются критерием закрытия.

## Порядок работы

Идём **сверху вниз по смыслу**: действие пользователя → договорённость клиента и сервера → конкретная функция. Проверок при этом больше на дешёвом модульном уровне, меньше на уровне интерфейса и ещё меньше полных дорогих сценариев. Переворачивать пирамиду автоматических тестов и заново вручную обходить каждый экран после каждой правки не нужно.

Порядок: B01 → B02 → B03 → B04 → B05 → B06 → B07 → B08 → B09 → B10 → B11 → одна финальная совместная проверка. Зависимые пункты следующего блока можно выполнять в ходе основного сценария и сразу записывать доказательство под их ID — затем повторно их не выполнять. Если внешняя проверка блокирована, отмечаем это и продолжаем независимую работу.

## Как не повторять работу

1. **Один писатель на блок и файл.** Руководитель назначает исполнителя и записывает занятые пути. Общие файлы B09 и сборка — только у одного владельца. Другой агент читает и сообщает находку, но не переписывает тот же файл или отчёт.
2. **Статусы меняет только руководитель.** Исполнитель передаёт результат с ID, путями, отпечатками, тестами, средой и ограничениями. Отдельные отчёты создаём лишь для нового доказательства, а не нового пересказа старого материала.
3. **Перед новым тестом ищем уже имеющийся результат по ID/сценарию.** Совпали содержимое, влияющие зависимости и среда — принимаем доказательство без нового прогона.
4. **Повтор только с записанной причиной:** изменился файл; изменилась влияющая зависимость; новая ошибка/новая проверяемая ветка; другая среда; финальная интеграция. Простое «продолжаем», смена агента или новый день не являются причиной.
5. **Сначала прицельные тесты, потом общий контроль в точке объединения.** Не повторяем сервер/PWA из-за изолированного изменения Android, если не затронут общий контракт. Прежний широкий результат остаётся историческим, не выдаётся за свежий.
6. **Не складываем пересекающиеся прогоны.** Считаем уникальные ID тестов и последние результаты по ним. «70 после 32» обычно включает 32, это не 102 независимых проверки.

## Отпечатки и влияние изменений

Из корня репозитория:

```text
python tools/audit_inventory.py
```

Команда не меняет файлы: показывает добавленные, изменённые и удалённые пути, прямые блоки и консервативный список зависимых блоков для рассмотрения. Этот список **не команда повторить все их тесты**. Руководитель выбирает конкретные зависимые сценарии и записывает причину. Граф зависимостей намеренно грубый: изменение общего ApiClient может влиять на много областей; изменение документа не требует тестов приложения.

Перед принятием нового состояния сохранить прежний JSON вместе с доказательствами проверки, затем выполнить:

```text
python tools/audit_inventory.py --write
```

Обновление снимка не обновляет статусы и не закрывает задачи. `python tools/audit_inventory.py --check` возвращает код 1 при изменении входящих файлов или алгоритма хэширования, 0 при отсутствии такого изменения; документация не входит в эти условия. `--check` несовместим с `--write`. Для изолированной проверки есть `--root <репозиторий>` и `--baseline <снимок>`. Вывод содержит пути/назначения, но не содержимое файлов. Если новый файл распределён неудачно, исправить правило в скрипте и сохранить изменение назначения.

Для каждой выполненной проверки записывать:

| Поле | Что требуется |
|---|---|
| ID и сценарий | Один существующий номер, шаги и ожидаемый результат |
| Файлы и зависимости | Пути + SHA256 из сохранённого снимка; ссылка на сам снимок |
| Среда | ОС/эмулятор/физический телефон, локальный или настоящий сервер, настройки без секретов |
| Воспроизведение | Команда или точные шаги; до исправления — наблюдавшийся сбой |
| Результат | Лог/XML/снимок/видео; пройдено/провалено/пропущено, без подмены пропуска успехом |
| Повтор | Обязательная причина из пяти разрешённых выше либо «первичная проверка» |
| Остаток | Что этот результат не доказывает |
| Принятие | Руководитель проверил доказательства и изменил статус |

Исторические отчёты без точного снимка содержимого не привязываем задним числом к новым SHA256. Их используем как контекст; необходимость нового запуска решается по изменениям и риску, с явным объяснением.
