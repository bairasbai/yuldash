## 2026-07-21 — G6 окно свежести рейтинга: ОДИН хелпер на профиль и карточку (иначе разъедутся)
- **Зачем:** «право исправиться» — среднее по последним 50 учтённым оценкам, а не по всем навсегда. Число оценок — полное (пороги/«N отзывов» не должны поехать).
- **Ключевое решение:** рейтинг считался в ДВУХ местах — `user_rating` (одиночный: профиль, лестницы качества) и `drivers_bundle` (батч: карточки водителей в ленте `/rides`, против N+1). Окно применил через ЕДИНЫЙ `_rating_from_rows`, который зовут ОБА. Если бы окно попало только в один путь, у водителя с >50 оценок рейтинг в профиле и на карточке **разошёлся бы** — классический тихий баг. Инвариант закрыт тестом `test_user_rating_and_bundle_consistent`.
- **Обратная совместимость:** при ≤50 оценок (сейчас у всех — до запуска) — простое среднее по всем, как раньше; весь прежний rating/quality/matcher-сюит зелёный без правок. Правка чисто серверная, клиенту ничего не надо.
- **Побочно:** старый ключ сортировки `(x[2] is None, x[2])` мог упасть `TypeError` на 2+ легаси-строках без даты (`None < None`) — заменил на безопасный, nulls трактуются как самые старые (корректно для окна).
- **Окно = константа `RATING_RECENT_WINDOW=50`** рядом с `RATING_PAIR_CAP` (правится одним числом; у Яндекса 150 — у нас мягче). Без миграций.

## 2026-07-21 — G3 пуш водителю по направлению: расширяем `RouteWatch` (watch_kind), а не новая таблица
- **Зачем:** F13 «Карауль поездку» покрывал только пассажира (жду поездки). Водителю нужна зеркальная сторона — «есть заявка по твоему направлению». Это суть попуток.
- **Решение — одно поле `watch_kind` (rides/requests/both) на существующем `RouteWatch`, а не второй `DriverRouteWatch`:** матчинг, анти-спам, протухание, CRUD, дедуп — всё уже есть, переиспользуем. `rides`-путь (create_ride) и новый `requests`-путь (create_request) фильтруют подписки по kind. Дефолт `rides` = прежнее поведение (старый клиент и старые строки не ломаются). Дедуп учитывает kind: один человек может быть и пассажиром, и водителем на одном маршруте (две подписки).
- **Анти-спам общий для обоих типов** (один `last_notified_at` на подписку): `both`-сторож получит максимум 1 пуш/сутки суммарно (заявка ИЛИ поездка) — осознанно, чтобы не спамить.
- **Тип уведомления `request_watch` (не `route_watch`):** семантически другое событие; старый клиент неизвестный тип покажет как обычную запись (безопасный фолбэк), не примет id заявки за id поездки.
- **Миграция** `g3_request_watch` (down=`g1_parcel_track`, новый единственный head) — идемпотентна, `server_default='rides'`.
- **Проверка:** backend `pytest` **879 passed / 1 skipped** (`test_request_watch.py` 10 + регресс `test_route_watch.py`). Android (переключатель kind + обработка пуша) — по чеклисту у Александра.

## 2026-07-21 — G1 трекинг-ссылка посылки: переиспользуем `TripShare`, а не новая сущность

## 2026-07-12 — Город в профиле (`User.city`) — закрыт реальный пробел
- **Зачем:** у человека не было своего города (город хранился только у партнёра/курьера/таксиста). Из-за этого «Скидки по пути» и посылки не могли по умолчанию показать «в моём городе» — выбор вручную каждый раз; плюс это блокировало бейдж «Земляк» (F8).

- **Миграция** `city_profile` (down=`courier_c3`) — идемпотентная, оба пути проверены; новый единственный head. **Порядок вливания:** после `courier_c3` (т.е. поверх всего стека курьера).

## 2026-07-02 — Кеш GET-ответов с TTL (не дёргать сервер зря)
- **Было:** кеша ответов нет, каждый GET бьёт сервер. `/me` вызывался **4 раза** (isAdmin + бейдж + рейтинг пассажира + рейтинг водителя); статика `/ad-packages`+`/boost/plans` тянулась на каждом открытии кабинета/буста; `/popular-routes` и `/feed` поллятся раз в 45/60с, хотя меняются медленно.
- **Стало:** generic TTL-кеш в `ApiClient` (`cachedGet(key, ttlMs){ fetch }` + `ConcurrentHashMap`). Обёрнуты 8 геттеров:
  - **Статика (TTL 30 мин):** `ad-packages`, `boost-plans` — меняются лишь при редеплое бэка.
  - **Медленное (TTL 5 мин / feed 3 мин):** `popular-routes`, `my-routes`, `feed` — срезает давление поллинга карты.
  - **Личное (TTL 90с + инвалидация на мутациях):** `me`, `referral`, `contacts`.
- **Инвалидация:** `updateName/updateAvatar → me`; `addContact → contacts`; `redeemReferral/boostFree → referral`; `logout → весь кеш` (иначе следующий юзер увидит чужие данные).
- **НЕ кешируем** живое: `/rides`, `/rides/near`, `/requests/*`, `/bookings/*`, `/trip-state`, `/messages`, `/conversations`, `/notifications`, `/ads/mine` — меняются/поллятся, кеш = устаревшее.
- Эффект: вход в Профиль — минус 3 запроса `/me`; кабинет/буст/карта не тянут статику; поллинг бьёт сервер в разы реже. Экранов не трогал — только обёртка в `ApiClient`.
- **Персист статики в prefs (добивка):** `ad-packages`/`boost-plans` (публичные цены) сохраняются в prefs (`static_*`, сырой JSON) и **прогреваются в кеш на холодном старте** (`seedStatic` в `init`) → цены видны мгновенно при запуске и оффлайн; сеть освежает по 30-мин TTL. Приватности нет (данные публичные). Персист-логика build-verified; рантайм-подтверждение seed — на реальном устройстве (эмулятор: ТСПУ + шифрованные prefs мешают проверке).

QR/ссылка Сбербанка (СБП по номеру) = быстрый **дополнительный** канал к переводу «на доверии», без нового бэкенда и без денег на клиенте. Эквайринг остаётся следующим уровнем (код `payments.py` частично готов).

Ссылка формируется из `SBP_PHONE_DIGITS` → `https://www.sberbank.com/sms/pbpn?requisiteNumber=<цифры>` (проверена curl → 200).

Меняем реквизиты/логику в одном месте — «один шов» под будущий эквайринг. Кнопка «Оплатить в Сбербанке» шлёт `ACTION_VIEW`: есть приложение Сбера → оно, нет → браузер, нет обработчика → Toast + QR/номер как фолбэк (не падаем).
- **Партнёрская оплата = тот же получатель:** на админ-экране «Заявки на оплату» показываем QR платформенного `SBP_PHONE_DIGITS`, чтобы админ показал/переслал его партнёру. Отдельного «партнёрского» счёта нет — деньги идут туда же.
- **QR по нажатию, не всегда на виду (после вопроса «не повторяется ли Сбербанк везде?»):** донат/буст QR уже раскрывались в момент оплаты (лист/результат). Свернул под кнопку (`AnimatedVisibility`): QR появляется по тапу. Один юзер и так не видит повтора (донат/буст — разные моменты; кабинет/админка — разные роли), а по-нажатию убирает визуальный шум там, где оплата не главное действие экрана.

## 2026-07-01 — Доверенные контакты не должны сидеть в ViewModel как демо-данные

**Decision:** `YuldashViewModel.trustedContacts` стартует пустым и наполняется только результатом `/trusted-contacts`.

**Reason:** доверенные контакты — чувствительный пользовательский список. Если сервер вернул `[]`, UI обязан показать пустое состояние, а не демо-персон `Айгуль`/`Рамиль`, иначе пользователь видит несуществующих близких и может подумать, что поездка реально отправится им.

**Verification:** в эмуляторе bottom sheet `Кому отправить поездку` показывает `Сначала добавьте доверенный контакт в профиле`; моковые отношения `Дочь`/`Сосед` отсутствуют. `YuldashViewModelTest` проверяет пустой стартовый список.

## 2026-07-01 — Серверные даты брони форматируем до передачи в карточку

**Decision:** карточки моих поездок и пассажирского кабинета получают `formatDepart(departAt)`, а не сырой `depart_at` из API.

**Reason:** backend отдаёт ISO-строку, в том числе с дробными секундами (`2026-07-03T12:44:19.838345`). Это контракт обмена между сервером и приложением, но не пользовательский текст.

**Verification:** `CoreLogicTest` проверяет `2026-07-03T12:44:19.838345` → `03.07, 12:44`; эмулятор на вкладке `Поездки` показал `03.07, 12:44` и не показал сырой ISO.


## 2026-07-03 — Мобильная оптимизация лендинга (web/): «эталон для телефона»

**Проблема (от Александра):** на iPhone лендинг лагает и долго грузится, на десктопе идеально. Диагноз по коду: главный убийца плавности — `Aurora` (3 пятна по 700px с `blur-140px` + 2 вращающихся курая крутились БЕСКОНЕЧНО без блокировки на мобиле → GPU телефона занят постоянно). Видео (4.9МБ) уже было отключено на мобиле — не при чём.

**Решение (десктоп НЕ трогаем, всё под `< lg = 1024px`):**
- Новый SSR-безопасный хук `components/useIsMobile.ts` — стартует `false` (сервер и первый клиентский рендер = десктоп-разметка → нет hydration mismatch), после mount переключается по `matchMedia("(max-width:1023px)")`.
- `Aurora`: на мобиле — статичный слой `radial-gradient` (тот же вид, БЕЗ `filter:blur` и БЕЗ анимации, ноль работы на кадр). На десктопе — прежняя живая аврора.
- `Hero`: на мобиле выкл. скролл-параллакс (`yText/yPhone/fade`) и спотлайт за курсором.
- `HeroBackdrop`: на мобиле выкл. «световые следы» и Ken-Burns-зум постера (постоянный трансформ большой картинки).
- `PhoneMockup`: на мобиле выкл. бесконечное «парение» телефона.
- `globals.css` `@media (max-width:1023px)`: глушим `glow-pulse` (drop-shadow всего заголовка), `shine-border` (border-beam), `coverage-runner`, `mockup-car`/`mockup-ping`.

**Что НЕ сделано (честно):** размер JS-бандла (~1.2МБ, framer-motion в 32 компонентах) НЕ уменьшен — я срезал стоимость АНИМАЦИЙ (рантайм/GPU/главный поток), это чинит «лагает» и улучшает отзывчивость, но радикальная диета JS (напр. `LazyMotion`) — отдельная бОльшая задача. Проверка: `tsc` 0 ошибок, `esbuild` OK. Финальная сборка/деплой — на Windows Александра.
