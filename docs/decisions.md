## 2026-06-28 — Нагрузочный тест прода + воркеры 2→5
- **Зачем:** Александр готовит запуск, ждёт ~10к человек. Нужен реальный потолок, не гадание.
- **Что сделано:** `gunicorn -w 2 → -w 5` в `/etc/systemd/system/yuldash-api.service` (бэкап юнита `.bak.*` рядом; 2 ядра → формула 2×cores+1=5; RAM хватает, 3.8ГБ). Прогнал нагрузочный тест на сервере против `127.0.0.1:8000` (минуя ТСПУ), уникальный `X-Forwarded-For` на запрос → обход IP-rate-limit (он берёт XFF первым, `middleware._client_ip`).
- **Результаты (реальные, 0 ошибок):**
  - Лёгкие чтения (`/feed`,`/rides`,`/popular`): потолок **~400 зап/с** (упор в воркеры).
  - Тяжёлые залогиненные (`/me`,`/bookings/mine`,`/conversations`,`/rides/near`): **~260 зап/с**, комфорт (p50<100мс) до ~20 одновременных, деградация но живой до 80.
- **Вывод по ёмкости:** комфортно **~1500–2000 одновременно активных**; деградация-но-работает до ~4–5к. База при размазанном входе: **~10–20к зареганных ок**.
- **НЕ протестировано (и почему):** реальный **вход через Telegram** (нельзя спамить бота/плодить юзеров) — это главный риск спайка запуска (Telegram ~30 кодов/сек + тяжёлый auth); **запись** (publish/book/SOS — не гадим в прод-БД). Их потолок ниже.
- **Узкое место запуска = вход, не лента.** Если 10к логинятся в один час — упрётся в Telegram OTP, а не в эти 260–400 зап/с. Рычаги дальше: сервер крупнее (4–8 ядер), очередь/троттл логина в UX, чат→Redis pub/sub, Postgres на отдельный хост.

## 2026-06-28 — Выжали максимум из текущего сервера (A+B+C), без апгрейда железа
> Александр: «выжать максимум, сервер крупнее добавлю после 5к подписчиков». Сделано 3 шага, каждый задеплоен+проверен на проде. Железо не меняли (2 ядра/3.8ГБ).
- **A. Throughput:** воркеры `gunicorn 2→5` + `--preload` (общий код в RAM); кеш `/rides` в Redis (горячий список, дефолтный вызов без фильтров, TTL 20с — был единственный горячий read без кеша); engine `pool_pre_ping=True`+`pool_recycle=1800` (не отдавать мёртвые коннекты PG под нагрузкой). **Замер до/после на лёгких чтениях: ~400 → ~594 зап/с (+50%)**, p50 при conc100 = 192мс, 0 ошибок.
- **B. Чат масштабируем:** `ConnectionManager` → **Redis pub/sub** (`PUBLISH chat:{booking_id}` + подписка на воркере; фолбэк local-only без Redis). Чинит разрыв живого чата между воркерами (на 5 воркерах собеседники падали на разные процессы). **Проверено на проде: 2 WS-клиента одной брони — оба получают сообщение.**
- **C. Вход:** аудит показал — **бэкенд входа уже спайк-безопасен**: код шлётся ОТВЕТОМ на вебхук Telegram (`return sendMessage`), сервер НЕ делает исходящий HTTP → воркер не висит. Узкое место = лимит самого Telegram ~30 сообщений/с (внешний, лечится клиентским UX-повтором, не сервером). Добавил только гигиену: чистка просроченных `TgAuth`/`OtpCode` в вебхуке (его частоту Telegram сам лимитирует → клиентский спайк не грузит).
- **Индексы БД** проверены на проде — все горячие колонки покрыты (вкл. композит `ix_ride_status_depart`, GiST-гео). Не трогали. PG-тюнинг (shared_buffers 128МБ) отложен — на текущих данных мало пользы, риск.
- **Итог (реалистичный микс чтения+гео+вход, 5 зелёных):** **~290 зап/с, комфорт (p50<100мс) до ~20 одновременных, 0 ошибок до 80.** Перевод: **~1500–2300 одновременно активных комфортно; база ~10–20к зареганных при размазанном входе.** Все проверки: pytest 48/48, smoke+security OK, прод 0 трейсбеков.
- **Следующий рычаг (после 5к подписчиков):** сервер 4–8 ядер — главный множитель. До тех пор текущий выжат.

Refresh-ротацию НЕ делаем (больший передел auth, не нужен): access 30 дней + ревокация достаточно.
- **Пагинация — опциональная и обратносовместимая.** `limit/offset` на растущих списках; `limit=None` (дефолт) = прежнее поведение (все, прежний порядок). `order_by` для брони/заявок добавляется только при пагинации — чтобы не менять порядок дефолта. Потолок 200/страница. Android (массивы) не трогаем — load-more UI отложен (YAGNI на текущем объёме).
- **Alembic ВВЕДЁН в строй (чистый baseline).** Прежние 3 миграции падали на sqlite (ALTER CONSTRAINT) и на проде не запускались → заменены одним `0001_baseline` = `SQLModel.metadata.create_all/drop_all`: работает на sqlite+postgres, всегда совпадает с моделями (нет ручного DDL для рассинхрона). Прод (таблицы уже есть): разовый `alembic stamp head`. Рантайм по-прежнему `create_all` — Alembic это верифицируемый путь миграций, а не обязательная зависимость старта.

## 2026-06-28 (scale-tier end-to-end, Opus, worktree → задеплоено)
- **Refresh-токен ротация.** Access короткий (`ACCESS_EXPIRE_MIN`=7д) + opaque refresh (90д, в БД лежит ХЕШ sha256). `/auth/refresh` ротирует (старый refresh гасится). logout ревокует все refresh + bump `tokens_valid_from`. Android: `ApiClient` хранит refresh, на 401 авто-обновляет (Mutex против пачки 401) и повторяет запрос один раз. Обратно совместимо: входы теперь отдают `{access_token, refresh_token, user}` (старый клиент берёт только access). Подвох: `issue_tokens` коммитит → объект `user` протухает → `session.refresh(user)` перед сериализацией.
- **Redis rate-limit с фолбэком.** `REDIS_URL` задан → счётчики в Redis (общие на воркеры/серверы, фикс-окно 60с INCR+EXPIRE); пусто/сбой → in-memory (на воркер). Сбой Redis не валит запрос. На проде Redis уже стоял (соседняя сессия) → код подхватил.
- **PostGIS — корневой prerequisite сделан.** From/to хранились только как названия → добавил геокод концов при публикации (`services.geocode_city`: CITY_COORDS бесплатно → иначе Яндекс) в колонки `ride.from_lat/lng,to_lat/lng`. `/rides/near` на postgres использует `ST_DWithin` (GiST-индекс по `geography`) как префильтр, фолбэк — Python-haversine по тем же координатам (sqlite/без PostGIS/ошибка). PostGIS extension+индекс на проде поставлены.
- **load-more.** Бэкенд `limit/offset` (обратносовместимо) на `/rides`,`/bookings/mine`,`/requests/mine`,`/rides/near` (последний отдаёт `count`=всего). Android: «Ближайшие» — карточка `NearbyMoreCard` в конце ленты, `nearbyLimit += 5`. Глобальную нав-архитектуру (все поездки в стейте `YuldashApp`) не трогал — load-more только в самодостаточном «Ближайшие».
- **init_db идемпотентен под воркерами:** `create_all` в try/except ProgrammingError (гонка gunicorn). См. lessons.
- **Кеш-стратегия (пункт промта, доделан):** Redis не только под rate-limit, но и кеш горячих глобальных read-эндпоинтов — `/feed` (TTL 60с), `/popular-routes` (120с). Хелперы `services.cache_get_json/cache_set_json` (sync redis, фолбэк — без кеша). Снимает full-table-scan при росте. Проверено: ключи `feed:v1`/`popular_routes:v1` живут в Redis на проде.
- **PostGIS-регрессия поймана+закрыта:** префильтр `WHERE from_lat IS NOT NULL` ронял существующие (негеокоженные) поездки из `/rides/near` с радиусом → изменил на `from_lat IS NULL OR ST_DWithin(...)` (NULL-координатные проходят, их фильтрует Python-haversine по CITY_COORDS) + бэкфилл координат существующих поездок (`migrate_geo_backfill.sql`). Проверено: `/rides/near` снова возвращает поездки (count=2, было бы 0).
