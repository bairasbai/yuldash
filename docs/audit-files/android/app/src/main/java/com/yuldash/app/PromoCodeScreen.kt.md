## Назначение

Один промокод на аккаунт (вход: Профиль → «Промокод»). Если код уже применён (`getMyPromo`) —
постоянный экран «Твой промокод CODE» с тем, что он дал (`welcome` — приветствие, `boost` — N
бесплатных поднятий, `taxi_ride` — скидка на ОДНУ поездку такси, которая срабатывает сама в цене
заказа и оплачивается Юлдашем из комиссии, а не водителем). Если кода ещё нет — поле ввода
(заглавные, моноширинно, не длиннее серверного предела) + «Применить» (`applyPromo`). Успех —
анимированная галочка + серверное сообщение на языке интерфейса. Код по желанию: отказ ничего
не блокирует (честный дисклеймер виден на всех состояниях, кроме экрана успеха).

## Связи

- Сеть (`data/ApiClient.kt`, вне зоны — только читал): `getMyPromo`, `applyPromo` (сам ещё раз
  делает `trim().uppercase()` перед отправкой — защита дублируется, не противоречит).
- Сервер: `backend/app/routers/promo.py`, `PromoCode`/`PromoApplyIn` в `backend/app/models.py`
  (`max_length=32` — источник предела длины в `normalizePromoCodeInput`). Серверная логика
  проверена листом 1.3 — переаудировал только то, как Android с ней разговаривает.
- `kopToRub` — из `CouponsScreen.kt` (тот же модуль, `internal`), для денежных подписей.
- Скидка `taxi_ride` реально применяется на экране заказа такси (вне зоны этого листа) — здесь
  только объясняется пассажиру и показывается её судьба.

## Найденные ошибки

| ID | Что было (по-человечески) | Как воспроизвести | Исправление | Тест: до → после |
|---|---|---|---|---|
| B1 | Поле ввода промокода не имело предела длины. Человек, вставивший в поле случайно скопированный длинный текст (например, весь абзац вместо кода), отправлял его ЦЕЛИКОМ на сервер — гарантированный отказ по длине (сервер хранит код максимум 32 символа) вместо того, чтобы поле просто не дало напечатать лишнее | `normalizePromoCodeInput("A".repeat(50))` — возвращал строку из 50 символов вместо 32 | Добавил `.take(32)` в `normalizePromoCodeInput` (предел — тот же, что `PromoCode.code max_length=32` на сервере) | `PromoCodeInputNormalizationTest::tooLongInputIsCappedAtServerLimit`: до фикса длина результата 50 (неверно) → после 32 (верно). Подтверждено мутацией M6 |

Это точечное усиление (не падение существующего теста до фикса, т.к. предела не было вовсе) —
честно: не было «до» с падающим тестом на СТАРОМ коде, потому что функции `normalizePromoCodeInput`
раньше не существовало отдельно (логика была инлайн в `onValueChange` без предела). Поведение
«до» воспроизведено и зафиксировано мутацией M6 (откат `.take(32)` → `.take(320)` на ИСПРАВЛЕННОМ
коде даёт тот же эффект, что отсутствие предела — тест падает).

## Остаток и ограничения

- `PromoPerkChip` (строки 331–358) проверен чтением кода (определение скидки по сумме, а не по
  виду кода — уже исправлено до этого листа, без регрессии), без отдельной мутации: это чистое
  отображение уже провалидированных сервером чисел, менее рискованно, чем явные пункты фокуса
  листа.
- Скидка `taxi_ride` реально СПИСЫВАЕТСЯ/ПРИМЕНЯЕТСЯ на экране заказа такси — это вне зоны
  (другой файл), здесь проверено только корректное информирование пассажира о её судьбе.
