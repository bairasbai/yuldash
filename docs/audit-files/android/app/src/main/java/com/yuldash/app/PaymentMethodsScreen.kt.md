## Назначение

«Способ расчёта с водителем» — НЕ кошелёк и не платёжный экран: деньги через приложение не
идут (Модель А). Пассажир выбирает «наличные / СБП / договоримся», выбор синхронизируется с
сервером ТОЛЬКО если уже есть живой заказ (`activeOrderId > 0`), иначе это просто память на
будущий заказ. Карты/корп-счёт — блок «скоро», нажатие считается заявкой (аналитика).

## Связи

- `ApiClient.setInstantPaymentMethod(orderId, method)` — `POST /instant/orders/{id}/payment`
  (ApiClient.kt, вне зоны, только чтение). Ответ ошибки не содержит специфичного кода —
  любой сбой трактуется как «не долетело».
- Вызывается из `YuldashApp`/`InstantOrderScreen`-подобных мест (передают `current`,
  `activeOrderId`) — сами экраны вне зоны листа, не трогал.
- Общий выбор хранится выше по дереву композиции (`PAY_METHOD_PREF`), экран сам prefs не
  трогает.

## Остаток и ограничения

Реальный `WebSocket`/push-уведомление водителю о смене способа — вне зоны (сервер); тут
проверена только честность клиента перед пассажиром. Контраст/48dp чек-боксов и доступность
визуально не проверялись на эмуляторе (только структурно по коду — `contentDescription` у
галочки двуязычный, строки ≥48dp по `heightIn`).

**P3, не блокирует (из отчёта ведущему):** ответ сервера при выборе способа сводится к
`.isSuccess`/`false` — на 409 «Поездка уже завершена» пассажир видит общую строку «Водитель об
этом не узнает» (как при обрыве сети), хотя сервер отдаёт человеческий текст на двух языках.
Решение за Александром (отдельная задача, не денежный риск).
