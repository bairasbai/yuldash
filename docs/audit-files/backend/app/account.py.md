# Карточка: `backend/app/account.py`

- Статус: verified
- Лист: leaf-2.1
- Проверял: Sonnet 5 (leaf-2.1); принимал: Opus 5.5

## Назначение

Необратимое удаление аккаунта и всех персональных данных человека (152-ФЗ, право на удаление) —
вызывается из `POST /me/delete` (`routers/auth.py`). Два слоя: честные гейты «сначала закрой вот
это» (`guard_can_delete`, 409 с объяснением на двух языках) и сам каскад удаления/обезличивания по
~30 таблицам в порядке, безопасном по внешним ключам (`delete_user_account`). Отдельно решает
классическую дилемму «жалоба/спор» — моя сторона стирается, сторона ещё живого оппонента остаётся
нетронутой.

## Связи

- Вызывается из `routers/auth.py::delete_me` (`POST /me/delete`): `guard_can_delete` →
  `delete_user_account`.
- `routers/courier.py::_commission_owed_kop` — единственный источник формулы долга курьера (ленивый
  импорт, чтобы не ловить цикл на старте).
- `storage.py::get_storage` — диск/S3 для удаления медиа; `instant_service.py::presence_offline` —
  снятие точки из Redis (ленивый импорт).
- Таблицы (неполный список самых чувствительных): `User`, `Consent`, `RefreshToken`, `OtpCode`,
  `TgAuth`, `DeviceToken`, `WebPushSubscription`, `TaxiApplication`, `CourierApplication`,
  `DriverProfile`, `Incident`, `Report`, `SosEvent`, `SupportTicket`+`SupportMessage`, `Trust`,
  `InviteCode`, `DeviceBan` (отвязка, не удаление).

## Найденные ошибки

Ошибок не найдено. Отдельно проверено: гейт удаления (R1, пять под-проверок) и сам каскад (R2–R4)
воспроизведены нарочной поломкой — действующий код ловит каждую. Подозрение, не подтверждённое
ошибкой: в `delete_user_account` строка `session.execute(delete(TextFlag).where(TextFlag.user_id
== uid))` встречается ДВАЖДЫ (раздел «3.17» и повторно перед «3.21», с комментарием про слияние
веток 2026-08-12). Вторая удаляет 0 строк (первая уже всё удалила) — избыточно, но безвредно
(идемпотентно, не меняет результат и не замедляет ощутимо). Не исправлял: правило листа — «трогай
только то, что нужно для задачи», а это не ошибка и не риск, упоминаю для чистоты карточки.

## Остаток и ограничения

- R5 (свобода номера после удаления) проверена ЧТЕНИЕМ кода (`if phone: delete(OtpCode).where(phone
  == phone); delete(WaitlistEntry)...`) и покрыта существующим широким тестом
  `test_delete_account_leaves_no_residual_anywhere`, но отдельной ТОЧЕЧНОЙ нарочной поломки именно
  на этот под-пункт я не заводил — посчитал избыточным против уже 4 мутаций на файл с деньгами и
  личными данными; если нужна строгая «одна поломка на каждый под-пункт R1/R5», это недостающий
  M19, можно добавить по запросу.
- Полный сквозной прогон «удалить аккаунт → тот же номер регистрирует НОВОГО человека → старый
  История недоступна» силами ТОЛЬКО этого файла не воспроизводил как HTTP-сценарий (это требует
  `routers/auth.py::verify`, уже проверено в его карточке через `test_a_recycled_number_is_a_new_person.py` —
  но там сценарий «номер молчал», а не «аккаунт явно удалён»); логика освобождения номера в
  `delete_user_account` идентична `antifraud.py::release_phone` по намерению (служебная пометка, не
  удаление строки целиком) — отдельно не сверял побайтово.
- Redis-зависимый шаг (`presence_offline`) не проверял на живом Redis (вне доступа песочницы) —
  обёрнут в `try/except`, при недоступности Redis не роняет удаление (это проверено: сам
  `delete_user_account` не падает, если импорт/вызов бросает исключение).
