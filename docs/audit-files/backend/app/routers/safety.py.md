# Карточка: `backend/app/routers/safety.py`

- Статус: verified
- Лист: leaf-3.1
- Проверял: Sonnet 5 (leaf-3.1); принимал: Opus 5.5

## Назначение

Все серверные двери безопасности поездки: красная кнопка SOS (с контекстом «где» и «с кем»,
SMS доверенным, Telegram дежурному), её админ-лента и приём в работу, запрос обратного звонка,
жалобы §9 (анонимные, с правом «не заплатил» и требованием фото по «грязно»), чёрный список
(блокировка + приватность имён), список «на кого можно пожаловаться», зимний протокол
(«застрял на трассе» + авто-проверка «доехал?» для попутки/такси/доставки). Один файл на все
три сценария (попутка/такси/доставка) — логика `_roadside`/`_winter_run` общая, различаются
только «кого спрашивать» и «кому звонить».

## Связи

- Таблицы: `SosEvent`, `Report`, `Block`, `TrustedContact`, `TripShare` (только читает —
  создание/отзыв живёт в `routers/family.py`, ВНЕ зоны), `Booking`/`Ride`/`InstantOrder`/
  `ParcelDelivery`.
- Зовёт `safety_logic.have_met` (приватность блок-листа), `safety_logic.trip_really_happened`
  (требование фото), `winter_escalate.escalate_now`/`ESCALATE_AFTER_MIN`, `quality.*`
  (пауза/лестница/уведомления — ВНЕ зоны), `debt.*`/`carphoto.*` (побочные эффекты — ВНЕ зоны),
  `app.observability.scrub_exc` (моя правка).
- Android: `SosScreen`, `RoadsideHelp.kt`, `WinterProtocol.kt`, `ActiveSharesList`,
  `BookingActiveTripScreen`/`InstantOrderScreen` (шторки «поделиться») — клиент вне зоны, не
  трогал.
- `sos_escalate.escalate_unhandled` читает `SosEvent.status`, который меняет
  `admin_sos_handle` — после «принял» повторная эскалация этот сигнал не видит.

## Остаток и ограничения

- **Честно про нестабильность на PostgreSQL.** Из 6 прогонов
  `python tools/audit_file_status.py run-tests --leaf leaf-3.1 ... --db postgres` один (первый)
  упал на `test_l3_1_log_privacy.py::test_сбой_требования_фото_по_жалобе_не_пишет_телефон_в_лог`
  — телефон оказался НЕ замаскирован, хотя код фикса (`scrub_exc`) не менялся между прогонами.
  Остальные 5 прогонов (включая отдельный запуск только этого файла, запуск пары «координаты
  → carphoto» и дважды полную ручную реконструкцию всего набора тестов листа на свежей базе)
  прошли зелёными. Я НЕ нашёл воспроизводимую причину: это не порядок тестов (полную
  последовательность воспроизвёл — прошла), не порча `_SCRUB` другим тестом (ни один тест
  листа/набора `grep` не трогает `app.observability`). Не выдаю это за «исправлено и
  доказано» — фиксирую как однократный, не воспроизведённый по требованию сбой. Прошу ведущего
  перепрогнать `--db postgres` несколько раз при приёмке; если повторится — это самостоятельная
  находка (нестабильность scrub_exc/логирования под нагрузкой), не часть M6.
- **ВНЕ ЗОНЫ — находка (не моя правка).** Две других места с тем же классом бага (сырой текст
  исключения в лог) живут в `debt.py`/`carphoto.py`/`services.py`/`db.py` и ещё ~38 файлах
  проекта (грубый подсчёт: `grep -rn 'except Exception as e:' app/ | wc -l` → 63 места, из них
  41 логируют `{e}` без `scrub_exc`). Это СИСТЕМНЫЙ паттерн, а не специфика моих трёх файлов —
  чинить его целиком силами одного листа не стал (вне OWNS, риск случайно задеть чужую логику
  в 40 местах без ревью). Предлагаемая правка: тест-сторож по образцу
  `test_errors_speak_both_languages.py` — ищет `except Exception as e:` рядом с
  `log.(warning|error)(f"...{e}"` без `scrub_exc` в радиусе пары строк, с перечнем принятых
  исключений (например, места, где `e` гарантированно не касается БД/пользователя).
  Ситуация человека: при сбое ЛЮБОГО из этих 38 мест телефон/секрет может осесть в логе сервера.
- **ВНЕ ЗОНЫ.** `routers/family.py` (создание/отзыв `TripShare`, GET .../shares) — читает мой
  фокус «поделиться поездкой отзывается / чужой не получит по id», но живёт в другом файле.
  Прочитал использование `TripShare` в СВОЁМ файле (только чтение для зимнего протокола) —
  утечек не нашёл (запрос фильтрует по `booking_id`/`order_id`, не отдаёт сам токен ссылки).
  Создание/отзыв/генерацию токена не проверял — не в OWNS.
- `_report_counterparty` без привязки к поездке (голый `target_user_id`) не проверяет, что
  автор и цель вообще пересекались — это СОЗНАТЕЛЬНО (можно пожаловаться на постороннего,
  админ увидит), и единственная защита от злоупотребления — `MAX_REPORTS_PER_HOUR` + дедуп
  суток + отсутствие авто-наказания (`trip_really_happened` в `quality.escalate_severe`,
  проверено `test_report_cannot_pause_a_stranger.py`). Специально не менял — это чужая, уже
  согласованная политика продукта, а не дыра.
- Двойное нажатие SOS (несколько `SosEvent` подряд за секунды) НЕ дедуплицируется сервером
  намеренно (комментарий в коде: «жизнь дороже») — каждое нажатие пишет свою запись и шлёт
  свой Telegram (не капится), SMS близким капятся потолком 6/час. Это подтверждённое
  ПРОЕКТНОЕ решение, не ошибка: не стал заводить «поломку», которая требовала бы дедупа,
  которого продукт сознательно не хочет.
- Производительность: все HTTP-вызовы (`httpx` внутри `notify_admin_telegram`/`send_text`)
  в этом файле либо в `BackgroundTasks` (после ответа), либо в `def request_callback`
  (синхронная FastAPI-ручка без `async` — выполняется в threadpool, не блокирует event loop).
  Ни одного `async def`-обработчика с синхронным HTTP внутри САМОГО запроса не нашёл (искал
  явно, п. 4а брифа).
- Postgres-гонки: в этом файле не нашёл места, где нужна настоящая параллельная транзакция
  (двойное нажатие SOS не гонка — каждое создаёт свою независимую запись намеренно; дедуп
  жалобы читает-потом-пишет без `with_for_update`, но цена ошибки — дублирующаяся жалоба от
  того же автора на тот же повод, не деньги и не чужие данные; отдельно нарочную поломку не
  заводил, честно фиксирую как открытую, не «защищено»).
