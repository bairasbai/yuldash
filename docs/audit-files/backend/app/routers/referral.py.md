## Назначение

Реферальная программа «позови своего»: свой код, кто пригласил, бонусы (1 бонус = 1 бесплатное
поднятие поездки, по прайсу 200 ₽). Два вида бонуса: за ввод чьего-то кода (обоим по одному) и
водителю-пригласившему за то, что приглашённый реально «раскатался» (≥3 живых поездки с ≥3
разными пассажирами). Два потолка: `MAX_REFERRAL_CREDITS` (остаток на руках) и
`MAX_REFERRAL_BONUS_LIFETIME` (пожизненный — ограда фермы), плюс месячный потолок водительских
бонусов на одного пригласившего.

`grant_referral_credit` — единственная точка начисления, её зовут обе двери: `/referral/redeem`
и `reward_driver_referral` (хуки на `done` в такси/попутке). Используется также `routers/promo.py`
(boost-бонус — тот же механизм и кэп).

(`backend/tests/test_referral_farm_cannot_be_raced.py`, волна 202, и

## Найденные ошибки

Ошибок не найдено ни мной, ни независимым ревью — единственное замечание по этому файлу было
к КАЧЕСТВУ моего теста R3 (см. «Остаток», исправлено).

Независимое ревью отдельно зафиксировало четыре МЕЛКИХ, не блокирующих денежных неточности —
записываю честно, без исправления (не входили в обязательный список правок):

1. **Кольцо из трёх в реферале (A→B→C→A).** Защита `referral_redeem` ловит только ПАРНЫЙ
   обмен (`referrer.referred_by == user.id`); цепочка из трёх ввела бы коды по кругу и каждый
   получил бы бонус, хотя новых людей не прибавилось. Серьёзность низкая: каждый вводит код
   РОВНО РАЗ в жизни аккаунта, и свежих фейковых аккаунтов для цепочки из трёх нужно минимум
   три — порог усилий тот же, что у фермы, которую уже режет пожизненный потолок.
2. **Гонка месячного потолка водительского бонуса (+1).** `reward_driver_referral`:
   `granted_driver_bonuses_this_month(...) >= DRIVER_BONUS_MONTHLY_CAP` — обычное «прочитал,
   потом решил», без лока. Два приглашённых «раскатались» в одну секунду → оба проходят
   проверку, потолок месяца продвигается на 6-й вместо 5-го. Цена — 200 ₽ сверх потолка,
   событие редкое (нужны два «раскатавшихся» в один момент у одного реферера).
3. **500 вместо честного отказа при той же гонке.** Второй параллельный `reward_driver_referral`
   падает на `IntegrityError` уникального индекса `ReferralBonus.invited_user_id` уже ПОСЛЕ
   `done`-перехода поездки — деньги целы (бонус не задвоится), но ответ пользователю — 500, а
   не аккуратный отказ.
4. **Потерянное обновление boost-бонуса в `promo.py`** (не в этом файле, но делит
   `grant_referral_credit`'s потолок): `user.referral_credits = min(старое+perk, MAX)`, где
   «старое» прочитано в начале запроса — при параллельной трате/начислении возможен ±1.
   `referral.py` сам этой ошибки избегает (атомарный `coalesce(...)+1`).

**Почему не чиню:** все четыре — не в списке обязательных правок независимого ревью для этого
круга, цена ошибки низкая (единицы бонусов по 200 ₽ в редких одновременных событиях), а
правка №2/№3 меняет поведение `reward_driver_referral` (общий с попутками и такси код,
вызываемый из `instant.done`/`bookings.driver-status`/`family.trip-status`) — не хочу трогать
общий хук ради второстепенного уточнения без отдельного запроса.

## Остаток и ограничения

**Исправлено по замечанию независимого ревью (Opus, круг 1):** мутация R3 (прежний M16) была
переделана. Раньше она просто убирала оба условия из WHERE атомарного UPDATE — такая поломка
ловится ДАЖЕ ПОСЛЕДОВАТЕЛЬНЫМ вызовом (без всякой гонки), то есть не доказывала защиту именно
от ПАРАЛЛЕЛЬНОГО выполнения. Теперь мутация подменяет атомарный UPDATE на наивную пару
«прочитал (`session.refresh`) — прибавил — записал» — РОВНО то, от чего предостерегают
комментарии в самом `grant_referral_credit` (волна 202). Эта поломка при ПОСЛЕДОВАТЕЛЬНОМ
вызове теста прошла бы (второй вызов увидел бы уже обновлённые счётчики и корректно
отказал), а ловится ТОЛЬКО настоящим пересечением двух потоков — перепроверено трижды
подряд на PostgreSQL, стабильно KILLED без дополнительных задержек (естественное окно гонки
достаточно широкое из-за отдельного `session.refresh`).

Все четыре правила защищены тестами (три — уже существовавшими до этого листа, один — новый,
переделанный) и нарочными поломками, включая две проверки на реальном PostgreSQL. Полный
существующий сюит файла прогнан и зелёный на SQLite и на изолированном PostgreSQL.
