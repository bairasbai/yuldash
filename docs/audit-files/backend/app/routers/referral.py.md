## Назначение

Реферальная программа «позови своего»: свой код, кто пригласил, бонусы (1 бонус = 1 бесплатное
поднятие поездки, по прайсу 200 ₽). Два вида бонуса: за ввод чьего-то кода (обоим по одному) и
водителю-пригласившему за то, что приглашённый реально «раскатался» (≥3 живых поездки с ≥3
разными пассажирами). Два потолка: `MAX_REFERRAL_CREDITS` (остаток на руках) и
`MAX_REFERRAL_BONUS_LIFETIME` (пожизненный — ограда фермы), плюс месячный потолок водительских
бонусов на одного пригласившего.

`grant_referral_credit` — единственная точка начисления, её зовут обе двери: `/referral/redeem`
и `reward_driver_referral` (хуки на `done` в такси/попутке/посылках). Используется также
`routers/promo.py` (boost-бонус, тот же механизм и кэп).

## Найденные ошибки

| ID | Что было (по-человечески) | Как воспроизвести | Исправление | Тест: до → после |
|---|---|---|---|---|
| R5 (найдено круг 2, исправлено круг 3) | `reward_driver_referral` читал реферера БЕЗ блокировки строки. Двое приглашённых водителей ОДНОГО пригласившего «раскатывались» почти одновременно — оба читали ОДИН И ТОТ ЖЕ месячный счётчик (`granted_driver_bonuses_this_month` — COUNT по строкам, не колонка со своим атомарным UPDATE) и оба проходили потолок: 6-й бонус за месяц вместо 5-го, 200 ₽ сверх потолка | test_concurrent_driver_bonuses_respect_monthly_cap (PostgreSQL, с задержкой внутри счётчика для надёжного окна гонки) | `select(User)...with_for_update()` на реферере перед проверками | тест падал бы (`[True, True]` вместо `[False, True]`) → проходит |
| R6 (найдено круг 2, исправлено круг 3) | Гонка на UNIQUE(invited_user_id, kind) (та же пара хуков такси/попутка/посылка для одного водителя) падала необработанным `IntegrityError` → 500 уже ПОСЛЕ чужого `done`-перехода. Человек, честно завершивший СВОЮ поездку, видел 500 из-за гонки вокруг ЧУЖОГО реферального бонуса — деньги были целы (бонус не задваивался), ломался только ответ | test_driver_bonus_race_on_unique_is_handled_gracefully (детерминированно: конкурирующая запись физически в базе, проверка `_driver_bonus_already_granted` её «не видит» — патчится одна эта функция) | `try: session.commit() except IntegrityError: session.rollback(); return False` вокруг вставки `ReferralBonus`, по образцу уже проверенного `post_promo_compensation`/`debt.accrue_for_order` | тест падал бы необработанным исключением → проходит, бонус остаётся ровно один |

**Почему не было отдельного PostgreSQL-теста специально на «два INSERT одновременно ловят
IntegrityError».** Row-lock реферера (R5) и уникальность пары (referrer↔invited_user_id,
driver.referred_by фиксирован) структурно делают это НЕДОСТИЖИМЫМ через настоящую
многопоточность: два вызова для ОДНОГО driver_id всегда вычисляют ОДНОГО И ТОГО ЖЕ реферера
и потому всегда сериализуются через его лок — вторая попытка увидит уже вставленный бонус на
проверке `_driver_bonus_already_granted` ДО того, как дойдёт до INSERT. Прямая попытка такого
нитевого теста (вторая сессия вставляет конкурирующую строку, пока первая держит
`with_for_update()` на том же референте) закончилась взаимной блокировкой: INSERT ждёт снятия
FK-блокировки с заблокированной `with_for_update()` строки, а она не снимется, пока не
вернётся функция, которая ждёт этот INSERT. Поэтому R6 проверен детерминированным
воспроизведением ИСХОДА гонки (см. тест), а не настоящими потоками — честно описано здесь,
чтобы в следующий раз никто не наступил на тот же deadlock.

## Остаток и ограничения

Круг 3 закрыл обе оставшиеся находки предыдущего круга (месячная гонка, необработанный 500).
Единственное, что остаётся ОТКРЫТЫМ по прямому указанию ведущего (не чинить, только
зафиксировать с оценкой):

**«Кольцо из трёх» в реферале (A→B→C→A).** Защита `referral_redeem` ловит только ПАРНЫЙ обмен
(`referrer.referred_by == user.id`, волна 165); цепочка из ТРЁХ ввела бы коды по кругу, и
каждый получил бы бонус, хотя новых людей в сервисе не прибавилось ни одного — платформа
раздала бы 6 бесплатных поднятий (3 пары «пригласил/был приглашён» × 2 бонуса) за пустое
место. **Серьёзность: низкая.** Каждый вводит код РОВНО РАЗ в жизни аккаунта — цепочка из
трёх требует минимум трёх свежих аккаунтов (или сговора троих реальных людей) ради 600 ₽
по прайсу, при том же пожизненном потолке `MAX_REFERRAL_BONUS_LIFETIME`, что уже режет
ферму на двоих. Порог усилий для N-угольного кольца растёт линейно с N, а выигрыш —
постоянный (2 бонуса на звено) — цепочки длиннее трёх ещё менее выгодны относительно
риска завести N поддельных аккаунтов разом. Закрывать нужно было бы ОБЩИМ антифрод-правилом
«не вводить код того, кто есть в цепочке твоих же приглашений» (обход графа `referred_by`
на глубину, не только на единицу) — отдельная задача, не изобретаю её решение здесь
по прямому указанию ведущего.

Все шесть денежных правил (R1–R6) защищены тестами и нарочными поломками, включая четыре
реальные проверки на PostgreSQL (R2, R3, R5 — настоящие гонки потоков; R6 — детерминированное
воспроизведение исхода, см. обоснование выше). Полный существующий сюит файла
(`test_referral_farm_cannot_be_raced.py`, `test_the_calendar_is_the_humans_not_the_servers.py`,
`test_flows.py`) прогнан и зелёный на SQLite и на изолированном PostgreSQL.
