## Что эта выкатка даёт людям

Пока сервер на старой версии, все эти дыры на проде открыты:

1. **Вход по SMS-коду.** Чужой больше не подберёт код к чужому номеру, в том числе к номеру админа. Код не сохраняется, пока сообщение реально не ушло (PR #118, правка Б-1).
2. **Вход через Telegram.** Если номер телефона перешёл к другому человеку (оператор отдал старую SIM-карту), новый владелец больше не попадает в аккаунт прежнего: в его поездки, чаты и доверенные контакты. Ещё новый владелец перестал навсегда упираться в отказ (PR #121).
3. **Деньги.** Двойное нажатие или два запроса одновременно больше не дают двойного списания или двойного возврата. В базе стоит запрет на двойной возврат комиссии. Если водитель успел оплатить долг картой, админ его не «простит» и не «отклонит». Нажатие водителем «я оплатил» или разбор жалобы в ту же секунду больше не возвращают оплаченный картой долг в неоплаченные, а админ видит «уже оплачено» (PR #118, #119, #125).
4. **«Договорились на 1 ₽».** Пассажир больше не может сам поставить сумму ниже цены поездки, снизить её может только водитель (PR #122).
5. **SOS.** Номера телефонов не попадают в журнал сервера. Сигнал «застрял» по чужой поездке ни к чему чужому не привязывается (PR #118, лист 3.1).
6. **Купоны и промокоды.** Один промокод нельзя взять дважды гонкой запросов. Номера в журнале промокодов хранятся зашифрованным отпечатком, а не открытым текстом (152-ФЗ) (PR #118, лист 1.3).
7. **Кнопки админа в Telegram.** ✅/❌ под платежом теперь сообщают правду, а отказ доходит до плательщика (PR #123).
8. **И всё, что накопилось с июля.** По записям прод последний раз обновляли **04.07.2026**, поэтому вместе с октябрьскими правками приедут три месяца работы: такси, курьер, кошелёк, доверие, исправления аудитов.

## Словарик (чтобы читать без программиста)

| Слово | Что значит |
|---|---|
| **Сервис `yuldash-api`** | Программа сервера, которая отвечает приложению. Ей управляет systemd, «диспетчер программ» Linux: `systemctl stop/start`. |
| **Будильники `yuldash-*.timer`** | Раз в N минут запускают фоновые задачи (автоподбор, чистка, напоминания). |
| **`.env`** | Файл с настройками и секретами сервера (`/opt/yuldash/.env`). Его **никогда** не показывают, не копируют в чат и не кладут в git. |
| **`JWT_SECRET`** | Секрет из `.env`, которым сервер подписывает «пропуска» (входы в аккаунт). С этой выкатки он же шифрует номера в журнале промокодов. |
| **База данных** | PostgreSQL, база `yuldash`. В ней все люди, поездки, деньги. |
| **Миграция** | Шаг перестройки базы под новый код: добавить колонку, таблицу, поправить данные. Их ведёт программа **alembic**. Метка «какие шаги уже сделаны» лежит в таблице `alembic_version`. |

| **Репетиция** | Прогон миграций не на живой базе, а на её копии. Если на копии всё прошло, на живой пройдёт так же. |
| **venv** | Папка с библиотеками Python для сервера (`/opt/yuldash/.venv`). |
| **tmux** | «Окно, которое не закрывается»: если связь по SSH оборвалась, команды внутри продолжают работать, а к окну можно вернуться. |
| **health** | Адрес `/health`. Сервер отвечает на нём `{"status":"ok", "db":"ok", ...}`, если жив и видит базу. |
| **Откат** | Возврат к старой версии, если новая сломалась. |

### Почему не просто «двойной клик `deploy-backend.bat`»

Фактическая процедура сейчас — `backend/deploy-backend.bat`: копирует `app/`, `alembic/`, `alembic.ini` по `scp`, затем `alembic upgrade head`, затем рестарт и `/health`. Эта инструкция делает **те же шаги**, но безопаснее, потому что у `.bat` есть пять дыр:

1. Он льёт код из папки `C:\Users\Bayra\Yuldash\backend` — из той ветки, что там открыта, вместе с несохранёнными правками. Мы берём архивом ровно проверенную версию.
2. Он копирует **поверх** старого. Удалённые в репозитории файлы остаются на сервере. Для `alembic/versions/` это опасно: старые июньские миграции и новые вместе дают «две головы», и alembic не накатит ничего. Мы заменяем папки целиком.
3. Он не делает резервную копию и не ставит библиотеки (`pip install`), хотя `requirements.txt` с июля поменялся.
4. Он гонит миграции сразу на живой базе, без репетиции.
5. Его откат («схему не откатываем, старый код работает с новыми колонками», `docs/deploy-checklist-2026-09.md` §7) верен только для добавочных миграций. В этой выкатке есть и необратимые (раздел «Что поменяется на сервере»).

`backend/ops/deploy.sh` тоже не годится: он делает `git pull` в `/opt/yuldash`, а это, по документам, не git-папка, и данные он не откатывает.

> **Как сервер выполняет миграции** (`backend/alembic/env.py`): все шаги одной транзакцией, с ожиданием блокировки не дольше 3 секунд. Две ревизии строят индекс «без остановки таблицы» (`money_holes_20260807`, `refund_unique_20261002`). На них сделанное **фиксируется**, и после первой из них ограничение в 3 секунды больше не действует: постройка индекса будет ждать **любое** открытое подключение к базе, хоть вечно.
> Поэтому:
> - перед миграциями выключаем всё, что ходит в базу, и проверяем, что подключений нет (шаг 4.1);
> - падение миграций означает откат из резервной копии (раздел 7): база может остаться перестроенной **частично**.

### Настройки (`.env`)
- **Новых обязательных переменных в октябрьских PR нет**: `backend/app/config.py` не менялся с 26.09.
- С июля добавились десятки настроек. У всех есть значения по умолчанию: курьер, ожидание такси, Web Push (`VAPID_*`), рейтинг автоподбора (`AUTOMATCH_RATING_PRIOR*`) и другие.
- Обязательны **только в связке**: например, `TELEGRAM_WEBHOOK_SECRET` при заданном `TELEGRAM_BOT_TOKEN`, `SBP_PHONE` при `PAYMENTS_PROVIDER=sbp_manual` (и он не должен совпадать с `ADMIN_PHONES`), `REDIS_URL` при `TAXI_ENABLED=true`, публичный `https` в `MEDIA_BASE_URL`.

- ⚠️ Одной проверки сервер **не делает**: незнакомое значение `PAYMENTS_PROVIDER` он не отвергает. Её делаем руками (шаг 1.5).

- По сравнению с июлем добавились: `pywebpush`, `sentry-sdk[fastapi]`, `boto3`, `Pillow`, `fakeredis` (последняя только для тестов).

Поэтому в живые библиотеки ставим только при выключенном сервисе (шаг 4.3), а репетиция идёт на отдельной копии библиотек (шаг 3.1).

**1.1. Место на диске**

```bash
sudo -u postgres psql -tAc "SELECT pg_size_pretty(pg_database_size('yuldash'))"
df -h / /var/lib/postgresql | tail -n +2; free -h | head -2
```
Свободного места нужно **не меньше 4 размеров базы + 2 ГБ**: туда лягут две копии, база-репетиция, временная база проверки и, при откате, ещё одна база. Меньше — стоп, сначала освободить место.

**1.2. Как запущен сервис и откуда он берёт настройки** (источник — `docs/server.md`; точного файла сервиса в репозитории нет, есть только пример `backend/deploy/yuldash-api.service.example`):
```bash
systemctl cat yuldash-api | grep -E '^(User|WorkingDirectory|EnvironmentFile|ExecStart)='
systemctl cat yuldash-api | grep '^Environment=' | sed 's/^Environment=//' | grep -oE '(^|[[:space:]"])[A-Za-z_][A-Za-z0-9_]*=' | tr -d ' "='
grep -cE '^[[:space:]]*export |\$\{' /opt/yuldash/.env
systemctl list-timers --all --no-pager | grep yuldash
crontab -l 2>/dev/null | grep -v '^#' | grep -i yuldash
crontab -u yuldash -l 2>/dev/null | grep -v '^#'
grep -ril yuldash /etc/cron.d 2>/dev/null
```
- **Первая команда.** Ждём `User=yuldash` и `WorkingDirectory=/opt/yuldash`. `EnvironmentFile=` должно **отсутствовать** или быть `/opt/yuldash/.env` (допустимо и `-/opt/yuldash/.env` с минусом). Иначе — стоп: все пути ниже рассчитаны на `/opt/yuldash`.
- **Вторая** печатает только **имена** переменных, заданных прямо в файле сервиса (значения не выводятся). Служебные вроде `WEB_CONCURRENCY` — можно. Если среди имён есть настройки из `.env` (`ENV`, `DATABASE_URL`, `JWT_SECRET`, `PAYMENTS_PROVIDER` и т.п.) — стоп. Сервис и миграции прочитали бы **разные** настройки, то есть другую базу или другой секрет. Это опасно для необратимой миграции промокодов.
- **Третья** должна вывести `0`: иначе systemd и Python читают `.env` по-разному. Стоп, разобраться со специалистом.
- **Четвёртая** — список будильников. **Пятая–седьмая** — что запускается по расписанию от root, от `yuldash` и из `/etc/cron.d`. От root ожидаем `monitor.sh` раз в минуту и `backup-db.sh` ночью. Запиши все списки.

Если `EnvironmentFile=/opt/yuldash/.env` есть, сверь, что сервис и миграции видят **одни и те же** секрет и базу. Печатаются только 12 знаков «отпечатка», сами значения не выводятся:
```bash
cd /opt/yuldash
sudo -u yuldash ./.venv/bin/python -c "import hashlib; from app.config import settings as s; print('миграции видят:', hashlib.sha256((s.jwt_secret+'|'+s.database_url).encode()).hexdigest()[:12])"
systemd-run --quiet --pipe --wait -p User=yuldash -p WorkingDirectory=/opt/yuldash -p EnvironmentFile=/opt/yuldash/.env /opt/yuldash/.venv/bin/python -c "import hashlib; from app.config import settings as s; print('сервис видит:  ', hashlib.sha256((s.jwt_secret+'|'+s.database_url).encode()).hexdigest()[:12])"
```
Отпечатки должны **совпасть**. Не совпали — стоп.

**1.5. Режимы сервера и сила секрета** (читает настройки тем же способом, что миграции; сам секрет не печатает, только длину):
```bash
cd /opt/yuldash && sudo -u yuldash ./.venv/bin/python -c "
from app.config import settings as s
j = s.jwt_secret or ''
print('ENV =', repr(s.env))
print('PAYMENTS_PROVIDER =', repr(s.payments_provider), '- годится' if s.payments_provider in ('mock', 'sbp_manual', 'yookassa') else '- ОПАСНО, СТОП')
print('SMS_PROVIDER =', repr(s.sms_provider))
print('JWT_SECRET: длина', len(j), '- СЛАБЫЙ, СТОП' if (len(j) < 16 or j.startswith('dev-secret')) else '- годится')
"
```
- **`ENV = 'prod'`** — обязательно.
- **`JWT_SECRET`** — нужно «годится», лучше длина 32 и больше.
  - «СЛАБЫЙ» — **стоп**: новый сервер не стартует, а миграция промокодов откажется работать (`backend/app/config.py:1019-1036`, `promo_claim_hmac_20261002.py`).
  - Новый секрет записывается без вывода на экран (во **втором** SSH-окне, не в tmux):
    `sed -i '/^[Jj][Ww][Tt]_[Ss][Ee][Cc][Rr][Ee][Tt]=/d' /opt/yuldash/.env && echo "JWT_SECRET=$(openssl rand -hex 32)" >> /opt/yuldash/.env`
    Затем повторить шаги 1.2 (отпечатки) и 1.5. Смена секрета **разлогинит всех**, поэтому это решение Александра, и сделать её нужно **до** выкатки.
  > ⚠️ **После этой выкатки `JWT_SECRET` не менять без крайней нужды.** Смена разлогинит всех и тихо обнулит правило «один промокод на номер» (`backend/app/routers/promo.py`, `_phone_claim_key`; `docs/decisions.md`, поиск «Отдельный секрет для журналов промокодов»).
- **`PAYMENTS_PROVIDER`** — допустимы ровно три значения:
  - `'sbp_manual'` — человек переводит по СБП, админ подтверждает вручную;
  - `'yookassa'` — карта через ЮKassa (нужны ключи);
  - `'mock'` — на проде оплата выключена: кнопки отвечают «Оплата скоро будет доступна» (`backend/app/routers/payments.py:593`).

  **«ОПАСНО, СТОП»** (пусто `''` или опечатка) — **дыра в коде**: сервер такое значение не отвергает, а при оплате выдаёт платёж «успешно оплачен» без денег (`backend/app/payments.py:72`), и платные функции включаются бесплатно. До выкатки вписать в `.env` одно из трёх значений — по решению Александра.

  В остальном **значение в этой выкатке не менять**. Есть открытый вопрос: при `sbp_manual` карточка «Оплатить онлайн» после новых правок экрана будет показываться на каждом чеке (`docs/tasks.md`, «Ждёт решения Александра», п.7). Запиши значение и передай Александру.
- **`SMS_PROVIDER = 'mock'`** — SMS выключены, вход только через Telegram. Значит, Telegram-вход после выкатки нужно проверить обязательно (шаг 5.3).

## 2. Резервная копия и проверка, что она восстанавливается (15–20 минут)

**2.1. Снять копию.** Так же, как в `backend/backup-db.sh`, но с тремя отличиями:
- копия не оборвётся «тихо»;
- файл читает только root (в копии личные данные всех людей);
- имя такое, что ночная ротация его не сотрёт (она удаляет старые `yuldash-*.sql.gz` сверх 14 штук).
```bash
mkdir -p /opt/yuldash/backups
F=/opt/yuldash/backups/prerelease-$(date +%Y%m%d_%H%M).sql.gz
( umask 077; set -o pipefail; sudo -u postgres pg_dump yuldash | gzip > "$F" ) && echo "КОПИЯ ГОТОВА: $F" && ls -lh "$F"
```
Запиши полный путь к файлу. Дальше он называется **КОПИЯ** (в окне tmux он лежит в переменной `$F`). Нет надписи `КОПИЯ ГОТОВА` — стоп.

**2.2. Убедиться, что копия поднимается** (источник — `backend/ops/restore-verify.sh`): поднимает копию во временную базу, считает таблицы и людей/поездки/брони, удаляет временную базу за собой. Боевую базу не трогает:
```bash
ALEMBIC_CMD=/opt/yuldash-release/venv/bin/alembic APP_DIR=/opt/yuldash-release/next/backend \
  bash /opt/yuldash-release/next/backend/ops/restore-verify.sh "$F"
```
- Ждём последней строкой `[verify] OK: ...`.
- Предупреждение `WARN: применённая ревизия ... != голова кода` (или «в дампе нет alembic_version») здесь **нормально**: база ещё не обновлена.
- `FAIL` — стоп, копия негодна.

**2.3. Унести копию с сервера** (если сервер умрёт посреди выкатки, копия на нём не поможет). С ноутбука, в отдельном окне PowerShell:
```powershell

scp root@85.239.52.55:КОПИЯ C:\yuldash-private\
```
⚠️ В файле **личные данные всех пользователей**:
- **не класть** в «Документы», на «Рабочий стол» и в другие папки, которые синхронизирует OneDrive (это выгрузка в чужое облако, 152-ФЗ);

## 7. Откат: если сломалось

Главное правило: **`alembic downgrade` на проде не использовать.** Часть миграций назад данные не возвращает: шифрование номеров промокодов, сдвиг времени, снятие «Проверен», удаление дублей. Вернуть базу можно только из ФИНАЛЬНОЙ КОПИИ (шаг 4.2).

Решение об откате принимает Александр. Ориентир: если новую версию не удаётся поправить **за 15–20 минут** после включения, откатываемся. Всё, что люди сделали между включением (4.9) и откатом, **пропадёт**: брони, сообщения, оплаты. Поэтому решать быстро.

Команды используют `$D` (метка из шага 4.4) и `$F2` (путь из шага 4.2). Если окно tmux потерялось, сначала задай их заново: `D=<метка>`, `F2=<полный путь к ФИНАЛЬНОЙ КОПИИ>` (как найти — начало раздела 4).

### Откат А — упало ДО миграций (шаги 4.1–4.4; `alembic upgrade` ещё не запускали)
База не тронута.
- Если до шага 4.4 не дошли — вернуть библиотеки (если шаг 4.3 уже был) и включить:
```bash
cd /opt/yuldash && sudo -u yuldash ./.venv/bin/pip install -q -r /opt/yuldash-release/pip-freeze-before.txt
systemctl start yuldash-api && systemctl start 'yuldash-*.timer'
```
- Если шаг 4.4 уже был — вернуть код. Первая строка проверяет, что копия старого кода с этой меткой **есть**. Нет надписи `КОПИЯ КОДА НА МЕСТЕ` — ничего не удалять: метку `D` найти заново (начало раздела 4).
```bash
cd /opt/yuldash && [ -d "app.bak-$D" ] && [ -d "alembic.bak-$D" ] && echo "КОПИЯ КОДА НА МЕСТЕ"
[ -d "app.bak-$D" ] && [ -d "alembic.bak-$D" ] && rm -rf app alembic && mv "app.bak-$D" app && mv "alembic.bak-$D" alembic && cp -a "alembic.ini.bak-$D" alembic.ini
[ -f "requirements.txt.bak-$D" ] && cp -a "requirements.txt.bak-$D" requirements.txt
[ -d "ops.bak-$D" ] && rm -rf ops && mv "ops.bak-$D" ops
[ -d "scripts.bak-$D" ] && rm -rf scripts && mv "scripts.bak-$D" scripts
chown -R yuldash:yuldash app alembic alembic.ini; [ -d scripts ] && chown -R yuldash:yuldash scripts
[ -d ops ] && chown -R root:root ops
sudo -u yuldash ./.venv/bin/pip install -q -r /opt/yuldash-release/pip-freeze-before.txt
systemctl start yuldash-api
for i in $(seq 1 60); do curl -sf http://127.0.0.1:8000/health && break; sleep 2; done; echo
systemctl start 'yuldash-*.timer'
```
(`pip install -r pip-freeze-before.txt` возвращает прежние версии библиотек. Новые библиотеки остаются, старому коду они не мешают.)

### Откат Б — миграции упали ИЛИ прошли, но новый сервер не работает
База могла перестроиться частично, а старый код на новой базе может не подняться: например, `0002_drop_dead_user_columns` удаляет колонки, которые старый код читает. Поэтому возвращаем **и базу, и код**. Вместо КОДИРОВКА, СОРТИРОВКА, СИМВОЛЫ, ВЛАДЕЛЕЦ подставь значения из шага 1.8:
```bash
systemctl stop yuldash-api; systemctl stop 'yuldash-*.timer'; systemctl stop 'yuldash-*.service'
# 1) запретить новые подключения и отключить тех, кто ещё подключён
sudo -u postgres psql -c "ALTER DATABASE yuldash ALLOW_CONNECTIONS false;"
sudo -u postgres psql -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='yuldash' AND pid <> pg_backend_pid();"
# 2) испорченную базу не удаляем, а переименовываем: пригодится, чтобы понять, что случилось
sudo -u postgres psql -c "ALTER DATABASE yuldash RENAME TO yuldash_failed_$D;"
# 3) пустая база с прежними владельцем, кодировкой, сортировкой — и ФИНАЛЬНАЯ КОПИЯ в неё
sudo -u postgres createdb -T template0 -E КОДИРОВКА --lc-collate=СОРТИРОВКА --lc-ctype=СИМВОЛЫ -O ВЛАДЕЛЕЦ yuldash
( set -o pipefail; gunzip -c "$F2" | sudo -u postgres psql -q -v ON_ERROR_STOP=1 -d yuldash > /dev/null ) && echo "БАЗА ВОССТАНОВЛЕНА"
```
- Если в шаге 1.8 у базы были особые права (`datacl`) или настройки (`\drds`) — вернуть их руками сейчас.
- Затем вернуть код — команды из «Отката А» (блок «Если шаг 4.4 уже был»), они же вернут библиотеки и снова включат сервис и будильники.

Проверка после отката:
```bash
curl -s http://127.0.0.1:8000/health; echo
sudo -u postgres psql -d yuldash -tAc 'SELECT count(*) FROM "user"' ; sudo -u postgres psql -d yuldash -tAc 'SELECT count(*) FROM ride'
```
Числа людей и поездок должны совпасть с записанными в шаге 4.2.

Испорченную базу `yuldash_failed_<метка>` удалить, когда разработчик разберётся с причиной: `sudo -u postgres dropdb yuldash_failed_<метка>`.

> **Почему не так, как в `docs/deploy-migrations.md`** («`gunzip -c … | psql yuldash`» поверх существующей базы): обычный дамп не стирает старые таблицы. Заливка поверх живой базы даст ошибки «уже существует» и смесь старого с новым. Чистая база плюс копия — надёжно.

## Как проверена инструкция (13.10.2026, на ноутбуке, без сервера)

На временном PostgreSQL 16 и SQLite с кодом `7b3f5f3b` (миграции и настройки совпадают с `3fe62996`):
- **Вся цепочка миграций** с нуля доходит до `bd_merge_heads_20261002`.
- **Метка `d1e2f3a4b5c6`** даёт `Can't locate revision` и ничего не меняет. После `DELETE FROM alembic_version` все 133 миграции проходят заново поверх готовой схемы. Время поездки при этом сдвинулось на −5 ч ещё раз — отсюда строгие условия варианта Б.
- **Дубли `refund:*`**: запрос 1.6 их находит, миграция останавливается и индекс не ставит. После `UPDATE … '#dup'` выкатка проходит.
- **Копия и откат**: `pg_dump | gzip` → переименование базы → `createdb -O` → заливка с `ON_ERROR_STOP` поднимают ту же базу с тем же владельцем.
- **Отзыв входов** (4.8): в режиме просмотра ничего не меняет; с `apply` гасит ключи только у аккаунта проверяющего и совпавшего по номеру, обычного не трогает. Номер с `8…` находится так же, как с `+7…`.
- **Адрес копии** (3.2) сохраняет пароль и параметры как есть; адрес со знаком `%` ловится проверкой.
- **Проверки 1.4 и 1.5** печатают только «задано/длину/годится», без секретов. Новый сервер стартует на перестроенной базе и отвечает `/health` и `/rides`.

**На сервере не проверено** (нет доступа): работа `sudo --preserve-env` и `systemd-run --pipe` на этом Ubuntu, точные права на папки, реальные данные прода. Это и ловят разведка (раздел 1) и репетиция (раздел 3).
