## Производный список исходников и общая сумма — 02.11.2026

В поручении и отчёте различать две суммы: `manifest_file_sha256` — байты всего JSON-файла; `source_sha256` — каноническая сумма массива `files` (JSON с сортировкой ключей, компактными разделителями, UTF-8). Сравнивать их друг с другом нельзя. При проверке источника сверить `source_sha256`, пересчитать массив и отдельно проверить каждый файл. Если дана только каноническая сумма, отличие суммы всего JSON не является изменением исходников; сначала уточнить тип величины.

При точных строковых преобразованиях Windows-файла сначала определить CRLF/LF, нормализовать только в памяти и восстановить исходный формат при записи. Проверять однозначность всех замен до первой записи, затем общий diff и исходные SHA. Root дважды получил отсутствие точного совпадения из-за CRLF в Completed; оба раза запись продукта не состоялась. Повтор после явной нормализации сохранил CRLF и исходный потолок строк. Это проверка конкретного преобразования, не новая общая автоматизация.

Не копировать top-level aggregate/описание родительского manifest в новый список без пересчёта. Предпочитать новый объект с явными parent/scope, текущими files и документированным SHA256 канонического JSON списка; проверить одновременно per-file SHA и aggregate до запуска. Старые доказательства не переписывать: если ошибочен только унаследованный aggregate при правильно проверенных files, оставить оригинал и отдельную errata с SHA самого manifest и верной суммой. ## Запуск зависимых тестов и идентичность Windows-процесса — 02.11.2026

После получения нового HTTP-ответа сравнение одного текста не отличает старые данные от повторно загруженных. ## Пропущенное скрытие и потерянный ответ чата — 21.10.2026

Не подменяй этот сценарий старым WS-кадром после закрытого соединения: connection/session-ограждения его уже отбрасывают. Реальная проверка: сервер сохранил отправку, клиент не получил подтверждение, другой свой сеанс скрыл сообщение, исходный клиент получил историю без ещё неизвестного id и повторил тот же ключ. Проверяй одновременно отсутствие содержимого в ответе, снятие именно своей очереди/отрицательной строки, отсутствие повторной загрузки медиа и сохранность истории собеседника. Отдельно задержи исходный POST200 через наблюдаемую границу отсутствия: replay при этом вообще не вызывается.

Для фоновой очереди сначала покажи положительный id в истории, затем пропусти скрытие и верни content-free receipt при GET503: удаление одного отрицательного id недостаточно. Проверь неверный ключ/владельца/дробный id, другую неподтверждённую строку, возврат после POST, начавшегося в фоне, и новый голос после более ранней потери канала. Стабильный новый голос и пропущенное изменение во время старого POST — разные утверждения. Подписчиков браузерных событий в компонентном стенде храни множеством: два visibilitychange-обработчика не должны затирать друг друга.

Два «Повторить» в Android — разные действия. После принудительного GET503 сначала дождись устойчивой строки ошибки истории, затем заново найди нижнюю кнопку действия по свежей XML. Снимок до завершения GET не годится для координат: появившийся блок ошибки сдвигает кнопку. Само отсутствие второго POST не доказывает неверный тап: в этом проходе правильное accessibility-нажатие нижней кнопки сопровождалось новой ошибкой соединения до запроса. Различай выбор кнопки и отказ транспорта; подтверждай второй POST по тому же ключу и порядок в журнале: чужой DELETE(me) → успешный native GET → повтор POST. Внешний ASGI-отказ может не попасть во внутренний HTTP-журнал: не приписывай ему несуществующую запись wire, укажи управляемую границу и реальную ошибку на экране.

Классический UiAutomator-runner требует совместимые `android.test.RepetitiveTest`/`FlakyTest`, как старый помощник ввода. Проверяй не только `OK (1 test)`, но и отсутствие `Exception`/`FAILURES`: оборванный runner тоже может напечатать OK. Для jdb в Windows явно выбирай SocketAttach; вывод дочерней Java декодируй с защитой от ошибки кодировки, а отсоединение отладчика и снятие своего adb-forward выполняй в finally/atexit. Пустой XML после остановки VM отладчиком не доказывает поломку экрана.

Нельзя «лечить» этот HTTP-сбой ожиданием: у установленного OkHttp4.12 глубокая проверка HTTP/1 idle начинается после10с, поэтому короткий повтор и повтор спустя минуты не равны. RED эмулятора: EOF в `okhttp3...Http1ExchangeCodec`→`RealCall.execute`→`ApiClient.call`, не путать с отдельным системным `com.android.okhttp` чтений или ожидаемым отказом WS на стенде. Regression: полный503→server FIN без close-header→200мс→один явный same-key POST. Проверять новое соединение и число запросов, сохраняя запрет автоматического replay. Артефакт байткода включает SHA фактически используемого jar; это не предположение о другой версии библиотеки.

## Помощники локальной проверки чата — 21.10.2026

`browser_run_code_unsafe` принимает `filename` только внутри разрешённых корней инструмента: для этого компьютера — основной проект и его `.playwright-mcp/`; файл из `%TEMP%` будет отклонён до открытия страницы. После проверки закрой только свои контексты, сверяй хэш и удали именно свой файл; не удаляй общие папки или браузер MCP.

DOM пузыря включает кнопку «⋯», поэтому exact-text к целой строке неприменим. Финальный PNG делай после анимации появления; сравни вычисленные цвета, прежде чем объявлять дефект контраста.
- Для Windows передавай rg каталог и `-g`, не shell-glob в имени пути. Сложные многострочные Python/PowerShell-помощники сохраняй файлом, не вкладывай несколько уровней кавычек в shell-команду.

## Локальный стенд (эмулятор ↔ свой сервер)

Адрес по умолчанию при отсутствии переопределений — `http://10.0.2.2:8000` (компьютер глазами стандартного эмулятора). Это не доказательство адреса установленного приложения: задавай `YULDASH_DEBUG_API_BASE_URL` явно и подтверждай фактический адрес собранного клиента; приоритет задан в [build.gradle.kts](../android/app/build.gradle.kts#L76).

Перед UI/API-входом обязательны условия [agent-reliability.md, §§2–3](agent-reliability.md#2-изоляция-тестов): отдельные тестовые БД/участники, явные dev/mock-настройки, готовность выбранного сервера и ограничение сети конкретного тестового запуска до первого запроса. Голая команда `uvicorn` этих условий не обеспечивает. Рабочий сервер не используется как запасной тестовый адрес.

Сначала ищи уже применявшийся стенд по `standard-ui-login01` в [реестре](audit-blocks.md). В ограниченном прогоне 06.11 использовался существующий `RootNative90`; это пример, а не обязательное имя AVD для всех компьютеров. Учитывай зарегистрированные `ANDROID_AVD_HOME`/`ANDROID_USER_HOME` и владельца эмулятора: отсутствие AVD в списке другого каталога не доказывает его отсутствие на компьютере. Чужую сессию, общий adb и ключи не трогать; новый тестовый контролёр ради повторения этого пути не нужен.

1. Сервер — из `backend/` своего чекаута, после перечисленных предпусковых условий и с зарегистрированным владельцем/PID/портом. Команда запуска и значения dev/mock — в [backend/README.md](../backend/README.md); готовность БД/сервера проверить до входа через интерфейс.
2. На экране «Нет связи с сервером», а в логе сервера ни одного запроса — обычно брандмауэр Windows.
   Обход: `& $adb reverse tcp:8000 tcp:8000` и сборка с
   `$env:YULDASH_DEBUG_API_BASE_URL='http://localhost:8000'`. Незашифрованный HTTP в debug разрешён
   только для `10.0.2.2`, `localhost`, `127.0.0.1`, `::1`
   (`android/app/src/debug/res/xml/network_security_config.xml`) — любой другой адрес режется молча.
3. Стендовые машины такси «пропали» (`POST /instant/presence` → 200, а машин ноль) — антифрод отбросил
   «телепорт» быстрее 200 км/ч и заклинил. Перезапусти стендовый сервер; машина в скрипте должна
   кружить вокруг точки, а не ехать по прямой.
4. Карта: ключ MapKit лежит в одном месте — `android/local.properties` основной папки
   `C:\Users\Bayra\Yuldash`, копий не делаем (решение Александра: не мусорить). В worktree карта
   пустая — всё остальное проверяется там. Нужна именно карта — собери и проверь её из основной
   папки, когда твоя ветка туда влита, с `$env:YULDASH_DEBUG_API_BASE_URL='http://10.0.2.2:8000'`
   (иначе сборка возьмёт адрес сервера из `local.properties` основной папки — там может быть прод). Сам ключ агент не читает и не копирует (§11 `AGENTS.md`).

5. Потеря сети через `adb reverse --remove` не обрывает уже открытый HTTP keep-alive-туннель.
   Перед проверяемым нажатием дождись закрытия прежнего соединения (на стенде Uvicorn с его
   стандартным keep-alive5с — более5с) и сверь журнал настоящих запросов. Сам факт удаления
   перенаправления не доказывает отсутствие сети; незаметно успешный запрос нельзя записывать
   как offline-проверку.
6. Для настоящей загрузки фото на локальном стенде задай `MEDIA_BASE_URL` тем же локальным
   адресом, что `API_BASE` клиента. Файл, сохранённый локально с возвращённым адресом рабочего
   сайта, правильно отвергается проверкой своего сервера и отображается текстом; это ошибка
   настройки стенда, а не доказательство поломки клиентского отображения фото.
7. В PowerShell передавай `rg` каталог и `-g 'маска'`, а не путь с `*`: оболочка может
   не развернуть маску и поиск не прочитает нужные файлы.

Подробности и история — `docs/lessons.md`, поиск «Локальный стенд».


## Клавиатура на экране с полем ввода (24.10.2026)

Экран с `imePadding()` / `WindowInsets.ime` включает `ResizeWindowForKeyboard()` — иначе на Android 15+ окно
сдвигается целиком поверх нашего отступа (двойной скачок, шапка под строкой состояния). Сторож —
`KeyboardResizeGuardTest`. Проверка на эмуляторе: касайся поля **у нижнего края** экрана — поле вверху окно не
сдвигает и поломку не покажет; проще всего поднять шрифт (`adb shell settings put system font_scale 1.3`, потом
вернуть `1.0`). Режим окна: `adb shell dumpsys window windows` → строка `sim={adjust=…}` у `MainActivity`
(`resize` — верно, `pan` — сдвигает). Заодно проверь, что кнопка формы достаётся прокруткой при открытой клавиатуре.
