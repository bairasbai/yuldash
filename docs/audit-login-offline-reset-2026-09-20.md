# Новый вход после отказа очистки — 20.09.2026

## Что воспроизведено

Первый пользователь вышел, но запись очистки его офлайн-хранилища не сохранилась. Второй пользователь успешно вошёл в том же процессе. После повторной инициализации из дисковых данных приложение снова читало паспорт поездки первого пользователя и его очередь сообщений.

Причина: новый сохранённый токен пропускал защитную очистку гостевого запуска. Незавершённая очистка была закрыта только в памяти прежнего процесса.

Новый LoginAfterOfflineResetFailureTest использует настоящие ApiClient.verifyCode, logout и init с локальным MockWebServer. Подменены только два офлайн-диска моделью SharedPreferences с раздельными памятью и диском. Наличие старой отметки очистки исключено явным проверяемым предусловием.

До исправления: **2 из 3 тестов упали** на конечном возврате данных A после входа B и нового init. Для очереди ожидалось0, получено1; вместо отсутствующего паспорта прочитан паспорт A. Контрольный сценарий с уже подтверждённой отметкой очистки прошёл. Источники: login-after-offline-reset-red-20260920.log/XML в C:\Users\Bayra\Yuldash\test-results.

Это проверка текущей совместной рабочей версии после предыдущих исправлений хранения. В локальном main есть отдельная очистка TripPassStore/Outbox, но ещё нет текущего persistNewSession/протокола журнала; нельзя выдавать построчное совпадение версий там, где его нет.

## Исправление

Перед сохранением новой авторизации ApiClient проверяет оба офлайн-хранилища. Если первая запись очистки не подтверждена, хранилище повторяет её. Пока подтверждения нет, токен нового пользователя не сохраняется и успешный вход не объявляется.

Подтверждённой отметки secure_clear_pending достаточно, даже если сам secure временно недоступен: при его возвращении старые данные будут очищены до использования. Это сохраняет существующий сценарий работы с временно недоступным шифрованием.

Минимальные изменения: запрос resetUnconfirmed в OfflineMigration; ensureResetCommitted в двух хранилищах; проверка перед AuthStorePolicy.writeSession в persistNewSession. Новых UI-строк и зависимостей нет.

## Проверки и границы

Расширенный профиль: **107 из 107 тестов, 20 классов, без ошибок и пропусков**. assembleDebug успешен за 1 минуту 47 секунд. Источники: login-after-offline-reset-green-20260920.log, login-after-offline-reset-green-counts-20260920.json и XML нового класса. Полный повтор Android с новым исправлением запущен отдельно; эти107 не выдаются за весь набор.

Тест проверяет отказ входа при непрекращающемся отказе очистки, восстановление записи и следующий успешный API-вход в том же процессе без дополнительного ручного logout. Ответы авторизации здесь тестовые: это не доказательство повторного использования настоящего одноразового кода. Если сервер уже выдал токен, а локальное сохранение не удалось, для нового реального входа может понадобиться новый код; этот пользовательский маршрут отдельно не проверен.

Приём сервером чужих сообщений и показ чужого паспорта обычным экраном не проверялись. Воспроизведён именно возврат данных в локальное хранилище. Настоящий процесс Android для этой новой группы пока не запускался: предыдущие три процесса относятся к переносу, а не к этому входу.

Другие случаи смешения старой secure-очереди и новой fallback-очереди, удаления паспорта при недоступном secure и обработки отказов кеша интерфейсом остаются отдельными задачами. Коммитов, push и публикации нет.

Read-only ревью проверило saveToken/commitAuth, позднийrefresh, порядокзамков и durablePENDING: обхода новойпроверки врассмотренномсценарии не найдено. Это не дополнительныйтест. Важнаяграница: уже существующую на диске комбинацию «токенB+данныеA» отпрежнейверсии новыйguard распознать не может; он предотвращает новое созданиеэтого состояния после неподтверждённойочистки.
