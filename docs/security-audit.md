## TL;DR (для Александра)

Кратко: **код в хорошем состоянии**. Базовая защита уже сделана грамотно (JWT + ротация
refresh, ревокация по logout, лимиты запросов, маскирование телефонов в логах, приватные
документы водителя, параметризованный SQL, секреты вне git, шифрованное хранилище токена на

по всему API, SQL-инъекции) **не найдено**.

Нашёл **3 реальные дыры в одном месте — WebSocket-чат** (он писался раньше остального и не
получил тех же проверок, что REST). Все три починены в этой задаче, только бэкенд, клиент не
трогаем — пользователи ничего не заметят. Ещё несколько мест — рекомендации на потом (не
срочно, ничего не ломаем сейчас).

## Найденные уязвимости

### 🔴 V1 — WebSocket-чат не уважает выход/ревокацию токена (обход logout)
- **Где:** `backend/app/routers/chat.py`, `websocket_endpoint` → `verify_token()`.
- **Суть:** REST-эндпоинты через `current_user` отсекают токены, выпущенные до `logout`
  (`tokens_valid_from`). А WebSocket аутентифицировался через `verify_token()`, который
  **только декодирует JWT** — не сверяет ревокацию и даже не проверяет, существует ли юзер.
- **Сценарий атаки:** пользователь нажал «Выйти» (потерял/украли телефон → разлогинил все
  устройства). Его access-JWT по REST уже мёртв, но по **WebSocket чат открывается ещё до 7
  дней** (срок жизни access). Злоумышленник с этим токеном продолжает читать/писать в чаты
  броней жертвы.
- **Критичность:** Medium (нужен валидный токен жертвы до logout + быть участником брони; но
  это прямой обход ревокации сессии — для приложения с SOS и «доверие = продукт» важно).
- **Исправление:** ввёл `authenticate_ws()` в `security.py` — декод + проверка существования
  юзера + та же проверка ревокации `_token_revoked`, что и в REST. WS теперь honors logout.

### 🟠 V2 — WebSocket-чат игнорирует блокировку пользователя
- **Где:** `chat.py`, цикл приёма сообщений в `websocket_endpoint`.
- **Суть:** REST `POST /bookings/{id}/messages` проверяет `is_blocked(...)` и возвращает 403.
  WebSocket-ветка сохраняла и рассылала сообщение **без проверки блокировки**.
- **Сценарий:** пользователь заблокировал собеседника, но тот через WS-канал продолжает слать
  сообщения (и push) — обход функции безопасности «заблокировать».
- **Критичность:** Medium (фича доверия/безопасности; харассмент в приложении про попутки).
- **Исправление:** перед сохранением/рассылкой каждого WS-сообщения проверяем `is_blocked` —
  если есть блок в любую сторону, сообщение тихо игнорируется (не пишем, не шлём, не пушим).

### 🟡 V3 — Утечка соединений БД в WebSocket-чате (DoS-риск)
- **Где:** `chat.py`, `session = next(get_session())` на **каждое** входящее сообщение.
- **Суть:** `next(get_session())` создаёт сессию SQLAlchemy в обход контекст-менеджера —
  она **никогда не закрывается**. Активный чат = утечка коннектов; пул Postgres
  (`pool_size+overflow ≤ 25/воркер`) выедается → `pool_timeout`, новые запросы падают.
- **Критичность:** Medium (доступность: достаточно нескольких болтливых чатов, чтобы исчерпать
  пул и положить сервис для всех).
- **Исправление:** обернул работу с БД в `with Session(engine) as session:` (коннект
  возвращается в пул сразу после обработки сообщения).

## Рекомендации (не срочно, НЕ ломаем живой клиент сейчас)

- **R1 — OTP 6 цифр.** Сейчас код 4-значный. Текущая защита (5 попыток/код + throttle 3
  кода/мин/номер + строгий IP-лимit 20/мин) делает перебор практически нереальным, но
  6-значный код — стандарт. ⚠️ **Ломает живой APK** (ввод кода жёстко `take(4)` в
  `LoginScreen.kt`): менять server+client одновременно и только в новом релизе. Отложено.
- **R2 — Квота/тип загрузок.** Загрузки (фото/голос) проверяют расширение и размер (≤10 МБ),
  но нет (а) проверки magic-bytes (можно залить произвольные байты под `.jpg`) и (б) квоты на
  юзера → теоретический disk-fill. Митигировано: загрузки требуют логина + общий rate-limit.
  Добавить: сниффинг сигнатуры изображения + суточный лимит загрузок на юзера.
- **R3 — `/ads/stats` без auth.** Отдаёт агрегаты показов/кликов рекламы кому угодно (Low —
  не персональные данные). Клиент зовёт без токена; гейт под admin сломает «Кабинет рекламы».
  Закрыть, когда кабинет станет admin-only на клиенте.
- **R4 — `?token=` в WS.** Для совместимости WS принимает токен и в query-string (утекает в
  логи прокси). Основной путь — токен первым сообщением (безопасно). Убрать query-вариант,
  когда весь живой клиент перейдёт на message-auth.

## Что проверено и оказалось НЕ дырой
- **Точка сбора (`pickup_lat/lng`)** в выдаче поездок — это *публичная* точка посадки,
  выбранная водителем для рекламы рейса (как в inDrive/BlaBlaCar), а не живая геолокация
  пользователя. Живые координаты на сервере вообще не хранятся. Утечки нет.
- **Telegram-webhook** — защищён секретом (`X-Telegram-Bot-Api-Secret-Token`), `validate_production`
  делает секрет обязательным при заданном токене бота. Принимается только *свой* контакт
  (`contact.user_id == from.id`) — чужой номер не подставить.
- **SQL** — пользовательский ввод нигде не склеивается в строку запроса; единственный сырой
  `text()` (`rides/near`) использует бинд-параметры.

## Верификация
- Фиксы — только `backend/app/chat.py` + хелпер в `backend/app/security.py`. Клиент и формат
  ответов не меняются.
- Прогон: `cd backend && python -m pytest` (см. раздел «Ревью» в `tasks.md`).

# Раунд 2 — аудит нового кода (платежи/Boost/admin), 2026-06-28

После первого аудита добавлен крупный платёжный слой (ЮKassa + СБП, Boost, `Payment`,
admin-эндпоинты, `/driver/rides`). Прогнал его тем же security-взглядом.

## Чисто (проверено, дыр нет)
- **Целостность суммы Boost** — цена берётся из серверного `BOOST_PLANS`, клиент шлёт только
  `tier`+`ride_id`. Подделать цену нельзя.
- **IDOR `/boost/create`** — поднять можно только свою поездку (`ride.driver_id == user.id`).
- **Admin-эндпоинты** (`/admin/payments/pending|confirm|reject`) — гейт `role==admin`.
- **Идемпотентность** — `_activate_boost` срабатывает только из `pending`; повтор вебхука =
  no-op (нет двойной активации/replay).
- **Прод-гард** — `mock` в проде → `/boost/create` 503 (нет бесплатных бустов); `validate_production`
  требует ключи ЮKassa / `SBP_PHONE` для соответствующего провайдера.
- **Инъекции** — везде ORM; сырых SQL/конкатенаций нет.

## 🟠 P1 (Medium) — вебхук: амплификация исходящих запросов — ИСПРАВЛЕНО
- **Где:** `routers/payments.py` `yookassa_webhook`.
- **Суть:** вебхук без авторизации (правильно — зовёт ЮKassa), но делал исходящий httpx-GET к
  ЮKassa на ЛЮБОЙ `provider_id` из тела ДО проверки, что такой платёж у нас есть.
- **Атака:** флуд `POST /payments/yookassa/webhook {"object":{"id":"<мусор>"}}` → каждый запрос
  = исходящий GET (15с таймаут) → воркеры висят, амплификация/DoS. Плюс чужой id уходил в
  URL-путь ЮKassa.
- **Критичность:** Medium (доступность; эндпоинт публичный по необходимости).
- **Фикс:** сначала ищем СВОЙ `Payment` по `provider_id` (параметризованный запрос). Нет
  совпадения/уже оплачен → выходим без исходящего запроса. Наружу ходим только за id, что сами
  выпустили. Регресс-тест `test_yookassa_webhook_only_known_payment`.

## Рекомендации (не код-баг)
- **R5 — СБП-номер виден всем авторизованным.** `/boost/create` (sbp_manual) отдаёт личный номер
  получателя любому вошедшему юзеру (нужно для перевода). Это осознанный выбор; риск — спам/
