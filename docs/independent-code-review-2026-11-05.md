## 4. Находки

### SEC-20261105-01 — критично: раскрытие access-токена при загрузке приватного документа

Клиентская проверка доверенного URL выполняется до окончательной браузерной канонизации. Существует класс неоднозначных относительных адресов, который проходит проверку как локальный, но при фактическом запросе получает другой origin. Запрос приватного документа добавляет `Authorization: Bearer ...`.

Серверная проверка владения документом проверяет имя файла и его наличие, однако сохраняет исходный URL; очередь модерации возвращает его клиенту без преобразования в канонический защищённый адрес.

Затронутые места:

- `webapp/src/api/client.ts:83-105` — `isOwnApiUrl`;
- `webapp/src/api/admin.ts:85-101` — `fetchSecureDoc`;
- `backend/app/routers/drivers.py:35-76` — разбор и проверка документа;
- `backend/app/routers/drivers.py:380-399` — сохранение исходного URL;
- `backend/app/routers/drivers.py:589-605` — выдача URL модератору;
- `webapp/src/screens/AdminDriversScreen.tsx:190-200` — автоматическая загрузка изображений.

Последствие: при специально подготовленной заявке access-токен модератора может быть отправлен на сторонний origin и использоваться против API до истечения токена. Refresh-токен этим запросом не передаётся.

Безопасное направление исправления:

1. Канонизировать адрес через `new URL(raw, API_BASE)` до проверки и использовать для запроса именно канонизированный результат.
2. Сравнивать фактический `origin`, разрешать только ожидаемые защищённые пути и HTTPS.
3. На сервере после проверки владения возвращать/сохранять новый канонический `secure_docs_url(name)`, а не исходную строку.
4. Добавить тесты на все неоднозначные формы slash/backslash и кодированные разделители; проверять не только результат предиката, но и фактический `origin` запроса.

Точное воспроизведение намеренно не публикуется в открытом репозитории.

### PAY-20261105-01 — высокий риск: потеря оплаченного времени при параллельной активации разных платежей

Разные тарифы Boost законно создают разные платежи: `backend/app/routers/payments.py:605-627`.

Активация блокирует только текущий `Payment`, после чего `Ride.boosted_until` изменяется через read-modify-write без блокировки поездки:

- `backend/app/routers/payments.py:168-191`
- `backend/app/routers/payments.py:315-337`
- общий `COMMIT`: `backend/app/routers/payments.py:414`

Два разных платежа могут прочитать один исходный срок и затем перезаписать результат друг друга. Оба станут `succeeded`, но часть оплаченного времени исчезнет. Аналогичный риск относится к продлению рекламы и подписки: `backend/app/routers/payments.py:338-378`.

Существующий PostgreSQL-тест проверяет две активации одного `payment_id`, а не двух разных платежей на один объект:

- `backend/tests/test_payment_postgres_concurrency.py:83-97`

Требуются блокировка затрагиваемого объекта в едином порядке либо атомарное прибавление в SQL и PostgreSQL-тест с двумя разными платежами.

### PAR-20261105-01 — высокий риск: `delivered` поверх начатого возврата

`parcel_status` читает посылку без блокировки, проверяет `in_transit`, а позже безусловно записывает `delivered`:

- `backend/app/routers/parcels.py:1260-1268`
- `backend/app/routers/parcels.py:1306-1325`
- `backend/app/routers/parcels.py:1345-1347`

Параллельная отмена отправителем использует `FOR UPDATE` и переводит посылку в `returning`:

- `backend/app/routers/parcels.py:912-961`

Допустимое чередование: курьер прочитал `in_transit` и проверил код → отправитель зафиксировал `returning` → курьер записал `delivered` поверх. Возможны противоречивый статус и одновременные финансовые последствия отмены и вручения.

Дополнительно `settle_courier_waiting` делает собственный `COMMIT` внутри перехода:

- `backend/app/routers/courier.py:513-542`

Нужны единая транзакция, блокировка/CAS по ожидаемому статусу и повторная проверка после ожидания блокировки. Последовательный тест запрета `returning → delivered` не закрывает конкурентный сценарий.

- `webapp/src/api/chat.ts:219-260`
- `webapp/src/api/chat.ts:286-319`

REST-варианты также отправляются без ключа повтора: `webapp/src/api/chat.ts:208-216`, `webapp/src/api/chat.ts:275-284`.

При обрыве сообщение может молча потеряться; при потерянном ответе ручной повтор может создать дубль. REST-история Android дополнительно присваивается целиком и может затереть более свежее WS-сообщение:

- `android/app/src/main/java/com/yuldash/app/InstantChatScreen.kt:75-83`

- `webapp/src/api/chat.ts:117-193`

Нужен общий надёжный контур отправки, а не независимое повторное изобретение в каждом режиме.

### PUSH-20261105-01 — средний риск: уведомления прежнего аккаунта после logout

`disableWebPush()` сначала обращается к серверу и лишь затем отписывает браузер. Любая ошибка проглатывается, локальный флаг уже снят:

- `webapp/src/push/webPush.ts:147-170`

`AuthProvider.logout()` всё равно продолжает локальный выход:

- `webapp/src/auth/AuthProvider.tsx:183-204`

Service worker показывает каждое полученное уведомление без проверки текущего аккаунта:

- `webapp/public/push-sw.js:13-38`

При offline/failed unsubscribe на общем устройстве возможны уведомления прежнего человека после выхода и входа другого. Нужен `finally` для локальной отписки и обязательная отложенная операция отзыва серверной привязки.
