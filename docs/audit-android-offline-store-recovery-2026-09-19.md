# Android: возвращение недоступного офлайн-хранилища — 19.09.2026

Проверяется рабочая ветка `codex/push-routing-audit`, без коммитов и публикации. В локальном main `527dbb0d2c3973899e3b6db0c6e9c4026f3da174` подтверждена исходная причина: TripPassStore.clearAll и Outbox.clearAll очищают доступные ссылки prefs, но не оставляют запроса на удаление недоступного secure.

## Воспроизведение

Последовательность: сохранить данные A в secure → открыть только plain, моделируя недоступность secure → выйти и очистить доступные данные → снова открыть прежний secure. До исправления возвращались паспорт и очередь A. При сохранении паспорта B в plain после выхода затем показывались паспорта обоих аккаунтов. Контрольные случаи: новая очередь B заменяла старую при переносе; временная недоступность без выхода сохраняла прежний паспорт.

Пять новых тестов дали **3 сбоя / 2 успеха**. Файлы доказательств: `C:\Users\Bayra\Yuldash\test-results\android-offline-recovery-red-20260919.log/.xml`. Перед RED из init выделен `initStores(plain, secure)` без изменения логики, чтобы тестировать настоящее поведение TripPassStore/Outbox с явно недоступным вторым хранилищем. Сам Keystore в этих модульных тестах не используется.

## Исправление

`OfflineStoreReset.kt` записывает в обычное офлайн-хранилище `secure_clear_pending` одновременно с очисткой его прежних данных. Если secure недоступен, отметка остаётся. При возвращении secure он сначала очищается синхронной записью; только после успеха удаляется отметка и разрешается обычный перенос новых plain-данных.

Если очистка secure или удаление отметки не подтвердились, TripPassStore/Outbox продолжают использовать plain, не открывая старые secure-данные. Следующий init повторяет очистку. Новые записи B в plain не удаляются при таком повторе. Временная недоступность без выхода сама по себе не создаёт отметку и не стирает старую поездку.

Оба хранилища используют общий helper. Отметка включена в SessionKeys.SURVIVES_LOGOUT с объяснением: в ней нет личных данных, она должна пережить выход до завершения удаления. Авторизация, UI и версии библиотек не менялись.

Добавлены два теста отказов: неуспешная запись очистки secure и неуспешное удаление отметки. Проверяются недоступность старых данных через приложение, сохранение новых plain-данных и успешный повтор после восстановления записи. Всего новых модульных сценариев семь.

## Границы

Последующая группа отдельно проверила новые save/enqueue без дополнительного commit-барьера и с Process.killProcess: [подтверждённая запись действия](audit-android-offline-durable-write-2026-09-19.md). Ниже остаётся историческая граница этой группы восстановления.

Отсутствие secure моделируется передачей null в тот же путь, который использует init при недоступном Keystore. Физическая поломка ключа устройства не создавалась. Полный отказ записи даже первичной отметки на диск не даёт гарантии удаления после перезапуска; это ограничение не скрывается успешными тестами последующей очистки. Проверка восстановления относится к данным, уже записанным на диск. Сохранность последнего нового действия при немедленном force-stop до завершения apply требует отдельного рассмотрения; первый неуспешный прогон не вычёркнут из доказательств. Гонки уже выполняющейся отправки с выходом, полный интерфейс ролей и живые внешние сервисы этой группой не подтверждаются.
