## ТЗ-1. Попутка: автоподбор выбирает проверенного водителя

**Зачем.** Заявки людей без приложения (пожилые, заказ по звонку) система закрывает сама: ждёт откликов водителей и берёт лучший. Сейчас «лучший» — самый высокий средний балл. Новичок с одной пятёркой (5,0) обходит водителя с 200 поездками и баллом 4,9. Для пожилого человека надёжнее тот, чей балл подтверждён многими поездками.

**Как сейчас**
- `backend/app/automatch.py:30–55` — `_best_response()`: ключ сортировки `(-средний_балл, цена_на_столе (0 → в конец), r.id)`.
- Балл — `services.driver_rating(session, driver_id)` (`backend/app/services.py:1319`): возвращает `(средний, число_оценок)`, но число оценок сейчас отбрасывается (`[0]`).
- Настройки: `automatch_enabled`, `automatch_grace_sec` (`backend/app/config.py:62–63`).

**Что сделать**
1. Считать «надёжный балл» (байесовское среднее):
   `надёжный = (m · C + средний · n) / (C + n)`, где `n` — число оценок, `m` — априорный балл, `C` — его вес.
2. Настройки рядом с `automatch_*` в `config.py`:
   - `automatch_rating_prior: float = 4.5`
   - `automatch_rating_prior_weight: int = 5`
3. Новый ключ сортировки:
   1) водители **с оценками** — раньше водителей **без оценок** (как сейчас: без оценок вперёд не проталкиваем);
   2) выше надёжный балл;
   3) ниже цена на столе (`price_on_table`; 0 / не указана — в конец);
   4) раньше откликнулся (`r.id`).
4. `driver_rating` звать один раз на водителя (словарь до сортировки, как сейчас) — без N+1.
5. Обновить docstring `_best_response` и шапку модуля: правило простыми словами.

**Примеры (m = 4,5, C = 5) — оформить тестами**

| Водитель A | Водитель B | Надёжный балл A / B | Выбор |
|---|---|---|---|
| 1 оценка, 5,0 | 200 оценок, 4,9 | 4,58 / 4,89 | B |
| 30 оценок, 5,0 | 200 оценок, 4,9 | 4,93 / 4,89 | A |
| без оценок | 1 оценка, 4,4 | — / 4,48 | B (с оценками всегда раньше) |
| 10 оценок, 4,8, цена 500 ₽ | 10 оценок, 4,8, цена 400 ₽ | равны | B (дешевле) |

**Тесты**
- Новый `backend/tests/test_automatch_prefers_proven_driver.py`: все строки таблицы + «`C = 0` возвращает старое поведение по среднему».
- Зелёные без изменения смысла: `test_automatch_picks_the_better_driver.py` (в т.ч. `test_automatch_ranks_by_driving_not_by_all_roles`, `test_automatch_still_prefers_the_cheaper_at_equal_driving`, `test_automatch_driver_without_ratings_is_not_pushed_ahead`), `test_automatch_more.py`, `test_automatch_wont_seat_a_banned_driver.py`.
- `python -m app.automatch --dry-run` отрабатывает без ошибок.

**Готово, когда**
- [ ] Новичок 1 × 5,0 проигрывает ветерану 200 × 4,9; водитель 30 × 5,0 выигрывает у 200 × 4,9.
- [ ] Водитель без оценок никогда не обходит водителя с оценками.
- [ ] Заявки пассажиров **с** приложением не затронуты.
- [ ] CI зелёный; `docs/decisions.md` и `docs/architecture.md` обновлены.

**Не делать:** не менять `driver_rating`, `automatch_grace_sec`, фильтр `may_ride_together`, логику обычных заявок.

## ТЗ-2. Такси: время подачи по дорогам, а не по прямой

**Зачем.** Уфа стоит между реками Белая и Уфа. Водитель на другом берегу по прямой «рядом», а через мост ему ехать 15–20 минут. Сейчас мы сортируем водителей по прямой и можем отдать заказ именно ему: пассажир ждёт, водитель злится. Как у Яндекса: сначала быстро находим ближайших по прямой (у нас — Redis GEO), потом для первых N считаем реальное время по карте дорог и выбираем по нему.

**Как сейчас**
- `backend/app/instant_service.py:3030` `candidates()` — круги `RADII_KM = (3, 7, 15)` (`:45`) через Redis `geosearch`; расстояние **по прямой**.
- `:3022` `rank()` → `:3008` `_score()`: `instant_w_dist / max(dist_km, 0.3) + instant_w_rating · рейтинг − штраф_низкого_рейтинга + бонус_приоритета` (веса — `config.py:758–760`, `:385–386`).
- `:3128` `try_offer_next()` — оффер лучшему, таймер `instant_offer_ttl_sec` (`config.py:635`), отказ → следующему.
- Карточка оффера (`:3800–3815`): `offer_pickup_km = прямая × instant_road_k` (`pickup_road_km`, `:589`; `instant_road_k = 1.3`), `offer_pickup_eta_min = км / instant_avg_speed_kmh` (`= 40`, `config.py:586–587`).
- Для **цены** внешний маршрут уже есть: `backend/app/pricing.py:131` `route_metrics()` → `https://api.routing.yandex.net/v2/route`, ключ `yandex_router_key`, таймаут `taxi_external_timeout_sec = 1.5`, кэш `taxi_route_cache_sec = 300` с округлением координат, запасной `fallback_route()`. Это образец для нового кода: httpx, таймаут, кэш, запасной путь.

**Что сделать**
1. Новый модуль `backend/app/road_eta.py`:
   - `pickup_etas(points: list[tuple[int, float, float]], dest: tuple[float, float], client=None) -> dict[int, RoadEta]`, где `points` — `(driver_id, lat, lng)`, `RoadEta` — `(duration_sec, distance_m, source)`.
   - Провайдер по настройке `pickup_eta_provider`:
     - `"none"` (**по умолчанию**) → `{}`; система ведёт себя ровно как сейчас;
     - `"osrm"` → **один** запрос Table API на всех кандидатов:
       `GET {osrm_url}/table/v1/driving/{dest_lng},{dest_lat};{lng1},{lat1};…?sources=1;2;…;n&destinations=0&annotations=duration,distance`
       (ответ: `durations[i][0]` — секунды, `distances[i][0]` — метры, `null` — недостижимо).
   - `client` — внедряемый httpx-клиент для тестов (по образцу `pricing.weather_metrics(client=...)`).
   - Кэш по округлённым координатам (~100 м) на `pickup_eta_cache_sec`.
   - Любая ошибка (таймаут, не 200, битый JSON, `code != "Ok"`) → `{}` + запись в лог **без координат**.
2. Настройки в `config.py`:
   - `pickup_eta_provider: str = "none"`  — `none | osrm`
   - `osrm_url: str = ""`  — например `http://127.0.0.1:5000`
   - `pickup_eta_top_n: int = 8`
   - `pickup_eta_timeout_sec: float = 0.8`
   - `pickup_eta_cache_sec: int = 60`
3. Встроить в `candidates()` после `eligible()`:
   - взять `pickup_eta_top_n` ближайших по прямой и одним вызовом `pickup_etas(...)` получить время;
   - у кого время есть — перевести его в «километры по прямой» теми же коэффициентами, что уже стоят в карточке оффера:
     `экв_км = duration_sec / 3600 × instant_avg_speed_kmh / instant_road_k`
     и отдать в `rank()` вместо прямой. Для обычной улицы `экв_км ≈ прямая`, поэтому веса `_score` не нужно перенастраивать; для «водителя за рекой» `экв_км` резко растёт;
   - у остальных (дальше top-N, `null`, ошибка) — прямая, как сейчас.
   Пример: A — прямая 1,0 км, по дорогам 12 мин → `экв_км ≈ 6,2`; B — прямая 2,0 км, 4 мин → `экв_км ≈ 2,1` → оффер получает B.
4. Карточка оффера (`:3800–3815`): если для текущего кандидата есть время по дорогам (через кэш `road_eta`, без нового запроса в пределах `pickup_eta_cache_sec`) — `offer_pickup_eta_min = ceil(duration_sec / 60)`, `offer_pickup_km = distance_m / 1000`; иначе — текущая формула.
5. Цены **не трогать** (`pickup_fee_rub`, `route_metrics`, surge) — это отдельное решение.
6. Провайдера «yandex» в этом ТЗ **не делать**: платно за каждый запрос, и координаты водителей уходят третьей стороне (нужны решение Александра и правка политики конфиденциальности). OSRM на своём сервере — координаты никуда не уходят.

**Граничные случаи:** 0 или 1 кандидат (запрос не нужен); все `null`; таймаут; строк в ответе меньше, чем кандидатов; водитель стоит в точке подачи (0 сек); `provider = "osrm"` при пустом `osrm_url` → как `none` + одно предупреждение в лог.

**Тесты** (`backend/tests/test_road_eta.py` + дополнение тестов matcher)
- «Река»: пример из п. 3 → оффер получает **B**.
- `provider = "none"` → порядок кандидатов идентичен текущему; `test_priority.py`, `test_quality.py`, `test_driver_is_judged_by_his_own_work.py` зелёные без правок.
- Таймаут / 500 / битый JSON / `code != "Ok"` → порядок по прямой, заказ не падает.
- `null` у части водителей → они ранжируются по прямой.
- Ровно один HTTP-запрос на круг подбора; повтор в пределах `pickup_eta_cache_sec` — из кэша.
- В запросе не больше `pickup_eta_top_n` кандидатов.
- Карточка оффера показывает минуты по дорогам, когда они есть.
- В логах нет координат (`caplog`).
- Фейковый OSRM — `httpx.MockTransport`; настоящий сервис в тестах не нужен.

**Готово, когда**
- [ ] При `pickup_eta_provider = none` поведение прежнее (регрессия зелёная).
- [ ] При `osrm` «водитель за рекой» проигрывает тому, кто реально быстрее доедет.
- [ ] Сбой сервиса маршрутов никогда не ломает подбор: запасной путь — прямая.
- [ ] Настройки — в `docs/architecture.md`; решение «OSRM, а не платный API» — в `docs/decisions.md`.

**Включение на проде — не в этом PR:** сначала Приложение А, потом переменные окружения `PICKUP_ETA_PROVIDER=osrm`, `OSRM_URL=http://127.0.0.1:5000` и перезапуск сервера.

## ТЗ-3. Такси: ночью заказ сначала опытным водителям

**Зачем.** Ночной заказ — самый чувствительный: человек один, темно, райцентр. Яндекс в таких случаях искусственно завышает время подачи рискованным водителям, и заказ уходит опытному. Мы делаем мягкую версию: ночью новичок стоит в очереди так, будто он на 1,5 км дальше. Если рядом только новички — заказ всё равно получит новичок, никого не блокируем. Правило **видно водителю**: у нас принцип «скрытый приоритет читается как заказы по блату» (`priority.py`), так нельзя.

**Как сейчас**
- Очередь офферов: `rank()` / `_score()` (`instant_service.py:3022`, `:3008`) — близость, рейтинг, штраф за низкий рейтинг, бонус приоритета (`priority.py:137` `taxi_points`, `:199` `score_bonus`).
- Ночное окно уже есть: `local_hour()` (`instant_service.py:403`), `in_night_window(hour, frm, to)` (`:411`); часы ночи — из тарифа (`night_k_for`, `:421`), по умолчанию `night_from_hour_default = 22`, `night_to_hour_default = 6` (`config.py:595–596`).
- «Новичок» в проекте уже определён: первые `fee_tier1_trips = 30` завершённых заказов — льготная ступень комиссии (`config.py:205`). Используем эту же границу, чтобы слово «новичок» везде значило одно и то же.
- Счёт опыта: `debt.done_trips_before(session, driver_id, when)` (`backend/app/debt.py:98`) — сколько быстрых заказов водитель завершил. Для пачки кандидатов нужен один групповой запрос (образец — `services.driver_trips_agg`, `services.py:1436`).

**Что сделать**
1. Настройки в `config.py`:
   - `matcher_night_novice_enabled: bool = True`
   - `matcher_night_novice_extra_km: float = 1.5`
   - порог — `settings.fee_tier1_trips` (новую настройку порога не заводить).
2. В подборе (`candidates()` / `rank()`): если сейчас ночь (часы тарифа заказа, иначе значения по умолчанию) и правило включено — **одним запросом** посчитать завершённые заказы такси по всем кандидатам; у кого их `< fee_tier1_trips`, в `_score` передавать `dist_km + matcher_night_novice_extra_km`. Если ТЗ-2 уже влито — прибавлять к `экв_км`.
3. Никого не исключать — меняется только порядок в очереди.
4. Прозрачность: в расклад приоритета (`taxi_points`) добавить информационную строку (0 баллов), только пока водитель новичок, например:
   «Ночью (22:00–06:00) заказы сначала получают водители от 30 поездок. У тебя 7 — осталось 23.»
   Часы и порог — из настроек / тарифа, не хардкодить. Две версии текста (`ru`/`ba`), в приложении — там, где водитель видит расклад приоритета (`appText`, `Canon*`).
5. Цены и комиссии не трогать.

**Примеры (одинаковые рейтинг и приоритет) — оформить тестами**

| Время (Уфа) | Новичок (5 поездок) | Опытный (50 поездок) | Оффер первым |
|---|---|---|---|
| 23:00 | 1,0 км | 2,0 км | опытный (у новичка «2,5 км») |
| 23:00 | 1,0 км | 3,0 км | новичок (2,5 < 3,0) |
| 14:00 | 1,0 км | 2,0 км | новичок (днём правило не действует) |
| 23:00 | 1,0 км | нет | новичок (никого не блокируем) |
| 23:00, правило выключено | 1,0 км | 2,0 км | новичок |

Плюс границы: 21:59 / 22:00 / 05:59 / 06:00 по местному времени; ровно 29 и 30 завершённых заказов.

**Тесты:** таблица выше; «один запрос на всех кандидатов» (без N+1); строка в раскладе приоритета есть у новичка и отсутствует у опытного; Android — UI-тест, что строка показывается и текст двуязычный; `CanonSourceGuardTest` зелёный.

**Готово, когда**
- [ ] Таблица примеров проходит.
- [ ] `matcher_night_novice_enabled = false` возвращает прежнее поведение.
- [ ] Новичок видит правило и свой прогресс.
- [ ] Башкирские черновики — в `docs/tasks.md`; в `docs/decisions.md` — почему «+1,5 км», а не запрет.

**Зависимость:** правит те же функции, что ТЗ-2 (`candidates` / `rank` / `_score`). Запускать после слияния ТЗ-2 или тем же агентом в той же ветке сразу после ТЗ-2.

## ТЗ-4. Курьер: ближние заказы наверху

**Зачем.** Сейчас лента курьера идёт от новых заказов к старым — курьер листает и сам прикидывает, что рядом. Нужно: ближние к нему сверху, на карточке «≈ 3 км до забора».

**Как сейчас**
- `backend/app/routers/courier.py:1134` `courier_available()` — сортировка `ParcelDelivery.id desc` (`:1148`, новые сверху), лимит `FEED_MAX = 200` (`visibility.py:281`), фора приоритетным (`:1154`), фильтр зоны (`:1169`), скрытие заблокированных (`:1173`).
- Сервер **не знает**, где курьер: `CourierOnlineIn` (`:1027`) — только зона и город; доплата за подачу считается от города работы (`:462`).
- В ленте координаты забора **округлены до 2 знаков (~1 км)** — `_parcel_available()` → `_parcel_base(p, blur_coords=True)` (`routers/parcels.py:602`, `:458–476`). Это сделано нарочно: до принятия курьер не должен знать точный адрес.
- Android: `ApiClient.getCourierAvailable(fromCity, toCity)` (`data/ApiClient.kt:4361`); экран — `CourierAvailableTab` (`CourierScreen.kt:928`), `LazyColumn` с ключами `"cav-…"` (`:1018`, `:1131`), карточка `CourierAvailableCard` (`:1172`). Разрешения — `rememberPermissionGate()` (`Permissions.kt:54`), `openAppSettings()` (`:133`). Геолокация курьера уже берётся через `LocationManager` в `CourierLocationService.kt` — тот же способ, без новых библиотек.

**Сервер**
1. `GET /courier/available` принимает необязательные `lat`, `lng` (float). Передан только один или значение вне диапазона (−90…90, −180…180) → 422.
2. Если переданы — для каждой заявки `pickup_km = haversine(lat, lng, from_lat_округлённая, from_lng_округлённая)`, **строго от тех же округлённых координат, что уходят в ответ**. Иначе, запрашивая ленту из разных точек, можно вычислить точный адрес отправителя. Округлить до 0,1.
3. Сортировка: заявки с `pickup_km` — по возрастанию (при равенстве новее выше); заявки без координат — после них, в прежнем порядке «новые сверху».
4. В каждый элемент — поле `pickup_km` (`null`, если не посчитано).
5. Фора приоритетным, фильтры зоны и блокировок — без изменений; сортировка применяется после них.
6. Координаты курьера не сохранять и не писать в логи. `/courier/online` не трогать.

**Приложение**
1. `getCourierAvailable(fromCity, toCity, lat: Double? = null, lng: Double? = null)`; координаты округлять до 3 знаков (~100 м) перед отправкой.
2. `ParcelDto.pickupKm: Double?` ← `pickup_km` (без падения на `null`). Добавить `pickup_km` в `numberKeys` контракт-теста `ApiClientEndpointContractTest` (`:85`).
3. `CourierAvailableTab`: разрешение на геолокацию есть → последняя известная точка через `LocationManager` (самая свежая из GPS / NETWORK / PASSIVE, не старше 10 минут) → в запрос ленты. Точки нет → запрос без координат (как сейчас).
4. Разрешения нет → над лентой мягкая плашка (закрывается; в эту сессию больше не показывать):
   «Покажем ближние заказы сверху — разреши геолокацию» + кнопка «Разрешить» (`rememberPermissionGate`); после разрешения — перезагрузить ленту. Запрещено навсегда → кнопка ведёт в настройки (`openAppSettings`). Появление / исчезновение — `AnimatedVisibility`.
5. `CourierAvailableCard`: чип «≈ N км до забора», N — целые км (меньше 1,5 км → «≈ 1 км»): точнее не бывает, координаты округлены до ~1 км. `pickupKm == null` → чипа нет.
6. Перестановку карточек анимировать `Modifier.animateItem()`, если текущая версия Compose его поддерживает (версии не поднимать; если нет — без анимации перестановки).
7. Всё — `appText(ru, ba)` и шкалы `Canon*`; состояния загрузки / пусто / ошибка остаются.

**Тесты**
- Сервер (`backend/tests/test_courier_feed_nearest_first.py`): сортировка; заявки без координат — в конце; только `lat` → 422; вне диапазона → 422; без параметров — порядок как сейчас (регрессия); `pickup_km` равен haversine от **округлённых** координат; фора приоритетным работает; координат нет в логах.
- Android: контракт-тест (`pickup_km`); `ApiClient` строит запрос с округлёнными `lat`/`lng`; UI-тест: чип есть при `pickupKm`, нет при `null`; плашка есть без разрешения и нет с разрешением; `CanonSourceGuardTest` зелёный.

**Готово, когда**
- [ ] С геолокацией курьер видит ближние сверху и «≈ N км до забора».
- [ ] Без геолокации всё как раньше + одна вежливая плашка.
- [ ] Точный адрес отправителя по-прежнему нельзя вычислить из ленты.
- [ ] Башкирские черновики — в `docs/tasks.md`.

**Зависимость:** `CourierScreen.kt` и `ApiClient.kt` уже изменены в ветке проверки ролей `audit/roles-remaining` (она на паузе). Запускать после её слияния в `main`; иначе — аккуратно решить конфликты, не потеряв её правки.

## ТЗ-5. Такси: «Комфорт» — только водители с рейтингом от 4,7

**Решение Александра (26.09.2026):** порог — 4,7.

**Зачем.** Пассажир «Комфорта» платит больше и ждёт не только машину получше, но и хорошего водителя. Правило: заказы «Комфорта» получают только водители с рейтингом за рулём от 4,7. Пассажиру пишем об этом в описании класса — это плюс к доверию. Водитель видит, почему «Комфорт» у него закрыт и что сделать, чтобы открыть.

**Как сейчас**
- Класс считается **только по машине** (`backend/app/car_class.py`; возраст «Комфорта» — `car_comfort_max_age = 10`, `config.py:395`), водитель включает доступные классы сам. Рейтинг на класс не влияет.
- Рейтинг влияет только на очередь: от 4,8 — плюс балл приоритета (`priority_rating_min`, `config.py:741`), ниже 4,6 — штраф (`matcher_low_rating`, `:385`).
- Подбор по классу — `eligible()` (`instant_service.py`, проверка класса около `:2981–2984`: `available_or_legacy` → `driver_takes`).
- Класс открывается в городе, когда набралось `car_class_min_drivers = 3` водителя (`class_rollout.class_counts()`, `class_rollout.py:81`; считает по машинам).
- Кабинет водителя: классы — `routers/taxi.py` около `:466–550` (`effective_classes`); в приложении — `ApiClient.getMyTaxiClasses()` / `setMyTaxiClasses()`, экран — `TaxiOnboardingScreen.kt` (загрузка около `:964`).
- Пассажир: карточки классов — `InstantClassInfo(...)` в `InstantOrderScreen.kt:3472` («Комфорт — новее и с кондиционером»).

**Правило**
- Водитель может брать «Комфорт», если одновременно:
  1) машина проходит в класс «Комфорт» (как сейчас);
  2) у него **не меньше 5 оценок за рулём** (`comfort_min_ratings`) — иначе новичок с одной пятёркой сразу попадал бы в «Комфорт»;
  3) его рейтинг за рулём **от 4,7** (`comfort_min_rating`).
- Рейтинг — `services.driver_rating()` (`services.py:1319`: только оценки за поездки, где он был водителем), **не** `DriverProfile.rating` (у новичков там заводское 5,0 — см. комментарий в `priority.taxi_points`).
- Сравнивать то же округлённое число, которое водитель видит в приложении (проверь, с каким округлением показывается рейтинг), — чтобы не было «у меня 4,7, а Комфорт закрыт».
- Новичок без 5 оценок возит «Эконом» на той же машине (оплата — по тарифу заказа, как сейчас), набирает оценки — «Комфорт» открывается сам.
- Рейтинг упал ниже 4,7 — «Комфорт» закрывается сам; поднялся — открывается сам. Идущая поездка не прерывается: правило действует только на новые предложения.
- Выключатель: `comfort_min_rating = 0` → правило выключено целиком, поведение как сейчас.

**Настройки** (`config.py`, в блоке классов машин, около `:391`):
- `comfort_min_rating: float = 4.7`
- `comfort_min_ratings: int = 5`

**Сервер — что сделать**
1. Одна функция-правило (например, `car_class.comfort_rating_ok(rating, count) -> bool`) и пакетный подсчёт рейтинга за рулём для списка водителей (по образцу `services.users_rating_agg`, `services.py:1296`, но по правилам `driver_rating`) — без N+1.
2. Подбор (`eligible()`): водитель не проходит правило → убрать `comfort` из его доступных классов **для этого заказа**. Заказы «Эконом» он получает как раньше.
3. Открытие класса (`class_rollout.class_counts()`): в счёт «Комфорта» идут только водители, прошедшие правило. Иначе появится кнопка «Комфорт», за которой никого нет. (Рейтинг меняется медленно, поэтому класс не будет мигать; если начнёт — добавить запас по порогу отдельной задачей.)
4. Кабинет водителя («мои классы», `routers/taxi.py`): добавить причину блокировки, например
   `"locks": {"comfort": {"reason": "ratings_count" | "rating", "min_rating": 4.7, "min_ratings": 5, "rating": 4.62, "ratings": 7}}`.
   Включить «Комфорт» при блокировке нельзя: понятная ошибка на двух языках.
5. Витрина классов для пассажира (сборка `options_out` в `instant_service.py`, около `:1400`): для `comfort` при включённом правиле отдавать `min_driver_rating: 4.7` — чтобы приложение не хардкодило число.
6. Цены, комиссии, переход на соседний класс через 20 секунд (`class_fallback_after_sec`) — без изменений.

**Приложение — что сделать**
1. Пассажир — карточка «Комфорт» (`InstantClassInfo`, `InstantOrderScreen.kt:3472`): если сервер прислал `min_driver_rating` — дописать к описанию «водители от 4,7 ★» (число из ответа, `appText`). Не прислал — как сейчас.
2. Водитель — экран классов (`TaxiOnboardingScreen.kt`): «Комфорт» при блокировке — выключенный переключатель с замком и подписью:
   - мало оценок: «Комфорт откроется после 5 оценок. У тебя 3 — осталось 2.»
   - низкий рейтинг: «Комфорт — при рейтинге от 4,7. Сейчас 4,62. Хорошие поездки вернут доступ.»
   Числа — из ответа сервера; тексты двуязычные; `Canon*`; смена состояния — плавная анимация.
3. `DriverClassesDto` и данные витрины — новые поля, без падения на старом сервере; новые ключи — в контракт-тест `ApiClientEndpointContractTest`.

**Тесты**
- Правило: 4,70 и 5 оценок → да; 4,69 → нет; 4 оценки по 5,0 → нет; 0 оценок → нет; граница с учётом округления, которое видит водитель; `comfort_min_rating = 0` → да всем, чья машина подходит.
- Подбор: заказ «Комфорт» не предлагается водителю с 4,6, даже если он ближе всех; заказ «Эконом» ему предлагается.
- Открытие класса: три водителя с «комфортными» машинами, у одного 4,5 → в городе двое → «Комфорт» закрыт (порог 3).
- Кабинет: причина блокировки приходит; попытка включить «Комфорт» при блокировке → двуязычная ошибка.
- Витрина: `min_driver_rating` есть при включённом правиле и нет при выключенном.
- Android: карточка «Комфорт» показывает «водители от 4,7 ★»; экран классов показывает замок и оба текста; `CanonSourceGuardTest` зелёный.
- Регрессия: существующие тесты классов, открытия классов и подбора зелёные.

**Готово, когда**
- [ ] Заказ «Комфорт» получают только водители от 4,7 и минимум с 5 оценками.
- [ ] Кнопка «Комфорт» не появляется в городе, где таких водителей меньше трёх.
- [ ] Водитель видит, почему «Комфорт» закрыт и что сделать.
- [ ] Пассажир видит «водители от 4,7 ★».
- [ ] Выключатель возвращает прежнее поведение; башкирские черновики — в `docs/tasks.md`; решение и порог — в `docs/decisions.md` и `docs/taxi-classes-2026-08.md`.

**Последствие, о котором надо знать.** На старте у водителей мало оценок, поэтому «Комфорт» в городе откроется позже — когда у трёх водителей будет минимум по 5 оценок и рейтинг от 4,7. До этого их машины возят «Эконом». Нужно быстрее — уменьшить `comfort_min_ratings` в настройках сервера (без обновления приложения).

**Зависимость:** правит `eligible()` в том же файле, что ТЗ-2 и ТЗ-3 (другая функция, конфликтов мало). Запускать после ТЗ-3 или аккуратно решить конфликт при слиянии. С ТЗ-4 не пересекается.

## Приложение А. Сервер маршрутов OSRM (для специалиста по серверам, один вечер)

OSRM — бесплатная программа, которая считает путь и время по карте дорог OpenStreetMap. Ставится рядом с нашим сервером, наружу не открывается, координаты никуда не уходят. Пробки она не знает — только дороги, мосты, развороты; для проблемы «водитель за рекой» этого достаточно.

1. **Ресурсы.** Подготовка карты — разово, примерно 2–4 ГБ памяти (если на сервере мало — подготовить на другой машине и скопировать файлы `bashkortostan.osrm*`). В работе — обычно меньше 1 ГБ. Проверить: `free -h`, `df -h`. Нужны `docker` и `osmium-tool` (`apt install osmium-tool`).
2. **Карта Башкортостана:**
   ```bash
   mkdir -p /srv/osrm && cd /srv/osrm
   wget https://download.geofabrik.de/russia/volga-fed-district-latest.osm.pbf
   # вырезать Башкортостан с запасом (левый, нижний, правый, верхний край)
   osmium extract -b 53.0,51.4,60.1,56.7 volga-fed-district-latest.osm.pbf -o bashkortostan.osm.pbf
   ```
3. **Подготовка:**
   ```bash
   docker run -t -v /srv/osrm:/data ghcr.io/project-osrm/osrm-backend osrm-extract -p /opt/car.lua /data/bashkortostan.osm.pbf
   docker run -t -v /srv/osrm:/data ghcr.io/project-osrm/osrm-backend osrm-partition /data/bashkortostan.osrm
   docker run -t -v /srv/osrm:/data ghcr.io/project-osrm/osrm-backend osrm-customize /data/bashkortostan.osrm
   ```
4. **Запуск — только для своего сервера, порт наружу не открывать:**
   ```bash
   docker run -d --name osrm --restart unless-stopped -p 127.0.0.1:5000:5000 \
     -v /srv/osrm:/data ghcr.io/project-osrm/osrm-backend osrm-routed --algorithm mld /data/bashkortostan.osrm
   ```
5. **Проверка** (две точки в Уфе, порядок «долгота,широта»):
   ```bash
   curl "http://127.0.0.1:5000/route/v1/driving/55.9721,54.7388;55.9578,54.7250?overview=false"
   ```
   В ответе — `"code":"Ok"` и `duration` в секундах.
6. **Включить в Юлдаше** (после влития ТЗ-2): в окружение сервера `PICKUP_ETA_PROVIDER=osrm`, `OSRM_URL=http://127.0.0.1:5000`, перезапустить backend. **Откат** — `PICKUP_ETA_PROVIDER=none` и перезапуск.
7. **Обновление карты** — раз в месяц повторить шаги 2–3 в соседней папке и перезапустить контейнер на новых файлах (новые дороги и мосты).

## Приложение Б. Что из ролика сознательно не берём

| Идея | Почему не сейчас |
|---|---|
| Венгерский алгоритм (раздавать машины пачкой) | Выигрывает, когда в одном районе за секунды приходят десятки заказов. У нас такие совпадения редки, а копить заказы — значит заставлять каждого ждать лишние секунды. Вернуться, когда в Уфе будут десятки заказов в минуту. |
| Предсказание заказа до нажатия кнопки | Малая польза при наших объёмах; ближайшего водителя для цены мы и так ищем заранее. |
| Цепочки заказов (заказ водителю, который ещё везёт) | Нужен новый режим в приложении водителя и новые состояния поездки — отдельный большой проект. |
| Категории аварийности по GPS и датчикам телефона | Нужны сбор данных о вождении, согласие водителей и правка политики (152-ФЗ). Отдельный проект; ТЗ-3 — первый мягкий шаг. |
