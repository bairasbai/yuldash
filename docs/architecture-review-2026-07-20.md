## 🟢 Вывод (коротко)

Юлдаш **давно не прототип**: реальный бэкенд, живой реалтайм, продуманная безопасность, полноценные фичи. Но приложение стоит на **нескольких «прототипных» опорах**, которые с ростом (пользователей, фич, разработчиков) будут кусаться всё сильнее. **Ничего не горит.** P0 по безопасности нет, секретов в git нет.

Но есть **один инфраструктурный P0** (математика соединений с БД — сервер может лечь на пике) и группа **P1-фундамента**, которые лучше начать чинить до массового запуска, пока они не «забетонировались».

Проблемы делятся на 4 кучки:
- **📱 Клиент (Android)** — фундамент прототипа: нет слоя данных, нет ViewModel у экранов, самодельная навигация, экраны-«свалки». → мешает добавлять фичи и работать нескольким людям.
- **🖥 Сервер** — упрётся в стену при росте: пул соединений, весь реалтайм на одном канале, залповая нагрузка на карту, хаос миграций, деплой с обрывом.
- **💸 Деньги/доверие** — платежи «на доверии» вручную + личный номер владельца виден всем.
- **⚙️ Процессы** — CI не собирает само приложение и тестирует не на той БД.

- Деньги не доверяют клиенту: цена Boost с сервера, СБП всегда `pending` до ручного подтверждения (сам себе оплату не подтвердишь), mock-платежи заблокированы в проде.

**Бэкенд — зрелые паттерны:**
- Redis pub/sub для WS между воркерами (`services.py:593-635`) — правильный паттерн с аккуратной отменой и мягким фолбэком.

**Клиент — правильные зародыши:**
- `UiKit.kt` спроектирован отлично: `AppStateContainer` со всеми состояниями (loading/error/empty/content), скелетоны, токены `Canon*`, тач-цели ≥54dp.

- Весь API на `Result<T>` + типизированный `ApiException` — готовая основа под `UiState.Error`. Single-flight refresh на 401 через `Mutex`, шифрованный токен.
- Container/Content-разрез уже применён местами (`PassengerCabinetScreen`→`PassengerCabinetContent`) — это правильный целевой паттерн.

## 🖥 Сервер (бэкенд)

### S0 [P0] Пул соединений переполнит Postgres при 5 воркерах
`db.py:16-23` — `pool_size=10, max_overflow=15` = **25 соединений на воркер**. Прод крутит **5 воркеров** → 5×25 = **125 > дефолтного `max_connections` Postgres (100)**. Плюс automatch/cleanup берут ещё.
**Сломается:** под наплывом воркеры разом раздувают пулы → Postgres отдаёт `FATAL: too many connections` → SQLAlchemy ждёт `pool_timeout=30` и валит в 500 → каскад ретраев. Это не «медленно», это «лёг на ровном месте».
**Фикс:** формула `(pool_size+max_overflow)×workers ≤ max_connections − резерв`. Для 5 воркеров: `pool_size=8, max_overflow=7` (=75) + поднять PG `max_connections` до 150-200. Идеально — **PgBouncer** (transaction pooling) перед PG. Число воркеров зафиксировать в одном месте. **1-2 ч.**

### B1 [P1] Весь реалтайм идёт через ОДИН Redis-канал
`services.py:533` — единственный канал `yuldash:chat`. Через него — **всё**: чат, гео-координаты поездок (`location.py:116`), «refresh» карты. На каждом воркере одна задача-подписчик получает **каждое** сообщение всех юзеров.
**Сломается:** 300 поездок × координата раз в 5-10с = ~60-120 сообщений/с, и каждое летит на **все 5 воркеров** (усиление ×5), где 4 из 5 десериализуют и выбрасывают. Единая точка сериализации → лаги «стрелки попутчика» и чата.
**Фикс:** разнести каналы `chat:{booking_id}` / `loc:{booking_id}`, подписываться точечно при `register`/отписываться при `disconnect`; троттлинг координат до 1/сек на участника. **1-2 дн.**

### B2 [P1] Thundering herd по некэшированному `/rides/near` — ✅ СДЕЛАНО (2026-07-20)
> **Сделано:** дебаунс `notify_map_changed` (`SET NX EX`, окно 3с → всплеск событий = 1 refresh) + кэш `/rides/near` 15с по ключу (from,to,округл.координаты,радиус). Скрытие заблокированных/пагинация — per-request после кэша. Тесты: `tests/test_b2_map_load.py`. Осталось (клиент, на машине с SDK): джиттер 0-3с на перезапрос; регионализация канала по городу — опц.

`notify_map_changed()` (`services.py:579-590`) публикует в **глобальный** канал, на который подписаны **все** открывшие карту; клиент по «refresh» тянет `/rides/near` — самый тяжёлый (гео-скан + haversine в Python), и он **не кэшируется** (кэш только у `/rides` без фильтров).
**Сломается:** 2000 человек с открытой картой + кто-то опубликовал поездку → 2000×2 запроса на самый дорогой эндпоинт в одну секунду. Каждая публикация = микро-DDoS по своей БД.
**Фикс:** серверный дебаунс «refresh» (1 раз в 3-5с); кэш `/rides/near` по сетке координат (округлять lat/lng + radius в ключ, TTL 15-20с); джиттер 0-3с на клиенте; регионализовать канал по городу. **1 дн.**

### B3 [P1, P0 по риску данных] Три механизма миграций, прод-путь ручной
Одновременно живут: `create_all()` на старте (создаёт таблицы, но **никогда не ALTER** существующих в Postgres); авто-добавление колонок **только для SQLite** (`db.py:55-74`); **Alembic — 3 ревизии, обрывается на 0003**; и **24 файла `migrate_*.sql`** руками. Деплой-скрипт применяет жёстко зашитые **5 из 24**.
**Сломается:** добавил колонку в `models.py` → на проде Postgres `create_all` её не создаст, Alembic отстал, новый `migrate_*.sql` в `.bat` вписать забыли → первый запрос к колонке = `UndefinedColumn` = 500 на живых людях. При росте частоты релизов — регулярная авария + дрейф «модели ≠ БД».
**Фикс:** **один** источник истины — Alembic. Autogenerate baseline = слепок прода (вобрать 0001-0003 + все `migrate_*.sql`); из прод-`init_db` убрать `create_all`; схему катит только `alembic upgrade head` шагом деплоя; `migrate_*.sql` удалить. **1 дн** на копии прод-БД.

### B4 [P1] Деплой не zero-downtime + SPOF
`deploy-backend.bat` — `scp -r app` поверх файлов + `systemctl restart`. Рестарт рвёт **все** WS (чаты, гео активных поездок). Один сервер `85.239.52.55`, без балансировщика; один Redis = SPOF сразу для реалтайма, rate-limit и кэша.
**Сломается:** каждый деплой в час пик = у всех пассажиров в поездке обрывается трекинг и чат. OOM (3.8 ГБ — немного) = полный простой + потеря in-memory стейта.
**Фикс:** zero-downtime без второго сервера — **два systemd-инстанса** за nginx `upstream` + graceful `reload` (SIGHUP) вместо `restart`; `rsync --delay-updates` или git-pull вместо `scp` + `alembic upgrade head` шагом; Redis с AOF-персистом. На перспективу — 2-й сервер + managed Postgres/Redis. ✅ Offsite-S3-бэкап уже есть (`backup-db.sh`) — худший сценарий закрыт. **1-2 дн.**

### B5 [P2] Схема БД: индексы, CSV-колонки, пагинация
- `RideRequest.status` **без индекса** (`models.py:194`), хотя `/requests/near` и `/requests/feed` фильтруют по нему → seq-scan (у зеркального `Ride.status` индекс есть — асимметрия).
- `Message.hidden_user_ids` — **CSV-строка** (`models.py:221`); `list_messages`/`conversations` грузят все сообщения и фильтруют в Python. `Ad.placements`/`cities` — тоже CSV.
- `/conversations` и `/notifications` (`services.py:145-158`) грузят **все** брони юзера без пагинации → активный водитель за год = выгрузка всей истории на каждое открытие инбокса.
- Денормализованный `DriverProfile.rating` рядом с таблицей `Rating` — риск дрейфа (кто пересчитывает?).
**Фикс:** индекс на `riderequest(status)` + составной `message(booking_id, id)`; «последнее сообщение» подзапросом `MAX(id) GROUP BY`; `hidden_user_ids` → таблица `MessageHide`; пагинация по курсору. **1-2 дн.**

### B6 [P3] `services.py` — «кухонная раковина» (634 стр.)
Медиа + SMS (2 провайдера) + FCM + гео + Redis-кэш + WS-менеджер + сид демо в одном модуле. Не God-object (свободные функции), но связывает несвязанное: правка SMS тащит перекомпиляцию модуля, от которого зависит реалтайм. **Фикс:** разнести `ws/manager.py`, `notifications/{push,sms}.py`, `geo.py`, `cache.py`, `media.py`. Механически. **0.5 дн.**

## 📱 Клиент (Android)

> ⚠️ Заявленная в доках «MVVM + Repository + Flow» архитектура **в коде отсутствует**. `kotlinx.coroutines.flow` не импортируется нигде; `Repository`/`UseCase`/`StateFlow` — 0 вхождений. Фактически: `object ApiClient` + прямые вызовы из composable + состояние сервера в `remember{}`.

### C1 [P1] Нет слоя Repository — экраны прибиты к `ApiClient`
**164 прямых вызова `ApiClient.*` из UI** (Profile — 30, BookingActiveTrip — 29, Secondary — 21, YuldashApp — 20). Между экраном и сетью нет интерфейса. `Mocks.kt` — не подставляемый источник, а глобальные `val`, которые экран сам мешает с сетью инлайн.
**Сломается:** заменить мок на API «одним швом» невозможно — швов 164. Оффлайн/кеш нельзя добавить централизованно. Тест экрана требует поднимать MockWebServer вместо подмены. Бэкенд-агент не может менять контракт параллельно — он растащен по UI.
**Фикс:** интерфейсы `RidesRepository`/`BookingsRepository`/`ChatRepository`/… + реализация над `ApiClient`+кеш; `Mocks` → `Fake*Repository` (тот же интерфейс). **Пилот на rides/map — 3-5 дн, дальше инкрементально.**

### C2 [P1] Нет per-screen ViewModel — серверные данные в composable
Счёт `by remember { mutableStateOf(серверные данные) }`: Accessibility — 47, Secondary — 42, Profile — 39, Map — 33. `YuldashViewModel` (90 стр.) — глобальный контейнер **навигации**, не слой состояния данных.
**Сломается:** каждый поворот экрана = полная **перезагрузка с сервера** (трафик, моргание, скачок скролла). Смерть процесса на брони = данные утеряны → костыль-редирект на Home (`YuldashApp.kt:371-375`). Новый разработчик копирует тот же паттерн → долг растёт линейно с числом экранов.
**Фикс:** на фичу — `ViewModel` + `data class UiState` (sealed Loading/Content/Error) в `StateFlow`; ключи (id брони) в `SavedStateHandle`; экран: `collectAsStateWithLifecycle()`, никаких `remember` для серверных данных. Container/Content-зародыш уже есть — сделать универсальным. **4-6 дн.**

### C3 [P1] Экраны-«свалки» — несколько несвязанных экранов в одном файле
`SecondaryScreens.kt` (1425) — **15 разных экранов** (Notifications/Safety/Settings/Rules/Admin*/Blocklist/Report…). `RidesRequestsChatScreens.kt` (2061) — **5 бизнес-потоков**. `ProfileScreen.kt` — 5 экранов. Доки говорят «UI разрезан» — но разрезан только из `MainActivity`, **не по экранам**.
**Сломается:** это делает невозможным правило CLAUDE.md §12 «2 UI-агента параллельно» — правка Настроек и Блок-листа = один файл = last-write-wins. Новичку с задачей «экран Правил» открывается файл с 14 чужими экранами.
**Фикс:** резать по одному экрану = один файл в пакеты по фиче (`ui/rides/`, `ui/chat/`, `ui/admin/`, `ui/settings/`). Сборка зелёная после каждого выноса. **2-3 дн — самый высокий ROI, разблокирует весь параллелизм (§12.H).**

### C4 [P1] Самодельная навигация + аргументы в глобальном состоянии
`enum Screen` (44 значения) + `when(screen)` на **44 ветки** (`YuldashApp.kt:516-881`), без Navigation-Compose. Аргументы — через глобальные поля VM (`selectedRide`, `activeBookingId`, `responsesRequestId`…); back-stack `navHistory` хранит **только enum, без аргументов**; «куда вернуться» — руками через флаги `createRideReturnScreen`/….
**Сломается:** путь `Booking(A)` → др. экран → «назад» берёт `selectedRide` из глобалки, а она сменилась → чужая поездка/краш. **Deep links невозможны** — пуш «водитель выехал» не откроет конкретную бронь (FCM уже готов, а открыть экран некуда). Каждый новый экран с аргументом = ещё поле в VM.
**Фикс:** **Navigation-Compose** — типизированные маршруты (`booking/{id}`), back-stack и restore из коробки, deep links под FCM. Мигрировать пачками (сначала листья), `Screen`-enum оставить мостом. Return-флаги удаляются сами. **3-5 дн.**

### C5 [P2] `ApiClient` god-object + дубли маппинга + `fireXxx`
`object ApiClient` (1598 стр.) смешивает транспорт (`HttpURLConnection`, Retrofit/OkHttp для REST — 0), auth+refresh, `EncryptedSharedPreferences`, парсинг JWT, TTL-кеш, ~90 методов и **40+ DTO** внизу файла. Как `object` — глобальное мутабельное состояние, инъекции нет. DTO→UI маппинг размазан (`Ride(...)` вне `data/` — 23 сайта). **10 `fireXxx`** запускают запрос в приватный scope без возврата — ошибка теряется молча (был баг «заявка отправлена», а на сервере нет).
**Фикс:** разнести `HttpEngine`/`TokenStore`/`*Api`-сервисы/`dto/`; один `RideDto.toUi()`; оставить только `suspend`-версии с `Result`. Простой ручной DI (`AppContainer`, без Hilt на старте). **4-6 дн, инкрементально.**

### C6 [P2] `UiKit` не внедрён + быстрые перф-победы
`AppStateContainer` (флагман) используется **0 раз** вне UiKit; `AppButton` — 13 раз против **100+ сырых `Button`**; состояния loading/error каждый экран собирает вручную. Списки без `key` в 8+ местах (`items(list.size){i->…}`) → лишние рекомпозиции и «прыжки» анимаций на live-данных (модерация, отклики). `derivedStateOf` — 0 использований; фильтры (`bookings.filter{…}`) считаются в каждой рекомпозиции.
**Фикс:** `Button`→`AppButton`, ручные состояния→`AppStateContainer`, `items(list, key={it.id})`, тяжёлые производные в `remember(key)`. Линт/ревью-чеклист против `Button(` в экранах. **1-2 дн, отлично параллелится.**

## 💸 Деньги и доверие

### M1 [P1/P2] Платежи «на доверии» + утечка личных данных владельца
- Платёж = СБП вручную: юзер переводит по реквизитам → заявка админу → админ сверил карту → подтвердил. Человек в цикле **не масштабируется** (при росте — очередь подтверждений), и это слабое место доверия (недавно в июльском аудите ловили «фантомную оплату»).
- `POST /boost/create` и `/donate` возвращают `payee: {phone, bank, name}` = **реальный телефон, банк и ФИО Александра** любому авторизованному (`payments.py:140-144,180-184`). Хуже: автоадмин выдаётся по номеру из `admin_phones` — если `SBP_PHONE` совпадает с админ-номером, раскрытый номер = ключ к захвату админки.
**Сломается:** личный номер+имя основателя массово собираются → имперсонация («официальный Юлдаш, переведите на +7…» с настоящим именем), таргет-спам; при совпадении с админ-номером — известно, что атаковать.
**Фикс:** (сейчас, часы) держать `SBP_PHONE` **отдельным** от `admin_phones`, не отдавать полное ФИО; (стратегически) **эквайринг ЮKassa** с вебхуками + идемпотентность — тогда личный номер вообще не покидает сервер, а подтверждение оплаты автоматическое. Код ЮKassa уже частично готов (`payments.py`).

## ⚙️ Процессы

### P1 [P2] CI собирает не то и тестирует не там
`.github/workflows/ci.yml` гоняет **только** `pytest` бэкенда на **SQLite**. Само приложение (Android, 21k строк) в CI **не собирается** — каждый «BUILD SUCCESSFUL» руками на машине Александра. Прод-БД — PostgreSQL+PostGIS, значит гео-запросы (ST_DWithin) и гонки (FOR UPDATE) автоматикой **не покрыты** — тестируется только haversine-фолбэк.
**Сломается:** Android-регрессии ловятся только вручную; «CI зелёный» ≠ «прод-путь проверен».
**Фикс:** добавить job сборки Android (`assembleDebug`) + прогон ключевых тестов на **Postgres-контейнере** (гонка брони, гео). **1-2 дн.**

### Безопасность — 8 структурных рисков (P2/P3, все чинятся точечно)
1. **[P2]** `/match/rides` отдаёт **сырой ORM** в обход `public_ride_payload` → сливает точную точку сбора чужих поездок до брони (`rides.py:395`). Фикс — 1 строка: `public_rides_payload(...)`.
2. **[P2]** Rate-limit держится на nginx `X-Real-IP` + лимитер **in-memory на воркер** (`middleware.py`). При выходе API за localhost (проброс порта, 2-й хост) атакующий шлёт свежий `X-Real-IP` и обходит все лимиты (перебор OTP, SOS-бомбинг). Фикс: слушать 127.0.0.1, nginx перезаписывает `X-Real-IP` из `$remote_addr`, `REDIS_URL` обязателен при >1 воркере.
3. **[P2]** Токен на Android тихо деградирует в **plaintext** при недоступном Keystore (`ApiClient.kt:91-113`), а refresh живёт 90 дней. Фикс: при недоступном Keystore — токен только в памяти, не персистить.
4. **[P3]** `/geocode` — открытый (без токена) прокси к квотируемому Яндексу (`discovery.py:131`). Фикс: повесить `current_user` + суточный кап.
5. **[P3]** `/docs`, `/openapi.json` публичны в проде → карта всех admin/payment-эндпоинтов. Фикс: `docs_url=None` при `is_prod`.
6. **[P3]** Нет пер-юзер капа на создание поездок/заявок → замусоривание ленты + амплификация геокодера. Фикс: лимит активных на юзера.
7. **[P3]** Тела SOS/семейных SMS **с именем** уходят в stdout при mock-SMS в проде (`services.py:285`). Фикс: логировать только тип события + маскированный номер.
8. **[P3]** Access-токен 12ч без индивидуального отзыва (только «logout со всех») — приемлемый компромисс, ротация refresh есть.

## 🏗 Как переработать дизайн (целевая картинка)

**Android — навести три слоя, которые декларированы, но не реализованы:**
```
UI (Compose, тонкий: рисует state, шлёт события)
      ↓ collectAsStateWithLifecycle
ViewModel (per-feature: StateFlow<UiState>, бизнес-операции, viewModelScope)
      ↓ интерфейс
Repository (единый ВЛАДЕЛЕЦ данных и кеша, отдаёт Flow; Fake* для тестов)
      ↓
ApiClient (только транспорт: HttpEngine + TokenStore + *Api)
```
+ **Navigation-Compose** (типизированные маршруты, back-stack, deep links под FCM).
+ **Файлы по одному экрану** (`ui/<feature>/<Screen>.kt`).
+ **UiKit — обязателен** (все состояния через `AppStateContainer`, кнопки через `AppButton`).

**Бэкенд:**
- Один источник схемы — **Alembic** (убрать `create_all` из прода + `migrate_*.sql`).
- **PgBouncer** + согласованная формула пула.
- Реалтайм — **per-booking каналы** Redis + троттлинг координат.
- `/rides/near` — **кэш по сетке + дебаунс refresh + джиттер**.
- Деплой — **два инстанса за nginx + graceful reload** (zero-downtime); позже 2-й сервер + managed PG/Redis.
- Разнести `services.py` по модулям.

**Деньги:** **эквайринг ЮKassa** (вебхуки + идемпотентность) — снимает человека из цикла и убирает личный номер владельца из ответов API.

**Процессы:** CI собирает **Android** + гоняет тесты на **Postgres**.
