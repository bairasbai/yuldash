# Удаление офлайн-паспорта — 20.09.2026

## Что воспроизведено

Пять красных тестов показали две связанные причины:

1. Удаление касалось только выбранного хранилища и не оставляло устойчивого запрета на восстановление. Проверены три последствия: возврат паспорта из временно недоступного secure, восстановление старым журналом переноса и запоздалый save после удаления. Во всех случаях проверяется сохранность другой поездки.
2. BookingScreen сохранял паспорт по одному contactUnlocked. Для завершённой поездки сервер может ещё разрешать контакты, поэтому экран снова запрашивал код и сохранял удалённую копию. UI-тест done подтвердил лишний запрос. Второй тест cancelled с принудительным contact_unlocked=true — защитный случай неконсистентного ответа, а не доказательство того, что настоящий сервер выдаёт такие контакты отменённой брони.

До исправлений: **5/5 тестов упали**. Источники: trip-pass-deletion-red-20260920.log, trip-pass-deletion-red-store-20260920.xml, trip-pass-deletion-red-ui-20260920.xml в C:\Users\Bayra\Yuldash\test-results.

В локальном main 527dbb0 remove тоже удаляет только выбранный источник, через apply/Unit; BookingScreen проверяет только contactUnlocked. Журнал переноса и Boolean/commit относятся к текущей совместной рабочей ветке. Проверяется рабочая версия codex/push-routing-audit, изменения не влиты в main.

## Как исправлено

Новый TripPassDeletion сохраняет в plain только номера удалённых броней, ключ trip_pass_deletions_v1. Запрос сначала подтверждается commit; затем удаляются доступные копии. Отметка не исчезает после физической очистки: иначе старый ответ или журнал могли бы снова записать паспорт. load и save учитывают её, updateBoardingCode читает через защищённый load.

При возврате secure или завершении переноса initStores повторяет физическую очистку только отмеченных ключей. Другие поездки не стираются. Незавершённый журнал сначала доигрывается штатным механизмом; отметка всё это время закрывает доступ к удалённому паспорту.

Результат requestRemoval различает:

- CLEARED: подтверждена очистка обоих источников.
- DEFERRED: запрос удаления сохранён, чтение и запоздалая запись закрыты; физическая очистка ещё ожидается.
- NOT_SAVED: запрос не удалось подтвердить. Если commit изменил лишь память, паспорт скрывается в этом процессе, но отсутствие возврата после его смерти не гарантируется.

Совместимый remove возвращает true только для CLEARED. Повтор запроса не принимает отметку только в памяти за доказательство сохранения. Повреждённые метаданные закрывают чтение/замену до исправления или согласованного общего сброса.

При выходе список номеров и неподтверждённые намерения снимаются только после успешного plain.clear + secure_clear_pending. Ключ учтён в SessionKeys.CLEARED_BY_STORE; общий apply-цикл не удаляет его раньше собственного протокола.

BookingScreen теперь сохраняет офлайн-копию только при открытых контактах и статусе confirmed/onboard. История завершённой/отменённой брони не запускает новое сохранение. Проверенный серверный путь повторного бронирования создаёт новый Booking, а существующим считает только pending/confirmed/onboard; постоянный запрет относится к прежнему номеру брони, не ко всем будущим поездкам.

## Открытые границы

Три обработчика завершения/отмены ActiveTripScreen пока вызывают Boolean remove и не показывают отказ первого сохранения намерения. Очистка уже удержанного tripPass в Compose-состоянии также не проверена отдельно. В этой группе исправлен протокол и повторное создание на BookingScreen, а не все пользовательские маршруты ошибок удаления. Следующая группа должна подключить различимые результаты, повтор в интерфейсе и привязку удаления к исходной сессии.

При полном отказе любой записи нет гарантии после смерти процесса. Физическая очистка отложенного удаления повторяется при initStores, а не бесконечным фоновым циклом. Открытие done больше не создаёт новый паспорт, но само это условие не удаляет ранее существующий паспорт, если обработчик удаления вообще не вызывался. Удалённые номера хранятся до выхода, чтобы поздний ответ не отменил удаление.

Новые пользовательские строки и зависимости не добавлялись. Коммитов, push и публикации нет. Эти результаты не подтверждают все роли и настоящие внешние сервисы.

Дополнительная регрессия эмулятора завершена: прежние шесть сценариев хранения — 12/12 фаз (android-storage-deletion-20260920.json); перенос — 3/3 фазы, процессы3750→3807→3860 (offline-migration-process-deletion-20260920.json).
