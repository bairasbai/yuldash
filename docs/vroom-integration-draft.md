# VROOM: изолированный черновик, 03.11.2026

Подготовлена возможность отдельно проверить распределение нескольких доставок между автомобилями.
Действующая одиночная доставка работает прежним способом. Черновик не назначает курьеров,
не двигает статусы, не меняет стоимость и не обращается к серверу VROOM.

Основание: «Можешь отдельным коммитом приготовить код? Не вливая».
База — `1b02947b56aa279f7721f475d26c0dd8018cda75`; отдельная ветка `draft/vroom-adapter-20261103`.
Прочитаны `AGENTS.md`, `courier-plan-2026-07.md`, актуальные проверки в `routers/parcels.py`
и `routers/courier.py`, тесты допуска, предела посылок, отмен и возвратов. `.agents/skills` в этом
снимке нет; использованы `.claude/skills/gotovo` и `orchestration` для обязательной приёмки.

## Что входит в коммит

- `backend/app/vroom.py`: отдельный сервисный модуль в существующем стиле backend,
  неизменяемый входной контракт, построение запроса, проверка ответа, внутренний результат.
- `backend/tests/test_vroom.py`: синтетические примеры и имитация транспорта, без HTTP и настоящих данных.
- Эта записка и короткие записи в `tasks.md`/`decisions.md`.

Нет подключений к роутерам, `main`, worker, моделям БД или клиентам. Нет миграций, зависимостей,
новых настроек окружения, контейнеров или адреса сервиса. Импорт модуля ничего не запускает.
`VroomAdapter()` возвращает `disabled`; нужны одновременно явное `enabled=True` и переданный
асинхронный транспорт. В коммите есть только транспорт-имитация в тестах, сетевой реализации нет.

## Узкий внутренний контракт

Вход `Snapshot` создаёт только доверенный backend после проверки прав. Это не публичная схема API
и не доказательство авторизации: адаптер не знает пользователя, БД и текущих блокировок.
`snapshot_id` связывает ответ с версией снимка; сам по себе он не проверяет актуальность и не даёт права применить ответ.
Идентификаторы — локальные псевдонимы; соответствие настоящим записям остаётся в backend.
В запрос не входят телефон, адрес текстом, имя, описание товара, коды вручения, цена или `snapshot_id`.
Координаты всё равно чувствительны: их нельзя посылать в публичный demo-сервер или чужой сервис без отдельного решения.

| Область | Правило черновика |
|---|---|
| Доставки | 1–50; только `delivery_type=courier`, `status=created`, `courier_id=None` |
| Машины | 1–10; только авто, пустой `active_parcel_ids`, явные начало/конец маршрута |
| Связи | Для каждой доставки обязателен непустой список допустимых машин; неизвестные и повторные id запрещены |
| Вместимость | Одна общая явно выбранная единица, положительные целые; автоматически переводить small/medium/large нельзя |
| Число заказов | `max_deliveries` отдельно ограничивает все назначения машине, а не только груз в пути |
| Время | Целые секунды 0–86400 от начала одного горизонта; окна начала обслуживания, длительности обслуживания; без смен часового пояса |
| Координаты | Конечные числа в диапазонах; в VROOM уходят `[долгота, широта]` |
| Лишние поля | Вход отклоняется, а не превращается в произвольные параметры solver |

Каждая доставка превращается в `shipment`: забор и вручение одной посылки на одной машине.
Допуск пары «заказ–машина» кодируется отдельным `skill` и повторно проверяется в ответе.
`max_tasks=2*max_deliveries` ограничивает число полных пар. Это не механизм расчёта тарифа.

Помощь по пути (`poputka`) отделена от платного курьера и отклоняется целиком, как и `buy_bring`.
Текущий код/старый курьерский план местами описывают сбор за посылку по пути; черновик не выбирает
новую денежную политику и не меняет обещание бесплатной помощи. Перед расширением на этот режим
нужно отдельно согласовать правила; платную курьерскую услугу нельзя незаметно включить вместо него.
Покупки требуют учёта авансов, факта покупки и возвратов — здесь их нет.

Любой принятый, везущийся, возвращаемый, отменённый или завершённый заказ отклоняет весь входной снимок.
Занятую машину также нельзя включить даже ради других свободных заказов. Уже взятую посылку нельзя
объявить новым забором, забыть или передать другому. Поддержка закреплённых обязательств/остаточного
груза и возвратов — отдельная будущая работа. Скрыто отфильтровывать их при подготовке снимка нельзя.

## Недоверенный ответ и отказ

Предел ответа — 256 КиБ до разбора JSON. Проверяются типы без преобразования строк/boolean в числа,
повторные JSON-ключи, синтаксис, числовые пределы, `code=0`, счётчики и пустые `violations`
на уровнях summary/route/step. Поддерживается только обычный режим решения, не plan mode (`-c`).
Проверяются известные машины и задания, начало/конец маршрута, уникальность, допустимость пары,
забор до вручения на той же машине, вместимость на каждом шаге, общее число заказов,
длительность обслуживания, порядок времени и окна. Неназначенные задания должны содержать обе
части пары; каждое входное задание должно встретиться ровно один раз в маршруте либо `unassigned`.
Неиспользуемые поля VROOM отбрасываются и наружу не возвращаются.

| Результат | Значение для вызывающего backend |
|---|---|
| `disabled` | Расчёт выключен, транспорт не вызывается |
| `unavailable` | Нет транспорта, таймаут или ошибка транспорта; маршрутов нет |
| `invalid_response` | Ответ не прошёл проверку; весь результат отклонён, частичного плана нет |
| `preview` | Проверенный предварительный вариант, включая явный список неназначенных доставок |

Общий бюджет ожидания — 2 секунды по умолчанию, явно допустимы `(0, 10]`. Нет повторных попыток.
Внешняя отмена задачи проходит наружу как `CancelledError` и отменяет транспорт; таймаут тоже отменяет его.
Транспорт обязан быть неблокирующим и корректно поддерживать отмену: `asyncio.wait_for` не может остановить
блокирующий вызов или транспорт, который подавляет отмену, и не гарантирует прекращение вычислений на сервере.
Проверка уже ограниченного ответа синхронная и в бюджет ожидания транспорта не входит.
Исключения транспорта/разбора не логируются и не возвращаются (могут содержать координаты/URL/тело).
Не логировать `Snapshot`, `ValidationError.errors()` и исходные тела в будущем вызывающем коде.
Любой отказ оставляет прежний рабочий путь доставки. Пустой результат не означает назначение или отмену.

## Честное время и качество решения

`estimated_arrival_seconds` — внутренняя оценка от начала горизонта; источник — `solver_estimate`.
Вручение не тождественно приезду: ожидание и обслуживание учитываются отдельно при проверке.
Без независимой дорожной матрицы проверяется лишь согласованность времени ответа,
а не фактическая скорость поездки, совпадение координат, пробки или достижимость дороги.
Нет обещания клиенту «будет через N минут». Нужны свежие координаты с согласием, время снимка,
дорожный движок/матрица, время обслуживания и погрешность. Центр города не заменяет положение машины.
VROOM ищет хорошее допустимое решение эвристиками; глобальный оптимум не гарантирован
(`optimality_proven=False`). `cost` solver не является ценой доставки и не используется для денег.

## До подключения к production

1. Явно согласовать включение, список пользователей и городов, критерии отката. Проверить модуль
   с выбранными закреплёнными версиями VROOM, HTTP-обёртки и дорожного движка на локальной синтетике;
   сейчас тестируется только контракт, а не установленный VROOM. Реальная совместимость не доказана.
2. Собрать снимок на сервере с текущими проверками `ensure_active`, `_guard_courier_enabled`,
   `_guard_courier_can_take`/`courier_can_take_now`, профиля/линии/зоны, блока между людьми,
   `live_parcel_conds`, запрета своего заказа, действующих флагов и лимитов. Учесть, что некоторые
   текущие проверки долга могут менять состояние: их нужно разделить для read-only preview.
   Ни клиент, ни solver не выбирают допустимых курьеров. Права на просмотр/запуск предварительного
   расчёта выделить отдельно; данные нескольких отправителей не отдавать обычному пользователю.
3. До любого применения повторно читать все заказы/курьеров под согласованными блокировками,
   проверять версию/срок снимка, отмены, уже появившиеся назначения/возвраты, допуски и все лимиты.
   Условное атомарное занятие **всего** набора, идемпотентность, согласие курьера и порядок уведомлений
   должны иметь тесты гонок на PostgreSQL. Нельзя просто вызвать `/accept` в цикле:
   это оставит половину набора принятой при отмене другого заказа.
4. Поддержку уже взятых посылок вводить лишь с закреплением перевозчика/оставшихся остановок,
   начальной загрузкой, запретом исчезновения обязательств, тестами отказов/возвратов/споров.
   До этого отклонять снимок, а не снимать назначения. Число будущих принятий должно соблюдать
   `flood_carrying_parcels_max` даже у маршрута с малой максимальной загрузкой.
5. Сетевой транспорт: адрес задаёт только оператор, точный список разрешённых scheme/host/port/path;
   проверка TLS обязательна (для своего локального стека — отдельно согласованная изоляция).
   Запрет пользовательских URL, credentials в URL, перенаправлений и неявных proxy из окружения.
   Защита от SSRF/DNS rebinding: проверять реальные адреса соединения и ограничить egress сетью,
   закрыть metadata/loopback/посторонние внутренние подсети; разрешить только конкретный сервисный адрес,
   если он внутри сети. Одного разбора строки URL или DNS до запроса недостаточно.
   Авторизация сервиса/mTLS, секреты вне git, без тел/геолокации в access-логах и трассировках.
6. Ограничить размер запроса, поток ответа **до загрузки целиком**, распаковку и Content-Type/HTTP status;
   текущий байтовый лимит не ограничивает память будущего HTTP-клиента. Настроить connect/read/write/pool
   deadlines, лимит параллельных расчётов/очереди, частоту по правам, бюджет solver и его дорожного движка.
   Повторные запросы при падении не добавлять без отдельного анализа; ошибки не должны мешать базовой доставке.
7. Проверить качество матриц/маршрутов/сроков на данных с разрешённым использованием, измерить время,
   долю неназначенных задач и качество по сравнению с простым маршрутом; отдельно проверить таймаут,
   недоступность, неверный ответ, отмену и приватность. Для клиентского времени нужны свой контракт
   свежести/погрешности и двуязычные состояния. Никакого автоматического распределения этим коммитом.

## Версия контракта и лицензии

Поля сверены с [официальным API VROOM v1.14.0](https://github.com/VROOM-Project/vroom/blob/v1.14.0/docs/API.md).
Это выбранная основа черновика, не утверждение о последней версии.
[Описание проекта](https://github.com/VROOM-Project/vroom/tree/v1.14.0) различает сам solver,
HTTP-обёртку и дорожные движки; при развёртывании их зависимости и лицензии проверяются отдельно.

VROOM распространяется под [BSD-2-Clause](https://github.com/VROOM-Project/vroom/blob/v1.14.0/LICENSE):
при заимствовании исходников сохраняются copyright, условия и отказ от гарантий;
в поставке двоичных файлов те же уведомления должны быть в документации/сопроводительных материалах.
В этом коммите нет заимствованного кода, примеров, бинарников или зависимости VROOM — адаптер написан
самостоятельно по формату протокола. Поэтому копия upstream LICENSE не добавляется.
Если позже будут включены исходники, примеры или бинарники, сохранить точные уведомления выбранной
версии вместе с поставкой; проверить также отдельные лицензии обёртки, движка и картографических данных.
