## КАРТА ДЕНЕЖНЫХ ПОТОКОВ (кто кому и через какие записи)

Настоящих денег в потоке «за поездку» нет: платформа их не касается. Учёт держат три
независимых журнала.

### 1. Такси (instant), Модель А «на доверии» — ЕДИНСТВЕННЫЙ живой денежный поток

```
пассажир --нал/СБП напрямую--> водитель          (мимо платформы, следов нет)
     |
     v  POST /instant/orders/{id}/done   (app/routers/instant.py:626-628)
debt.accrue_for_order()                  (app/debt.py:308-354)
     |-- процент = driver_fee_percent(): промо запуска 0% | лесенка 3/5/8% по стажу,
     |   ставка фиксируется на order.created_at
     |-- база = price_final ?? price_estimate, ₽ -> копейки, Decimal ROUND_HALF_UP
     |-- скидка промокода гасится комиссией платформы (promo_ride.split_commission)
     |     остаток > комиссии -> LedgerEntry(kind=adj, ext_id="promo:{order_id}") водителю
     v
CommissionDebt(driver_id, order_id UNIQUE, amount_kop, week, unpaid, due_at=+7д)
     |
     |-- водитель жмёт «Я оплатил»  -> declare_paid(): unpaid -> pending, declare_count+1
     |-- админ подтверждает         -> admin_confirm(): весь pending -> paid
     |-- админ отклоняет            -> admin_reject(): pending -> unpaid
     |-- админ прощает              -> POST /admin/debts/{id}/forgive -> paid + note
     |-- жалоба «пассажир не заплатил» подтверждена -> void_debt_for_order (safety.py:510)
     |-- оплата картой (ЮKassa)     -> mark_all_paid(up_to=payment.created_at)
     v
taxi_block_reason()  -> "overdue" | "over_threshold" (>1000 ₽) | "declare_abuse"
     -> гейт в POST /instant/presence и /accept (instant.py:39, 524), офферы не показываются (483)
```

### 4. Купоны / промокоды / рефералы — денег не двигают


### [P0] Удаление аккаунта ПАССАЖИРА стирает долг по комиссии ВОДИТЕЛЯ (и его ledger)

- **Файл:строка** — `/home/user/yuldash/backend/app/account.py:222-223` (сбор `order_ids`)
  + `:329-335` (каскад), гейт `:60-98` (`guard_can_delete`).
- **Что не так.** `order_ids` собирается по заказам, где пользователь **пассажир ИЛИ водитель**:

  ```python
  order_ids = list(session.exec(select(InstantOrder.id).where(
      or_(InstantOrder.passenger_id == uid, InstantOrder.driver_id == uid))).all())
  ```

  а дальше долг и ledger сносятся по **ИЛИ** двух условий:

  ```python
  debt = [CommissionDebt.driver_id == uid]
  ledg = [LedgerEntry.driver_id == uid]
  if order_ids:
      debt.append(CommissionDebt.order_id.in_(order_ids))
      ledg.append(LedgerEntry.order_id.in_(order_ids))
  dele(CommissionDebt, *debt)      # dele == DELETE ... WHERE or_(*conds)
  dele(LedgerEntry, *ledg)
  ```

  `guard_can_delete` проверяет долг **только удаляющегося** (`CommissionDebt.driver_id == user.id`),

- **Сценарий поломки.**
  1. Водитель катает пассажира P, набирает долг по комиссии; такси уже заблокировано за просрочку.
  2. P (у него самого долгов нет) удаляет аккаунт → 409 не срабатывает.
  3. Каскад сносит заказы P → вместе с ними **CommissionDebt и LedgerEntry водителя**.
  4. Долг обнулён, блокировка снята, в отчётах комиссии дыра.

  Умышленный вариант: водитель заводит второй аккаунт-«пассажира» (телефон — единственный
  барьер, DeviceBan только ручной), возит сам себя / друзей через него, раз в неделю удаляет
  бурнер — комиссия не платится **никогда**.

  Тот же класс бага у курьера: `account.py` делает `delete(ParcelDelivery).where(sender_id == uid)`,
  а неоплаченная комиссия курьера считается именно по этим строкам
  (`routers/courier.py:914-926`) → удаление отправителя стирает долг курьера.
- **Доказательство** (`proof_debt_wipe.py`, `proof2.py`, прогон на реальном коде):

  ```
  ДО удаления пассажира:
    долг водителя: [(1, 15000, DebtStatus.unpaid)]
    баланс водителя, коп: 50000
    блок такси ДО: overdue
  guard_can_delete(пассажир): ПРОПУСТИЛ
  ПОСЛЕ удаления пассажира:
    долг водителя: []
    записи ledger: []
    блок такси ПОСЛЕ: None
  ```
- **Как чинить.** (1) Сузить каскад: удалять `CommissionDebt`/`LedgerEntry` только по
  `driver_id == uid`, а по чужим заказам — **обезличивать** (`order_id = NULL`), как уже
  сделано для `Report`/`Incident` (тот же приём, `account.py:288-300`). Долг живёт, ссылка
  на удалённого человека уходит — 152-ФЗ соблюдён. (2) `InstantOrder` пассажира не удалять
  целиком, а обезличивать, если у заказа есть водитель с непогашенным долгом. (3) В
  `guard_can_delete` добавить проверку «на моих заказах висит чужой непогашенный долг» —
  но это второй эшелон, основное — (1).

### [P1] Долг в статусе `pending` не блокирует, не входит в порог и не имеет срока

- **Файл:строка** — `/home/user/yuldash/backend/app/debt.py:395-420` (`taxi_block_reason`),
  `:461-479` (`declare_paid`).
- **Что не так.** Блокировка считается **только по `unpaid`**:

  ```python
  unpaid = _unpaid(session, driver_id)
  abused = [d for d in _pending(session, driver_id)
            if (d.declare_count or 0) > settings.debt_max_declares]
  if abused:      return "declare_abuse"
  if not unpaid:  return None
  if any(d.due_at is not None and d.due_at < now for d in unpaid): return "overdue"
  if sum(d.amount_kop for d in unpaid) > settings.debt_block_threshold_kop: return "over_threshold"
  ```

  `pending` не проверяется ни на просрочку (`due_at`), ни на порог, и `paid_declared_at`
  нигде не используется — таймаута у «слова» нет. Защита `declare_abuse` считает попытки
  **по каждой строке долга отдельно**, а `declare_paid` переводит в `pending` только
  текущий `unpaid`, поэтому каждая новая недельная партия долга приходит с
  `declare_count = 0` и после первого тапа имеет 1 — порог `> 2` не достигается никогда,
  если админ не отклоняет вручную.
- **Сценарий поломки.** Водитель не платит вообще: раз в неделю жмёт «Я оплатил» →
  весь долг уходит в `pending` → блокировка снимается → работает дальше. Александр — один
  человек и должен вручную нажимать «Отклонить» по каждому, иначе `declare_abuse` не
  включится никогда. Долг в `pending` растёт без потолка.
- **Доказательство** (`proof2.py`):

  ```
  долг: 500000 коп (порог 100000); блок: overdue
  после «Я оплатил» переведено в pending: 500000 коп; блок: None
  summary: unpaid_kop=0  pending_kop=500000  blocked=False
  новая партия, блок: overdue
  снова «Я оплатил», блок: None ; declare_count по долгам: [1, 1]
  DEBT_MAX_DECLARES = 2
  ```
- **Как чинить.** (а) Считать порог по `unpaid + pending` (в `debt_summary` обе суммы уже
  есть); (б) добавить таймаут доверия: `pending` старше N дней (`paid_declared_at`)
  автоматически возвращается в `unpaid` — это же снимет нагрузку с админа и включит
  `declare_abuse` без ручных отклонений; (в) считать `declare_count` **на водителя**, а не
  на строку долга.

### [P1] Двойная компенсация промокода: check-then-insert без уникального ключа

- **Файл:строка** — `/home/user/yuldash/backend/app/ledger.py:176-202`
  (`post_promo_compensation`), вызов — `app/debt.py:329-331`.
- **Что не так.** Идемпотентность держится на прикладной проверке без блокировки и без
  БД-барьера; функция коммитит сама:

  ```python
  ext = promo_comp_ext_id(order_id)                       # "promo:{order_id}"
  prev = session.exec(
      select(LedgerEntry).where(LedgerEntry.ext_id == ext, LedgerEntry.kind == LedgerKind.adj)
  ).first()
  if prev is not None:
      return prev
  entry = LedgerEntry(..., ext_id=ext, ...)
  session.add(entry); session.commit()
  ```

  У `LedgerEntry.ext_id` (`models.py:907`) обычный индекс, **не** `unique` — и уникальным
  его сделать нельзя как есть: тем же `ext_id` помечаются и запись `payout`, и её
  компенсация `adj` (`ledger.py:139-141` и `:160-163`). Для сравнения, долг от гонки
  защищён `UniqueConstraint("order_id")` (`models.py:946`) — компенсация такой защиты не получила.
- **Сценарий поломки.** Два параллельных `POST /instant/orders/{id}/done` (двойной тап,
  ретрай сети, дубль пуша). `transition` идемпотентен и оба вызова возвращают заказ в
  статусе `done` (`instant_service.py:694-696`), после чего оба идут в `accrue_for_order`:
  оба не находят долга, оба считают компенсацию, оба вставляют её. Вставку долга отобьёт
  `UNIQUE(order_id)` → `IntegrityError` → rollback, но компенсация к этому моменту **уже
  закоммичена дважды**, потому что коммитит сама.
- **Доказательство** (`proof2.py`, заказ 700 ₽, промо 300 ₽, комиссия 3% = 21 ₽,
  компенсация 279 ₽):

  ```
  обе сессии видят prev = None None
  записей компенсации: 2 ; баланс водителя, коп: 55800
  дашборд promo_comp_today_kop: 55800
  ```

  Вместо 279 ₽ водителю начислено 558 ₽. При этом `/driver/taxi-rides` покажет одну
  компенсацию (`debt.py:258-263` кладёт записи в dict по `order_id` — остаётся последняя),
  а `driver_dashboard` — обе (`debt.py:96-107` суммирует). Две денежные цифры расходятся.
- **Как чинить.** Дать компенсации собственный namespace ключа (напр. `ext_id="promocomp:{order_id}"`)
  и повесить частичный уникальный индекс на `(kind, ext_id)` для `kind='adj'` — или,
  проще, `UNIQUE(order_id, kind)` для компенсаций. Плюс перехватывать `IntegrityError`
  и возвращать существующую запись (как уже сделано в `accrue_for_order:344-352`).

### [P1] Обход комиссии: не нажимать «Завершил» — заказ авто-закрывается в `done` без долга

- **Файл:строка** — `/home/user/yuldash/backend/app/cleanup.py:399-403`
  (`close_stale_orders`), начисление — `app/routers/instant.py:626-628`.
- **Что не так.** Долг заводится **только** из HTTP-ручки `/done`. Ночная чистка
  переводит зависшие заказы в `done` сырым SQL и комиссию сознательно не начисляет:

  ```sql
  UPDATE instantorder SET status = 'done'
  WHERE status = 'onboard' AND created_at < :cut       -- cut = now - TAXI_STALE_HOURS (12 ч)
  ```

  Решение задокументировано (`cleanup.py:380-384`: «брать деньги за поездку, которую никто
  не подтвердил, хуже, чем не взять») — но как побочка оно даёт водителю управляемый способ
  не платить. Санкции нет: страйк за брошенный заказ считается только по
  `status='cancelled' AND cancel_by='driver'` (`instant_service.py:605-613`), а тут статус
  `done` и `cancel_by` пустой. `done_at` авто-закрытие тоже не ставит, поэтому такая
  поездка выпадает и из заработка (`debt.py:122-129`), и из стажа для лесенки (`debt.py:79-85`).
- **Сценарий поломки.** Водитель просто не жмёт «Завершил» на последней поездке дня.
  Утром заказ сам становится `done`, комиссии нет, штрафа нет. Единственная цена —
  нельзя взять новый заказ, пока висит активный (`instant.py:528-536`), т.е. до 12 часов
  от создания заказа. Для последнего рейса перед сном цена нулевая → **одна бесплатная
  поездка в сутки на водителя, повторяемо**.
- **Доказательство** — код-путь: `accrue_for_order` вызывается ровно из одного места
  (`grep` по репозиторию: `app/routers/instant.py:628`), а `cleanup.py` его не зовёт и
  прямо об этом пишет в комментарии. Чистка реально работает — systemd-таймер
  `backend/deploy/yuldash-cleanup.timer`, вызов в `cleanup.main()` строка 454.
- **Как чинить.** Не начислять «вслепую» — правильно. Но: (а) считать авто-закрытый
  `onboard→done` как брошенный заказ для лестницы качества (сейчас он ничем не отличается
  от честного завершения); (б) слать водителю пуш «подтверди поездку, иначе она не
  зачтётся» до истечения окна; (в) при пассажирской оплате такого заказа
  (`wallet.py:113-139` пускает — статус `done`, `paid=False`) начислять комиссию, потому
  что там факт поездки подтверждён второй стороной.

### [P2] Прощённая/оплаченная онлайн комиссия всё равно показана водителю как удержанная

- **Файл:строка** — `/home/user/yuldash/backend/app/debt.py:269-271` (`driver_rides`),
  `:136-138` (`driver_dashboard`).
- **Что не так.** Тернарник вырожденный — обе ветки одинаковые:

  ```python
  fee_kop = int(d.amount_kop) if d and d.status != DebtStatus.paid else (
      int(d.amount_kop) if d else 0
  )
  ```

  То есть `fee_kop = d.amount_kop` при любом статусе долга. Комментарий над строкой
  обещает «долга нет / списан → комиссия ноль», код этого не делает.
- **Сценарий поломки.** Админ простил комиссию (`POST /admin/debts/{id}/forgive`,
  `routers/debt.py:164-190`) или снял её по жалобе «пассажир не заплатил»
  (`routers/safety.py:508-517`) — водителю пришёл пуш «комиссия списана», но экран
  `/driver/taxi-rides` и дашборд по-прежнему вычитают её из «чистыми». Это ровно тот
  экран, который построили, чтобы закрывать спор «Юлдаш говорит 4200, я насчитал 4600»
  (`debt.py:234-241`) — и он врёт в минус водителю.
- **Доказательство** — цитата выше: `d.status != DebtStatus.paid` не влияет на результат,
  ветки идентичны.
- **Как чинить.** `fee_kop = 0 if (d is None or d.status == DebtStatus.paid and d.note.startswith("Списан")) else ...`
  — точнее, различать «paid, потому что реально оплачено» и «paid, потому что прощено».
  Проще всего завести отдельный статус `voided`/`forgiven` в `DebtStatus`, тогда обе
  функции читаются однозначно.

### [P2] Отменённый платёж (`canceled`) можно активировать — гейт стоит только на `succeeded`

- **Файл:строка** — `/home/user/yuldash/backend/app/routers/payments.py:59-60`
  (`_activate_payment`), `:456-458` (вебхук), `:394-400` (админ-подтверждение).

- **Доказательство** — цитата гейта; в `_activate_payment` (payments.py:55-60) и в вебхуке
  (payments.py:456-458) нигде нет `!= "canceled"`.
- **Как чинить.** Гейт `if payment.status != "pending": return` вместо `== "succeeded"`.

### [P2] Ретрай выплаты после отказа банка навсегда возвращает «already»

- **Файл:строка** — `/home/user/yuldash/backend/app/ledger.py:111-121` (`_existing`),

  `ext_id=f"{scoped_key}:refund"` + отдельная колонка `voided_at` у payout-записи), либо

## ПРОВЕРЕНО И ЧИСТО

**Идемпотентность начисления в ledger.** `settle_instant_order` / `settle_booking`
(`ledger.py:236-296`) берут строку заказа/брони под `SELECT ... FOR UPDATE` и гейтят по
флагу `paid`. Проверил гонку двух вебхуков по цепочке: внутренний `commit()` в `settle_*`
снимает и row-lock платежа, но второй вебхук всё равно упирается в `order.paid == True` и
возвращает `"already"` — двойного `earn/fee` нет. Покрыто тестами
`tests/test_ledger.py:168` (`test_settle_idempotent_no_double`) и `:194`
(`test_webhook_repeat_does_not_double_ledger`).

**Идемпотентность начисления долга.** `accrue_for_order` — прикладная проверка
+ `UniqueConstraint("order_id")` (`models.py:943-946`) + перехват `IntegrityError`
с возвратом существующей записи (`debt.py:344-352`). Двойной тап «Завершил» долг не
задваивает.

**Баланс кошелька.** Отдельного поля баланса нет вообще: `driver_balance` — это
`SUM(amount_kop)` в SQL по append-only журналу (`ledger.py:48-55`). Разъехаться с журналом
физически нечему. Единственное место, где журнал перестаёт быть append-only — каскад
удаления аккаунта (см. P0).

**Отрицательный баланс.** Не воспроизводится: `earn` всегда ≥ `fee` (процент ≤ 100,
`fee_kop_for` при `percent<=0` возвращает 0), компенсация промо всегда «+», `payout`
проверяется против баланса под row-lock и коммитится до похода в банк
(`ledger.py:135-144`). Админской ручки «правка баланса» нет — `LedgerEntry(...)`
создаётся только внутри `app/ledger.py` (5 мест), больше нигде в репозитории.

**Деньги — целые копейки.** Ни одной суммы во `float`: `amount_kop`, `budget_kop`,
`discount_kop`, `cancel_fee_kop`, `waiting_fee_kop` — `int`/`BigInteger`. Комиссия —
`Decimal ROUND_HALF_UP` (`ledger.py:33-45`). Промо-скидка режется `Decimal` **вниз**, в
пользу платформы (`promo_ride.py:70-82`). Проверил подозрительное
`price_final = price_estimate + waiting_fee_kop // 100` (`instant_service.py:715`):
`waiting_fee_kop` всегда кратен 100 (`billable * rub_per_min * 100`, `:533-538`), потери нет.
Единственный `float` в деньгах — `amount_rub: e.amount_kop / 100.0` в ответе
`/wallet/ledger` (`routers/wallet.py:184`), рядом отдаются точные копейки — на учёт не влияет.

**Двойное погашение купона.** `coupon_redeem` (`coupons.py:212-248`) берёт
`CouponRedemption` под `with_for_update()`, гейтит по `status == "redeemed"` → 409, счётчик
инкрементит SQL-выражением `redeemed_count = redeemed_count + 1` (не read-modify-write).
Право гасить — только владелец бизнеса, чужой код → 404. Чисто.

**Двойное применение промокода.** `PromoRedemption` имеет `UniqueConstraint("user_id")`
(`models.py:1320`) — «один код на жизнь аккаунта» держится БД, а не только проверкой;
`promo_apply` берёт `PromoCode` под row-lock и перехватывает `IntegrityError`
(`routers/promo.py:162, 191-195`). Проверяются: `active`, окно дат (`in_window`),
`limit_total` под тем же локом, «свой же код нельзя» (`promo.owner_id == user.id` → 409).
Свой реферальный код тоже нельзя (`referral.py:148`, `referrer.id == user.id`).

**Захват скидки на заказ.** `promo_ride.consume` (`promo_ride.py:173-219`) — row-lock
плюс атомарный CAS-`UPDATE ... WHERE used_order_id IS NULL` с проверкой `rowcount`;
проигравший гонку просто едет без скидки. Освобождение при отмене (`release`) снимает обе
отметки, «оживший» из `expired` заказ скидку удерживает (проверка `status.in_(_DEAD)`).
Инвариант «водитель получает `price − C` при любой скидке» покрыт property-тестами
`tests/test_money_invariants.py:70-115`.

**Двойная комиссия при онлайн-оплате такси.** `settle_instant_order` после начисления
`fee` гасит долг Модели А (`void_debt_for_order`, `ledger.py:271`), причём по **той же**
ставке, что и долг (обе фиксируются на `order.created_at`, `ledger.py:254-260` и
`debt.py:324`). Двойного взятия нет; согласованность ставок покрыта
`tests/test_fee_percent_consistency.py`.

**Оплату нельзя занизить с клиента.** Сумма всегда серверная: такси —
`promo_ride.payable_kop(order)` (`wallet.py:132`), бронь — `booking.price * 100`
(`wallet.py:157`), boost/реклама/подписка — из серверных словарей `BOOST_PLANS` /
`AD_PACKAGES` / `PARTNER_PLANS`. Тело запроса цену не содержит.

**Анти-IDOR на деньгах.** Оплатить чужой заказ нельзя (`wallet.py:120`), чужой кошелёк
и ledger не видны (всегда `user.id`), `/driver/debt` — по своему токену, все `/admin/*`
за `_require_admin`. Покрыто `tests/test_ledger.py:269, 280` и `tests/test_debt.py:314`.

**Реклама без оплаты не показывается.** Публичная выдача `/ads` отбрасывает партнёрские
объявления без `Payment(purpose="ad", status="succeeded")` (`ads.py:83-88`,
`_paid_ad_ids`). Редактировать можно только свой черновик/отклонённое (`_own_editable_ad`,
`ads.py:311-319`), чужое → 404. Статус `active` ставит только админ. `budget_kop`
берётся из серверного пакета, из тела не читается.

**Подтверждение платежей в Telegram.** `_handle_admin_callback` (`auth.py:304-421`)
сверяет `from.id` с `ADMIN_TELEGRAM_CHAT_ID`, вебхук защищён
`X-Telegram-Bot-Api-Secret-Token` через `hmac.compare_digest`, а прод-конфиг падает без
секрета (`config.py:545-546`). Карточные платежи (`provider_id != ""`) вручную не
подтверждаются ни в Telegram (`auth.py:398-401`), ни по HTTP (`payments.py:396-399`), ни в
списке `/admin/payments/pending` (`payments.py:363-365`) — «начисление без денег» закрыто.

**Денежные флаги.** `PARCEL_FEE_ENABLED`, `PAYOUTS_ENABLED`, `TIPS_MONEY_ENABLED` = `False`
(`config.py:125, 133, 244`). Выплаты → 503 «Выплаты скоро» (`wallet.py:274-275`),
`payouts_ready` дополнительно требует ключи в проде. Чаевые: платформа денег не касается —
при выключенном флаге СБП водителя вообще не отдаётся (`routers/family.py:480-510`),
включённый флаг лишь показывает номер. Онлайн-оплата поездки в проде без ЮKassa —
жёсткий 503 (`wallet.py:75-76`), Boost/донат/поддержка — 503 при `mock` в проде.
Прод-старт кричит `launch_warnings`, если денежный флаг включён при оферте «комиссия не
берётся» (`config.py:618-632`).

**Мультипликаторы цены.** Сурж/ночь/погода/подача перемножаются один раз и режутся общим
потолком `surge_max_k` (`pricing.py:293-299`), внешние источники fail-open в детерминированный
локальный расчёт. Цену клиент не присылает никогда.

## НЕ ДОКАЗАНО

- **Второй аккаунт как обход долга.** Долг привязан к `user_id`; новый телефон = новый
  аккаунт без долга. `DeviceBan` (`models.py:1132-1144`) существует, но банит **только
  админ вручную**, авто-Sybil-защиты нет (`routers/sybil.py` — просто список подозрительных
  пар для ручного разбора, «без авто-наказаний»). Это осознанное ограничение, честно
  описанное в комментарии к модели («заголовок контролирует клиент → целевой обход сменой
  X-Device-Id возможен»). Отдельной дырой не считаю — но именно оно превращает P0 выше из
  «неприятной случайности» в рабочую схему.
- **Смена роли как обход долга.** Не нашёл: `taxi_block_reason` смотрит только
  `CommissionDebt.driver_id`, роль не участвует; смена роли ничего не гасит. Обхода нет.
- **Накрутка рефералов.** Взаимный реферал A↔B даёт каждому +2 кредита (оба редимят код
  друг друга, `referral.py:152-154`), потолок `MAX_REFERRAL_CREDITS = 20` и 5 водительских
  бонусов в месяц. Награда — бесплатные поднятия, не деньги. Проверка «живой поездки»
  (`_live_driver_trips`) опирается на `o.distance_km`, то есть на оценку по координатам
  заказа, а не на фактический трек — теоретически ферма из 3 фейк-пассажиров пройдёт.
  Реальным ущербом это назвать не могу: потолок жёсткий, деньги не выводятся.
- **Двойная оплата пассажиром (нал + живая ссылка ЮKassa).** Механика описана в P2 выше,
  но провайдер сейчас не `yookassa`, реальных списаний нет — на живом сервисе не проверить.
- **Расхождение сверки.** `GET /admin/ledger/reconcile` сравнивает `SUM(earn)` с
  `SUM(Payment ride|booking)`. Логика верная, но алерта на `diff != 0` в коде нет — сверку
  надо смотреть глазами. Не дыра, а отсутствующий мониторинг; фактических расхождений
  на проде я не смотрел (боевой сервер не трогал).
- **«8% с такси vs "0 ₽ комиссия" на сайте»** — противоречие реальное, но это **уже
  известный и записанный** пункт (`docs/tasks.md:5581`, `docs/00-INDEX.md:153`), не новая
  находка. Новое в этой части — только то, что предупреждение `launch_warnings` не
  упоминает попутку, хотя `settle_booking` тоже удерживает 8% (см. P2).
- **Statement партнёра (10 ₽ за погашение).** Считается (`coupons.py:435-446`), но нигде
  не превращается в `Payment` и ничем не обеспечен: партнёр может накопить статемент и
  удалить аккаунт (`guard_can_delete` его не проверяет). Пока это чисто информационная
  цифра — списания нет, поэтому дырой не считаю, но при включении реального выставления
  счёта это станет ею.
