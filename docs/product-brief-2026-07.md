### Фаза 2 — «Быстрый заказ» MVP (моя: ~5–6 веток, 2–4 недели календарно) — флагман
Зависимости: Фаза 0 (вся), Фаза 1.1 (Sentry — новую механику без глаз не выпускаем).
1. **Presence:** heartbeat координат водителя «на линии» (переиспользуем `TripLocationService`-механику) → Redis GEO (`GEOADD presence`), TTL 60с.
2. **Тарифы:** таблица Tariff (зона, базовая, ₽/км, ₽/мин, мин. цена) + `POST /instant/estimate` (оценка до заказа).
3. **Заказ:** модель InstantOrder + машина состояний + `POST /instant/orders`, matcher-цикл (D1), офферы водителям пушами, accept/decline/timeout, отмены обеих сторон с причинами.
4. **UI пассажира:** экран «Куда едем?» (А=моя позиция, Б=поиск/карта) → цена → «Ищем машину» (анимация) → «Водитель едет» (трек на карте, ETA, телефон после accept — политика приватности та же).
5. **UI водителя:** тумблер «на линии» уже есть → входящий оффер (полноэкранная карточка, 20с таймер, маршрут+цена) → навигация к пассажиру → «приехал/посадил/завершил».
6. **Сквозные тесты:** state machine покрыть полностью (все переходы+гонки), e2e сценарий на эмуляторе.
- ✅ Готово когда: в Уфе/Сибае тестовый заказ проходит цикл created→done с реальными пушами и треком; отмены/таймауты не оставляют «зависших» заказов (проверено тестами на гонки).

### Фаза 3 — «Деньги» (моя: ~3–4 ветки; юр./банк. шаги — твои)
Зависимости: Фаза 2 (для оплаты быстрых заказов), F21 (ЮKassa-инфра — уже на ветке #25).
1. **v1:** оплата поездки картой/СБП через ЮKassa (пассажир платит после done; наличные остаются опцией), комиссия сервиса % в конфиге, **кошелёк-ledger водителя** (таблица LedgerEntry: начисления−комиссия; append-only, без «изменяемого баланса»).
2. **v2:** двухстадийный платёж (холд при заказе → капчер по done) = «безопасная сделка»; выплаты водителям (v1 вручную по реестру, v2 API).
3. Чеки/54-ФЗ — через ЮKassa-чеки; оферта и тарифы комиссии — юр.тексты (шляпа юриста, тебе на подпись).
- ✅ Готово когда: тестовый платёж проходит холд→капчер→ledger; сумма комиссий сходится с ledger за день (сверка-скрипт).

### Фаза 4 — «Свои: доверие формализовано» (моя: ~2–3 ветки)
1. **Уровни:** L0 телефон → L1 +имя+фото → L2 +документы (водители — уже есть модерация) → L3 «свой» (по инвайту от L2/L3). Бейджи уровня в профиле/карточке (расширяем F8).
2. **Инвайт-коды:** персональные, ограниченный запас, трек цепочки приглашений (расширяем реферал F19); опция «поездка только для L3+».
3. **Мэтчинг с учётом доверия:** буст в выдаче и в matcher (D1) по уровню+рейтингу.
4. **152-ФЗ:** политика хранения (сроки по типам данных), процедура удаления, реестр согласий (галочки с таймстампом).
- ✅ Готово когда: новый пользователь видит свой уровень и путь наверх; «только для своих» реально фильтрует.

### Фаза 5 — «Масштаб до 100k» (моя: ~2 ветки + нагрузочное; твоя: выбор хостинга)
Параллельно Фазам 2–4, форсировать при >5k MAU.
1. PostgreSQL: managed/отдельный инстанс + PgBouncer; пройтись EXPLAIN по горячим запросам (лента, near, matcher), добить индексы.
2. Redis: пароль+persistence (AOF), вынести с app-сервера при росте.
3. Медиа → S3-совместимое хранилище (VK Cloud/Selectel), URL-подпись.
4. Приложение stateless → 2+ uvicorn-воркера за nginx, WS-стикинг по ip_hash (Redis pub/sub уже разносит события между процессами — заложено в чате).
5. Нагрузочное: Locust-сценарии (лента, брони, matcher) → цель p95<300мс при 200 RPS.
- ✅ Готово когда: нагрузочный прогон держит целевые цифры; убийство одного воркера не роняет сервис.

### Фаза 6 — «Расширение» (после PMF)
Веб-админка (Next.js, на базе лендинга), iOS (Kotlin Multiplatform: шарим data-слой, UI SwiftUI/CMP — отдельное решение), EN-локаль, открытие категорий (межрегион).

## C. Архитектура и стек (с обоснованием)

### Сейчас (после Фазы 0)
```
[Android Kotlin/Compose] ──HTTPS──> [nginx] ──> [FastAPI (uvicorn), SQLModel]
        │  WS: чат / карта / трек            │
        │<──FCM push───[Firebase]<───────────┤
                                             ├── PostgreSQL (прод) / SQLite (тесты)
                                             ├── Redis (pub/sub чат+карта, кэш)
                                             ├── Yandex Geocoder / MapKit (клиент)
                                             └── ЮKassa (create/fetch/webhook)
[Next.js лендинг yulbash.ru] (статика; /r/{id} OG-превью рендерит FastAPI)
```

### Целевая (Фазы 1–5): **модульный монолит**, НЕ микросервисы
```
[Android] ─┬─> [nginx: TLS, limit_req, ip_hash WS] ─> [FastAPI ×N воркеров, stateless]
[iOS Ф.6]─┘        │                                    ├─ модули: rides / instant / payments /
[Веб-админка Ф.6]──┘                                    │   trust / notifications / admin
                                                        ├─ PostgreSQL (managed) + PgBouncer
                                                        ├─ Redis: pub/sub + GEO presence + кэш + rate
                                                        ├─ S3-совм. бакет (медиа)
                                                        ├─ Фоновые задачи: arq (Redis) — matcher-циклы,
                                                        │   авто-чек «доехал», протухание, сверки
                                                        └─ Наблюдаемость: Sentry + /health + TG-алерты
```

**Почему монолит:** 100k пользователей РБ ≈ пики в сотни RPS — это один хороший сервер с запасом. Микросервисы/Kafka на этом масштабе = сложность без выгоды и смерть темпа соло-команды. Границы модулей держим чистыми (роутер+сервис на домен) — если какой-то модуль упрётся (matcher), его можно вынести отдельно ПОТОМ без переписывания.

**Почему стек не меняем:** FastAPI+SQLModel+PG — уже 190+ тестов и прод; Kotlin/Compose — уже отполирован под «уровень iPhone»; Redis уже в деле. Единственные добавки: `arq` (фоновые задачи, тот же Redis), `sentry-sdk`, S3-клиент. Минимум новых кубиков — максимум надёжности.

## D. Ключевые модули — детально

### D1. Мэтчинг «Быстрого заказа»
**Presence:** водитель «на линии» → клиент шлёт координаты каждые 10–15с (механика `TripLocationService` уже есть) → `GEOADD presence <lng> <lat> driver:{id}` + `SET presence:hb:{id} EX 60`. Пропал heartbeat → водитель невидим (TTL сам чистит).

**Подбор (matcher, фоновая задача arq на заказ):**
1. `GEOSEARCH presence FROMLONLAT <A> BYRADIUS 3 km ASC` → пусто? расширяем 3→7→15 км (межгород РБ!).
2. Фильтры: `online`, верифицирован, не занят другим заказом, не в чёрном списке пассажира, women_only-совместимость.
3. Скоринг: `score = w1·(1/дистанция_подачи) + w2·рейтинг + w3·уровень_доверия(L, Фаза 4) + w4·бейдж_свой`. Веса в конфиге.
4. Оффер top-1 пушом (data-payload, полноэкранная карточка, таймер 20с) → decline/timeout → следующий по score. 3 круга без accept → пассажиру «рядом никого, оставить заявку-сторож?» (мост в F13 route-watch — переиспользуем!).
5. Все переходы состояний — под row-lock (`with_for_update`, паттерн из bookings), идемпотентные ручки.

**Машина состояний заказа:**
```
created → searching → offered → accepted → arriving → onboard → done
   └──────┴──────────┴────┬─────┴─────┬──────┴───────┘
                       expired    cancelled(by, reason, штраф-логика later)
```
Инварианты: из терминальных (done/cancelled/expired) выходов нет; каждый переход валидирует «кто может» (пассажир/водитель/система) и пишет `*_at` таймстамп. Полное покрытие тестами переходов и гонок (двойной accept двух водителей → второй получает 409).

### D2. Тарифный движок
`price = max(min_price, base + per_km·dist + per_min·eta)`, округление до 10₽.
- Таблица `Tariff(zone, category, base, per_km, per_min, min_price, active)`; зоны v1: «город» (Уфа/Сибай/…) и «межгород» (дистанция > порога). Surge — поле `k` на будущее, v1 = 1.0.
- `dist/eta` — MapKit-роутер с клиента при оценке + серверная проверка по прямой×коэффициент (защита от подмены клиентом: сервер не верит цене из приложения, считает сам).
- Плановые поездки (BlaBlaCar-режим) не трогаем: там цену ставит водитель, подсказка `getPriceHint` уже есть.

### D3. Платёжный flow (Фаза 3)
```
v1 (после поездки):  done → пассажиру экран оплаты → ЮKassa (карта/СБП) или «наличные»
                     → webhook/поллинг подтверждает → LedgerEntry(+сумма −комиссия) водителю
v2 (безопасная сделка): заказ accepted → ХОЛД на карте (two-stage ЮKassa)
                     → done → капчер (list капчерим фактическую цену ≤ холда)
                     → cancel → отмена холда (деньги не списаны)
```
- **Ledger вместо «баланса»:** только append-записи (начисление, комиссия, выплата, корректировка) → баланс = SUM. Не редактируем историю денег никогда.
- Ежедневная сверка-скрипт: SUM(ledger) ↔ отчёт ЮKassa; расхождение → алерт в TG.
- Наличные остаются всегда (реальность РБ); фикс договорённости уже есть (F10).

### D4. Модель данных — новое (эскиз)
```sql
instant_order(id, passenger_id, from_lat/lng, to_lat/lng, from_text, to_text,
              status, price_estimate, price_final, tariff_id, driver_id NULL,
              created_at, offered_at, accepted_at, arrived_at, onboard_at,
              done_at, cancelled_at, cancel_by, cancel_reason)
tariff(id, zone, category, base, per_km, per_min, min_price, k, active)
```

**Presence + подбор (backend/app/instant/matching.py):**
```python
RADII_KM = (3, 7, 15)                      # город → пригород → межгород РБ

def alive(r, driver_id: int) -> bool:      # heartbeat жив?
    return r.exists(f"presence:hb:{driver_id}") == 1

def candidates(r, session, lat, lng, order) -> list[tuple[int, float]]:
    for radius in RADII_KM:
        found = r.geosearch("presence", longitude=lng, latitude=lat,
                            radius=radius, unit="km", withdist=True, sort="ASC")
        ids = [int(m.split(":")[1]) for m, _ in found if alive(r, int(m.split(":")[1]))]
        drivers = eligible(session, ids, order)      # online, verified, не занят, не в блоке
        if drivers:
            return rank(drivers, found)              # score: подача/рейтинг/доверие
    return []

def rank(drivers, found):
    dist = {int(m.split(":")[1]): d for m, d in found}
    return sorted(((d.user_id, score(d, dist[d.user_id])) for d in drivers),
                  key=lambda t: -t[1])

def score(d, dist_km: float) -> float:
    return (W_DIST / max(dist_km, 0.3)) + W_RATING * (d.rating or 4.0) \
         + W_TRUST * trust_level(d.user_id)
```

**Переход состояния под замком (паттерн из bookings.py, тот же row-lock):**
```python
ALLOWED = {  # (из, кто) -> куда
    (OrderStatus.offered,  Role.driver):    OrderStatus.accepted,
    (OrderStatus.accepted, Role.driver):    OrderStatus.arriving,
    (OrderStatus.arriving, Role.driver):    OrderStatus.onboard,
    (OrderStatus.onboard,  Role.driver):    OrderStatus.done,
}

def transition(session, order_id: int, actor: Role, target: OrderStatus, user_id: int):
    order = session.exec(select(InstantOrder).where(InstantOrder.id == order_id)
                         .with_for_update()).first()          # гонка двух accept → 409 второму
    if not order: raise HTTPException(404, "Заказ не найден")
    if ALLOWED.get((order.status, actor)) != target:
        raise HTTPException(409, f"Нельзя {order.status}→{target}")
    guard_actor(order, actor, user_id)                        # мой ли заказ/оффер
    setattr(order, f"{target.value}_at", utcnow())
    order.status = target
    session.commit()
    push_order_update(order)                                  # FCM обеим сторонам + Notification
```

```python
def estimate(session, frm, to, category) -> int:
    t = active_tariff(session, zone_for(frm, to), category)
    dist_km = max(haversine_km(frm, to) * ROAD_K, 0.5)        # ROAD_K≈1.3: прямая→дорога
```
