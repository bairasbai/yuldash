## 3. ⚠️ Узел №2 — линеаризация миграций alembic

10 фич добавили миграции, и **все стартуют от одного родителя `0004_booking_boarding_code`**:

```
0005_notification_table      (F5  #11)
0005_route_watch             (F13 #10)   ← имя файла 0005, но revision id уникален
0005_rating_text_review      (F7  #12)
f9_driver_gender             (F9  #16)
f10_payment_agreement        (F10 #14)
f12_winter_safety            (F12 #17)
f14_pickup_points            (F14 #21)
f17_driver_schedule          (F17 #20)
f19_invite_drivers           (F19 #23)
f22_medical_partner          (F22 #27)
```

Revision **id** у всех разные (коллизии id нет), но `down_revision` у всех = `0004` → после мержа нескольких получишь **несколько alembic heads**, и `alembic upgrade head` заругается «multiple heads».

**Как чинить — по мере вливания каждой ветки с миграцией:**
Открой её файл миграции и поменяй `down_revision` с `"0004_booking_boarding_code"` на **id последней уже влитой миграции**. Выстраиваешь линейную цепочку:

```
0004 → (F5)0005_notification_table → (F7)0005_rating_text_review →
      (F13)0005_route_watch → f9_driver_gender → f10_payment_agreement →
      f12_winter_safety → f14_pickup_points → f17_driver_schedule →
      f19_invite_drivers → f22_medical_partner
```

Порядок в цепочке — любой; важно чтобы каждый следующий `down_revision` = предыдущий. Все миграции идемпотентны (гейт `has_table`/`create_all`-first), так что повторный `alembic upgrade head` безопасен.

Проверка после сведения: на чистой БД `alembic upgrade head` проходит без «multiple heads» и создаёт все таблицы.

*(Альтернатива — `alembic merge heads`, но линейная цепочка чище для истории.)*
