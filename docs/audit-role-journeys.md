## Какие роли действительно существуют

В БД **три** значения `UserRole`: `passenger`, `driver`, `admin` (`backend/app/models.py:13`). Android предлагает **два** исходных варианта `RideRole`: Passenger/Driver (`MainActivity.kt:566`), а внутри сервиса **три** режима `RideMode`: Pooling/Taxi/Courier (`ModeSwitchHome.kt:78`). Это разные уровни, их нельзя складывать как независимые роли. Один аккаунт может участвовать в разных поездках с разных сторон.

Для проверки ниже выделены **13 пользовательских контекстов**. Это составленная по коду карта сценариев, а не 13 ролей в БД.

| Контекст | Чем определяется | Основной путь |
|---|---|---|
| Гость | Нет действующей сессии | Публичная витрина → вход; закрытые действия требуют входа |
| Пассажир попутки | Участник Booking | Поиск/заявка → бронь/торг → подтверждение → посадка → завершение → чек/оценка |
| Водитель попутки | Владелец Ride, профиль водителя | Публикация → пассажиры/места → подтверждение → поездка → завершение/отмена |
| Пассажир такси | `InstantOrder.passenger_id` | Цена → заказ → поиск → принятие → прибытие → посадка → завершение → следующий заказ |
| Водитель такси | TaxiApplication/Profile и допуски | Заявка → одобрение → документы/готовность → линия → оффер → поездка → расчёт |
| Отправитель | `ParcelDelivery.sender_id` | Создание → выбор перевозки → передача → вручение/возврат → квитанция/спор |
| Попутный перевозчик | Назначенный перевозчик посылки | Лента «по пути» → принятие → получение → вручение по коду; профессиональная заявка не обязательна |
| Профессиональный курьер | CourierApplication/Profile и допуски | Заявка → одобрение → линия → заказ → выполнение → ожидание/комиссия/оценка |
| Получатель посылки | Контакт, ссылка и код вручения | Отслеживание → получение по коду → закрытие доступа к живым координатам; отдельного кабинета нет |
| Рекламодатель | `is_advertiser` + владение Ad | Черновик → правка → модерация → размещение/оплата → управление своим объявлением |
| Бизнес-партнёр | Владение Partner | Регистрация → модерация/исправление → подписка → купоны → погашение/отчёт |
| Администратор | `UserRole.admin` | Очереди/проверки → одобрение или отказ → разбор обращений/споров/платежей → журнал |
| Доверенный близкий / получатель ссылки | TrustedContact / ограниченный token | Получить ссылку → разрешённый статус/гео → окончание или отзыв доступа |

«Попутчик» не отдельное значение прав аккаунта: поездка связывает пассажира и водителя. «Купи и привези» — вариант пути отправителя и курьера. Заказ для родственника — вариант пассажирского пути; пользователь купонов — клиент бизнеса. Отдельных учётных ролей модератора, кассира и оператора не найдено: соответствующие действия относятся к владельцу бизнеса или администратору. Медицинские партнёры представлены справочником, собственного кабинета клиники в backend нет.

Дополнительные источники: `backend/app/models.py:67` (рекламодатель), `:594` (доверенный контакт), `:1661` (бизнес); `routers/courier.py:845/966/1045` (заявка/одобрение/линия), `routers/parcels.py:1188` (попутная перевозка), `routers/family.py:119/349`, `routers/share.py:124`, `routers/medical.py:1/31`.

## Найденные и исправленные ошибки

1. **Два активных заказа такси одного пассажира.** Ранний commit снимал блокировку до проверки/создания; второй скрытый commit находился внутри журнала модерации. Сохранение очереди объединено с созданием, модерация перенесена после записи заказа. Red: `roles-transport-race-red.xml`, `roles-transport-moderated-red.xml`; green: `roles-transport-final-pg.xml`.
2. **Посылка назначалась даже при 403 за чужое фото.** Проверка перенесена до изменения назначения. Red: `roles-delivery-atomic-red.xml`; green: delivery-профили.
3. **Ошибочное фото останавливало платное ожидание.** Исправлены два перехода — получение и вручение. Проверки теперь выполняются до расчёта ожидания. Red: `roles-delivery-waiting-red.xml`; green: delivery-профили.
4. **Отклонённый бизнес не мог вернуться на модерацию.** Реальная правка разрешённых полей теперь переводит rejected в pending; неизменённые данные, paused и archived не разблокируются. Red: `roles-business-red.xml`; green: `roles-business-green.xml`.

5. **Один таксист принимал два разных заказа одновременно.** Проверки чужого активного заказа было недостаточно: два запроса одновременно видели пустой результат. Добавлена блокировка строки водителя `FOR NO KEY UPDATE` перед проверкой и назначением. PostgreSQL: до исправления оба ответа 200, после — один 200 и второй 409. Red: `roles-transport-cross-taxi-red.xml`; green: `roles-transport-cross-final.xml`.
6. **Кнопка выхода из PWA зависала без установленной службы уведомлений.** `disableWebPush` ожидал `serviceWorker.ready`, который может никогда не разрешиться. При выходе теперь запрашивается существующая регистрация `getRegistration()`, без ожидания её установки. Тест выполняет настоящий `AuthProvider.logout`: pending-ready без регистрации и с существующей подпиской. Red: 2 timeout; green: `roles-web-logout-green.log`, 24 набора / 248 проверок; сборка TypeScript/Vite/PWA успешна (`roles-web-logout-build.log`). После исправления в том же браузере выполнены выход и последовательный вход четырьмя участниками.

Все шесть дефектов сверены с локальным main. Первые пять затрагивают три серверных файла: `routers/instant.py`, `routers/parcels.py`, `routers/coupons.py`; шестой — `webapp/src/push/webPush.ts`. Новых пользовательских переводов не добавлено.

Отдельно проверено совмещение такси и доставки (`test_role_transport_cross_mode.py`): уже взятую посылку допускается везти параллельно с такси, но взять новую курьерскую доставку во время активного такси нельзя. После завершения такси новая доставка снова доступна. Это текущая политика кода, а не симметричный запрет обоих режимов.

## Проверка живого локального веб-интерфейса

Стенд: отдельная SQLite, четыре синтетических аккаунта; `test-results/roles-local-server.py`. Внешняя сеть сервера запрещена, SMS/платежи — локальные заменители. Для входа Vite запущен с `VITE_SMS_LOGIN_ENABLED=1` только в окружении процесса. В обычной конфигурации интерфейс сообщает, что SMS-вход пока недоступен. Это не проверка Telegram или настоящих SMS.

- Гость: публичная лента и закрытый профиль с предложением войти открылись.
- Пассажир: штатный запрос локального кода → подтверждение → профиль пассажира и опубликованная поездка другого пользователя загрузились.
- **Незавершённый веб-путь попутки:** `webapp/src/components/RideCard.tsx` рисует `article` без перехода и бронирования. Нажатие карточки в браузере ничего не открывает. Серверная бронь проверена отдельно, но прохождение бронирования из этой веб-ленты не подтверждено; Android этим наблюдением не оценивается.
- **Граница локального такси:** форма показывает «Карта подключится с ключом» и ждёт место отправления; полный заказ через эту форму на стенде пока не исполнен.
- Водитель: свой рейс, кабинет попуток, допуск в такси, линия включена → ожидание заказа → линия выключена. Курьер: смена зоны, линия включена → пустая лента, кабинет/баланс, линия выключена. Это не исполнение заказа такси/профессиональной доставки через UI.
- Предприниматель/администратор: активный бизнес → изменение адреса → pending → администратор видит новый адрес → отклонение с причиной → владелец видит причину → исправляет адрес → pending → администратор видит исправленный адрес → одобряет → active. Весь этот цикл выполнен через интерфейс, запросы сохранены в `roles-browser-server.log`.
- Рекламодатель: кабинет загрузил принадлежащий ему черновик. Размещение и настоящая оплата через UI не исполнялись.
- Отправитель/попутный перевозчик: подготовленная посылка видна отправителю → другой аккаунт берёт её из «Возить» → она появляется в «Везу» → «В пути» → неправильный код отклонён → правильный код завершает доставку → у отправителя «Доставлено» → оценка 5 сохранена → открыта квитанция без телефонов/адресов. Создание этой конкретной посылки выполнено подготовкой данных, а не формой; отсутствовавший у синтетической записи код добавлен непосредственно в изолированную SQLite. Это не проверка генерации/доставки кода получателю.
- Клиент/бизнес: витрина показывает одобренный бизнес с исправленным адресом → клиент активирует купон → получает код → владелец вводит тот же код → «Код погашен», 1 активация и 1 погашение → повтор того же кода отклонён («Код уже погашён»). Действия выполнены через интерфейс; это синтетический купон, денег не переводили.
- Курьерский кабинет на стенде показывает серверные 15% и отдельную статическую фразу 3→5→8%; это несогласованность текстов/конфигурации, а не подтверждение правильности отображения всех тарифов. Нельзя закрывать тарифные тексты одним успешным API-тестом.

## Что не следует считать доказанным

Серверный сценарий с TestClient/SQLite/PostgreSQL доказывает обработку запросов и состояния, но не всю поездку через Android UI. Экран с MockWebServer проверяет реальный экран и клиентский запрос, но серверные права подтверждаются другими тестами. Проверка admin-роутов с пустым JSON и ответом 422 — не успешный административный путь.

Не подтверждены все математически возможные сочетания состояний, все успешные административные действия через интерфейс, физическое движение/GPS на двух устройствах, реальная доставка SMS/FCM, платежи банка и удалённое хранилище. Подтверждение естественности башкирского требует носителя. Эти границы не закрываются числом зелёных тестов.
