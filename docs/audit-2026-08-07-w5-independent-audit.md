## 2. НЕ СОШЛОСЬ

### 2.1. ⛔ «Закрыты обе двери» — дверей три (БЛОКЕР)

Заявлено: «Бейдж «N поездок» накручивался без поездки — закрыты обе двери (bookings.py и
family.py)».

Есть **третья**: `POST /rides/{ride_id}/complete` (`backend/app/routers/rides.py:642-660`)
переводит **все живые брони рейса** в `done` и не смотрит на время выезда вообще:

```python
for b in affected:
    b.status = BookingStatus.done if b.status != BookingStatus.pending else BookingStatus.cancelled
```

**Воспроизведение** (гонял на текущем, «починенном» коде):

```
POST /rides                      {depart_at: 2030-01-01}      -> 200
POST /bookings                   (второй аккаунт)             -> 200
POST /bookings/1/confirm                                      -> 200
POST /bookings/1/driver-status   {status: done}   ДВЕРЬ №1    -> 409  ✅ закрыта
POST /rides/1/complete                            ДВЕРЬ №3    -> 200  ❌ прошло
GET  /bookings/mine              статус брони                 -> "done"
GET  /users/1/trust              trips                        -> 1
POST /bookings/1/rate  {stars:5}                              -> 200  (оценка открылась)
```

Пять таких кругов = 15 запросов, ноль метров дороги. Публичная карточка водителя,
**которую отдают вообще без входа**:

```
GET /drivers/1/public -> 200
{'trips_count': 5, 'rating': 5.0, 'rating_count': 3, ...}
```

По-человечески: женщина открывает карточку незнакомого водителя, видит «5 поездок,
рейтинг 5.0» и садится в машину. Ни одной поездки не было. Бейдж доверия — и есть продукт
«между своими», ради него весь этот аудит и затевался.

**Почему так вышло.** Планку «поездка должна была выехать» поставили в двух местах записи,
а из трёх мест чтения — только в одном:

| место чтения | планка `depart_at <= now` | файл |
|---|---|---|
| бейдж в ленте поездок | **есть** | `services.py:713-714` (`driver_trips_agg`) |
| витрина доверия `/users/{id}/trust` | нет | `safety_logic.py:201-209` (`completed_trips_for`) |
| публичная карточка `/drivers/{id}/public` | нет | `drivers.py:294-300` |

То есть даже без третьей двери починка несогласованна: один и тот же «бейдж» считается
тремя разными функциями по трём разным правилам.

Побочно та же дверь открывает оценку (`/bookings/{id}/rate` требует `done`), то есть
анти-накрутка рейтинга обходится тем же путём. Кап на пару аккаунтов при этом работает
(`rating_count: 3` вместо 5) — это единственное, что удержало рейтинг от полной подделки.

### 4.1. Доставки со статусом `returned` не чистятся никогда

`_FINAL_STATUSES = ("delivered", "canceled", "returned")` (`parcels.py:65`), а правило

**ровно это правило** (добавил в него два `NOT EXISTS`) и мимо прошёл. Возвращённые
доставки копятся в базе вечно. Не безопасность, а рост таблицы — но неаккуратно.

### 4.2. Из `returning` некуда деться без человека

Выходы из «везу обратно»: только `/parcels/{id}/return-done` самим курьером, либо админ
(`/admin/parcels/{id}/close`, `/admin/parcels/{id}/release-courier`). Отправителю отмена
запрещена (`parcels.py:635`), а `close_stale_parcels` закрывает только `created`
(`cleanup.py:399`). Курьер пропал на обратном пути — заявка висит, пока не вмешается
Александр. Для `in_transit` это сделано осознанно (в коде так и написано), для `returning`
про это никто не подумал.

### 4.3. Роутеры, которых аудит не касался

Правились: ads, auth, bookings, chat, courier, discovery, family, instant, parcels,
