## ГРАФЫ СТАТУСОВ (по коду, а не по докам)

### RideStatus

```
                 (нет входа)  expired ──cancel──► cancelled
                                  ▲    └─complete─► done
                                  │
  [create_ride] ──► active ───────┼── /rides/{id}/cancel ──► cancelled  (терминал)
  [accept_request_response]       │                          + каскад живых броней → cancelled
      создаёт active,             ├── /rides/{id}/complete ─► done       (терминал)
      seats_left=0                │                          confirmed→done, pending→cancelled
                                  │
                                  └── cleanup.close_past_rides (раз в сутки, 04:00, depart_at < now-6ч):
                                        есть confirmed-бронь → done
                                        иначе               → expired
```

* `expired` ставится **только** ночной чисткой (`app/cleanup.py:276`). В API-коде — ни одного присвоения.
* `active` → `active` (правка) — `edit_ride`; при живых бронях можно менять только комментарий и цену **вниз**.
* Из `done`/`cancelled`/`expired` обратных переходов нет. `expired` **не тупик**: водитель может cancel/complete.

### BookingStatus

```
  [POST /bookings] ──► pending ──/confirm (водитель)──► confirmed
                          │                                │
                          │                                ├─ /no-show (водитель) ─► cancelled (+места назад)
                          │                                │
     /cancel (обе стороны)┤                                ├─ /cancel (обе стороны) ─► cancelled (+места назад)
                          │                                │
     /driver-status done ─┼────────────────────────────────┼─► done  (водитель, БЕЗ confirm, БЕЗ проверки времени)
     /trip-status done ───┤ (пассажир)                     │
                          │                                │
     ride/complete ───────┴─► cancelled (pending)          └─► done (confirmed)
     ride/cancel ─────────► cancelled
     cleanup ──► confirmed+ride:done → done ; pending → cancelled

  onboard: НЕДОСТИЖИМ — ни одного присвоения во всём backend/app.
```

Проверка: `grep -rn "status = BookingStatus\.\|status=BookingStatus\." app/` даёт 8 мест —
`confirmed` (2), `cancelled` (3), `done` (3). `onboard` не ставит никто.

### RideRequest.status (строка, не enum)

```
  active ──/cancel (владелец)──► cancelled            (терминал)
     │
     ├──/responses/{id}/accept ──► matched            ⚠ ТУПИК: ни cancel, ни edit, ни чистка
     │
     └── cleanup.close_past_requests ──► expired      (только из active)
```

### RequestResponse.status

```
  offered ──/counter (по очереди, ≤3 хода на сторону)──► offered
      ├── /accept (чей ход) ──► accepted   (терминал; DELETE запрещён)
      ├── /decline (любая сторона) ──► declined
      ├── DELETE /responses/{id} (автор) ──► строка удалена
      └── cleanup: если заявка стала expired ──► expired
   На matched-заявке отклик навсегда остаётся offered (чистка его не видит).
```

## ПОДТВЕРЖДЁННЫЕ ДЫРЫ

### [P1] «Только для своих» обходится прямым `POST /bookings`

- **Файл:строка** `backend/app/routers/bookings.py:92-116` (`book`)
- **Что не так** Фильтр `only_trusted` стоит на выдаче (`rides.py:69-80` `_hide_trusted_only`,
  применён в `/rides`, `/rides/near`, `/rides/{id}`, `/r/{id}`, `/match/rides`) и на отклике
  (`requests.py:450-451` — там прямо написано «IDOR-защита: прямой id не обходит фильтр»).
  В самом бронировании проверки **нет**: `book()` смотрит только `status==active`, «не своя поездка»,
  блокировку и число мест.
- **Сценарий поломки** L0-пользователь (не «свой») перебирает `ride_id` (id последовательные) или берёт id
  из пуша «карауль маршрут» (см. следующую находку) и бронирует закрытую поездку. Дальше он —
  полноправный участник: чат, детали брони, телефон водителя после подтверждения. Обещание «круга своих»
  ложное на самом важном шаге.
- **Доказательство** пробник на живом API:
  `[PROBE only_trusted] лента скрывает=True  GET /rides/id=404  POST /bookings=200`
  (поездка `only_trusted=True`, бронирует свежий L0-аккаунт).
- **Как чинить** в `book()` после проверки блокировки:
  `if ride.only_trusted and trust_level(session, user) < INSIDER_LEVEL and ride.driver_id != user.id: raise herr(403, ...)`.
  Текст ошибки — как у отклика (`requests.py:451`), чтобы не раскрывать существование поездки.

### [P1] Повторное чтение «под локом» отдаёт УСТАРЕВШИЙ объект → овербукинг и двойное принятие заявки

- **Файл:строка**
  `backend/app/routers/bookings.py:359-361` (`cancel_booking`), `:405-406` (`mark_no_show`),
  `backend/app/routers/requests.py:713-719` (`accept_request_response`, вызван из `accept_response` — `requests.py:764,767`),
  а также `app/automatch.py:54,74`.
- **Что не так** Везде используется паттерн «сначала `session.get(...)`, потом `session.exec(select(...).with_for_update())`
  и перепроверка статуса». SQLAlchemy при повторной загрузке уже присутствующего в сессии объекта
  **не перезаписывает загруженные атрибуты** (нужен `.execution_options(populate_existing=True)`).
  Блокировка строки берётся, но код читает старые значения → все три комментария в коде
  («перепроверяем статус: первая отмена уже могла отработать», «два параллельных accept не пройдут оба
  проверку status==active») описывают защиту, которой нет. На Postgres хуже: ожидание на локе
  **гарантирует**, что объект был прочитан до чужого коммита.
- **Сценарий поломки**
  1. *Овербукинг.* Пассажир жмёт «Отменить бронь», параллельно другой бронирует последнее место.
     Отмена возвращает места, исходя из старого `seats_left` → место чужой брони «возвращается» второй раз.
  2. *Две поездки на одну заявку.* Пассажир (или админ из Telegram, или ночной автоподбор `automatch`)
     принимает отклик, одновременно принимается второй отклик. Оба видят `status=="active"` →
     создаются два `Ride`+`Booking`, за пассажиром приезжают два водителя.
- **Доказательство** прямой ORM-пробник (SQLite, но причина не зависит от диалекта):
  ```
  s1 initial status: active
  s2 committed status=matched
  s1 re-read under FOR UPDATE -> active | same object: True
  RAW db value: matched
  ```
  и арифметика мест:
  ```
  [STALE] A видела seats_left=1; в БД сейчас 0; A после «перечитывания под локом» видит seats_left=1
  [STALE] ИТОГ: seats_total=3 seats_left=3 занято живыми бронями=1 → сумма=4 (должно быть 3)
  ```
- **Как чинить** во всех местах, где до лока объект мог быть загружен:
  `session.exec(select(X).where(...).with_for_update().execution_options(populate_existing=True))`
  либо `session.expire_all()` перед локом. Дополнительно в `accept_request_response` брать под лок
  и сам `RequestResponse` и проверять `resp.status == "offered"` (сейчас `accept_response` отвергает
  только `declined`, `accepted` не проверяется вовсе — `requests.py:776`).
  Хорошая новость: `POST /bookings` (`bookings.py:97`) грузит `Ride` **впервые** в своей сессии,
  поэтому обычный овербукинг «две брони на последнее место» действительно закрыт.

### [P1] Рейтинг и бейдж «N поездок» накручиваются без единой реальной поездки

- **Файл:строка** `backend/app/routers/bookings.py:279-297` (`driver_status`, ветка `done`),
  `backend/app/routers/family.py:376-430` (`rate_booking`), `backend/app/services.py:670-683` (`driver_trips_agg`)
- **Что не так** Водитель одним запросом переводит `pending → done` («Идемпотентно… pending→done — легитимный
  поток»), не подтверждая бронь и **без всякой проверки времени выезда, гео или согласия пассажира**.
  Как только бронь `done`, обе стороны могут поставить оценку. Средний балл защищён капом
  «3 оценки от одной пары за 30 дней» (`services.py:616-645`), а бейдж доверия «N поездок» —
  **ничем**: `driver_trips_agg` считает `count(distinct booking.ride_id) WHERE booking.status='done'`.
- **Сценарий поломки** Два аккаунта. Цикл из 3 запросов: `POST /rides` → `POST /bookings` →
  `POST /bookings/{id}/driver-status {"status":"done"}`. Сто повторов = бейдж «100 поездок»
  на карточке в ленте. Для «между своими», где бейдж и есть продукт, это подделка доверия.
  Плюс 3 честных пятёрки в месяц на пару — рейтинг 5.0 при нуле поездок.
- **Доказательство** пробник:
  `[PROBE instant-done] pending->done=200  пассажир оценил=200 {"rating":5.0,"count":1}  водитель оценил=200 {"rating":5.0,"count":1}`
  (бронь создана и закрыта за одну секунду, `depart_at` — 2030 год).
- **Как чинить** минимум: запретить `driver-status done` раньше `ride.depart_at` (или раньше `depart_at - N минут`)
  и по броням в статусе `pending` (сначала `confirm`); для бейджа «N поездок» — применять тот же
  анти-парный кап, что и для рейтинга (не больше K done-поездок с одним и тем же пассажиром за окно).

### [P1] SOS делит строгий лимит запросов с `/auth` — «красная кнопка» может отдать 429

- **Файл:строка** `backend/app/middleware.py:24-28` (`_STRICT_PREFIXES`), `:128,135,148`
  (ключ бюджета `rl:s:{ip}` — **один на весь префиксный набор**), `backend/app/config.py:405`
  (`rate_limit_auth_per_min = 20`)
- **Что не так** `/sos` и `/auth/*` лежат в одном строгом бюджете: 20 запросов в минуту **на IP**,
  счётчик общий. Мобильные операторы в РБ раздают клиентов через CGNAT — сотни абонентов с одного
  публичного IP. Двадцать человек, одновременно вошедших в приложение (или один перебор кодов),
  выжигают бюджет, и следующий `POST /sos` получает 429.
- **Сценарий поломки** Вечер, много входов с одного NAT оператора. Человек в машине жмёт SOS →
  «Слишком много запросов. Подожди немного.» Событие в БД не создаётся, SMS близким не уходит,
  админ ничего не узнаёт. Внутренние капы SOS тут ни при чём — они гасят только SMS
  (`safety.py:30,124-132`), а само событие пишется всегда; здесь запрос не доходит до роутера.
- **Доказательство** цитата из `middleware.py`:
  ```python
  _STRICT_PREFIXES = ("/auth", "/sos", "/callback", ...)
  ...
  if strict:
      over, retry_after = await self._over_redis(client, f"rl:s:{ip}", settings.rate_limit_auth_per_min)
  ```
  Ключ `rl:s:{ip}` не зависит от пути → бюджеты `/auth` и `/sos` — один и тот же счётчик.
- **Как чинить** вынести `/sos` (и `/bookings/*/stuck`) в собственный бюджет с ключом `rl:sos:{ip}`
  и щедрым лимитом, либо освободить их от IP-лимита совсем — злоупотребление уже ограничено
  авторизацией и капом SMS (`SOS_SMS_PER_HOUR=6`). Цена ложного 429 на панической кнопке
  несопоставима с ценой спама.

### [P2] Заявка залипает в `matched` — из этого статуса нет выхода

- **Файл:строка** `backend/app/routers/requests.py:737` (ставит `matched`), `:328-347` (`cancel_request` —
  требует `active`), `:291-325` (`edit_request` — требует `active`), `backend/app/cleanup.py:311-330`
  (`close_past_requests` — обновляет только `status='active'`)
- **Что не так** После принятия отклика заявка становится `matched` навсегда. Если сделка развалилась
  (бронь отменили, водитель пропал), заявку нельзя ни отменить, ни поправить, ни она протухнет сама.
  Чужие отклики на ней навсегда остаются `offered` (чистка ловит только отклики `expired`-заявок).
- **Сценарий поломки** Пассажир принял отклик, водитель через час отменил бронь. В «Моих заявках»
  висит заявка «в работе», кнопка «Отменить» отдаёт 400, водители по ней больше не откликаются.
  Единственный выход — создать новую заявку, а старая копит место в потолке `flood_active_requests_max`?
  (нет — потолок считает только `active`, здесь спасает).
- **Доказательство** пробник:
  `[PROBE accept] отмена брони=200  заявка после=matched  cancel_request=400  edit_request=400`
- **Как чинить** при отмене брони, созданной из отклика, возвращать заявку в `active`
  (и `resp.status` в `declined`), либо разрешить `cancel_request` из `matched`,
  либо закрывать `matched`-заявки в `close_past_requests` наравне с `active`.

### [P2] Мат и телефоны в открытых полях не фильтруются — только счётчик (проверка утверждения из доков)

- **Файл:строка** `backend/app/antifraud.py:287-352` (`moderate_text` / `moderate_open_text`),
  `rides.py:144,254` (`check_contact=False` — телефон в объявлении не помечается даже флагом)
- **Что не так** Утверждение из доков подтверждается **по факту**, но неточно по механике:
  мат детектируется (`abuse_flag`, `antifraud.py:271-284`) и телефоны детектируются, но
  **текст никогда не меняется и не блокируется** — только инкремент счётчика в Redis
  («ПОМЕЧАЕМ, не блокируем»). В комментарии поездки телефон не помечается вовсе (`check_contact=False`).
  Итог для пользователя ровно такой, как в доках: мат и номера публикуются как есть.
- **Доказательство** пробник:
  `[PROBE open text] комментарий поездки сохранён как: 'звони 8 917 123 45 67, ты дебил'`
- **Как чинить** продуктовое решение, не баг. Если оставляем «помечаем, не блокируем» — стоит хотя бы
  вернуть метку клиенту (сейчас `moderate_open_text` возвращает вид метки, а роутеры его выбрасывают),
  чтобы автор видел «в тексте нашли грубость».
  Отдельно: текстовые отзывы (`Rating.text`) модерируются человеком до публикации (`family.py:417`,
  `text_published=False`) — тут дыры нет.

### [P2] «Карауль маршрут» рассылает поездки/заявки «только для своих» и заблокированных

- **Файл:строка** `backend/app/services.py:329-380` (`notify_route_watchers`), `:383-430` (`notify_request_watchers`)
- **Что не так** Матчинг подписки не смотрит ни на `ride.only_trusted` / `request.only_trusted`,
  ни на блок-лист (`blocked_user_ids`). Пуш и запись в Центре уведомлений уходят всем, у кого совпал маршрут,
  с `ref_kind="ride", ref_id=ride.id`.
- **Сценарий поломки** (а) закрытая поездка «для своих» анонсируется чужим — и вместе с id, который дальше
  бронируется в обход фильтра (см. первую находку); (б) человек, которого водитель заблокировал,
  продолжает получать пуши о его поездках.
- **Доказательство** во всём `services.py` нет ни одного упоминания `only_trusted`
  (`grep -n "only_trusted" app/services.py` → пусто), а `blocked_user_ids` в функциях-сторожах не вызывается.
- **Как чинить** в обеих функциях: `if getattr(ride, "only_trusted", False) and trust_level(session, watcher) < INSIDER_LEVEL: continue`
  и пропускать `w.user_id in blocked_user_ids(session, ride.driver_id)`.

### [P2] Принятие отклика и подтверждение брони обходят паузу «Справедливости»

- **Файл:строка** `backend/app/routers/requests.py:756-783` (`accept_response` — нет `ensure_active`),
  `backend/app/routers/bookings.py:316-340` (`confirm_booking`), `:269-313` (`driver_status`)
- **Что не так** `ensure_active` стоит на публикации поездки (`rides.py:107`), создании заявки
  (`requests.py:108`), отклике (`:446`), торге (`:639`) и бронировании (`bookings.py:93`), но **не** на
  принятии отклика и не на подтверждении брони. В `counter_offer` прямо написано: «Без этой строки
  отстранённый доводил до конца сделку, начатую до паузы (аудит 2026-08-06)» — а именно эта дверь открыта.
- **Сценарий поломки** Водителя отстранили по разбору жалобы. Его отклик, оставленный до паузы,
  пассажир принимает → создаётся поездка с отстранённым водителем, который везёт человека.
  Или: водитель отстранён, но подтверждает уже висящие брони и работает дальше.
- **Как чинить** `ensure_active(session, user.id)` в `accept_response` (для принимающего) плюс
  проверка `account_paused(session, resp.driver_id)` внутри `accept_request_response` — сделка не должна
  создаваться с отстранённой второй стороной. То же в `confirm_booking`.

### [P2] Карта (`/rides/near`) не отсекает уже уехавшие поездки

- **Файл:строка** `backend/app/routers/rides.py:486`
- **Что не так** `q = select(Ride).where(Ride.status == RideStatus.active, Ride.seats_left > 0)` —
  фильтра по `depart_at` нет. В списке (`/rides`, `rides.py:317-320`) он есть — грейс 2 часа,
  и там же в комментарии описан этот самый баг («аудит 2026-07-04: у поездки не было отсева по времени →
  вчерашние висели в ленте»). В `/requests/near` фильтр по времени тоже есть (`requests.py:171`).
  Чинили в одном месте из трёх.
- **Сценарий поломки** Поездка уехала вчера. `close_past_rides` закроет её только ночью в 04:00
  (плюс грейс 6 часов) — до тридцати часов её пин висит на карте. Человек тапает, бронирует
  (в `book()` проверки времени тоже нет) и звонит водителю, который вчера доехал.
- **Как чинить** добавить в `rides_near` то же условие, что в `search_rides`:
  `Ride.depart_at >= utcnow() - timedelta(hours=RIDE_PAST_GRACE_HOURS)`.
  Заодно осмысленно закрыть бронирование поездки, время которой прошло больше чем на грейс.

### [P2] Поездка из принятого отклика публикуется в общую ленту с нулём мест

- **Файл:строка** `backend/app/routers/requests.py:726-729` (`Ride(..., seats_left=0, status=RideStatus.active)`),
  `backend/app/routers/rides.py:317-320` (`/rides` не фильтрует `seats_left > 0`)
- **Что не так** Приватная договорённость «пассажир ↔ водитель» превращается в публичное объявление:
  маршрут, время, цена и имя водителя видны всем в ленте, хотя мест ноль и забронировать нельзя.
  `/rides/near` такие поездки прячет (`seats_left > 0`), `/rides` — нет. Асимметрия.
- **Доказательство** пробник:
  `[PROBE accept] booking=confirmed ride=active seats_left=0/1 request=matched видно_в_ленте=1 шт`
- **Как чинить** либо не показывать в `/rides` поездки с `seats_left <= 0` (единообразно с `/rides/near`),
  либо помечать поездки, рождённые из отклика, отдельным признаком и не пускать в ленту.

### [P2] `BookingStatus.onboard` — мёртвое состояние, но контракт его обещает

- **Файл:строка** `backend/app/models.py:38-44` (значение объявлено), присвоений нет нигде;
  читается в `bookings.py:110,159,364,402`, `chat.py:756`, `location.py:90,127`, `share.py:116,119`;
  `docs/route-tracking-contract.md:12,21,44` описывает его как рабочий статус
- **Что не так** Ни один эндпоинт не переводит бронь в `onboard`: `driver-status` принимает
  `departed|arriving|done` (`bookings.py:277`), `trip-status` — `sat|arrived|done` (`family.py:332`).
  Контракт трекинга при этом пишет `booking.status ∈ {confirmed, onboard}` и перечисляет
  `"status":"onboard"` в сообщениях сокета.
- **Следствия** фаза «В пути» на публичной live-ссылке (`share.py:116`) недостижима — близкий всегда
  видит «Машина едет к точке посадки» вплоть до финала; все проверки `in (confirmed, onboard)`
  фактически означают «только confirmed»; клиент, отправивший `onboard`, получит 400.
- **Как чинить** либо завести переход (`driver-status` / `trip-status` `sat` → `onboard`) и обновить граф,
  либо убрать `onboard` из контракта и из проверок. Сейчас это расхождение кода и контракта.

### [P2] Неявку нельзя отметить по неподтверждённой брони

- **Файл:строка** `backend/app/routers/bookings.py:402-403`
- **Что не так** `mark_no_show` требует `confirmed`/`onboard`. Но у попутки подтверждение — необязательный
  шаг: водитель может вообще не жать «Подтвердить». Пассажир, который не пришёл к неподтверждённой броне,
  не отмечается как no-show — сигнал доверия теряется, и водителю остаётся обычная отмена,
  которая в «Надёжности» бьёт по нему самому (`bookings.py:375` — `cancelled_by = user.id`).
- **Доказательство** пробник: `[PROBE no-show on pending] 409 {"detail":{"ru":"Неявку можно отметить только по подтверждённой брони"...}}`
- **Как чинить** разрешить `no-show` и для `pending` (после `ride.depart_at`), либо в `cancel_booking`
  не записывать инициатором водителя, когда причина — `no_show`.

### [P3] Админ отклоняет отклик — пассажир об этом не узнаёт

- **Файл:строка** `backend/app/routers/requests.py:686-703`
- **Что не так** Для админа `_bargain_role` возвращает `None`, и `other_id = req.passenger_id if role == "driver" else resp.driver_id`
  всегда даёт водителя. Пассажир, чью заявку админ закрыл по звонку, уведомления не получает.
- **Как чинить** при `role is None` (админ) слать пуш обеим сторонам.

### [P3] Отзыв отклика физически удаляет строку

- **Файл:строка** `backend/app/routers/requests.py:786-800` (`session.delete(resp)`)
- **Что не так** История торга (`bargain_history`) исчезает бесследно, а `responded`/`my_response_id`
  в ленте позволяют откликнуться заново без следа. Для спора «он предлагал 300, потом отказался»
  доказательств не остаётся. Всё остальное в проекте не удаляет, а помечает статусом (`declined`/`expired`).
- **Как чинить** ставить `status="withdrawn"` вместо `delete`, а из ленты фильтровать по статусу.

## ПРОВЕРЕНО И ЧИСТО

**Овербукинг и места (кроме гонки из P1 выше)**
- `POST /bookings` берёт `Ride` под `FOR UPDATE` **первой** загрузкой в своей сессии (`bookings.py:97`) —
  устаревания там нет, обычная гонка «две брони на последнее место» действительно закрыта.
- Больше мест, чем есть — 400 (`bookings.py:115`); повторная бронь тем же человеком идемпотентна,
  места второй раз не списываются (`:106-114`).
- Отмена и no-show возвращают места с потолком `min(seats_total, ...)` (`:376`, `:414`) — даже при
  двойном срабатывании число не превысит вместимость.
- Бронь своей поездки запрещена (`:100`), бронь в связке блокировки — 403 (`:102`), покрыто тестами
  (`tests/test_api.py:80,105`).
- `edit_ride` при живых бронях не даёт менять время/места и поднимать цену (`rides.py:242-273`).

**Жизненный цикл**
- `cancel_ride` каскадно гасит живые брони одной транзакцией и шлёт запись в Центр уведомлений
  на двух языках (`rides.py:595-632`); `complete_ride` корректно делит `confirmed→done` / `pending→cancelled`
  (`:635-668`); обе идемпотентны.
- `close_past_rides` честно разделяет `done` (была подтверждённая бронь) и `expired`, закрывает
  зависшие брони и уведомляет водителя (`cleanup.py:261-298`) — покрыто `tests/test_nothing_hangs_forever.py`.
- Из `expired` есть выходы (cancel/complete) — не тупик.

**Поток заявок**
- Отклик на свою заявку — 400 (`requests.py:439`); повторный отклик идемпотентен (`:452-455`);
  отклик на заявку «для своих» от не-L3 — 403 (`:450`); отклик на прошедшую заявку — 404 (`:436-438`).
- Торг: ходы строго по очереди, лимит 3 встречных на сторону, принять свою же цену нельзя
  (`:644-652`, `:779-781`), цена клампится до 100 000 при создании поездки (`:724`).
- **Последовательное** двойное принятие блокируется: `[PROBE two accepts sequential] первый=200 второй=400 «Заявка уже закрыта»`.
- `accept_request_response` создаёт `Ride`+`Booking`+статусы одной транзакцией (`flush` без `commit`, `:731`).
- Отозвать принятый отклик нельзя (`:796`), чужой отклик — 403 (`:794`).

**Оценки**
- Оценить можно только `done`-бронь и только участнику; проверка участия идёт **до** проверки статуса
  (чужой — 403, свой недозавершённый — 409) — `family.py:382-396`.
- Одна оценка на пару (бронь, автор), повтор редактирует существующую (`:400-414`); себя оценить нельзя
  структурно (ratee — всегда вторая сторона).
- Текстовый отзыв публикуется только после ручной модерации админом (`text_published=False`,
  `reviews.py:170-190`); правка текста снова снимает публикацию (`family.py:410-413`).
- Метки — из закрытого списка через `clean_tags`; «щит рейтинга» (`excluded`) исключает оценку из среднего
  (`services.py:665`); анти-накрутка парой — 3 оценки за 30 дней (`services.py:616-645`).

**Чат**
- Доступ только участникам брони и в REST, и в WS (`chat.py:222`, `services.booking_and_ride_for_user`),
  покрыто `tests/test_api.py:93`.
- Токен принимается **только первым кадром**, не через query-string; ревокация перепроверяется
  каждые 15 сообщений (`chat.py:238-247`).
- Блокировка глушит запись на всех путях; анти-флуд 30 сообщений/мин действует и в REST, и во всех трёх сокетах.
- Окно записи закрывается через 48ч после `depart_at` для `done`/`cancelled` (`chat.py:111-123`),
  «забыл вещь» открывает его на 48ч обеим сторонам (`bookings.py:515-544`).
- Правка/удаление — только своего сообщения (`chat.py:666`, `:698`); `_msg_in_booking` проверяет
  принадлежность сообщения броне (анти-IDOR, `:649-653`).

**Приватность и гео**
- Телефон водителя открывается только участнику брони и только при `confirmed/onboard/done`
  (`bookings.py:159,175`); телефон пассажира не отдаётся водителю нигде.
- `public_ride_payload` вычищает `pickup`/`pickup_lat`/`pickup_lng` из **всех** публичных выдач
  (`services.py:744-755`) — лента, near, карточка, публичная OG-страница.
- `/requests/near` округляет координаты пассажира до 2 знаков (~1 км, `requests.py:212-213`);
  в `/rides/near` координаты — геокод **города**, не адреса.
- `/ws/trip/{id}/location`: только участник, только `confirmed`, перепроверка токена и статуса каждые
  15 кадров, анти-телепорт, координаты в БД не пишутся (`location.py:64-149`).
- `/t/{token}`: токен ≥16 байт, unique, TTL 24ч, гео только в живой фазе, после финала — без координат,
  токен маскируется в access-логе и в алертах (`share.py`, `middleware.py:211,225`).
- `/r/{ride_id}` отдаёт белый список полей без ПДн и только для `active` и не-`only_trusted`
  (`share.py:428-441`), покрыто `tests/test_privacy_tails.py`.

**SOS и доверенные контакты**
- Событие пишется **синхронно и всегда**, даже когда SMS подавлены капом (`safety.py:110-134`);
  кап 6/час гасит только SMS близким и админу, Telegram админу не капается.
- SOS из брони требует участия в поездке (`booking_and_ride_for_user`); близким уходят машина и ссылка
  на карту, имя и телефон водителя — только админу (`safety.py:55-80`).
- Доверенные контакты: формат телефона валидируется, потолок 10 (анти-SMS-бомбинг, `family.py:61-77`);
  удаление контакта гасит его шаринги (`:85-97`).
- Открытые SOS ретеншеном не удаляются (`cleanup.py:44`).

**Прочее**
- `places.py` — строго свои строки, чужое → 404 (анти-IDOR), лимиты 20/10.
- `route_watch.py` — только свои подписки, чужая → 404, TTL 14 дней, потолок 20.
- `discovery.py` — агрегаты без ПДн, лимит скана 20 000 строк, кеш.
- Анти-флуд: 30 активных поездок на водителя, 15 заявок на пассажира, дедуп «двойного тапа»
  по всему содержимому в окне 60 с (`rides.py:83-102`, `requests.py:89-103`).
- Публиковать поездку и откликаться может любой авторизованный пользователь без проверки документов —
  это **осознанное** решение для попутки (ручная модерация только у такси), не дыра.

## НЕ ДОКАЗАНО

1. **Включён ли на проде таймер `yuldash-cleanup.timer`.** Unit-файлы есть (`backend/deploy/yuldash-cleanup.{service,timer}`,
   ежедневно в 04:00), но в скриптах деплоя явный `systemctl enable --now` найден только для
   `yuldash-automatch.timer` (`backend/deploy-automatch-timer.bat:19`). Если чистка не включена, `expired`
   не появляется **никогда**, прошедшие поездки висят `active` вечно, а пины на карте — тем более
   (см. P2 про `/rides/near`). Проверяется одной командой на сервере, но прод трогать запрещено.
2. **Поведение гонок на реальном Postgres.** Причина (устаревший объект в identity map при
   `with_for_update`) доказана на уровне ORM и от диалекта не зависит; последствие для мест
   воспроизведено арифметически. Настоящий двухсоединительный прогон на Postgres не выполнялся —
   в окружении его нет. Штатный тест `tests/test_api.py:333 test_overbooking_concurrent` пропускается
   на SQLite и проверяет только `book()` (который как раз чист), а не `cancel_booking` и не `accept`.
3. **Шлёт ли Android `onboard`** и что он делает с фазой «В пути» — это клиентская сторона, вне среза.
   Со стороны сервера статус недостижим, контракт его обещает.
4. **Реальная нагрузка CGNAT** (сколько абонентов делят один IP у операторов в РБ) — оценка, не измерение.
   Механика общего бюджета `/auth`+`/sos` доказана по коду; частота срабатывания — нет.
5. **Сговор двух аккаунтов на проде** — модуль `app/collusion.py` в срез не входил и на путь
   `rate_booking` / `driver_trips_agg` не подключён (проверено грепом), но его собственная логика
   не изучалась: возможно, он ловит такие пары в отчётах админа постфактум.
