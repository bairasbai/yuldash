# Pro Команда transporting и отмена локальных request tokens

## Восстановленный street-hail заказ

Выбранная подписка фильтрует состояния по streetHail.enabled. При restore-complete берётся order из захваченного состояния; если его status равен driving, формируется команда transporting. ## Конкретные keyed cancellation стратегии

При использовании выбранной зарегистрированной factory RequestConfirm получает Proxy с Regular либо WeakRef strategy. В этих стратегиях create(K) создаёт новый wrapper и заменяет mapping, не отменяя прежний token и не переиспользуя его. Это отличается от другого generic handler; переносить его контракт сюда нельзя.

Cancel удаляет текущий mapping по ключу и пытается отменить найденный token; Weak-вариант пропускает исчезнувший target. CancelAll обходит snapshot ключей без собственного per-item recovery, поэтому нижняя ошибка может прервать оставшуюся очистку. Локальный cancel не доказывает socket abort, remote rollback или бизнес-отмену.

API cleanup обращается по ключу после завершения post. Условный тест create(K) для T1 → create(K) для T2 → поздний cleanup T1 показывает, почему key-only cleanup требует анализа владельца. Но достижимость такого перекрытия на одном handler ещё должна быть доказана; это не установленная production race.

## Проверка перекрытия дала ограниченный отрицательный результат

Следующая итерация одного уже запущенного queue callback ожидает завершения предыдущего API-вызова, включая его cleanup, прежде нового create. Поэтому именно этот последовательный retry не является свидетельством описанного перекрытия.

Новый factory edge связывает Sender с RequestConfirmApi захваченного core scope при использовании этих зависимостей. Второй одновременно живой Sender или подписка с тем же конкретным handler и ключом не установлены; их отсутствие тоже не доказано. Live provider overrides, создание/disposal, transport lifetime и server arbitration остаются открытыми. Обычный RequestConfirm путь может использовать request path вместо queued UUID; это не доказывает совпадение ключей этих путей.

Разделить локальную команду статуса, серверное принятие и физическое начало перевозки. Missing manager должен давать явный исход, а повторная доставка команды иметь version/idempotency contract.

# Pro Локальная нормализация combo маршрута

## Подтверждённый контракт ComboSyncManager

В выбранных ветвях менеджер согласует локальные multi-order route/currentOrder и основной заказ. Это не самостоятельная сетевая синхронизация. Два источника событий имеют разные guards; после фильтра callbacks не используют event payload для расчёта, а перечитывают актуальное состояние OrderManager.

Расстояние сравнивает первую route-точку с pickup address, не с GPS водителя. Обычный конечный результат до 1 метра включительно допускает продолжение; null от geo helper тоже не останавливает ветвь. Это не доказательство валидной близости или наблюдавшегося дефекта. При непустом хвосте снимается первая remaining-точка и выбирается следующий currentOrder; пустой хвост даёт возврат без setter.

Setter сначала публикует multi-info, затем ожидает cache operation и только после этого при syncCurrentOrder=true согласует основной заказ, перечитывая текущее subject state. Ошибка cache может следовать за ранней публикацией. Ни общий атомарный commit, ни rollback, ни durable save, ни server ACK этим не доказаны. Две подписки не являются доказанным общим lock.
