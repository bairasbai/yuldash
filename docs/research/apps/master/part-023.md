# Go C69 Уточнение верхней DI-привязки отмены

## Что уточнено после C68

В исследованном component graph доказана цепочка: поле cancel provider i0 получает of30 с discriminator 15, а эта ветвь factory создаёт x780. Смысл изменяемого флага, disk persistence, process-death recovery, серверная отмена, стоимость и финансовый итог по-прежнему не доказаны. Отсутствие локального сравнения версии в выбранных телах не означает, что backend принимает произвольную цену.

Final bounded report получил независимый статический PASS; все шесть записей manifest и финальные хэши совпали. Проверять production binding cancel coordinator, а не только форму UI. # Go C70 Observer предварительной отмены

## Дополнение к C68–C69

В исследованном graph есть отдельный UI observer: отсутствие notification либо непригодность одного из двух текстов даёт false и инициирует guarded goBack. Тексты должны быть непустыми и содержать непробельный символ. Null внутри текстового поля не доказан как тот же false-путь; decoder и гарантии nonnull не исследованы.

Этот predicate не сравнивает цену, quoteId, revision, orderId или прежнее предложение. Поэтому observer уточняет прежний вывод о click handler: дополнительная UI-защита существует, но она проверяет пригодность уведомления, а не атомарную актуальность согласия.

False вызывает общий callback возврата, не cancel-specific callback C68; для исследованного callback этот общий метод пуст. Запрос goBack проверяет состояние router/payload. Физическое исчезновение экрана, успешная очистка подписок и отсутствие уже поставленного в очередь click не доказаны.

Ошибка source передаётся onError, а не преобразуется этим обработчиком в false. Поведение самого onError, retry и подписок за границами. Нет доказанной UI-гонки, зависания, серверной отмены или финансового исхода.

## Проверка, требования и тесты

Независимая статическая QA PASS, финальные хэши и все шесть manifest entries совпали. C70 является bounded final report, не frozen checkpoint: 16 выбранных методов, 14 полных локальных тел и 2 фрагмента, 298 выбранных instruction records. Raw extraction 1 120 не равно прочитанному объёму. Общий ledger C01–67 не пересчитан.

Для Юлдаша предлагается отдельно проверять пригодность отображения и действительность согласия. Смена условий должна инвалидировать quote и блокировать submit независимо от закрытия UI; уже отправленная операция сохраняет Unknown и прежний operationId для проверки исхода.

Восемь сценариев предложены, не выполнены: исчезновение notification; пустые/пробельные тексты; новая цена при пригодном тексте; false одновременно с click; ошибка source/decoder; detached router или missing payload; process death; завершение/смена состояния заказа при открытом modal. APK, API и SDK не запускались.

# Pro Завершение заказа: готовность данных, цена и lifecycle

## Новое ограниченное уточнение

Независимая claims/bytes/novelty QA получила PASS с документированными границами; проверены все 70 хэшей комплекта. Общие Progress/preview/error и offline fallback были описаны ранее и не объявляются новым открытием. Новое здесь: точные readiness/paymentConfirmation условия, источники суммы и локальные lifecycle/DI связи.

readCompleteData и DI init не являются барьером готовности результата сервера и трёх запускаемых чтений. onUpdate сначала публикует Progress; если makeCompleteData возвращает null, в этом вызове не появляется следующий Success/Error. Ненулевое представление становится Success, включая offline fallback. Это не доказательство постоянного spinner или финансового завершения.

## Условия готовности и сумма

Server-data gate зависит от наличия настройки useServerCompleteData, не от её boolean true. При наличии настройки точный Full без paymentConfirmation проходит; Full с paymentConfirmation ждёт, если receive-error не выставлен. Preview/null без receive-error не проходит. При отсутствии настройки этот gate обходится. Это условия построения UI, не backend-правила оплаты.

Для Full при обычном выборе cash использует userPrice, noncash использует driverPriceWithSubventions; явный driverPrice=true всегда выбирает второе. В non-Full пути локальная сумма заменяет null на 0 и применяет нижний clamp; Full-поля через этот guard не проходят. Это не доказательство поступления ошибочных сумм или дефекта расчёта.

Запасная подпись «оплачено» выбирается по типу оплаты и эксперименту без отдельного settlement check в выбранной ветви. Успех представления, подпись и наличие данных не равны подтверждённому расчёту с клиентом.

## Связь с текущим scope и ограничения

Callback order stream не применяет переданный Order: он перечитывает текущий scope и Bloc state для фиксированного ID. Поэтому поздний payload нельзя автоматически объявлять применённым к другому заказу. Замена поколения scope с тем же ID и порядок событий остаются открытыми.

onRemoved вызывает отмену подписки без ожидания, затем очищает поле; dispose ожидает cancellation и делегирует base dispose. При исключении последующая очистка не гарантирована прочитанным normal path. Эти различия не доказывают runtime-гонку или утечку.

Локальный объём: 44 new full-local claims, 3 prior-partial upgrades, 4 prior-full context и один DI fragment. Проверка более широкого raw capture не расширяет semantic scope. Это bounded анализ, не аудит всей функции или APK; общая coverage не пересчитана. Server freshness, settlement, runtime lifecycle, полный калькулятор и фактическое UI-поведение не установлены.

## Собственные требования Юлдаша и непроведённые проверки

Разделять accepted/loading/preview/offline estimate/reconciled amount/payment settled; явно маркировать источник суммы клиента и доход водителя. Проверять ID и поколение запроса/scope при применении результата. Не превращать технический 0 или текст оплаты в authoritative money state.

Предложены, но не выполнены проверки cash/noncash и источников суммы; Full/Preview/null с настройкой, paymentConfirmation и receive-error; отсутствующей/невалидной суммы; замены scope и cancellation failure; изменения подписи без settlement evidence. APK, API и SDK не запускались, код Юлдаша не менялся.

# Go C71 Обновление окна отмены и захваченного действия

## Уточнение C68–C70

В исследованной цепочке открытое окно действительно получает обновления содержимого. Валидная notification проходит построение состояния и два сравнения; доставленное отличающееся UI-состояние пересоздаёт кнопки и listeners с новыми captured actions. Поэтому отсутствие version-check в отдельном click callback C68 не означает, что окно вообще не обновляется, и не является доказанной уязвимостью.

Первое сравнение учитывает orderId, type, notification, translator и pendingChanges. Сравнение notification включает тексты и кнопки, а кнопки включают action. Второе, UI-сравнение, тоже учитывает список кнопок и action. Значит, изменение текста или действия может привести к обновлению, а фильтр не ограничен наличием уведомления.

При этом порядок сравнения не гарантирует неизменяемый snapshot: есть same-instance fast paths и сравнения вложенных объектов. OrderId не является отдельным полем итогового UI equality; различный вход может дать равное представление без повторного render. Это не доказательство реальной смены заказа в открытом окне или неправильной отмены.

## Ошибки и границы

Отсутствующая либо невалидная notification пропускает emission в content-потоке, а не выдаёт пустой экран. Отдельный dismiss observer C70 нельзя подменять этим поведением; порядок между подписками и физическое закрытие не установлены.

При отличии ключ записывается до downstream.emit. Откат ключа или автоматический retry при ошибке этим кодом не гарантированы; внешняя политика восстановления не исследована. Рендер заменяет listeners, но не доказывает уничтожение уже поставленного в очередь старого callback.

Обновление представления не равно атомарной проверке order/quote revision при подтверждении. Runtime-гонка, серверная защита, фактическая стоимость и финансовый исход не установлены.

## Статус и учёт

Bounded final report получил независимый статический PASS; report pin, manifest pin и все шесть manifest entries проверены. 49 выбранных scopes: 43 полных локальных тела, 6 фрагментов и 965 выбранных instruction records. 3 032 raw records не объявляются изученными целиком. Это не frozen checkpoint и не новый cumulative unique total. Ledger C01–67 сохранён, пересечения C68–71 отдельно не пересчитывались.

## Собственные требования Юлдаша и предложенные тесты

Согласие следует связывать с отдельным token: orderId, quoteRevision, displayRevision и expiry. Существенные изменения инвалидируют старое согласие до нового подтверждения; Confirm проверяет текущий domain snapshot, а не равенство текста/цветов. # Pro Входные данные оплаты и граница локального ACK

## Новый ограниченный результат

Generated Full parser читает nullable payment_confirmation: null сохраняется как null, а ненулевое значение должно быть Map и проходит через ранее разобранный context parser. Результат становится полем FullCompleteData. Это локальный контекст ожидания/модалки, не доказанный банковский receipt.

Dispatcher различает только type=preview. Остальные значения направляются в Full parser, но это не гарантирует успешный разбор: обязательные поля, типы и вложенные parsers остаются проверками. При успешном разборе nonnull строка type сохраняется, null получает default full. Non-string не становится допустимым только из-за выбора этой ветви. Это схема входа, не доказанный bypass.

Full требует две числовые цены и cash-признак типа bool. В выбранном внешнем parser нет собственных finite/range/currency проверок или арифметической сверки сумм и деталей. Это ограниченное наблюдение: numeric helper, входной codec, другие слои и сервер могут иметь дополнительные правила. Поступление неверных сумм или финансовый дефект не доказаны. Preview не извлекает price/cash/payment_confirmation.

## Привязка к прежнему ACK без нового зачёта

Ранее разобранный caller выбирает applyingFinalData по nonnull CompleteData, не по проверке Full или paid. Новый dispatcher способен создать Preview; это не доказательство, что реальный refresh-ответ содержит Preview.

Ранее разобранная обработка ждёт updateOrder и выбирает локальный результат finalData/fallback/keepLocal по типу клиентского event. Это не разобранный ответ банка или refund provider. Совпадение phase/result может привести к readyToClose, но не подтверждает settlement.

Названия FullCompleteData, finalData, readyToClose, экранный Success и флаг was_recalculated относятся к разным уровням. Ни одно само по себе не подтверждает окончательную сумму или оплату. Server provenance, версия/порядок событий, идемпотентность, persistence и финансовый исход остаются за границами.

## Проверка и объём

Независимая claims/bytes/novelty QA PASS с документированными ограничениями; report/manifest pins и 22 хэша комплекта совпали. Новое чтение: пять полных локальных dependency-limited тел, 4 140 bytes. Ещё 28 prior-full context records используются с нулевым новым credit; их повторная сверка не является новым охватом. Общая coverage не пересчитана. Это не полный аудит оплаты или APK; runtime, APK, API и SDK не запускались.

## Собственный контракт Юлдаша и непроведённые проверки

Отдельно моделировать parsed payload, preview, applied data, authoritative final amount и provider settlement/refund. Явно определить поведение unknown discriminator, денежные типы/валюту/точность и источник финансового статуса. Отсутствующий confirmation context не смешивать с ошибочным форматом; локальный fallback не подтверждает банковскую операцию.

Предложены, но не выполнены проверки preview/full/missing/null/unknown/non-string type; обязательных cash/price и крайних чисел; отсутствующего/ошибочного confirmation context; transport/parse failure и keepLocal/fallback; позднего или несовпадающего локального ACK. # Go C72 Ответ отмены и локальная финализация

## Главное различие

В выбранной success-ветви ответ уже содержит CANCELLED и применён к локальному заказу согласно ранее разобранному C01. Затем processing tracker публикует COMPLETE ещё до получения Zone и completion callback. Поэтому COMPLETE не означает, что все последующие локальные действия завершены.

Если Zone отсутствует и srcPoint=null, выбранный путь делает logging fallback без вызова финализирующего callback. Ошибка получения Zone до callback также не вызывает его на этом проходе. Но catch охватывает и сам callback: при ошибке внутри него часть локальных действий уже могла выполниться. Нельзя обобщать это до «при любой ошибке callback не запускался».

Это условная статическая последовательность, не воспроизведённый сбой. Ответ потерян и ответ CANCELLED получен, но локальная финализация не закончена, являются разными случаями. Неудача загрузки Zone не превращает уже полученный ответ в неизвестный серверный исход.

## Дополнительные локальные контракты

ERROR tracker используется и после сетевого onError, и после ответа с состоянием, отличным от CANCELLED. Это локальное событие, не wire-status FAILED и не доказательство исключительно транспортной ошибки.

При достижении финализатора выполняются локальные изменения заказа, repository/controller вызовы и лишь затем Runnable. Эта последовательность не доказана как транзакция или durable save; ошибка до Runnable может оставить частичные изменения. Точный смысл отдельных boolean/copy-флагов не переименован в серверное подтверждение.

Completion callback получает прежний, захваченный DriveState, а не новое чтение CANCELLED. Его непосредственный получатель здесь ещё не исследован.

Один потребитель processing events выдаёт Boolean: DEFAULT/ERROR → true, STARTED → false, COMPLETE → false для равного target holder и true для другого. Это не доказанное разрешение повторно отправить отмену или доступность кнопки: downstream render и DI identity observer/controller не замкнуты.

## Проверка и границы

Независимая семантическая/байтовая/scope QA PASS; report/manifest pins и все шесть manifest entries совпали. C72 является bounded final report, не frozen checkpoint. Выбраны 27 scopes: 22 полных локальных тела, 5 фрагментов, 545 instruction records. Raw capture 28 тел и 1 768 records не объявляется прочитанным целиком. Ledger C01–67 и прежние результаты не пересчитаны.

Runtime-достижимость отсутствующих Zone/srcPoint, другие recovery-механизмы, durable reconciliation неизвестного серверного исхода и UI-последствия не установлены. Это не заявление об отсутствии recovery во всём Go. APK, API и SDK не запускались.

## Собственные требования Юлдаша и непроведённые проверки

Разделить server outcome, local finalization и UI notification. Потерянный ответ сохраняет Unknown с lookup по operationId. Полученный Cancelled фиксируется отдельно; повторяемый local finalizer не должен создавать новую платную отмену или стирать известный исход из-за вторичной ошибки.

Десять сценариев предложены, не выполнены: потерянный ответ; CANCELLED без Zone/srcPoint; ошибка Zone до callback; частичные мутации; COMPLETE без доставки callback; restart; события двух заказов; callback с историческим состоянием; CancellationException; ошибка durable save после изменения памяти.

# BlaBlaCar Финальный экран бронирования и навигация

## Проверенный ограниченный контракт

Исследован modern мультимодальный booking success consumer, не исключительно обычная попутка и не прежний universal flow. CompleteState, выбор CTA и открытие следующего экрана являются разными стадиями; новый срез не устанавливает серверное подтверждение брони или оплаты.

Только CompleteState с непустым escCheckItems выбирает ESC-content и соответствующий callback. Null/пустой список выбирает обычный success content; InitialState показывает loading. Это выбор представления, не автоматический запуск ESC, не проверка документов и не доказательство доступности leaf-кнопки.

ESC event сначала вызывает YourRides без конкретного ID, затем пассажирский ESC navigator с rideId и BOOKING_FLOW. Ранее проверенный producer берёт этот rideId из tripOfferId, не из flowId. Идентификаторы нельзя считать взаимозаменяемыми из-за переименования поля. При исключении первого navigator второй вызов не достигается; при ошибке второго первый уже был вызван, но завершение экранных переходов этим не доказано.
