**Статус и граница.** Это final report с явно открытыми пробелами, не frozen checkpoint. Конкретный PROFILE provider и внутренняя цепочка DOMAIN от coroutine через транспорт к mapper не замкнуты. Преобразование DTO рассмотрено отдельно, не как доказанная сквозная цепочка до HTTP или банка.

**Подтверждено статически.** Полученный SUCCESS проходит дополнительную локальную обработку. Её ошибка может прервать обновление кэша, но не превращает исходный статус проверки в банковский отказ. Fallback после ошибки preflight зависит от уже закреплённого backend; нельзя утверждать, что любая ошибка DOMAIN автоматически повторяется через PROFILE.

Отсутствующее поле статуса получает UNKNOWN в рассмотренной модели. Это не доказывает, что произвольный будущий строковый статус также станет UNKNOWN: конкретный JSON decoder и его настройки не проверены. Отдельный DOMAIN mapper принимает пять рассмотренных статусов проверки; остальные enum в нём приводят к исключению протокола. Это не устанавливает неспособность всей цепочки обрабатывать промежуточные состояния до mapper.

**Собственные требования Юлдаша.** Хранить отдельно исходный результат provider, локальный результат обработки и состояние платёжной операции. Локальная ошибка не должна переписывать VERIFIED в DECLINED. При неизвестном исходе прежнего действия сначала восстанавливать ту же session/operation и проверять результат, а не автоматически создавать новую привязку.

**Предложенная приёмка, не выполнена.** Отсутствующий статус, explicit null, новый неизвестный token отдельно от значения unknown, неподдержанный mapper-статус, SUCCESS с ошибкой последующей обработки, отмена preflight, ошибка при разных закреплённых backend и повтор с потерянным ответом.

## BlaBlaCar Ожидание статуса оплаты

**Подтверждено статически.** Успешное получение статуса может вернуть PENDING; успех запроса не равен оплате. DONE преобразуется в SUCCESS и ведёт к событию закрытия с успехом. PENDING планирует следующую проверку. HTTP404 означает категорию «не найдено или истекло», не доказанную единственную причину. Неизвестная ошибка ведёт к повтору, а не к успеху.

В этой функции не обнаружены собственные exponential backoff, jitter или лимит попыток; общесистемные ограничения не исключены.

**Собственные требования Юлдаша.** Разделить успешный запрос, ожидаемую оплату, подтверждённую оплату и подтверждённую бронь. Не создавать повторное списание из-за таймаута, ошибки сети или 404. # Уточнение сценария Моё местоположение в BlaBlaCar

Согласованная ограниченная цепочка получения координаты, reverse geocode и обработки результата дополняет ранее опубликованный разбор точки встречи. Она уточняет прежнее исключение общей геолокации, но не повторяет общий сценарий выбора места и контракт terminal subject.

## Координата ещё не готовый адрес

**Подтверждено статически.** Presenter вызывает stopLoadingWithSuccess до запуска преобразования координаты в адрес. Поэтому этот ранний visual success не подтверждает успешное геокодирование. При null Location или ошибке преобразования рассмотренный use case не создаёт фиктивный успешный адрес.

При этом обработка ошибки существует: прямой downstream подписчик журналирует причину, очищает результаты и вызывает ErrorController. Отсутствие отката раннего loader success в самой coroutine нельзя превращать в утверждение, что весь экран скрывает ошибку. Передача места в локальный subject не доказывает подтверждение точки сервером или пользователем.

## Разрешение и расстояние не доказывают качество позиции

**Подтверждено статически.** Проверенный provider допускает разрешение FINE либо COARSE; наличие разрешения не обещает точную позицию. При отсутствии baseline новая координата принимается, а при существующем baseline distance gate требует расстояние строго больше порога, по умолчанию 500. Равенство порогу не проходит. Это порог перемещения, не точность, возраст координаты или длительность ожидания.

При canReuseLocation=true этот gate обходится. Переданные SDK интервалы и priority не гарантируют фактическую частоту или точность callback. В рассмотренных consumer, use case и distance-filter телах проверка age/accuracy не установлена; это не утверждение обо всех слоях приложения.

## Уточнение исходного значения из preferences

**Подтверждено статически.** Точное базовое тело PreferencesHelper.getLastLocation при каждом нормальном возврате возвращает null. Внутренний вызов может бросить исключение, поэтому это не означает, что каждый вызов успешно завершается. Для точного базового dispatch hasLastLocation нормально возвращает false; непрочитанные virtual overrides остаются за границей.

Следовательно, baseline provider нельзя считать доказанно восстановленным из этих preferences-тел. Он может появиться из Bundle, SDK или предыдущего принятого callback; distance gate остаётся условным путём, а не наблюдавшимся таймаутом неподвижного пользователя. В setter видны записи editor без собственного apply/commit, но внешнее применение editor не закрыто. Вывод «весь кэш не работает» не обоснован.

## Остановка экрана и освобождение ресурсов

**Подтверждено статически.** В непосредственной цепочке остановки экрана точное тело provider.onStopped является no-op. Сам этот вызов не доказывает остановку updates, удаление timer или disconnect.

Presenter.unbind отдельно обнуляет screen и вызывает helper отмены coroutine scope. Эти действия нельзя объединять в один универсальный stop. Полный lifecycle-порядок и доставка SDK callback не установлены; утечка, зависание и сломанный повтор на устройстве не доказаны.

## Самостоятельные требования Юлдаша

Разделить разрешение, получение координаты, проверку её качества, преобразование в адрес и подтверждение точки. Возраст и accuracy хранить отдельно от порога перемещения. При приблизительной или недостаточно качественной позиции предлагать ручную правку, не считать источник CURRENT_LOCATION гарантией безопасной посадки.

# Go C54 и C55 Два контракта PROFILE проверки

Два ограниченных final reports уточняют ранее открытую в C53 границу конкретного PROFILE provider. Это не новые frozen checkpoints и не полный платёжный аудит. В проверенном статическом DI-графе найдены реализации m и n; обе прослежены до собственного typed request/response контракта. Фактический runtime-выбор у пользователя, JSON converter и закрытый сервер этим не установлены.

## Доказанная связь и различия контрактов

**Подтверждено статически.** В конкретном DI-графе варианты j641/m641 связаны с реализацией m, а k641 с n. Это установлено по телам фабрик и конструкторов, не по названиям классов. Кэшированный verifier может обойти новый выбор factory; статический binding не означает одинаковый путь на всех экранах и аккаунтах.

В рассмотренной ветви m запрос V4 возвращает VerificationsStatusResponse. Ответ проходит локальную validation, затем его статус переносится в общий Verification. Альтернативная ветвь m.c остаётся вне этого результата.

Реализация n вызывает другой typed API с VerificationRequest и получает PaymentVerificationsResponse с вложенным Verification. В request сопоставлены binding и verification references, флаг invalidation, country/currency, supported features и условный antifraud payload. Наличие этих полей не доказывает серверные полномочия, реальную отправку или полный формат вложенного payload.

## Отсутствующий статус и UNKNOWN не взаимозаменяемы

**Подтверждено статически.** В DTO обеих рассмотренных PROFILE ветвей отсутствующий status становится null и при достижении общего validator отвергается. Это отличается от default UNKNOWN в отдельной DOMAIN модели C53. Неизвестный wire token, отсутствующее поле и explicit null нельзя объединять: конкретный JSON decoder и coercion не проверены.

Для n отсутствующее вложенное verification также становится null. При этом null внешнего wrapper разыменовывается раньше validator, поэтому его нельзя обещать как гарантированный InvalidResponseException. Дополнительно проверяется идентификатор вложенного Verification.

Общий validator требует status; для REQUIRED_3DS проверяет непустые по длине URL-поля, а для AMOUNT_EXPECTED ненулевое число оставшихся попыток. Это shape validation, не проверка доверенности URL или положительности числа попыток и не подтверждение банковского результата.

## Polling и локальные callbacks

**Подтверждено статически.** Обе ветви преобразуют IN_PROGRESS и RECEIVED_3DS_STATUS в сигнал продолжения ожидания; аналогичная ветка существует для повторного 3DS URL при включённом required3dsPolling.

В m дополнительно есть ограниченный guard неизменного статуса и двух ненулевых равных version. В полном рассмотренном action n этого сравнения нет, хотя поле version присутствует в DTO. Правило V4 нельзя автоматически переносить на второй provider. FAILURE в m имеет отдельный ранний возврат, а в n проходит обычное конечное построение результата.

В n на первой попытке до API вызова выполняется callback: его исключение предотвращает API вызов в этой попытке. Его назначение не установлено, поэтому он не называется ни авторизацией, ни заведомо безопасной аналитикой. В обеих ветвях SUCCESS вызывает отдельный локальный callback до успешного возврата результата. Ошибка такого применения не переписывает полученный статус в банковский отказ, но может прервать возврат наружу.

Общий interceptor отдельно перебрасывает cancellation, а остальные ошибки action передаёт handler. Автоматический retry любого сбоя не доказан: handler может бросить исключение. В m null результата превращается в локальную ошибку, тогда как n непосредственно возвращает результат interceptor; дальнейшая реакция UI на null этим не установлена.

## Самостоятельные требования Юлдаша
