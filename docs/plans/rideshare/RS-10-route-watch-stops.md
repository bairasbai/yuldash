## 1. Что получит человек
Гульнара живёт в Ургазе, ей нужно в Акъяр, поездок нет — она подписалась на «Ургаза → Акъяр». Рамиль публикует «Сибай → Акъяр через Ургазу». Сейчас Гульнара не узнает: приложение сверяет только начало и конец маршрута, а Ургаза — остановка посередине. «Каждый понедельник» дал бы сообщение лишь про первый рейс.

Теперь подписка работает как поиск: для совпавших поездок создаётся сообщение в центре уведомлений («садишься в: Ургаза»). Про уже сохранённые даты серии — одно сообщение на доступную по суточной квоте группу; непроверенные даты успехом не объявляются. На сайте кнопка «Следить за маршрутом» стоит там, где поездок не нашлось. В «Подписках» видно, когда создано последнее сообщение. Наличие зарегистрированного канала и разрешение уведомлений на этом устройстве показываются отдельно; доставку не обещаем.

## 3. Что сделать
### Сервер (`backend/`)
1. **S1 (совпадение).** `route_watch_fit(session, watch, ride, entry)` в `services.py`: `stop_search.variants` + `stop_searchable` + `route_fit(ride, fv, tv, entry, …)`; для `direction == "both"` ещё раз наоборот. `entry = request_snapshot(settlements_snapshot(session))` один на рассылку; вердикт кешируется по (откуда, куда, направление, вид маршрута). `_city_keys` остаётся для `notify_request_watchers` (заявки — вне плана).
2. **S2 (долговечное событие, единственный владелец API — RS-10 А).** `enqueue_route_watch(session, ride, *, source_key, group_key: Optional[GroupKey]=None, siblings: Sequence[Ride]=())` записывает `RouteWatchEvent` **в переданную доменную транзакцию до commit**, без сети/собственного commit. Одиночный create передаёт `siblings=()`; recurrence — точные созданные копии, RS-09 Б — точные известные созданные рейсы. По каждому ride/version создаётся отдельное событие; `source_key` события ВСЕГДА = SHA256 канонического массива `[owner_id,operation_scope,caller_source_key,ride_id,terms_version]`, включая каждый sibling. `caller_source_key` — исходный ключ команды/даты, для правки — строка ride-edit:id:version, а у старого одиночного create без ключа — server-строка ride:id:version после flush; включение ride/version обязательно и при наличии ключа команды. Входной `GroupKey(kind,value)` — отдельный внутренний дескриптор группы: `GroupKey("series",base_key)` либо `GroupKey("recurrence",persistent_publish_key)`; одиночный рейс — None. В БД `group_key = SHA256([owner_id,kind,value])`, не повторный хеш уже готового group_key и не per-ride source_key. При recurrence без Idempotency-Key server один раз создаёт publish group UUID и использует его для всех копий одной транзакции; повтор старого клиента без ключа не получает новую гарантию дедупа. Payload/координаты не сохраняются. Unique делают повтор enqueue безопасным. Брать рейсы из близости `created_at` (10 с) запрещено: это не идентичность серии.
   Worker `notify_route_watchers(session, event_id)` заново читает только committed события и актуальные рейсы, группирует точный committed subset одной `group_key` (series либо recurrence); pending/unresolved дату успехом не считает. Для одиночного события группы нет. Только `watch_kind in {rides,both}`; `requests` не получает поездки. Применяются S1, S3, `direction`, `watch_date` (местный день). Для подошедшего watch создаётся одно оповещение по всем ещё не объявленным committed рейсам группы, ref — самый ранний, Notice — на **каждый** ride. Позднее committed событие не теряется: ждёт доступной квоты и может объявить только новые ride; сводка не называется полной, пока клиентский итог серии неизвестен. Recurrence: основная поездка и четыре копии записывают пять разных event/source_key в одной доменной транзакции с одним неизменным group_key; worker видит весь committed набор и создаёт одну Notification с пятью Notice. Периодический обработчик читает due-события после рестарта; crash после доменного commit не теряет уведомление центра.
3. **S3 (кому нельзя).** К существующим (свой рейс, `may_be_notified`) добавить: водитель на паузе (`safety_logic.suspended_user_ids`), рейс не активен, уже уехал и **мест нет — так же, как в ленте**. После RS-02 `seats_left` — минимум по всем участкам и отсеял бы подписчика на свободный хвост, поэтому участок берётся из `Fit` (`matched_*`, правило предвыбора карточки): однозначен → `ride_seats.free_on(участок) ≥ 1`, иначе `ride_seats.max_free ≥ 1` (RS-02, п. 8). Зависимость — RS-02 А; отдельную временную реализацию по `seats_left` не вводить.
4. **S4 (текст).** RU: «Появилась поездка» / «Появились поездки»; тело `«{откуда} → {куда}»` + « · садишься в: {matched_stop}» / « · выйдешь в: {matched_dropoff_stop}» при совпадении по остановке + « · рейсов: N», если подошло больше одного. Язык пуша — по `User.language` (один запрос на всех); BA — черновик исполнителя. При частичной/ещё неизвестной серии текст «Сохранённых рейсов: N», без «вся серия опубликована»; N считает только committed подходящие рейсы. Ночью (`_is_quiet_hour`) запись в «Уведомлениях» есть, пуша нет, а сутки (`last_notified_at`) тратятся — **намеренно**: человек увидит запись утром, второй пуш за сутки не нужен.
5. **S5 (N3, атомарное право).** Добавить `RouteWatchNotice` с unique `(watch_id, ride_id)` (раздел 4). Пакетный SELECT уже объявленных рейсов — только ускорение, не защита. Для каждого подходящего watch открыть короткую транзакцию, перечитать `RouteWatch FOR UPDATE` с `populate_existing`, повторить актуальные сроки/дату/вид/направление и приватность S3. Условный UPDATE `last_notified_at` по прежнему значению (`NULL` отдельно), только когда истекли 24ч, — общий CAS для SQLite/PostgreSQL. Проигравший откатывает и ничего не создаёт. Победитель исключает уже объявленные ride_id, вставляет unique-строки всех новых подошедших siblings и **одну** `Notification`, связывает их `notification_id`, фиксирует вместе с `last_notified_at`. Конфликт unique / ноль новых → rollback всей транзакции, без расходования суток. `push_notification` сейчас пишет своей сессией, поэтому для этой ветви выделить помощник записи Notification **в переданную сессию без commit/сети**; менять общий способ вызова остальных уведомлений не требуется. Только после успешного commit победитель один раз ставит best-effort push в очередь `_push_async`; проигравший не отправляет. Если watch ещё в суточной квоте, событие остаётся pending с `next_attempt_at >= last_notified_at + 24ч`; после истечения повторно проверяются доступность/приватность/дата. Событие завершается, когда все актуально подходящие watch получили Notice либо больше не могут быть оповещены (истекли, скрыты, рейс уехал); новые подписки после завершения не запускают ретрорассылку. Конкурентную запись `next_attempt_at`/`finished_at` сериализовать row-lock события, не помечать finished при оставшихся quota-waiters. Сбой до commit не оставляет права/уведомления; сбой после commit не создаёт новую запись при повторе. Доставку или exactly-once сеть этот протокол не гарантирует: при сбое после commit запись в центре есть, push мог не уйти, автоматического повторного сетевого эффекта нет.
6. **S6 (статус).** `RouteWatchOut` + `last_notified_at` (время записи в центре), `registered_push_channels{app, web}` (есть `DeviceToken` / `WebPushSubscription`), `quiet_from`, `quiet_to` (`settings.quiet_hours_*`, 0 = выключены). Сервер не знает действующее разрешение ОС и не называет канал доставкой. Android отдельно читает системное разрешение уведомлений, PWA — `Notification.permission` и наличие browser subscription на **этом** устройстве. Копия записи/вызов провайдера не являются статусом «доставлено».
7. **S7 (ввод и повтор подписки).** `POST /route-watch`: место проходит `stop_searchable` и ≥ 2 букв, иначе `herr(400, "Название места — буквами, без цифр", <ba: черновик>, code="watch_place_invalid")` (RS-01). Идентичность кнопки пассажира: нормализованные `from/to` + `watch_kind=rides` + `direction=forward` + текущий `watch_date` (либо null). Не переиспользовать `requests`/`both` и обратные направления: «Не следить» удаляет только ID точно созданной/найденной подписки. Конкурентные создания сериализовать коротким замком по user_id (SQLite — write transaction, PostgreSQL — user row lock), повторить поиск дубликата и лимит 20 под ним. Повтор активной идентичной подписки возвращает ту же строку без сброса `last_notified_at`; смена даты — отдельное намерение, не скрытая перезапись чужой водительской подписки.

## 4. База данных
- Новая миграция `route_watch_dispatch_<дата>`, после RS-02 А и по линейной очереди индекса: таблица `routewatchevent` (`id`, `ride_id` FK ride ON DELETE CASCADE, `terms_version`, `source_key` varchar(64) unique, `group_key` varchar(64) nullable indexed (вид+устойчивый ключ series/recurrence, NULL у одиночной), `created_at`, `next_attempt_at`, `finished_at` nullable), unique `(ride_id, terms_version)`, индекс due-очереди. `RouteWatchEvent` не хранит текст/координаты; `enqueue` и доменная запись обязаны commit вместе. Таблица `routewatchnotice` (`id`, `watch_id` FK routewatch ON DELETE CASCADE, `ride_id` FK ride ON DELETE CASCADE, `notification_id` nullable FK notification ON DELETE SET NULL, `created_at`), unique `(watch_id, ride_id)`, индексы FK. Уведомления прежние, время 24ч в `RouteWatch.last_notified_at`; отдельной таблицы настроек нет.
- Старые Notification не дают надёжной связи watch_id: migration создаёт обе служебные таблицы. Перед включением нового обработчика засевать Notice для старых route_watch-уведомлений, сопоставимых по владельцу и рейсу, **для всех** его совпадающих активных подписок (без отправки), а неоднозначные старые строки пометить консервативно для этих подписок; существующее `last_notified_at` не обнулять. Так развёртывание не отправит заново уже объявленный рейс. Защита race начинается на согласованной остановке старого обработчика до включения нового; смешанную работу версий не обещать.
- Event: pending хранится до обработки либо окончательной утраты права рассылки; чистка **не удаляет** его по одному возрасту. Finished-события — 30 дней после `finished_at`, затем удалить; удаление ride каскадное. При удалении аккаунта удалить события его rides до удаления/обезличивания ride.
- Хранить Notice пока он нужен для подавления повторного объявления: удалить вместе с watch/ride; ночная чистка — `created_at < now - 180 дней` **и** рейс уже вне разрешённого окна публикации/правки и уведомлений (`depart_at < now - RIDE_PAST_GRACE_HOURS`). Будущие рейсы не чистить по одному возрасту Notice; `notification_id` может стать null после 90-дневной чистки Notification, дедуп при этом остаётся. Удаление аккаунта: удалить Notice принадлежащих его watch **до** RouteWatch (`account.py:554`), также проверить cascade при удалении ride. Не хранить названия маршрутов, номера или текст пуша повторно.
- Миграция — одна голова; previous-main schema + синтетические старые watches/notifications/рейсы → upgrade: значения сохранены, backfill без сети, unique работает; down → up на SQLite/PostgreSQL. `downgrade` удаляет Event и Notice: до него остановить enqueue/worker, проверить отсутствие pending Event (при наличии — сначала завершить/согласовать судьбу очереди, откат заблокирован). Защита дедупа при откате теряется, отправки старого обработчика не включать; безопасный онлайн rollback не обещается. `test_nothing_grows_forever.py`, `test_account_deletion.py`, оба migration guards обязательны. Production и реальные данные не использовать; применение ждёт владельца.

## 9. Риски и границы
- «Как в поиске» для голых названий подстрочное; защита — S7 и «раз в сутки». Не входит: заявки водителя (`notify_request_watchers`), новый интерфейс выбора дня подписки (существующий `watch_date` сохраняется), автоотписка после брони, подтверждение доставки. Дедуп гарантирует запись центра; best-effort push не гарантирует доставку.
- **Фиксированная интеграция RS-15 А.** RS-10 А вводит enqueue/worker; RS-15 А идёт после него и в транзакции изменения остановок записывает событие с source_key от ride_id/новой terms_version, `siblings=()`. Тест: rollback правки → ни события, ни уведомления; commit → crash/restart worker → подписчик новой Ургазы оповещён один раз, повторная правка не дублирует ride для того же watch. Файловая пауза не отменяет эту API-зависимость.
- Общие файлы (`MapScreen.kt`, `HomeScreen.tsx`, `tests/run.mjs`) — по очереди с RS-11, RS-12. Приватность: в тексте только названия мест; «братья» — рейсы того же водителя.
- **Мозг:** `architecture.md` — подписка сверяется через `route_fit`; `decisions.md` — «сутки, потраченные ночью» намеренно, статус только известного серверу; `tasks.md` — BA-черновики; `lessons.md` — подписка расходилась с поиском (концы маршрута вместо `route_fit`).
