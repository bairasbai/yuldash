## 1. Что получит человек
**Было.** Рустам опубликовал «Сибай → Уфа через Акъяр», а потом решил заехать в Баймак вместо Акъяра. Остановки не исправить —
только снять поездку и опубликовать заново. Пассажиры из Баймака рейс не находят.

**Стало.** В кабинете — «Изменить остановки»: добавить (до четырёх), убрать, переставить и тут же поправить цену до каждой.
Пассажир из Баймака сразу находит рейс, подписчик «появилась поездка» получает одно уведомление. Если кто-то уже забронировал —
честный отказ: «Пассажиры уже выбрали, где садиться. Отмени брони или договорись в чате». Если Айгуль бронирует в ту же секунду,
когда Рустам меняет остановки, побеждает кто-то один — брони «на остановку, которой больше нет» не бывает.

## 3. Что сделать
### Сервер (`backend/`)
1. **Вход и версия.** `RideEditIn.waypoints: Optional[str] = Field(None,max_length=500)`, `drop_offers:bool=False`, `expected_terms_version:int|None`; цены — входной `stop_prices:list[int]|None` из RS-02Б. Новые клиенты передают `expected_terms_version` из `RideOut`; версия охватывает маршрут, время, цену/`stop_prices_json`, вместимость/свободные места, опции и машину. Legacy без поля получает серверную исходную версию при первом чтении; это совместимость запроса, а не обход повторной проверки. Ошибки `herr(...,code=...)`.
2. **Подготовка без доменной записи.** Прочитать исходную версию/владельца, нормализовать вход (`_clean_publish_stops`, до четырёх; те же `stops_too_many/stop_invalid`), сохранить только исходное намерение и expected-version. Предварительные проверки не окончательны. Не присваивать `ride`/`Booking` новые значения до модерации. `moderate_open_text` комментария и остановок выполняется до новой бизнес-транзакции: его `session.commit()` (`backend/app/antifraud.py:446–458`) не должен фиксировать цену или удерживать нужный нам lock. Не рассчитывать окончательный `new_price`/суммы броней на этой устаревающей копии.
3. **Окончательная проверка после модерации.** Начать транзакцию заново; PG: `FOR UPDATE` рейса, затем живых броней в порядке id (общий `Ride → Booking`); SQLite: взять writer-lock условным no-op `UPDATE Ride WHERE id/status/terms_version = expected`, затем перечитать строку и брони. `expire/refresh` исключает значения из identity-map до модерации. Сравнить `terms_version` с ожидаемой; конфликт — rollback и 409 `ride_terms_changed`, вернуть актуальную безопасную сводку без применения части запроса. Повторить **все** проверки по текущим данным: владелец, active, время, места по участкам, опции/машина, реальные pending/confirmed/onboard, открытые отклики, нынешняя `price` и `stop_prices_json`. После этого до commit нет функции, самостоятельно коммитящей сессию.
4. **Правила остановок/предложений.** Те же нормализованные остановки и цены — no-op 200, в том числе при бронях. При фактической смене остановок живая бронь (включая принятый отклик) — 409 `ride_stops_booked`, из запроса не применяется ничего. Открытые `RequestResponse` из `LIVE_RESPONSE_STATUSES`: без `drop_offers` — 409 `ride_stops_offers_open` с числом и вопросом; с явным подтверждением — закрыть их **в той же транзакции**. Отменённые/завершённые не мешают. Отправка сообщения о закрытии отклика — после успешного commit по устойчивому событию, не из середины проверок.
5. **Цена — полное текущее соглашение.** `stop_prices` относится к новому набору остановок: `None` при изменении маршрута с прежней таблицей — 400 `stop_prices_count`; `[]` явно означает одну цену на весь путь. Валидация — одна функция RS-02Б. При живых бронях маршрут/время и ручное изменение seats_total запрещены. Сохраняется прежний отдельный пересчёт cap от допустимых опций (main rides.py:458–465, RS-02 А9): max занятости каждого участка ≤ новый cap, обещанные удобства сохранены, pure snapshot и один общий CAS. Это не разрешает произвольную правку вместимости; эффективная цена каждого занятого участка только снижается либо остаётся той же относительно **текущего**, уже перечитанного значения. Пересчитать `Booking.price` из цены её участка × числа мест и, если `pay_amount` выше нового итога, уменьшить его; ни одна активная бронь не дорожает. D7: legacy целые рубли, без умножения сохранённых сумм на 100; код этого денежного изменения не начинать до owner gate.
6. **Один атомарный commit.** На основании заново проверенных условий построить новый рейс, суммы броней, закрытие откликов, пересчёт участков чистой функцией `ride_seats.occupancy_snapshot` (без UPDATE/commit/bump) и устойчивые события уведомления. Не вызывать пишущий `recompute` до финального CAS: иначе он сам изменит версию и сделает CAS устаревшим. Последняя запись — CAS `UPDATE Ride ... WHERE id AND status='active' AND terms_version=expected`; применяет весь новый набор и `terms_version=expected+1`. Если сменились остановки — дополнительно проверить отсутствие живых броней; все создатели/отмены/посадка брони и смена машины используют тот же lock/CAS и bump RS-02А. Ноль строк — rollback **всего**, включая цены броней/события, 409. Успех — один commit; no-op не увеличивает версию и не создаёт событие. На PG блокировки и на SQLite writer-lock/CAS сериализуют изменения; частичного успеха нет.
7. **Бронь/отклик.** `bookings.book()` и `ride_seats.take()` сравнивают полную `expected_terms_version` RS-02А, а не только `waypoints`/остатки. После перечитывания изменившийся договор — 409 `ride_terms_changed`, без попытки незаметно пересчитать старую посадку по новым остановкам и без резерва. Принятие отклика проверяет тот же договор; `request_segments.RIDE_FIELDS` дополнить версией и новыми ценовыми/машинными условиями RS-02/14, если эти поля уже влиты. Все писатели используют одну функцию проверки, не альтернативные цены.
8. **Ответ и повтор.** Возвращать актуальные `RideOut.terms_version`, `stop_prices` как объекты `{stop,price}` RS-02Б. Старый запрос с прежней expected-version после известного успеха/потерянного ответа — не новая правка: сначала GET/reconciliation по RS-05; совпавший результат показать, конфликт — запросить новое осознанное действие. Повтор с текущей версией и теми же значениями — no-op 200. Не обещать вечный дедуп произвольного POST без протокола RS-05.
9. **Поиск/карта.** После успешного commit `notify_map_changed`; поиск по остановкам сразу, общая лента ≤20 с кэша. Список changed и события содержат только действительно применённые изменения, rollback ничего не рассылает.
10. **Рассылка — фиксированный владелец RS-10А.** Его API/схема обязательны до RS-15А. В той же доменной транзакции вызвать `enqueue_route_watch(session, ride, source_key="ride-edit:<ride_id>:<terms_version>", group_key=None, siblings=())` (без commit/сети); создаёт `RouteWatchEvent` с UNIQUE `(ride_id,terms_version)`/`source_key`. После commit обработчик вызывает `notify_route_watchers(session,event_id)` RS-10А. Пустой siblings означает правку одного рейса, не повторный поиск братьев серии. Атомарные Notice/claim и антидубль принадлежат RS-10, здесь второй механизм не создавать. При rollback события нет, crash после commit не теряет событие; повтор обработки не даёт второй Notice; push — best-effort после commit Notification, фактическая доставка не обещается. Смена остановки не уведомляет уже уведомлённого по этому ride подписчика повторно, а подходящему новому подписчику отправляет один раз.

## 9. Риски и границы
- Не входит: правка при бронях с согласием пассажиров (позже, отдельной командой), правка начала и конца, правка всей серии.
- API/данные RS-02 (`terms_version`, `stop_prices`, `leg_free`, `take`, `recompute`) — единый договор; менять его можно только согласованной правкой всех зависимых планов/клиентов, не угадывать новые имена.
- Перестановка порядка в `edit_ride` (шаги 2–6) меняет и старые пути (цена, время, места) — их нынешние тесты должны остаться зелёными.

- Legacy без `expected_terms_version` сохраняет доступность API через серверную исходную версию и повторную атомарную проверку. Новые клиенты всегда передают её; их неизвестный результат не превращается в новую правку.
