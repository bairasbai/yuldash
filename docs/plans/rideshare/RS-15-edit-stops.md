## 1. Что получит человек
**Было.** Рустам опубликовал «Сибай → Уфа через Акъяр», а потом решил заехать в Баймак вместо Акъяра. Остановки не исправить —
только снять поездку и опубликовать заново. Пассажиры из Баймака рейс не находят.

**Стало.** В кабинете — «Изменить остановки»: добавить (до четырёх), убрать, переставить и тут же поправить цену до каждой.
Пассажир из Баймака сразу находит рейс, подписчик «появилась поездка» получает одно уведомление. Если кто-то уже забронировал —
честный отказ: «Пассажиры уже выбрали, где садиться. Отмени брони или договорись в чате». Если Айгуль бронирует в ту же секунду,
когда Рустам меняет остановки, побеждает кто-то один — брони «на остановку, которой больше нет» не бывает.

## 3. Что сделать
### Сервер (`backend/`)
1. **Вход:** `RideEditIn.waypoints: Optional[str] = Field(None, max_length=500)`, `drop_offers: bool = False`; цены —
   `RideEditIn.stop_prices` из RS-02 (п. 10 его плана). Ошибки — `herr(status, ru, ba, code=...)` из RS-01.
   **Порядок всей `edit_ride`** (не только остановок): прочитать (`FOR UPDATE` `:386`, живые брони) и запомнить в локальных
   переменных `old_raw`, `seats_left0`, `leg_free0`, цену; затем **все** проверки — время, места, опции мест, цена, остановки,
   предложения — без изменения объектов `ride`/`Booking`, новые значения копятся в словаре; затем модерация комментария и остановок;
   и только потом запись, условный `UPDATE` рейса — последним перед `commit`. Причина: модерация при помеченном тексте делает
   `session.commit()` (`antifraud.py:446-458`) — фиксирует уже изменённое и снимает `FOR UPDATE`; сейчас так цена уходит в базу
   раньше 409 (§2). После модерации прочитанное считать устаревшим — его сверяет только условие `UPDATE`.
2. **Разбор:** `new = _clean_publish_stops(...)` — те же 400, что при публикации; `old = " | ".join(split_raw(old_raw))`. `new == old`
   и цены те же — не правка (клиент шлёт форму целиком), 409 при бронях быть не должно.
3. **Живые брони** — 409 `ride_stops_booked`, `bookings: N`, из запроса не применяется ничего: «На рейс уже есть брони — пассажиры
   выбрали, где садиться. Остановки меняются, пока броней нет: отмени брони или договорись в чате». Принятый отклик — тоже живая бронь;
   отменённые и завершённые не мешают.
4. **Открытые предложения по заявкам** (`RequestResponse.ride_id == ride.id`, статус из `LIVE_RESPONSE_STATUSES`): без `drop_offers` —
   409 `ride_stops_offers_open`, `offers: N` («Ты предложил этот рейс по заявкам (N). Если поменять остановки, предложения
   перестанут действовать. Изменить всё равно?»). С `drop_offers` — после записи `status="closed"` и пуш пассажиру заявки
   (`ref_kind="request"`): «Водитель изменил остановки — его предложение больше не действует. Заявка активна — жди других откликов».
5. **Модерация** (после всех проверок): `moderate_open_text(new, user.id, check_contact=False, place="waypoints", ref_id=ride.id,
   session=session)` и, как сейчас, комментария (`:416`).
6. **Запись без гонки** — последней перед `commit`, одним условным `UPDATE` со всеми новыми значениями:
   `WHERE id = :id AND status = 'active' AND waypoints = :old_raw AND seats_left = :seats_left0 AND leg_free = :leg_free0` и при смене
   остановок ещё `AND NOT EXISTS (живая бронь рейса)` → `waypoints = new`, `stop_prices_json` (RS-02), прочие поля. Изменения цен
   броней (правило цены) — тем же `commit`, до `UPDATE` рейса; 0 строк — `rollback` всего, 409 `ride_changed_retry` («Рейс только что
   изменился — появилась или отменилась бронь. Обнови и попробуй ещё раз»). Поля мест той же строки ловят чужую бронь на PostgreSQL
   (перепроверка строки после блокировки), `NOT EXISTS` и текст — на SQLite (там `FOR UPDATE` пуст). Затем `ride_seats.recompute`
   (RS-02: участки нового набора, броней нет — все места свободны), `changed` += («остановки», <BA — черновик>), `commit`.
7. **Бронь** (`bookings.py`, после RS-02 списание идёт через `ride_seats.take(..., extra_where=[...])` вместо `:610-618`): в `extra_where`
   добавить `Ride.waypoints == ride.waypoints` (остановки, по которым разобраны место и участок). Внутри `take` (`ride_seats.py`,
   RS-02) — параметр `expect_waypoints`: если после перечитывания рейса остановки другие — сразу `False`, без повторов (повтор
   пересчитал бы участок по новым остановкам со старой посадкой). `False` — после `rollback` перечитать рейс: остановки другие —
   409 `ride_stops_changed` («Водитель только что изменил остановки. Открой поездку ещё раз и выбери место»), иначе прежний отказ
   RS-02 `seats_taken_now`. Места и брони не трогаются.
8. **Принятие отклика** уже защищено (`requests.py:1320-1328`) — только тест.
9. **Цены до остановок:** при смене остановок `stop_prices` — для нового набора, проверка `ride_seats.validate_stop_prices` (одна
   функция с публикацией); `None`, а у рейса есть цены остановок, — 400 `stop_prices_count` (старые цены привязаны к старым
   названиям); `[]` — одна цена на весь путь. Правка одних цен — правило RS-02 (п. 10: при бронях только вниз).
10. **Сторожа маршрута — правило дыры между планами:** кто из RS-10 и RS-15 вливается **вторым**, тот добавляет вызов рассылки
    при правке остановок и его тест. RS-15 первым — шаг не делает и пишет в PR «вызов добавит RS-10»; вторым — делает: после `commit`
    `notify_route_watchers(session, ride, siblings=())` (сигнатура RS-10: `siblings: Sequence[Ride] | None = None`), затем
    `session.refresh(ride)`. `siblings=()`: правится один рейс, запасной поиск «братьев» серии (S2 RS-10) не нужен — они ищутся по
    одинаковым остановкам, а у исправленного рейса их больше нет. RS-10 сверяет остановки (S1) и не шлёт повторно по рейсу (S5). Без RS-10 вызов не делать:
    нынешняя функция смотрит только концы и через сутки повторила бы старое оповещение.
11. **Поиск и карта:** поиск по остановкам видит правку сразу; лента без фильтров — через ≤20 с кэша, как после публикации.
12. **Повтор и границы:** тот же запрос второй раз — 200 без уведомлений; права — существующие 403/400; правится один рейс серии.
