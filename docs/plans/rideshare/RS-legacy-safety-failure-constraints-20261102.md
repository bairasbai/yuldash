## GPS: отдельное разрешение в памяти текущего процесса/вкладки

- Пустое при запуске. Ключ: APIorigin, пользователь/сессия, экземпляр процесса/вкладки, canonical rideId, случайный grantId. Хранить признак отзыва; после отзыва тот же grant не оживает.
- Только явное живое действие водителя создаёт pending grant. Исходные deadlineElapsed/deadlineWall задаются **в момент нажатия до сети**; актуальный успешный ответ активирует тот же grant. Отказ, таймаут, повтор/replay/queued status/восстановление снимка не создают новый grant и не сдвигают срок.
- Передавать координаты можно только с активным grant, актуальным владельцем, точным геодоступом и действующим рейсом/бронью. Смена обслуживающей брони внутри рейса сохраняет исходный срок. Последняя бронь/завершение рейса/смена входа/отзыв доступа отзывают соответствующую публикацию.
- Возврат из Settings в **том же процессе без отзыва геодоступа** может возобновить уже разрешённую передачу на остаток срока. Обнаруженный отзыв точного геодоступа окончательно отзывает прежний grant; последующее разрешение ОС само его не возвращает — нужно новое явное действие водителя. Первичная выдача после живого запроса разрешения отличается от отзыва уже выданного доступа; отказ пользователя не превращать в разрешение. Новая сессия, смерть процесса, перезагрузка или холодное восстановление поездки не выдаёт grant. Сервис не должен START_STICKY/redelivery воссоздавать право из старого Intent/prefs.
- Остаток ограничен монотонным временем и исходным wall deadline. Перевод часов вперёд может завершить grant, но обратный перевод не отменяет истечение. Не сохранять «вечное согласие» в preferences и не продлевать срок при смене брони/повороте экрана/ответе сети.

## Офлайн: холодное восстановление требует свежего подтверждения сервера

Одновременный отказ всех локальных записей не оставляет новому процессу надёжного признака, что старый файл уже закрыт. Решение — не вводить второе постоянное хранилище и не объявлять другой способ записи безотказным.

- Общий **process-local authority gate**, пустой при запуске, охватывает snapshot repository, старый TripPass и все пути VM/navigation/draw, способные открыть активную поездку. Ключ: APIorigin + user + durableScope + generation + bookingId; квитанция и активная поездка имеют разные права.
- После холодного запуска локальный ciphertext/TripPass/сохранённая навигация — кандидат, а не разрешение на активный экран. Нужен новый авторизованный `/role` или `/details` для captured owner/request epoch; старые in-flight ответы, offline fallback, WS-кэш и durable markers не дают такое право.
- `/role` разрешает только свою проверенную live-проекцию. Посадочный код и RS03-точные места раскрываются лишь из **свежего `/details` соответствующего участника и разрешённой фазы**; не разблокировать весь старый private blob одним ответом `/role`. При terminal/403/401/битом контракте право не выдаётся.
- Отсутствие сети после холодного запуска: понятное RU/BA состояние с повтором; прежний файл не превращается в активную поездку, код/чужие точные места и GPS не показываются/не запускаются. **Цена решения:** восстановление активной поездки после перезапуска требует сети; ранее подтверждённый в этом процессе тёплый офлайн-путь сохраняется в пределах его срока/владельца.
- Принятая сервером отмена/завершение сначала закрывает память/epoch, затем выполняет доступную дисковую очистку. Отказ диска не блокирует нужную человеку серверную отмену и не превращается в сообщение об успешном сохранении. Late write/GET с прежним ticket не снимает memory tombstone. После перезапуска свежий серверный terminal снова отклоняет старый файл.
- NOT_DURABLE и DURABLY_BLOCKED остаются различимы. Первый не обещает дисковую сохранность; безопасность холодного пути обеспечивается обязательным gate. Второй подтверждает записанный запрет. Ошибку записи не подменять успехом/новым атомарным store.
- Свежая `/trips/{id}/receipt` даёт только history authority для своей квитанции и текущую безопасную проекцию. Она не активирует поездку, посадочный код или публикацию GPS. Поздняя запись live-снимка после квитанции не возвращает live authority.

## Обязательные новые реальные проверки

1. GPS Android/PWA: восстановление activeTrip с уже выданным OSpermission не стартует передачу; явное действие запускает, повтор ответа и queued action не создают/не продлевают grant. Два booking одного рейса → закрытие одного → продолжение с исходным сроком → последняя/рейс terminal → stop. Смена входа/APIorigin, Settings grant/revoke, поворот, процесс/страница/reboot, часы вперёд/назад, просроченный ответ и потеря сети. Отдельно: действующий grant → отзыв точного доступа → повторная выдача ОС без нового действия — нет подписки/сокета/кадров; новое явное действие может создать только новый grant.
2. Офлайн: payload fail/barrier fail/оба fail/clear-protection fail. Для каждого — закрытие, late write/GET, новый repository и настоящий новый process-authority context, смена пользователя/origin и перезапуск. Холодный сетевой отказ не открывает active UI и не раскрывает код/private поля. Свежий terminal/403 тоже; свежий active details открывает только актуальные разрешённые данные. Отдельно: свежий успешный role + старый приватный паспорт + ошибка details — код и точные места остаются скрыты.
3. Собственная квитанция повторно открывается через history-путь без live authority; чужая/закрытая поездка не оживает из receipt/TripPass/navigation. Прямые unit-проверки repo дополняются tests реальной проводки всех restore-выходов.
4. Сохраняются все тесты согласия/микросекунд/late responses из блока2 и RS01–03/D7. Если прежний R-тест ожидает небезопасный cold load, сохранить его как воспроизведение ограничения R, новый продуктовый тест требует отказа до fresh authority. Не ослаблять действующие защитные проверки и не подменять тесты реализации grep-assert.
5. Затем сборки/сторожа, реальный Android/PWA UI в двух темах/языках, узкий/крупный текст, свежая независимая приёмка. Без этого перенос не принят. Реальные телефоны и человеческая BA-проверка остаются отложенными по решению Александра.
