## Тест перед продуктом

После сохранённого полного прогона один автор получает один новый тестовый файл и, только если нужно, минимальный существующий fixture. Два управляемых actualHTTP/Compose случая через настоящие родительские входы: бронь с редактором встречи; завершённая поездка с выданной HISTORY. Положительный контроль должен подтвердить рабочее действие/HTTP и доступный редактор/оценку. Для ОБЕИХ цепочек провести независимые случаи: только смена экрана; только смена брони; только смена поездки; только privateNavigationRevision; отдельно pendingBookingNavigation; отдельно pendingScreenNavigation; отдельно pendingPublicRideNavigation. В каждом случае удержать настоящее действие и вызвать его в том же кадре до disposal, после единственного выбранного изменения. Нельзя одним изменением одновременно закрыть другие условия и объявить их проверенными. Отдельный случай для обеих цепочек: начать настоящий запрос, удержать ответ, изменить родителя и отпустить ответ — поздняя публикация запрещена. Положительные контроли рабочего действия и другого текущего окна сохранить в обеих цепочках. Требовать отсутствие дополнительного POST/Intent, запрет позднего результата и отсутствие частных данных из старого экрана. Сам общий gate остаётся действующим для другого ещё текущего окна; глобальный revoke при уходе отдельного экрана запрещён. Исходные owner/session/disposal/route проверки повторить. Не менять ожидания для получения GREEN; UI15с сохраняются.

## Минимальный продукт после свежей проверки плана и настоящего RED

- BookingScreen получает parent predicate от единственного рабочего вызова YuldashApp. Он проверяет экран Booking, бронь/поездку, owner/session, захваченную privateNavigationRevision и отсутствие всех трёх pending-navigation. Передать его в PassengerMeetingPoints. Использовать перед HTTP, в запускаемой coroutine и перед публикацией результата, сохранив fresh DETAILS и собственный scope.
- Защитить parent-предикатом не только editor, но и отрисовку/semantics всей частной области брони (телефон и точные места). Текущая BookingScreen552/696 сохраняет эти данные за fresh DETAILS без parent; передача одного callback в picker этого не закрывает. Использовать существующую границу TripAuthorityContent/tripAuthorityDraw либо равно узкую проверяемую границу, сохранив публичную часть экрана.
- Привязать выдачу rawDetails/rawReceipt и coroutine scope к исходному контексту отображения: owner/session/booking/ride/privateNavigationRevision. Новый parent predicate при перекомпозиции не узаконивает старые данные remember(bookingId). При смене этого контекста старые частные данные/ответы недоступны; новый контекст получает нужное свежее подтверждение. Допустим узкий key/идентификатор контекста на существующем caller; нормальные обновления той же поездки не должны без причины уничтожать черновик. Независимые ride-only/revision-only случаи обязаны запрещать старые phone/point/history-marker и позднюю публикацию, а не только лишний POST.
- Completed получает isCurrentParent от ::isTripSessionCurrent активного экрана; не от isTripDetailsCurrent, который намеренно запрещает done. Передать до CompletedSession и включить в общий isCurrent, чтобы retained actions и поздние ответы использовали один предикат. HISTORY и его fingerprint/current instance остаются обязательными отдельно; новый parent не выдаёт права истории или LIVE/private.
- Для standalone unit/preview допустим совместимый необязательный параметр, только если source-guard доказывает, что каждый production caller передаёт predicate явно. Не превращать отсутствие текущего родителя рабочего приложения в разрешение.
- Нет новых надписей/денежных действий/изменений бизнес-ответов, версий или зависимостей. Не менять тарифы, цену, оплату или backend. Ветка, без main/push/prod.

Если требуемые параметры переполняют текущий Screen3541, сделать один точный перенос уже затронутой связанной секции в маленький тематический файл; не уплотнять код искусственно, не переписывать экран и не переносить постороннее. Для чека проверять booking_id и соответствие выбранной ride ДО публикации и при использовании. ## Приёмка

Уточнение отрицательных фаз после actual source29 DIAG: lifetime owner/session получают новый actual DETAILS (1→2/newref/fresh), а публичный loader снимает синтетический pending после GET/rides/34 без новой revision. Поэтому одинаковый текст после окончания фазы не доказывает старую выдачу. Разрешено только разделение времени: удержать новое подтверждение A после положительной подготовки lifetime; в независимом pending-only удержать точный GET/rides/34 и отдельно проверить, что pending ещё есть перед приватным assert. Все исходные проверки действий/данных/15с/B сохраняются, барьеры освобождаются finally/@After. Основной код для этих трёх случаев не менять без нового доказанного дефекта.

Существующие загрузка/ошибка/Retry/Back и помощь сохраняются, тексты/деньги/HTTP не меняются. Это не ослабление исходного теста25; нормальный exact-stub26 и окно B обязательны.
