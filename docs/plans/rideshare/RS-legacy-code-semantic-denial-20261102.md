Source57/887, blank-code-ordering-red01: четыре настоящих транспортных случая, два FAIL на закрытии LIVE/private после blank CODE при новом ROLE либо DETAILS с тем же полным private fingerprint. Причина контролируемого отказа: generic failedRead пропускает ошибку при более новом опубликованном ROLE/DETAILS.

## Узкое изменение

Отдельный путь Hooks → OfflineTripSnapshots → Gate для подтверждённого успешного ответа CODE со строкой blank. Обычные сетевые ошибки, отмена и общий failedRead сохраняют прежние правила порядка. Под lock проверить текущие owner/session/booking/TTL/эпоху, исходное состояние и тот же полный приватный fingerprint. Только этот подтверждённый семантический отказ может игнорировать превосходство более нового ROLE/DETAILS той же проекции; выполнить существующий мягкий expire с увеличением эпохи, сохранив HISTORY и долговременные байты.

Старый отказ не может отменить более новый успешно принятый CODE. Последний CODE нельзя надёжно отличить по общему read kind: сейчас он использует DETAILS; после следующего DETAILS текущий permit уже не хранит историю CODE. Предложен один RAM-счётчик lastSuccessfulCodeSequence в существующем Entry, без новой карты/журнала/дисковой схемы. Обновлять только после действительно принятого непустого CODE (пассажир/водитель согласно их отдельным проверкам). Сохранять при совместимом обновлении ROLE/DETAILS, проверять до применения старого blank. Контрпример одинакового значения CODE обязателен: сравнения строки или текущего permit недостаточно. Точную минимальность счётчика и guards сверяет свежий независимый план-ревьюер.

## Границы и доказательства

Не запрещать свежий DETAILS после отказа вообще. Не выдавать LIVE/private из старого диска, не продлевать сроки, не ослаблять владельца/сеанс/бронь/эпоху/смену приватных данных. Не использовать семантический путь для обычной IOException. При изменившемся private контексте и более новом CODE старый ответ игнорируется. Отдельно проверить, какие существующие проверки покрывают прочие статусы HTTP; не расширять их трактовку без фактического основания.

До MAIN добавить/сверить настоящие негативные контроли: более новый CODE с тем же значением; CODE-success → DETAILS с возвратом того же полного fingerprint; смена fingerprint/состояния/owner/session; отдельная бронь12. Старые driver-positive сами по себе эти проверки не заменяют. Никакой подмены authority после подготовки или дополнительных запросов в observer. Тот же исходный Blank12s/UI/no-private/durable запрет сохраняется.
