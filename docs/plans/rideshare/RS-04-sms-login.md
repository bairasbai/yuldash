## 1. Что получит человек
- **Было → стало.** Тётя Гульназ из Акъяра не пользуется Telegram — войти ей нечем. Станет: первым на экране входа — «Номер телефона»; пришла СМС — телефон сам подставил код. Не пришла — через минуту «Отправить ещё раз» или «Прислать в WhatsApp». Telegram и VK — ниже.
- **Один человек — один аккаунт.** Рустам вчера входил через Telegram, сегодня по СМС с тем же номером — тот же аккаунт с поездками и отзывами.
- **Выключатели у Александра.** Экран «Выключатели»: СМС, Telegram, VK, WhatsApp. Без договора с sms.ru СМС не включить — переключатель серый и говорит, чего не хватает; перед выключением СМС — сколько людей не смогут войти. Выключенное люди не видят; видно, кто и когда переключал.
- **Защита.** Код не подобрать, номер не завалить СМС, админом по СМС не войти.

## 3. Что сделать
### Сервер (`backend/`)
**А1. Выключатели владельца (D1).**
1. `owner_switches.py` — реестр: значения, умолчание (прод / вне прода), блокеры, правило группы. Ключи `login.sms|telegram|vk|whatsapp` (RS-08 добавит `rideshare_card_payments`). Умолчания: `telegram` — вкл.; `sms` — выкл. на проде, **вкл. вне прода** (17 тестов через `request-code`); `vk`, `whatsapp` — выкл.
2. `appsetting` (`key` PK, `value`, `updated_at`, `updated_by` nullable SET NULL) и `appsettingchange` (`key`, `old_value`, `new_value`, `admin_id` nullable SET NULL, `created_at`, `note`); строки ключей — из миграции, начальное значение — `NULL` = «по умолчанию из реестра».
3. Блокеры — имена недостающих переменных: `SMS_PROVIDER=smsru` + `SMS_RU_API_ID` (или smsdar); `TELEGRAM_BOT_TOKEN` + `TELEGRAM_WEBHOOK_SECRET`; `VK_ID_CLIENT_ID`, `VK_ID_REDIRECT_URIS`; `WHATSAPP_PROVIDER` + ключи.
4. Группа `login.*`: нельзя выключить последний действующий способ (`switch_last_login_method`) и `login.telegram` (вход админа, А2 п. 8); выключение `sms`, когда у `N > 0` аккаунтов не останется способа (нет `telegram_id`, `vk_id`, WhatsApp выкл.), — только с `confirm: true`, иначе 409 `switch_needs_confirm` + `affected`.
5. Запись — `SELECT … FOR UPDATE` по ключам группы в порядке ключей; то же значение — 200 без строки; иначе `appsettingchange` + `admin_action`. Чтение: `owner_switches.get(key, fresh=False)` — с кешем ≤ 10 с; при `fresh=True` — прямо из базы (нужно RS-08 для денег).
6. `routers/admin_switches.py`: до А2 все серверные GET/POST выключателей fail-closed 403 `admin_auth_upgrade_required` (никакой выдачи журнала/смены значений по старой role=admin); после А2 только `require_telegram_admin` по проверенной сессии (исключение — выключение `rideshare_card_payments`, RS-08: любой `role=admin`): `GET /admin/switches`, `POST /admin/switches/{key}` `{value, confirm?, note?}` → `{stored, effective, blockers, updated_at, updated_by_name, history[50]}`.
7. `available_methods()` (RS-01) = `login.*` с `effective`; видно людям ≤ 40 с.

**А2. СМС, один аккаунт, роль админа.**
1. Номер — только `+79\d{9}`, иначе 422 `phone_not_supported` (иностранные платные номера разоряют счёт).
2. Строки выдачи живут ≥ 24 ч: уборку `OtpCode`/`TgAuth` из вебхука (`auth.py:690-705`) убрать, остаётся ночная (`cleanup.py:152`).
3. **Атомарный бюджет до провайдера (B7).** Лимиты всех каналов вместе: номер раз в 60 с, ≤5/час и ≤10/сутки; IP ≤40/час; устройство (`X-Device-Id` обеих платформ) ≤5/час; сервис `SMS_DAILY_CAP`/UTC-сутки (300). Одного замка номера недостаточно: `OtpBudgetBucket` хранит scope (`service_day|ip_hour|device_hour|phone_hour|phone_day|phone_cooldown`), HMAC-subject, начало окна, used, cap, version, updated_at, next_allowed_at с unique(scope,subject,window) (для phone_cooldown окно=0, условие next_allowed_at≤now, запись now+60с; остальные лимиты по именованным UTC-окнам); `OtpSendAttempt` хранит id UUID, provider_idempotency_key, state `reserved|sent|failed|unknown`, резервированные bucket keys, created_at. В короткой транзакции сначала взять группу login.* в том же порядке, что переключатель А1, и прочитать effective нужного канала АВТОРИТЕТНО без кеша; выключен — резерва/вызова провайдера нет. Затем создать отсутствующие buckets безопасным upsert, взять ВСЕ их замки в одинаковом порядке scope/subject/window и условно увеличить used, только если каждому хватает. SQLite — условные UPDATE/CAS и rollback всей транзакции при любом проигрыше. Нехватка — rollback всех резервов, 429 `otp_rate_limited` + retry_after_sec либо 503 `sms_daily_cap`. Пределы сервиса/IP/device не опираются на отдельные phone-locks.
   Commit резерва ДО вызова провайдера — точка допуска отправки. Выключение login.sms не допускает новых резервов после своего commit; уже допущенные попытки могут завершить отправку (их число показывается владельцу), не выдавать это за отзыв провайдеру уже отправленного запроса. По одному attempt только одна отправка, provider idempotency key передаётся, если поддерживается; потерянный исход не повторяет платную отправку автоматически. HMAC-код с attempt_id сохраняется вместе с резервом (открытый код только в памяти адаптера); пока reserved, verify его не принимает. Успех фиксирует sent, timeout — unknown; для sent/unknown введённый пользователем совпавший код можно проверить до expires_at, для failed код погашается. Так реально доставленный при потерянном provider-response код не становится бесполезным. Код не отправлять заново по тому же attempt. Доказанный отказ до принятия провайдером → failed и идемпотентный возврат резерва суточного денежного bucket (однократный CAS состояния); phone/IP/device anti-abuse попытка остаётся учтённой. Timeout/неизвестный исход → unknown, денежный резерв остаётся; сверка статуса провайдера переводит в sent/failed, только доказанный отказ возвращает деньги в бюджет. Нет status/idempotency у провайдера — unknown считается расходом до окончания суток. Код и номер не кладутся в ledger. `OtpBudgetAlert` с unique(service_day,kind) атомарно забирает право одного внутреннего уведомления о cap; запись состояния и резерв в одной транзакции. Пуш дежурному — после commit, ровно одно намерение, без платной СМС и без номера.
4. `OtpCode` + `channel`, `ip_hash`, `device_hash` (HMAC с секретом сервера); `OtpCode.code`, `TgAuth.code` — HMAC, сверка `compare_digest` (живые коды при выкладке пропадут — допустимо).
5. Ответ один для любого номера: `{"sent": true, "resend_after_sec": 60, "expires_in_sec": 300}`; тело — `{phone, lang, channel}`. СМС — на языке экрана, ≤ 70 знаков, последней строкой `@app.yulbash.ru #<код>`.
6. Журнал: код/verifier — никогда, во всех средах; номер — только mask_phone. Ошибка провайдера содержит безопасный код причины без его request/response body.
7. `send_text` — отдельный `SMS_NOTIFY_ENABLED` (по умолчанию `false`), им же `sms_will_reach`: вход по СМС молча не включает СМС SOS и уведомлений (Q2, Q11).
8. **Роль и сессии админа (D8/B2).** СМС/VK/WhatsApp → `_complete_login(promote_admin=False)`; уже admin так не входит — 403 `admin_login_telegram_only` только после успешной сверки/погашения кода. request-code одинаков для любого номера. Повышение — только проверенным Telegram владельца (`admin_telegram_chat_id`) либо ADMIN_PHONES из Telegram-контакта с `contact.user_id==from.id`.
   Сервер сохраняет `User.auth_epoch: BIGINT=0`, `RefreshToken.auth_method=legacy|sms|telegram|vk|whatsapp`, `auth_time`, `auth_epoch`; JWT содержит подписанные `amr`, `auth_time`, `auth_epoch`. Клиент их не задаёт. Центральные current_user/current_user_optional и WS identity не допускают admin-личность с amr!=telegram к привилегированной обработке; отсутствие/слабый метод fail-closed, optional-auth не превращает её в привилегированный User. Дополнительно `require_telegram_admin` на КАЖДОЙ привилегированной двери (админка, switches и будущие денежные команды) требует текущую роль admin И amr=telegram, иначе 403 `telegram_step_up_required`; роль User сама не доказывает способ входа. Найти все role/admin-проверки, optional-auth и WebSocket-входы, чтобы обходной путь не возвращал привилегии.
   При Telegram-повышении под существующим `lock_refresh_user` (User→RefreshToken) в ОДНОЙ транзакции: записать роль, атомарно увеличить User.auth_epoch, сдвинуть tokens_valid_from, отозвать ВСЕ старые refresh и выдать новую Telegram-пару с новым epoch строго после границы. Проверка access и refresh/recovery требует token epoch==User.auth_epoch; отсутствие epoch трактуется как0, без повышения до актуального из роли. Это закрывает старые пары даже в ту же секунду/при округлении JWT iat; новая пара не отзывает себя. Существующее make_token(issued_after) сохраняет дробный iat>cutoff, но отзыв при повышении опирается на целый epoch, не на точность часов. Старый SMS access отсекается `_token_revoked` в REST/optional/WS, старый refresh/recovery-child не выпускает новую пару. Ротация/восстановление переносят auth_method/auth_time/auth_epoch из серверной строки, сверяют epoch владельца и не обновляют время и не усиливают метод из актуальной роли. Порядок блокировок совпадает с logout/refresh; гонка refresh↔promotion либо выдаёт пару до границы, которая тут же отзывается, либо отклоняет старый refresh. Уже выданный Telegram access/refresh новой сессии работает. Это закрывает сессию, полученную ДО повышения, а не только новый вход.

Остальные прежние refresh — legacy, старый JWT без amr не получает админских прав; после повышения все прежние пары отозваны. Историческим auth_time не придумывать свежую проверку: NULL требует новый вход перед сменой номера. Существующим OTP перевод в HMAC не угадывать: удалить/истечь их по согласованному deployment gate, нужен новый код.
- **Сроки:** budget buckets и alert — 48ч после конца окна; phone_cooldown с window=0 — 48ч после updated_at, не от 1970г.; attempts — 30 дней (минимальные псевдонимные метаданные без номера/кода); unknown до сверки/конца суток остаётся зарезервированным, уборка не возвращает расход. Новые таблицы в cleanup/account policy; попытки с user_id удалять при удалении аккаунта, агрегаты без user_id истекают по сроку. Проверить previous-main schema со старыми User/RefreshToken/OTP → target и оговорённый downgrade/upgrade на SQLite/PostgreSQL; rollback не восстанавливает отозванные токены/коды и требует повторного входа. **Ждёт «да»** на применение/политику данных, платную отправку не выполнять тестом.
