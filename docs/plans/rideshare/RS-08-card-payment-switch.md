## 1. Что получит человек
За попутку по-прежнему платят водителю напрямую. В админке видна подготовка будущего выключателя и причины недоступности. Договор, ключи провайдера, выплаты и желание водителя по отдельности либо все вместе не открывают списание: нужен отдельный реализованный и независимо принятый банковский проект и явное решение владельца.

В этом плане выключатель нельзя включить. Пассажир не получает кнопку «Картой», водитель не получает обещание принять карту. Сохранённый выбор не становится оплатой, а запись журнала не становится банковской приёмкой.

## 2. Что уже есть в коде
- `backend/app/payments.py:1-5` — ЮKassa для собственных услуг, проезд мимо приложения. `:25-36` общие gates; при живом провайдере `:102-121` выполняется HTTP с `capture: true`.
- `backend/app/routers/wallet.py:76` `_pay_cashless`, `:180-188` создаёт и коммитит Payment, затем вызывает провайдера; `:258-286` публичная оплата завершённой брони сейчас до hard lock RS-01 доходит до этого пути. Это будущая граница, не безопасный mock по умолчанию.
- `config.py:198-202` — `payments_provider`, выплаты; `:365` ключи, `:1152` предупреждения. Ни одна настройка не доказывает приёмку банка; существующие `.env` и секреты не читать и не менять.
- `/config/features`, `OnlinePayGate`, `ApiClient.kt:2766` и `PayTripCard.tsx` — общие существующие механизмы. Убрать оплату брони и поставить hard lock должен RS-01 Г **до** RS-08. Такси/Boost не затрагиваются.
- Общий реестр, таблицы `appsetting`, `appsettingchange` и экран «Выключатели» вводит RS-04 А1, assurance и защита старых сессий — А2. `DriverPaySettings` вводит RS-07 Б; на указанном main их ещё нет.

## 3. Что сделать
### Сервер — `[RS-08А]`
1. В `card_payments.py` задать **неустранимый в этом проекте** блокер `bank_project_unaccepted`. Он не читается из пользовательского флага, env, настроек БД или флага `bank_contract`: константный результат каркаса. Другие причины (нет договора/провайдера/выплат) могут выводиться как сведения, но их устранение не убирает этот блокер. Никакого изменяемого `bank_project_accepted=true` в этом плане.
2. Добавить в общий реестр `owner_switches` ключ `rideshare_card_payments`, default `off`. Попытка `on` → 409 `bank_project_unaccepted`, значение/журнал успешных изменений не меняются; `off` допустим идемпотентно. Выключить (`off`) может любой администратор (`role=admin`) из любой своей действующей сессии, в том числе вошедший по СМС/VK/WhatsApp: это безопасное направление, оно только закрывает оплату (решение Александра 24.10). Такой сессии видны состояние ключа и кнопка «Выключить»; журнал и остальные выключатели — по D8 (`require_telegram_admin`). Включить сейчас нельзя никому (409); право включать определит банковский этап, не ниже D8. Не-админ и отозванная сессия — 403/401 до чтения журнала и изменения значения; `ADMIN_PHONES` права не расширяет.
3. Единый ответ админки: `{stored, effective:false, blockers:[{code,ru,ba}], updated_at, updated_by_name, history[50]}`. Даже ошибочно сохранённый/старый `stored=on` даёт `effective=false`. Диагностическое состояние можно кешировать для интерфейса, оно никогда не разрешает действие.
4. Для сохранения будущего API добавить `DriverPaySettings.accepts_card: bool = false`, `accepts_card_at: datetime|null`. GET отдаёт `card_switch_on:false`, `accepts_card:false`, `card_blockers`. PUT `accepts_card:true` → 409 `bank_project_unaccepted`; `false` всегда допускается своему водителю. Наличие этой строки не является согласием на банк. `RideOut`, `BookingDetailsOut`, квитанция: `card_payment:false` во всех случаях, вычисляет сервер, только явное поле DTO (D9).
5. **Hard lock RS-01 Г не менять.** Публичный `POST /bookings/{id}/pay` для `card`/`sbp` после проверки прав всегда возвращает 503 с прежним кодом RS-01 **до paid-replay, Payment, `_pay_cashless` и любого вызова провайдера**. `booking_cashless_allowed` остаётся `False`. Даже все пользовательские флаги true, `stored=on`, `accepts_card=true` и настроенный живой провайдер не меняют результата. Наличные и прямая договорённость — прежний путь, без новых реальных списаний.
6. **Точка выключения и гонка.** Запись `off` блокирует строку `appsetting` в транзакции, фиксируется вместе с журналом; commit — авторитетная точка линеаризации (момент, после которого сервер считает off сохранённым). Будущий разрешающий код не может читать кеш: чтение/проверка денежного gate и создание Payment должны сериализоваться с этой строкой до сетевого эффекта. В **текущем** каркасе любой concurrent pay до/после commit отвергается hard lock, поэтому к гонке off↔pay не добавляется разрешённой ветви. Не обещать, что будущий off отменяет уже начатый банк: политику незавершённых платежей/вебхуков определит отдельный проект. Исход настройки неизвестен → перечитать stored/history, не утверждать сохранение.
7. Сохранить отрицательные endpoint-тесты RS-01 Г (8 исходных файлов: `test_booking_payment_agreement_amount.py`, `test_pay_agreement_payment_concurrency.py`, `test_pay_agreement_only_driver_lowers.py`, `test_audit_fix_be35.py`, `test_pay_agreement_after_charge.py`, `test_ledger.py`, `test_audit_fix_be06_retries.py`, `test_promises.py`). **Не** вводить endpoint-фикстуру `cashless_on`/`card_on`, подменяющую hard lock на true. Изолированные тесты нижних helper могут использовать локального fake provider без HTTP; они не принимают публичную оплату.

### PWA — `[RS-08Б]`
1. На общем экране «Выключатели» — строка каркаса, выключенное/заблокированное состояние, причины, история, повтор загрузки. Попытка включить прямым API запрещена сервером, скрытая кнопка не защита.
2. В кабинете водителя можно показать «Оплата картой пока недоступна» с причинами; активный переключатель не показывать. `card_payment` разбирается только как серверная информация, в этом пакете всегда false.
3. Не возвращать кнопки `card`/`sbp` для `kind=booking`, не вводить действующий `cardAllowed`, не ослаблять `honest-promises-test.mjs`, не показывать «Картой после поездки». Старый сервер без поля = false.

### Android — `[RS-08В]`
1. Та же строка каркаса на экране «Выключатели» RS-04: `Canon*`, доступность ≥48dp, `AnimatedContent`, все загрузка/ошибка/пустой журнал/причины. Нового Screen нет.
2. Информация в кабинете водителя совпадает с PWA. `cardPayment` в DTO по умолчанию false; оно не возвращает `PayOnlineCard` в `BookingActiveTripScreen.kt` или `RideshareCompletedScreen.kt`. Сторож RS-01 продолжает запрещать эти вызовы, поимённых исключений нет. `OnlinePayGate` такси не менять.

## 4. База данных
- Миграция `card_switch_<дата>` после RS-04 А1/А2 и RS-07 Б: строка ключа `appsetting` со значением off (или NULL = default off по общему реестру), в `driverpaysettings` — `accepts_card` server_default false, `accepts_card_at` nullable. Данные сумм, Payment, ledger не мигрировать.
- Одна голова. previous-main schema + синтетические старые строки → upgrade сохраняет способы оплаты, суммы и false; down → up на SQLite/PostgreSQL. `downgrade` удаляет только ключ/новые поля; журнал остаётся историей по правилам RS-04. Откат каркаса не снимает hard lock RS-01.
- Таблиц новых нет. Поля DriverPaySettings удаляются с аккаунтом по RS-07; журнал настроек — retention RS-04, admin_id при удалении SET NULL. Сверить `cleanup.py`/`account.py`, не дублировать уже выполненную работу. Миграции guards/retention/account tests обязательны до реализации. Production не использовать.

- «Выключить подготовленный режим?»; «Оплата картой останется недоступной». Неизвестный итог настройки: «Не удалось подтвердить сохранение. Обнови состояние».
- Отказ платежа — существующий текст RS-01. Строк о завершившихся/зачисленных банковских деньгах нет.

## 6. Состояния экрана
Загрузка, ошибка/нет сети с «Повторить», пустой журнал, постоянный блокер каркаса. Длинный BA, 320dp, шрифт 200%, тёмная тема. Кеш/потеря сети не превращают false в true. На пассажирских экранах по-прежнему только прямая договорённость.

## 7. Тесты
Все сценарии — **NOT_EXECUTED**, пока действительно не запущены. Никакой сетевой банковской операции в тестах этого плана.
- Сервер: default off; попытка on →409 без журнала успешного изменения; off сохраняется с журналом; seeded stored=on, все пользовательские флаги/признаки провайдера true, accepts_card=true → `effective=false`, `card_payment=false`, `/pay card` и `/pay sbp` →503, **0 новых Payment, 0 `_pay_cashless`, 0 provider calls**. Повтор paid-брони не выдаёт ложный успешный cashless-replay. `cash` — регрессия прежнего поведения.
- Две PostgreSQL-сессии с барьером: off↔pay, до/после commit off, устаревший кеш on → только503 и ноль Payment/сети. Проверить атомарность off+journal, rollback ошибки. SQLite — сопоставимая транзакционная проверка.
- Любой администратор — и Telegram-, и СМС/VK/WhatsApp-сессия — выключает: 200, одна строка журнала, повтор — no-op; не-админ и отозванная сессия →403/401 без изменения и без журнала; включение любой сессией →409; СМС-сессия админа не видит журнал и не меняет другие ключи (403). `accepts_card:true` →409; false допускается; все поля карточной доступности false.
- PWA/Android: постоянные причины/история/повтор, нет карточной кнопки пассажира при любом поддельном DTO; сторожа RS-01 без исключений. `card-switch-test.mjs`, Compose-тест раздела, endpoint contract tests, все затронутые guards; при реализации — `ruff`, `pytest`, Android assemble/guards, PWA check/build.
- Мутации: удалить hard lock, разрешить по любому mutable flag, довериться кешу или вернуть PayOnlineCard → соответствующий отрицательный тест красен.

## 8. Приёмка
Независимый агент, по умолчанию не принято; принятие каркаса не принимает банк.
- [ ] Все флаги true/старое stored on не включают карту:503, 0 Payment, 0 provider calls; direct API, replay и гонка off↔pay проверены.
- [ ] Отключение фиксируется авторитетно с журналом; выключить может любой администратор из любой сессии, включить — никто, пока нет банковского этапа. Не-админ и отозванная сессия не проходят.
- [ ] Каркас не меняет тело hard lock на разрешающее, не использует разрешающие endpoint-фикстуры, не ослабляет сторожа RS-01 и не возвращает карту в попутку Android/PWA.
- [ ] Миграция проверена на старой схеме и синтетических строках, линейная голова, retention и удаление аккаунта согласованы.
- [ ] Diff без реальных списаний, возвратов, выплат, вебхука, такси/Boost, новых SDK, секретов/конфига production; все тексты RU/BA, состояния и доступность проверены.
- [ ] Выкладка/слияние и любой будущий банковский запуск требуют отдельных разрешений. Реальная оплата, два телефона, носитель BA и выпуск не объявлены проверенными.

## 9. Риски и границы
Вне scope: договор/банк, реальные платежи, чеки, комиссия, возвраты/споры, выплаты, сверка и вебхуки, включение production. Денежные суммы не пересчитываются, D7 остаётся owner gate. Наличие кода старого `_pay_cashless` или ключей не делает этот путь принятым. Отдельный банковский проект должен заново определить единую границу проверки разрешения/Payment/provider, момент выключения и судьбу уже начатых платежей; заменить hard lock можно только там после его независимой приёмки и решения владельца.

Мозг при реализации: `decisions.md` — постоянный блокер каркаса и «выключить может любой администратор», без утверждения банковского разрешения; `tasks.md` — BA-черновики; `architecture.md` — строка каркаса у существующих «Выключателей».
