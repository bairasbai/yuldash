## 1. Что получит человек
Рамиль возит Сибай → Акъяр через Ургазу. Утром отвёз, вечером едет домой. Раньше обратную поездку набирали заново: оба села, остановки задом наперёд. Теперь есть кнопка «Обратно»: форма открывается с Акъяром в начале, Сибаем в конце, Ургазой посередине. Время, место встречи и комментарий не переносятся (они про ту поездку) — так и написано.

Кто ездит по пн, ср и пт, отмечает дни в календаре — всё публикуется сразу. Если у дня время прошло: «Опубликовано 2 из 3» и причина по третьей. Само ничего не бронируется; повтор с сохранённым намерением RS-05 возвращает тот же результат. Неизвестный исход сначала сверяется, срок таймера не означает новую публикацию.

## 3. Что сделать
### Часть А — «Обратно»
**Сервер.** **А-S1.** `GET /rides/{ride_id}/return-template` — только владелец (чужая → `herr(403, "Это не твоя поездка", "Был һинең сәфәрең түгел", code="not_owner")`), ничего не пишет. `RideTemplateOut`: `from_city`/`to_city` переставлены, `waypoints` задом наперёд, `category` hospital/parcel/cargo → `regular`; места, цена, удобства (в т.ч. `only_trusted`, `women_only`), после RS-14 `car_id`. Не берутся: `depart_at`, `pickup*`, `comment`, `receiver_name`, `parcel_size`, `partner_id`, `recurrence`. Плюс `dropped`, `suggested_date`. **Денежная часть — после RS-02 Б (рубли, D7):** входные накопленные цены `stop_prices: list[int]` разворачиваются как `[price − p for p in reversed(stop_prices)]` (Ургаза 300 из 500 → 200 из 500); в ответе шаблона использовать именно входной shape RS-02, не объекты `RideOut.stop_prices`. Денежный шаблон вливается после «да» (D7).

**Сайт.** `fetchReturnTemplate` (`api/driver.ts`), `utils/rideTemplate.ts`. «Обратно» в `DriverCabinetScreen.tsx:486` и в архиве (`:591`) → `navigate("/create-ride", {state:{template}})`. `CreateRideScreen.tsx`: брать `location.state.template`; **до первого рендера** `clearDraft(RIDE_DRAFT)` (иначе `:133-150` вернёт черновик поверх); потом `navigate(path, {replace:true, state:null})` — F5 не применит повторно; заметка «Не перенесли: …». На экране «опубликовано» (`:259`) — «Опубликовать обратно» (шаблон по `createdId`).

**Android.** `data/RideSeriesApi.kt` `getReturnTemplate(id)` (образец — `RouteWatchApi.kt`), `RideTemplate.kt`. Кнопка «Обратно» (`SwapHoriz`, ≥ 48dp, `contentDescription` RU+BA) в карточке (`ProfileScreen.kt:3143`) и на `ArchiveRideCard` (`:3417`) → шаблон → форма; ошибка — «Повторить». `YuldashApp.kt`: состояние `createRideTemplateJson` (saver как `:415`), `:1305`, `:1579`. `CreateRideScreen.kt`: параметр `template`; дата пустая, пикер на `suggested_date`. ### Часть Б — «Несколько дат»
**Сервер.**
1. **Б-S1 (раздел).** `create_ride` делится без смены поведения: `_prepare_publish(body, user, session)` — один раз на пачку (`ensure_active`, `guard_delivery_ride`, `guard_women_only_publish`, зажимы, города, модерация ×3, остановки, клиника, `geocode_city`, точка сбора); `_check_depart(depart_at)` — `herr(400, <тот же текст>, code="time_passed")`; у одиночной публикации порядок проверок прежний, время раньше подготовки проверяется только в серии (Б-S3); `_insert_ride(…, depart_at, request_key)` — на каждую дату (блок отдыха, потолок 30, квитанция RS-05, `_recent_twin_ride`, вставка, копии `recurrence`, `car_id`, буст, enqueue событий RS-10 А внутри той же транзакции, коммит) → `(ride, created, copies)`. Зелёными остаются `test_rides_edges.py:73`, `test_wave1_scenarios.py:243`, `:258`.
2. **Б-S2.** `POST /rides/series`: `RideSeriesIn{ride: RideIn, departures: list[datetime]}` (до `MAX_SERIES_DATES = 10`, `ride.depart_at` игнорируется). `Idempotency-Key` **обязателен** (нет → 422 `series_key_required`), базовый ≤ 115 знаков (иначе 422 `idempotency_key_invalid`): к нему добавляется `-ГГГГММДДччмм` (≤ 128, формат RS-05). Даты приводятся к UTC с точностью до минуты (`10:00+05` и `05:00Z` — одна), дубли склеиваются, порядок по возрастанию. `recurrence != "none"` → 400 `series_with_recurrence` («Выбери одно: повтор или несколько дат»); больше 10 → 400 `series_too_many` («За один раз — не больше 10 дат»); везде `herr(…, code=)` (RS-01).
3. **Б-S3 (порядок).** (1) ключ даты; (2) `replay` по **всем** датам — найденные идут в ответ как `already:true`, без побочек; (3) для остальных `_check_depart` (прошедшие → `time_passed`, модерация на них не тратится); (4) остались новые — **один** `_prepare_publish` (его подтверждённый отказ — элемент `{outcome:"rejected", code, ru, ba}` каждой новой дате, сохранённый по RS-05, ответ 200); (5) `_insert_ride` на каждую новую: `herr` до доменной записи → сохранённый rejected с `code`; иная ошибка → rollback, затем сверка квитанции новой сессией. Доказан commit → applied, доказан откат без эффекта → rejected, БД не дала установить исход → unknown, без нового ключа. Цикл не прерывается. Ответ 200: `{published, failed, unresolved, items:[{depart_at, outcome:"applied"|"rejected"|"unknown", ride_id, already, code, ru, ba}]}`, published считает applied, failed — только rejected, unresolved — unknown; создаётся только `Ride`; блок отдыха и потолок работают сами (`rest_block`, `too_many_rides`).
4. **Б-S4 (повтор части).** Отпечаток квитанции даты = общая часть `ride` + эта дата; состав пачки в него не входит. «Сверить неизвестные» шлёт unresolved-подмножество с **тем же базовым ключом** (ключи остальных дат не меняются); при потере всего ответа — исходный набор с тем же ключом. Терминальный rejected не превращается в applied при повторе старого ключа: после его сверки пользователь отдельно подтверждает новую попытку, и только для этих дат создаётся новый базовый ключ; ранее applied ID остаются в результате исходной серии. Исходы и tombstone хранятся по RS-05; завершённый отказ сверяется, новое намерение возникает только по явному подтверждению. Истечение 15 минут/24 часов не меняет базовый ключ. Сохранённый `series`-контекст содержит общий payload, исходный набор UTC-дат, базовый ключ и результаты по каждой дате.
5. **Б-S5 (оповещение).** API принадлежит RS-10 А и уже должен быть в main. Каждая дата записывает `enqueue_route_watch(session, ride, source_key=<ключ намерения даты>, group_key=GroupKey("series",base_key), siblings=<точно известные созданные рейсы>)` **до** своего доменного commit, вместе с receipt RS-05; одиночная дата передаёт `siblings=()`, recurrence — точные копии. События содержат серверные хеши по RS-10: source_key дополнительно включает ride_id и terms_version каждого рейса, group_key отделён и неизменен для серии/recurrence; без payload. Worker читает committed subset серии; неизвестная дата не входит в число успехов/сводку. После восстановления поздний commit будет обработан, при занятой суточной квоте дождётся её; ранее объявленные ride защищены Notice. В конце цикла `notify_map_changed()` и обновление результатов; сами уведомления не зависят от удачного выполнения этой строки. Никакого fallback поиска «родственников за 10с».

**Сайт.** `publishRideSeries` (`api/driver.ts`; ключ — `commandIntent.ts` RS-05: один базовый на пачку); `components/DatesPicker.tsx` + `ui.css` (сетка `role="grid"`, ячейки ≥ 48px, до 10 дат, одно `<input type="time">`); «Несколько дат» в блоке `:594` исключает остальные. Экран `:259` → итог по датам: «Опубликовано 2 из 3»; «в ленте» / «уже была опубликована» / причина; `time_passed` → «Выбрать другую дату»; «Сверить неизвестный результат» для unresolved и «Создать заново» только после завершённого отказа и отдельного подтверждения. Любая повторная сверка/отправка начатой серии использует `/rides/series`, даже когда осталась одна дата; endpoint одиночной публикации не подменяет серию.

**Android.** `ApiClient.publishRideSeries` (`CommandIntent.prepare("ride.series", …)` RS-05, отпечаток без дат). `RideDatesPicker.kt`: сетка месяца, до 10 дней не раньше сегодня, одно время; в ряд «Повтор» (`:658`) — «Несколько дат», взаимоисключает остальные; **Для нового намерения:** ≥ 2 дат → серия, одна → `publishRide`. **Для уже начатого намерения `ride.series`: всегда `publishRideSeries` с прежним базовым ключом и схемой ключа даты, даже если повторяется одна дата.** Режим намерения сохраняется при рестарте, не выводится из длины текущего массива. `RideSeriesResultSheet.kt` — итог как на сайте, «Готово» → `onPublish`; 0 опубликовано — форма и даты целы; unknown показывается «Результат пока неизвестен», без обещания отсутствия рейса; строки — `AnimatedVisibility`, `CanonMotion`.

## 4. База данных
Новой миграции RS-09 нет: используются ledger/tombstone RS-05 и RouteWatchEvent/Notice RS-10 А. Служебный `group_key` событий связывает committed subset для рассылки; публичной модели/отмены серии нет. Retention и удаление аккаунта — соответствующие планы, не создавать конкурирующие таблицы. Состояние исходного набора/результатов на клиентах хранится до разрешения намерения по RS-05.
