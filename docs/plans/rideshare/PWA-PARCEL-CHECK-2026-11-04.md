## PF-01 — начало перевозки не сообщает об ошибке

Уровень: **подтверждено исполнением извлечённого обработчика**. Приоритет исправления **P1**, тяжесть **S3**
(есть обход через обновление/сверку, не заявлена потеря данных). Связь: P29/D53/BC-08, F6.3/G5/G7.

1. Начальные локальный и синтетический серверный статусы — accepted.
2. Выполнить настоящий `onDepart(7001)` через настоящий API-wrapper.
3. Отдельно подать отказ fetch до записи и HTTP 409 с понятным текстом.
4. В обоих случаях promise обработчика завершается без исключения; статусы остаются accepted.
   Единственные записанные callbacks — busyId=7001, затем busyId=null. Обновления элемента,
   сообщения об ошибке и сверки результата обработчик не вызывает.

Это воспроизводит проглатывание ошибки в обработчике. Внешний toast/другой эффект всего приложения этим
экспериментом не исключён; в просмотренной ветви `CarryingList` обработчик не передаёт ошибку дальше.
При потере ответа после записи отдельно нужно определить неизвестный исход, а не только вернуть кнопку.

Критерий исправления: известный 4xx показывает локализованную причину и допустимое обновление; сетевой/неизвестный
исход даёт сверку актуальной посылки, сохраняет контекст и не объявляется успешным началом. Нужны тест обработчика
и отдельный DOM-прогон с проверкой видимого сообщения. Новый UI-договор пока предложение; исправление не внесено.

## PF-02 — ошибка чтения успешного ответа названа неверным кодом

Уровень: **подтверждено исполнением обработчика и настоящего API-wrapper** на синтетическом транспорте.
Приоритет **P1**, тяжесть **S3**. Связь: P29/D53/BC-08, F6.5/G7.

1. Начальный локальный статус — in_transit; вводится искусственный допустимый код.
2. Синтетический транспорт фиксирует delivered, затем возвращает HTTP 200 с обрезанным JSON.
3. Настоящий `Response.json()` выдаёт SyntaxError. В реальном `request` чтение успешного тела находится вне
   catch сетевого fetch; ошибка доходит до `onDeliver` без обёртки ApiError.
4. `onDeliver` возвращает false, локальный элемент остаётся in_transit, busy сброшен.
   В RU/BA записывается существующая подсказка о неверном коде; запросов только один, последующего GET нет.

**Уточнение прежней гипотезы:** обычный обрыв fetch до получения заголовков после синтетической записи
превращается реальным транспортом в ApiError(0), и обработчик показывает сетевую фразу, **не** «неверный код».
При настоящем HTTP 422 с текстом о коде этот текст сохраняется корректно. Поэтому не утверждаем,
что любая потеря ответа ошибочно объявляется неверным кодом. Полная сверка неизвестного исхода при обычном
обрыве также не доказана: в контрольном случае локально in_transit, синтетически delivered, GET отсутствует.

Критерий исправления: отдельно известный отказ кода, ошибка связи/чтения ответа и неизвестный результат.
После неизвестного исхода сначала авторитетное чтение/сверка существующей посылки; не предлагать менять код
или заново передавать уже отданную вещь. Семантику повторов backend нельзя предполагать по этому тесту:
полный серверный/браузерный сценарий до/после доказанного commit остаётся отдельной работой.
