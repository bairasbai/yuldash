## 1. Что получит человек
**Было.** Водитель из Акъяра на трассе в Сибай, связь — одна полоска. Жмёт «Опубликовать» — «нет связи», хотя сервер поездку записал. Через минуту жмёт снова — в ленте две одинаковые поездки, пассажиры бронируют разные копии одной машины.
Пассажирка из Ургазы бронирует место, ответ потерялся, водитель тем временем отказал. Она жмёт ещё раз — и появляется **новая** бронь.
Водитель в Баймаке без сети нажал «Сел», ошибся, нажал «Отменить» — а очередь позже снова отправила старое «Сел».

**Стало.** Одно подтверждённое действие получает сохраняемый номер намерения. При неизвестном ответе Android и PWA удерживают этот номер и сверяют серверный итог; перезапуск, 15 минут и заполненное хранилище не превращают его в новое действие. Текст: «Не удалось подтвердить результат. Проверим, что сохранилось». Гарантия действует для этого протокола с сохранённым ключом и журналом, а не для любого старого клиента/нового нажатия.

## 3. Что сделать
### Сервер (`backend/`)
1. **Минимальный журнал** `CommandReceipt` (`commandreceipt`): id, user_id FK CASCADE/index, request_key (128), scope (40), target_id nullable, payload_hash (64), state `applied|rejected|closed_no_effect`, ref_kind (`ride|booking`), ref_id nullable, result_code nullable (без текста), created_at/index; unique(user_id,request_key) `uq_command_receipt_owner_key`. Тел запросов/ответов, телефон, координаты и свободный текст не сохраняем. user/key/hash/ref — псевдонимные метаданные, это не «отсутствие ПДн».
2. **`app/idempotency.py`:** ключ `[A-Za-z0-9_-]{16,128}` (UUID допустим); нет заголовка → старый путь, плохой → 422 `idempotency_key_invalid`. D11 серии: базовый ≤115 + `-YYYYMMDDhhmm` (UTC до минуты, 13 знаков), подмножество той же серии сохраняет базу. `fingerprint(scope,target,body)` = SHA-256 канонического JSON до изменения body (sort_keys, компактно, даты/enum строками); условия брони/отмены, expected_terms_version, expected_terms_key, точки и машина входят в хеш. Другой body/scope/target по ключу → 409 `idempotency_key_reused`, автоматически новый ключ не создавать.
3. **Одна транзакция и сериализация:** после аутентификации/права владельца сериализовать все операции одного user+key, включая close, до чтения журнала и изменения доменных данных. PostgreSQL — transaction advisory lock детерминированного user+key; SQLite — writer reservation до чтения + unique/CAS. Одинаковый порядок: intent lock → Ride → Booking; никакая модерация/утилита с внутренним commit после взятия замка недопустима: их выполнить до транзакции, затем перечитать и повторить проверки. Доменные изменения выполняются во вложенном savepoint, внешний intent lock остаётся до окончательного commit. Успех доменной команды и applied-row фиксируются одним commit. Конфликт unique → rollback ВСЕХ доменных изменений, заново прочитать квитанцию; не повторить эффект. Уведомления/бонусы/прочие внешние эффекты — только после commit победителя.
4. **Повтор:** право на исходный объект → replay → ограничения нового эффекта (`ensure_active`, burst, сроки/места). Прежний applied не исчезает из-за последующей паузы; текущий безопасный DTO того же объекта по политике RS-03/D9 (не сырые `_booking_out`/Booking/model_dump). Повтор брони после отказа отдаёт 200 cancelled, после done — done; «Сел» после undo отдаёт текущий confirmed. Без нового резерва/пушей/notify_map_changed/notify_route_watchers/trip_wake/денег. Объект удалён → `idempotency_result_gone`, ключ остаётся закрытым для исполнения. rejected/closed_no_effect → сохранённый безопасный код/состояние, без эффекта.
5. **Срок 24ч НЕ срок жизни ключа:** до `REPLAY_HOURS=24` applied отдаёт текущее представление; позже POST возвращает 409 `idempotency_key_expired` и путь сверки, но НИКОГДА не считает ключ новым. Минимальный tombstone (user,key,scope,target,hash,state,ref,result_code,created_at) живёт до удаления аккаунта. Нельзя удалить его через2д/по TTL или из-за отсутствия объекта. Если требуется другая политика хранения — отдельный owner gate и новый безопасный протокол, не молчаливое ослабление гарантии.
6. **Сверка результата** (`routers/command_intents.py`, только текущий владелец): `GET /command-intents/{key}` → `{state:applied|rejected|closed_no_effect|unseen,scope,ref_kind,ref_id,result_code,current?}`; current собирается через разрешённый DTO и актуальные права, без текста запроса. Форма отсутствующего результата: state=applied, result_code="idempotency_result_gone", current=null, ref_kind/ref_id исходные; state=result_gone не существует. Tombstone не меняется/не удаляется. У unseen scope/ref_kind/ref_id/result_code/current=null. unseen означает «журнал ещё не видел», а не «можно создать новым ключом»: исходный пакет мог задержаться.
   `POST /command-intents/{key}/close` `{scope,target_id,payload_hash}` под ТЕМ ЖЕ intent lock: существующий applied/rejected вернуть; отсутствующий → атомарно вставить closed_no_effect tombstone; существующий другой hash → 409. Поздний исходный запрос увидит closed_no_effect и не исполнится. Close не отменяет уже созданную поездку/бронь; она требует своей команды. После терминального сверенного результата человек отдельно подтверждает новое намерение, если оно нужно. Endpoint не принимает чужой user_id и не делает поиск по хешу без владения ключом.
7. **Ручки с ключом:** `POST /rides` (ref первого рейса recurrence), `/rides/{id}/cancel`, `/complete`; `POST /bookings`; `/bookings/{id}/confirm`, `/cancel` (CancelIn reason + expected_terms_key RS-07), `/no-show`, `/driver-status` (все фазы), `/trip-status`. `record` есть на каждом успешном пути включая twin, _booking_retry и no-op по состоянию. Доказанный окончательный отказ без эффекта откатывает доменный savepoint, сохраняет rejected/result_code и commit внешней транзакции до построения ответа; key-lock между проверкой и записью rejected не отпускается; transient 408/429/5xx не объявлять окончательным. Полученный `cancel_terms_changed` закрывает только тот отказанный payload; подтверждение новых условий — новое намерение. Человек с неизвестным cancel-ответом сначала сверяет старое.
8. **Совместимость/хранение:** без ключа остаётся прежний дедуп60с и его ограниченная гарантия; клиенты такого режима не обещают абсолютной защиты. `commandreceipt` в KEEP_FOREVER с причиной «запрет повторного применения известного ключа до удаления аккаунта» и в account deletion. Tombstone без координат не заменяет данные объекта и не расширяет доступ к ним.

### Android (`android/`)
1. `data/CommandIntent.kt`: account-scoped durable slots `scope → {key,fingerprint,target,created,state,ref?}` без body/текста/точек. `prepare` сначала атомарно сохраняет metadata, затем посылает запрос; storage error — команда не отправляется, честное сообщение. Тот же unresolved scope не меняет ключ/хеш по таймеру, перезапуску или редактированию формы. TTL15мин/6ч запрещён; заполнено64 слота — не вытеснять неизвестные, сначала сверить/закрыть. Выход скрывает namespace и удаляет credentials, но не стирает unresolved metadata прежнего аккаунта; повторный вход тем же user восстанавливает, другой user не читает. Удаление аккаунта удаляет namespace.
2. Состояния `prepared → sending → unknown | applied | rejected | closed_no_effect`. Любой обрыв/таймаут/408/429/5xx — unknown. Повтор с доступным неизменным body использует прежний key; потерян body после перезапуска — GET сверки, затем при необходимости явная close, а не новый UUID. После 24ч — GET/close, не автоматический retry новым key. Только доказанный терминальный итог и отдельное явное подтверждение человека создают новый key; окончательный успех не означает автоматическую новую отправку при возобновлении экрана.
3. `ApiClient.kt` и `BoardingApi.kt` передают key в каждой ручке п.7; refresh/auth retry сохраняет его. Ответ 2xx читать по status/current: cancelled/done открывает реальный итог, не «бронь отправлена»; confirmed после undo не показывает «в машине». DTO полностью следует RS-03 и текущим правам. GET state=applied с result_code=idempotency_result_gone/current=null показывает «Результат больше недоступен»; не трактовать его как unseen или право автоматически послать новый ключ.
4. Outbox.newDriverStatus/newTripStatus сохраняют requestKey первой попытки и payload hash. Истечение бизнес-срока статуса прекращает фоновую отправку и переводит intent в сверку/close, не удаляет неизвестный intent и не отправляет его новым key. Последующее противоположное действие не оживляет старое; FIFO сам по себе исход не доказывает.
5. CreateRideScreen/YuldashApp/BookingActiveTripScreen: unknown → предупреждение и «Проверить результат»; до сверки нельзя отправить изменённую копию. Кнопка «Повторить это действие» — тот же ключ в окне24ч и неизменный body. После applied/rejected/close показать сохранённое сервером состояние; «Создать другую поездку/бронь» требует отдельного подтверждения. Публикацию/бронь не ставить в фон/очередь.

### Сайт (`webapp/`)
1. `utils/commandIntent.ts`: те же account namespace/state machine и атомарное сохранение до сети в durable storage; нет хранилища → не посылать новую мутацию, только прочитать состояние/сообщить ошибку. Перезагрузка/смена вкладки не стирает unknown; две вкладки сериализуют prepare по scope (Web Locks с storage CAS/fallback), оба вызова получают один key. Logout не даёт другому аккаунту прочитать metadata; после возвращения прежнего аккаунта оно восстанавливается.
2. `api/{driver,bookings,rides,family}.ts` передают прежний key; API-коды, status/current, 24ч/close и типы строго как Android, включая applied+idempotency_result_gone+current=null. `outbox.ts` и ActiveTripScreen сохраняют ключ первой попытки статуса; никаких автоматических новых намерений при expiry/clean.
3. CreateRideScreen/RideSheet: те же тексты и подтверждение нового намерения; черновик не очищать при unknown. Сначала сверка серверного результата, затем отдельное новое действие; интерфейс не заявляет об успехе отмены/публикации по сетевому исключению.

## 4. База данных
Миграция `<префикс>_command_receipt_<дата>`, down_revision — текущая голова main после предшественников индекса. Создаёт commandreceipt с полями/unique/индексами п.3.1; прежние данные не пересчитывает. На previous-main schema со старыми синтетическими Ride/Booking проверить upgrade/defaults/сохранность, отдельно SQLite/PostgreSQL. Up → down → up только на временной БД.
- **Срок:** минимальный tombstone KEEP_FOREVER до удаления аккаунта; запись user/key/hash/ref — псевдонимная и скрыта от других. account.py удаляет строки владельца, cleanup не удаляет по возрасту. Ответы/тела/координаты не сохраняются.
- **Rollback:** downgrade удаляет журнал и теряет защиту старых ключей. Нельзя откатить сервер и продолжить прежний протокол; до downgrade остановить мутации, сверить все поддерживаемые unresolved intents и сменить protocol generation с явным клиентским gate. Этот эксплуатационный переход и политика хранения ждут отдельного «да»; обычная проверка временной БД не разрешает rollback production.

## 9. Риски и границы
- Гарантия ограничена описанным протоколом стабильного ключа; старый клиент без него и отдельное сознательное новое намерение вне неё. При unknown изменение поля не создаёт новое намерение автоматически.
- Бессрочный минимальный ledger имеет цену хранения и требует owner approval политики. Иной срок не внедрять без безопасного протокола запрета повторного применения.
- Заявки/отклики, правка поездки и договорённость об оплате не включаются молча. Серверные права проверяются при каждой сверке; нет новых платежей/СМС. SQLite writer/CAS и PostgreSQL row/advisory locks проверять раздельно.
