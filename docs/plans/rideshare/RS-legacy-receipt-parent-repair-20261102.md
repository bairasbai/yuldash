# Квитанция при восстановлении назначения и черновик после поддержки

02.11.2026, Root. Только текущая ветка, без main/push/prod/денег. Статусы — audit-blocks.md. Product source39 уже исправляет пустой CODE и направление done-восстановления; общая приёмка открыта.

## Подтверждённое и неизвестное

В actual blank-main-navigation01 Legacy.currentReceiptCallbackSurvivesLostGlobalSnapshotNotification проходит первоначальный Hero, затем получает Notifications вместо TripReceipt. Тест намеренно уже переключил Screen.TripReceipt до удержанного callback. Специальный wrapper currentReceipt допускает такое назначение с собственным ID или ещё нулевым receipt-ID, но до него callback не доходит: Completed.onReceipt использует общий isCurrent → ActiveTrip.isTripSessionCurrent → currentLive, который требует Screen.ActiveTrip. Это подтверждённая причина; другие действия уходящего экрана должны оставаться закрытыми.

Completed.supportBackRetainsExactDraftWithoutAutomaticPost проходит ввод и уходит в поддержку, но падает в checkDraft после возврата. Конкретная причина ещё неизвестна: rawReceipt загружается заново, а тест ждёт Hero, не подтверждённую форму. Гипотеза отзыва HISTORY обычным ROLE(done) опровергнута source gate.close, который сохраняет history/historyEpoch. Нельзя чинить её предположением или убирать проверки черновика.

## Действия и приёмка

1. Только тестовая диагностика Completed после возврата: безопасные счётчики GET/формы/загрузки/ошибки, текущесть собственной HISTORY и сохранность синтетического черновика логическими признаками. Прежние точные проверки текста, звёзд, тега и нуля бизнес-POST сохранить; при необходимости отдельно доказать ограниченную готовность формы перед checkDraft. Без подмены ответа History/установки полномочий.
2. Предложить отдельную проверку именно открытия квитанции сквозь рабочую цепочку. Она использует уже существующий полный wrapper currentReceipt: текущие active booking/ride/owner/session/revision, отсутствие всех pending, экран ActiveTrip либо TripReceipt с ID0/своим. Свою текущую HISTORY/экземпляр и живой scope проверять отдельно. Общий parent для оценки/благодарности/потерянного/отрисовки не ослаблять; потерянный activeBookingId, чужой ID/поездка/сеанс/другое назначение не становятся разрешением. Все рабочие callers должны передавать/содержать доказанную проверку; отсутствие родителя не разрешает production-действие.
3. Точный main-diff и нужные положительные/отрицательные проверки независимо принять до применения. Те же Legacy RED→GREEN и parent26, новая квитанционная граница против Settings/другой брони/поездки/revision/pending/owner/session/disposal, прежние сохранённые состояния и черновики. Пределы3541/1064 не повышать, без уплотнения; допустим только точный связанный вынос. Затем guards/широкие проверки/актуальный APK/R8/UI и свежая приёмка; не объявлять весь режим принятым по одному callback.

Root единственный применяет source и запускает инструменты. Авторы работают только с RAM patches, процессы/эмулятор не запускают. Ни новых надписей, ни версий/зависимостей без необходимости.

## Узкий план сохранения черновика при закрытии приватного дочернего экрана — source43

Факт booking-reference-scope02/source43: beforeSupport положительный контроль performSave видит точный синтетический текст и тег; onSupport и после возврата оба отсутствуют. Владелец/сеанс/бронь/поездка/ссылка/revision неизменны, HISTORY текущая, обычное повторное получение квитанции успешно. Старый observer03 пропускал State; исправленный04 сначала требует положительный контроль. Отказы/архив8f57a3d1de59167157b2a98bec64c4c8b0751745b12b6294274a38baa798463e сохранены.

Кандидат, ещё не код: в существующем key(owner, booking, session, ride, revision) GuardedActiveTripDestination запомнить стандартный rememberSaveableStateHolder. Только ActiveTripScreen внутри TripAuthorityContent поместить в локальный SaveableStateProvider с постоянным приватным подключом. При запрете дочерняя композиция и её provider удаляются вместе, локальный holder остаётся до удаления внешнего экранного provider и может сохранить зарегистрированные пользовательские поля. Сами DTO, разрешения, coroutine scopes (области выполнения) и сетевые загрузки не делать сохраняемыми. Не оставлять закрытую композицию работающей и не менять предикаты рисунка/действий/owner/session/TTL.

Перед применением нужна независимая проверка порядка Dispose/Save, корректности ключей и существующих восстановлений. Риск: новый вложенный namespace меняет positional сохранение текущих draft; старое сохранённое состояние нельзя угадывать. Если совместимость не доказана — отдельный version namespace/явный отказ, без отключения Legacy-тестов. Не расширять общий TripAuthorityContent/VM. Квитанционный callback этим планом не считается исправленным.

Приёмка: прежний supportBackRetainsExactDraftWithoutAutomaticPost с обязательным working observer RED→GREEN, полный CompletedNavigationRestorationTest11 (звёзды/точный текст/теги/подтверждённые успехи/нуль лишних POST/сохранённое состояние), все42 parent+caller, Legacy25 включая старые недоверенные состояния, сторожа. Затем общие требуемые сборки и UI текущего APK. При смене владельца/сеанса/броньи/поездки/revision старые данные и действия недоступны; без собственных текущих HISTORY приватные поля не открываются.

## Уточнение версии приватного сохранения

Свежая независимая plan-only приёмка completed_nested_holder_plan_review1 требует не трактовать старое плоское сохранение как новый holder. Использовать явный новый локальный key("active-trip-private-saveable-v1", owner, booking, session, ride, revision) вместо прежнего немаркированного key в этой границе. Старые flat values не читать/не угадывать; новая ветвь стартует пустой, сохраняя те же исходные значения по умолчанию. Риск обновления: черновик старой сборки может потребовать повторного ввода. Это не обещание миграции старого layout; современное сохранение/возвраты проверить прежними полноценными тестами. Root namespace других экранов не менять.

## Квитанция: подтверждённый срок жизни дочернего callback — source44

Факт legacy-clickable-scope01/source44/885: оба исходных Legacy-callback FAIL, original1, XML280f3fc43cb47a9a115c9c6fc1233aa64e2c818010b23945636d95a3e9e272e9. Observer проходит точный локальный AbstractClickableNode.onClick без вызова функций: visited20, limited=false, inaccessible0, scopes3; до screen-change все3 активны, внутри исходного DisposableEffect перед callback активна1 родительская, две дочерние закрыты. Own HISTORY и все booking/ride/owner/session/revision/noPending признаки текущие. Таким образом прежнее требование обеих дочерних областей выполнения несовместимо с допустимым callback во время удаления приватного child; его нельзя исправлять удержанием закрытой private UI.

Предлагаемый контракт: только receipt navigation синхронно делегирует срок жизни ЯВНОМУ receipt-parent из GuardedActiveTripDestination. Parent уже требует живой собственный scope, исходные owner/session/booking/ride/revision, три pending=null и допустимое назначение ActiveTrip либо TripReceipt с ID0/своим. ActiveTrip и Completed сохраняют собственные проверки owner/session; Completed дополнительно требует собственную текущую HISTORY/экземпляр/срок. При explicit receipt-parent == false действие запрещено, без fallback. Если explicit receipt-parent отсутствует (standalone/tests), по-прежнему требуется ЖИВОЙ локальный scope и прежний generic-parent. Меняется только receipt; canAct, draw, rating/thanks/lost, сетевые effects и disposal не менять. Никаких writes/фоновых jobs в этом navigation handler.

Ожидаемый минимальный diff: Active.isTripReceiptSessionCurrent и Completed.canOpenReceipt выносят localScope.isActive в ветку отсутствующего explicit receipt-parent, сохраняя session/owner/HISTORY. Отдельная новая capability/API или общая библиотека не нужны. Риск: удержанный child callback умышленно живёт до disposal сильного родителя в узком разрешённом receipt-переходе. Запрет после disposal родителя, смены identity/pending/чужой receiptID/HISTORY обязателен. Все рабочие callers передают явный parent; caller guard сохраняется.

До применения независимая plan-only/source приёмка. Приёмка: оба исходных Legacy-callback GREEN без изменения исходных assert; полный Legacy25, родитель42+caller со всеми отрицательными disposal/owner/session/booking/ride/revision/pending/foreignreceipt/HISTORY, полный Completed11 и History15. Дополнительный отдельный негатив: standalone callback после удаления child не получает разрешения при отсутствии явного receipt-parent (использовать существующий подходящий тест либо адресный UI случай). Затем обязательные guards/текущие сборки/UI и свежая независимая фактическая приёмка. Успех только unit/source не завершает режим.
