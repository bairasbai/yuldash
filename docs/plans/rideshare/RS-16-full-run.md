### 3.2.1 Управляемая потеря результата (B20)
Все действия сначала **NOT_EXECUTED**. Fault-proxy не меняет продуктовый код, не обращается к рабочему серверу и не активирует платежи/SMS.

Доказательство зависит от реально существующего протокола операции. Общая CommandReceipt не выдумывается для чата/откликов:

| Операция | Устойчивый идентификатор повтора | Независимое чтение после commit и итог повтора |
|---|---|---|
| Публикация, бронь, confirm/cancel/no-show/driver-status/trip-status в составе RS-05 | account+исходный Idempotency-Key и неизменный payload/hash | CommandReceipt applied + целевой Ride/Booking и стадия/места. Replay/GET возвращает исходный ref и актуальное разрешённое представление |
| Сообщение | исходный request_key записи Outbox/chat, не новый CommandIntent RS-05 | Message + ChatMessageRequest того же owner/key/hash (main backend/app/routers/chat.py:700–757); одна Message и тот же message_id после REST/WS retry |
| Принятие отклика своим рейсом | исходные request_id/response_id, прежние условия отклика; новый отклик не создаётся | RequestResponse.status=accepted, прежний booking_id, Request.status=matched, связанная Booking и резерв участка (main backend/app/routers/requests.py:1245–1347). Повтор bound-accept возвращает прежнюю бронь либо после допустимого отказа она восстанавливается чтением состояния |
| Принятие отклика без привязанного рейса | тот же request_id/response_id и прежнее подтверждение | matched/accepted + единственные созданные Ride/Booking и booking_id. Прежний API может ответить «уже закрыто»; клиент сверяет исходную заявку/отклик/свои поездки, не предлагает заново принять другим намерением и не создаёт вторую поездку |

1. До действия сохранить начальные count/свободные места, стадию и соответствующий идентификатор из таблицы. На стороне теста сопоставление по id/hash, а не по личным данным. Прокси перехватывает **одну** заданную операцию, следующие GET/reconciliation проходят. Для чата либо выбрать существующий REST fallback с тем же request_key (WS недоступен), либо удерживать WS ack этого ключа; HTTP-заголовки не заменяют WS-проверку.
2. **До commit:** proxy принимает запрос, не передаёт upstream (`held_before_forward`), закрывает соединение. Независимое чтение временной БД подтверждает отсутствие нового эффекта/соответствующей квитанции и прежние остатки/стадию; уже существующие Ride/Booking/заявка остаются на месте. Клиент показывает неизвестный исход, сохраняет прежний идентификатор/неизменные условия. После перезапуска и снятия fault сверить сервер и повторить по тому же протоколу: один эффект либо допустимый окончательный отказ без эффекта.
3. **После commit:** proxy передаёт запрос, удерживает весь HTTP-ответ либо нужный WS ack до клиента. Отдельное соединение с временной БД в новой транзакции видит именно доказательства из таблицы и соответствующее списание/возврат мест. CommandReceipt обязательна только операциям RS-05; ChatMessageRequest не подменяется ею, для принятия отклика достаточно атомарного сохранённого результата. Это свидетельство commit с временем, id и count сохраняется; SQL-лог до commit недостаточен. Если commit не доказан — BLOCKED, after-commit не засчитывать.
4. Убедившись в commit, закрыть удержанный ответ/ack. Force-stop Android либо закрыть вкладку до результата, снова открыть: исходный key либо request/response_id и условия восстановлены. GET/reconciliation и допустимый ручной повтор сохраняют их; не создают новое намерение по таймеру. Итог: тот же ride_id/booking_id/message_id, один резерв/возврат и правильная стадия, обе точки сохранены. Допустимый 4xx старого accept не выдаётся за отмену результата. Для terminal replay проверить D9 — нет чувствительных данных сверх текущего права.
5. Повторить после 16 минут и перезапуска для публикации/брони; 24-часовую границу CommandReceipt/tombstone — только для команд RS-05 серверными тестами управляемого времени, отдельно «не UI». Чат и отклики проверяются по своим правилам хранения/повтора. Если клиент не умеет сверить/повторить без нового намерения, сценарий FAIL, не заменить его голым HTTP-тестом. Частичная серия: три даты, два успеха/один unknown, повтор одной даты остаётся `/rides/series` с прежним базовым ключом.
6. Два независимых подтверждения: `fault-events.jsonl` с before-forward/удержанием/обрывом после commit и `commit-proof.jsonl` с чтением БД **после** commit + counts до/после replay. Записать SHA/версию скрипта, вид протокола/ledger из таблицы, роль/клиент, метод/путь, безопасный id, время UTC и фактические IDs/результат. Контроль: отключить соответствующий dedup/CAS в отдельной тестовой мутации — сценарий краснеет; мутация не касается рабочей базы.
