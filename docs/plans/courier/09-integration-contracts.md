# Интеграционные договоры и безопасное переключение

Этот документ дополняет C/F/D конкретными межмодульными правилами после аудита R1. Статус: R4_PENDING_REVIEW. Все runtime проверки NOT_EXECUTED. Авторские нормы здесь не утверждают тариф, договор или юридический допуск; отдельное подтверждённое решение владельца о zero on-route комиссии записано в F1A и source register. Приоритет имеет согласованный пакет целиком, а не выбор удобной строки из старой редакции.

## K1 Места посылки и итог всего заказа

`DeliveryItem` — минимальная единица физической ответственности: item_id, parcel_id, item_version, description_ref, pickup_stop_id, destination_stop_id, fulfillment_state, custody_kind, holder_ref, custody_evidence_level, active_assignment_id nullable, obligation_state, last_transfer_id. Legacy parcel создаёт один `legacy_logical_parcel` с неизвестным количеством физических мест; backfill не выдумывает коробки или их содержимое. Новая multi-item capability требует перечисленных мест до quote и CP-18.

Каждое место в каждый момент имеет ровно одну подтверждённую custody запись либо `unknown` с case. Допустимые holder kinds: sender, assigned_carrier, recipient, return_receiver, storage_custodian, unknown. Holder_ref указывает реальную роль/party, а не общую строку «склад». Carrier assignment-item active slot уникален по item_id; разные места одного заказа могут иметь разных держателей только при включённой CP-18 capability. Scalar Parcel.active_assignment_id вычисляется только при общем назначении, иначе NULL; потребитель не угадывает первого курьера.

Challenge/evidence неизменно содержит sorted item_ids, item_set_hash, item_versions, stop/phase, old/new assignment при transfer, receiving_party_ref, recipient_authority_version, terms_version. Разница даже в одном item означает другой proof. Consumption и transfer updates одной транзакцией; повтор того же ключа/набора возвращает applied без второй передачи. Частичный физический результат, не совпадающий с challenge scope, записывается в exception case и принимается отдельным разрешённым recovery proof, не растягивается на весь набор.

Детерминированная проекция order:

1. Есть unknown physical outcome → fulfillment=delivery_exception, custody=unknown, obligation active с case. Уже доказанные переданные items сохраняют свой outcome, не откатываются.
2. Все items resolved: если хотя бы один имеет approved exceptional outcome, aggregate=closed_exception; иначе все delivered → delivered; все returned → returned; все canceled → canceled; любая смесь delivered/returned/canceled → completed_mixed. У каждого item сохраняется его собственный исход. Пустой список не означает completed.
3. Есть unresolved storage proposal → storage_pending; все оставшиеся unresolved у хранителя → stored, obligation=stored_pending_release. Это не returned/resolved.
4. Есть unresolved return_required → returning. Есть одновременно resolved и другие unresolved без return/storage/unknown → partially_completed. Иначе базовая стадия активного leg/stop.
5. custody агрегата: все одинаковый kind+holder → этот holder; разные известные → mixed; любой неизвестный → unknown. obligation агрегата resolved только если все item obligations resolved. Денежные obligations не закрываются этим правилом.

Item outcome `canceled` разрешён только при доказанном no-transfer/no-purchase/no-COD-collection для этого item: custody=sender, obligation=resolved, его assignment slot закрыт и неиспользованные proof challenges отозваны. Общий или неразделимый purchase commitment/unknown, чужая physical/cash custody блокируют такую отмену до recovery; cancel_requested не terminal outcome. Частичная отмена ещё не полученного item допустима только через scoped cancel/amendment: уже переданные items остаются delivered/returned либо active, общие маршрут/суммы меняются по consent. Деньги за допустимую отмену остаются отдельными obligations. Повтор projector/GET/restart/backfill воспроизводит canceled или completed_mixed и не открывает tracking/assignment заново.

Stop complete только когда все назначенные ему items получили разрешённый outcome; itinerary complete только когда все его orders/legs/обязательства выполнения разрешены. Tracking закрывается по разрешённым scopes предметов/заказов, не по первому stop. Наличие других активных deliveries сохраняет service; return GPS остаётся выключен по прежней privacy policy, пока владелец отдельно не утвердит иной режим. Хранение не требует непрерывного GPS хранителя.

До CP-18 старым клиентам доступны только single-item действия через adapter. New multi-item, mixed, storage/handoff сценарии требуют minimum client capability; legacy API не принимает команды, которые не может однозначно выразить. UI может показывать historical legacy status, но action/terminal/оплата берутся из канонических осей. `completed_mixed` нельзя выдавать за обычный delivered/returned старому клиенту.

Проверки: два delivered+один returning; один returned+один unknown; RMA продавец принял два из трёх; правильный stop/код с другим item set; duplicate partial proof; один order завершён, другой того же itinerary активен. Для каждого trace перечислить item holders, агрегат и открытые денежные obligations.

## K2 Полный каталог изменяющих операций

Общий envelope domain-команды: `type`, `expected_version`, `terms_version`, `item_ids/item_set_hash` при физическом действии, `assignment_id/generation` при работе курьера, actor определяется auth, Idempotency-Key из C3. Lock order C3 обязателен. Ошибка до допустимого эффекта возвращает code и сохраняет окончательный rejected только при доказанном no-effect; неизвестный внешний результат — reconcile, не rejected.

Путь по умолчанию `POST /courier/v2/orders/{id}/commands`. Специализированные endpoints ниже являются адаптером к той же операции/receipt, не второй write-логикой. Ни один CP не вправе вводить неучтённый type: сначала изменение каталога/review. Quote без order — отдельный неизменяемый ресурс; не доменный side effect заказа.

## K3 Gate и право безопасно разрешить уже возникшее обязательство

| Ограничение | Новые create/accept/budget/charge | Active proof/return/storage | Деньги/callbacks/помощь |
|---|---|---|---|
| Зона/capability paused | Запрещены; новые paid extras только отдельное разрешение | Существующее безопасное исполнение по frozen scope, без расширения зоны; опасное → support | Проверенный callback/reconcile/refund по уже разрешённой модели продолжаются |
| Истёк НПД/transport eligibility, обычная suspension | Запрещены новые offers/поручения | Текущая аутентифицированная сторона может сообщить статус/проблему; продолжение движения только если законно/безопасно, иначе support-mediated handoff/storage | Уже заработанное/собранная выручка сохраняются; settlement по правовой модели |
| Подозрение takeover/revoked auth | Всё этой сессии запрещено | Никаких исключений для скомпрометированного token. Support после безопасной проверки личности связывает case с новым ограниченным каналом; handoff принимает новый authorized actor | Provider webhooks по provider authority, не user token; собственник получает минимальное восстановление, не полный повторный export ПД |
| Provider outage/unknown debit | Новые potentially duplicating collections запрещены | Custody не исчезает, операции безопасности продолжаются | Reservation остаётся до достоверного исхода; не новый debit по timeout |
| Account deletion requested | Новые обязательства запрещены, credentials revoked | Support-mediated recovery, без восстановления обычного доступа | K6 retention и F10–F12 reconcile; удаление не paid/void/return |

Это не blanket bypass gates для «active order». Каждая операция проверяет current auth, role и ограниченное resolution permission; денежное/правовое расширение требует своего gate. Поддержка не вправе подделать SMS/OTP за сторону.

## K4 Время и handshake предложения

Подтверждённый источник: [timeutil.py1–40](https://github.com/bairasbai/yuldash/blob/0ef03f4194012431e0996be4d8e748d37e34d63d/backend/app/timeutil.py#L1-L40) хранит **naive UTC** и возвращает его utcnow/client_dt_to_utc. Courier сохраняет эту persistence convention. Общий utcnow/local_date и существующие taxi/RS данные не меняются этим планом.

V2 API принимает timestamp только ISO8601 с Z/явным offset; timezone-naive вход → 422 TIMEZONE_REQUIRED. Adapter сначала нормализует instant в UTC, затем снимает tzinfo для DB. На выходе к naive UTC добавляется именно UTC tzinfo и выдаётся Z; нельзя трактовать DB как местное время. Для windows отдельно IANA zone per stop; проверяется согласованность local wall time/offset с zone, неоднозначный local time требует явного offset/fold, не автоматического выбора. Date-only legacy deadline сохраняется как date-only, не фальшивое точное окно.

Legacy routes сохраняют свой явно documented naive_means=local или utc до deprecation, не распространяют уфимский offset на v2/соседние регионы. Все внутренние сравнения lease/expiry/worker — naive UTC. Предлагаемый `backend/app/courier_time.py` и DTO adapters реализуют границу, не глобальная смена timeutil. Tests SQLite/PG roundtrip, aware/naive input, midnight/Ufa → Kazan, same instant different offset, old worker+new API; неизменность taxi/RS.

Один GET offer пример полей: offer_id=O, order_id=P, dispatch_generation=7, order_state_version=12, eligibility_version=4, item_set_hash=H, lease_token=secret, expires_at=Z, remuneration_snapshot_preview, quote/terms_version=3. Accept отправляет O, lease_token, dispatch_generation=7, expected_version=12, item_set_hash=H и accepted_terms_version=3 с intent key. **Assignment_generation клиент не выбирает**: сервер выдаёт её только после successful assignment. Accept response содержит assignment_id/generation и current version. Новый dispatch cycle повышает dispatch_generation; каждый новый carrier transfer повышает assignment generation. Expired/revoked offer не revived таймером UI. Token в логах/неавторизованном replay запрещён.

### Ручной on-route claim через self-offer

Проверенный legacy `/parcels/{id}/accept` имеет отдельный guard для delivery_type=poputka и не требует профессионального CourierApplication. Это сохраняется как режим, но не как обход state/intent/capacity service. `GET /courier/v2/on-route/requests` с selection context возвращает доступные открытые requests и подписанный claim_preview: order/state/terms/dispatch/eligibility versions, item_set_hash, route_context_hash, net/quote hash, expiry. Он ещё не назначение и не резерв места. Целевой R4 on-route claim требует опубликованный active Ride с parcel_enabled и trip/parcel/resource versions по 11. Standalone legacy не получает выдуманную связь и сохраняет recovery старого обязательства; для новой сделки водитель публикует собственную поездку, включая parcel-only. Отсутствие пассажиров само по себе не нарушает этот договор. Новые требования такого допуска остаются отдельным owner/legal gate. Для zero-fee on-route предлагается binding к заранее объявленному собственному пути/направлению и согласованному крюку; thresholds/evidence policy ещё не утверждены. Client selection не переклассифицирует dedicated заказ, а спор о классификации не даёт права задним числом начислить fee.

`claim_on_route` отправляет preview token/hash, expected versions, item scope и C3 intent key. Сервер после locks проверяет реальный stored delivery_type, actor/mode guards, block/self/expiry, coverage/route context, все commitments и capacity, согласованный net. Затем создаёт внутренний CourierOffer(kind=on_route_self, issued_to=actor, current dispatch generation) и вызывает тот же transactional accept service, что accept_offer. Self-offer не выдаётся другому actor и не живёт как второй публичный резерв; order, offer consumption, assignment, net snapshot, capacity, event/outbox и один receipt фиксируются одной транзакцией. Любое изменение preview → 409 CLAIM_PREVIEW_STALE, не тихая новая цена. Item custody остаётся sender до отдельного pickup proof.

Legacy accept adapter с поддержанным intent key/preview вызывает ровно claim_on_route для stored kind=poputka; для профессионального заказа сохраняет профессиональные guards и canonical offer accept. Клиент не выбирает режим query/body. Старый клиент без безопасного intent/preview после cutover получает UPGRADE_REQUIRED и помощь; функция ручного выбора сохраняется в поддерживаемых Android/PWA, а unsafe status-only writer не возвращается. Не генерировать новый ключ на каждый retry старого клиента.

Regression: GET open → claim → одно assignment; два claim и claim/cancel обе очередности; lost response → тот же receipt; changed route/net → stale; professional заказ нельзя взять через on_route endpoint без его допуска, даже если actor умеет бытовую попутную помощь.

## K5 Legacy backfill и cutover

Для каждого старого parcel сохраняются legacy_status/legacy monetary fields и source SHA/версии миграции; raw history не переписывается. Новый автомат не считает status/commission_paid/settled доказательством физического или клиентского платежа. Confirmed historical evidence признаётся только после проверки его применимости, не наличия любой фотографии.

| Legacy input и достоверные дополнительные факты | Новые workflow/custody/obligation | Payment/settlement/dispute projection | Allowed actions/case |
|---|---|---|---|
| created; courier NULL; нет purchase/collection/transfer signals | searching; sender с evidence=legacy_declared, не verified pickup; active | Service/goods payment unknown/unverified obligations; commission по отдельным источникам; dispute из Incident иначе none | Без новой передачи допускается cancel/новое assignment после проверки; противоречие → case |
| accepted; есть courier, нет доказанного pickup/расхода | assigned; custody unknown, asserted_holder=courier/sender не факт; active | Service/goods unknown, commission не captured; existing Incident сохраняется | read/contact/reconcile/cancel_requested; release/cancel terminal только после доказанного no-custody/no-purchase |
| accepted + доказанный pickup конкретной стороны | collected; carrier, evidence=verified historical по policy; active | Обязанности/оплаты независимо, payout не выводится | Продолжить через current assignment/proof policy |
| in_transit/returning без пригодного transfer proof | delivery_exception; unknown, active/return_required по заявленному намерению | Все известные суммы сохранены; unverified status не paid; existing dispute сохраняется | Mandatory custody recovery case, next_action_at; не release/auto returned |
| in_transit/returning с пригодным подтверждённым carrier custody | delivering/returning; carrier; active/return_required | По отдельным obligations/evidence | Delivery/return/storage только через новые разрешённые proof commands |
| delivered/returned с пригодным proof нужного item/receiving party | delivered/returned; recipient/return_receiver; resolved physical obligation | Service/goods/commission/payout по своим доказательствам; dispute не закрывается автоматически | Statement/rating/dispute и finance reconcile; нового физического действия нет |

Оси оплаты создаются так: verified provider Payment комиссии → только obligation комиссии satisfied на доказанную сумму; manual flag без evidence → manual_unverified; delivery_price/cod_amount/goods_cost задают договорные/заявленные amounts, не факт оплаты; settled/commission_paid не означают payout клиентских денег. Payout unknown/not_due определяется наличием отдельного payable/source, не status. Incident открытый → opened/подтверждённая стадия; resolved только по реальному decision record; отсутствующий Incident → none, не «споров никогда не было». Если missing amount/terms нельзя законно установить — legacy_unknown obligation, сбор запрещён до reconcile, не сумма 0.

### Барьер K-CUTOVER

M1 — expand foundations и безопасная замена старых автоматических timeout terminal на alert/Incident; новые поля ещё не основание для новых обещаний. Минимальные Stop/assignment/item/proof/event identity существуют уже в M1; точные columns/FKs M1 → M3 заданы D2. M3 добавляет общие amendments/consents; M7 только расширяет proof policies/recipient/wait, не создаёт впервые необходимый FK.

V2 mutating traffic и обязательный legacy adapter включаются только после CP-02A,07A,09A,12A,21B-core и нужных M1…M8, проверенной data/retention policy и staffed recovery. До этого v2 read/shadow only, новые capabilities закрыты. Подготовительные миграции не требуют человеку пользоваться отсутствующим будущим proof endpoint.

Переключение: остановить новые order admissions → остановить/дождаться old workers и in-flight status writers → deploy все API/worker adapters одной compatible generation → под write fence снять финальный backfill/delta и классифицировать активные ambiguous rows → проверить invariant counters/legacy writer scan → открыть только поддерживаемые команды/новые single-item заказы. Неизвестные active rows остаются в recovery, ни одна не теряется; если поддержки/нового client пути нет, активация остановлена.

Каждый новый writer обновляет canonical axes/version/event и legacy projection одной транзакцией. После barrier status-only старый worker/API не допускается запускать; DB generation fence и readiness отказ предотвращают rollback на него. Старые клиенты работают только через adapter и разрешённые limited actions; unsupported → UPGRADE_REQUIRED + доступ к помощи, не скрытая прямая запись. Downgrade на временной БД допустим по тесту, эксплуатационный rollback — только совместимый код с сохранёнными snapshots/ledger/events; иначе forward fix.

## K6 Actor anchor и удаление аккаунта

M5 явно расширяет общий RS-05 receipt, а не полагается на `user_id FK CASCADE`. Proposed shared `CommandActorAnchor`: UUID id, principal_kind=user|service, user_id nullable FK SET NULL, service_principal_id nullable, account_generation либо service_generation, deleted_at, retention_policy_id/expires_at, hold_reason/ref. CommandReceipt.actor_anchor_id NOT NULL FK RESTRICT; unique(anchor_id, request_key) заменяет уникальность user/key после проверенного backfill один anchor на существующий user generation. user_id в receipt nullable SET NULL или удаляется после cutover как redundant reference. Один общий ledger для RS/courier; миграция и regression всего shared protocol отдельный owner/legal prerequisite, не молчаливое изменение RS текста.

Для principal_kind=user auth разрешает публичные GET/replay/close только живому user, связанному с anchor этой generation. После deletion credentials/grants revoked, user link удаляется, API не разрешает доступ к tombstones по одному UUID. Новый аккаунт даже с тем же телефоном получает новый anchor и не наследует receipt/custody/PII. Minimal receipt hash/key/scope/ref/result хранится по утверждённой цели; request body/OTP/адреса не хранятся. Эти псевдонимные метаданные тоже являются данными с retention gate, не «безличные навсегда».

Pending provider/custody obligations удерживают только минимально необходимый lawful hold с ответственным и сроком пересмотра. Provider webhook/outbox dedup привязан к неизменяемому obligation/provider reference, не CASCADE user; callback проверяет собственную authority. Удаление аккаунта не разрешает новое списание/раскрытие, но не стирает подтверждённый долг/приход. После разрешения hold уничтожение/псевдонимизация по approved policy; если нельзя законно удерживать нужную защиту, соответствующая финансовая capability не запускается до альтернативного approved protocol. Нельзя молча бесконечно удерживать всё.

Worker principal: общий anchor имеет взаимоисключающие user/service references. Внутренний service principal заранее зарегистрирован владельцем интеграции с generation и allowlist операций/merchant/provider account; это не пользовательский admin actor и не новая авторизация создать credentials. Worker receipt namespace = service anchor + детерминированный operation key по obligation/attempt/action generation, в том же CommandReceipt и intent lock. Internal reconcile/close использует тот же сервис C3, но через проверенный machine context; публичный endpoint не принимает service_principal_id/actor_id. Close закрывает лишь неисполненную внутреннюю команду, не unknown внешний банковский/COD результат. Смена worker процесса не создаёт новый principal/key; rotation credentials не обнуляет receipts. Revoked machine grant запрещает новые effects, read/reconcile продолжаются только новым разрешённым service grant с тем же causal reference и журналом полномочий. Provider webhook dedup остаётся provider/account/event reference, а dispatch в command service использует проверенный service principal, не user token.

Тесты: user cannot spoof service principal; worker restart/key replay один effect; revoked worker grant не new capture; public GET не читает service receipt. Delete против applied/unknown/close; задержанный original request после delete denied; callback по уже существующему payment учитывается один раз; новый аккаунт не видит старый ref; payload удалён, money proof retained по policy; expires_at/hold review реально исполняются.
