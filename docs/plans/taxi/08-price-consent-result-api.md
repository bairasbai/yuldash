# Проверка только положительного исхода защищённого заказа «сейчас»

Зависимый follow-up от опубликованного `2ae7e0ec5c1329bde30cf5dfa8ed7a9c45159804`. Это не подключение PWA/Android, не окончательное отрицание, не разрешение включать режим пользователям и не outbox.

## Минимальный read-only контракт

Авторизованный `POST /instant/orders/result/v1` принимает строго `{"request_key":"<server UUID>"}`. Ключ — коррелятор, не bearer credential; его нельзя помещать в path/query/логи. Актуальный current_user проверяет сессию, SQL выбирает только запись с текущим passenger_id и этим ключом среди всех статусов. Нужны существующие consent metadata из API07. Дополнительные поля запрещены; стандартный validation handler не возвращает входные значения. Успешные ответы и503 имеют Cache-Control:no-store.

Положительный ответ200:

```json
{"schema":"taxi-consent-result-v1","state":"committed","order_id":77,"initial_payable_kop":45000,"next":"fetch_order"}
```

ID — синтетический пример. Сумма берётся из `consent.accepted.payable_kop`, проверяется целостность структурных денежных инвариантов. Это **первоначально принятая сумма**, не обещание текущей суммы terminal/изменённого заказа. Следующий шаг — существующий авторизованный `GET /instant/orders/{order_id}`: только он даёт актуальные статус, сумму и доступ. Lookup не объявляет поездку активной и не запускает reconcile/matcher. Заказ может быть удалён между чтением и следующим GET.

Для незнакомого, чужого, выданного но ещё не использованного, не закоммиченного или уже удалённого ключа один ответ200:

```json
{"schema":"taxi-consent-result-v1","state":"unknown"}
```

Ни пустой SELECT, ни expiry, ни потеря Redis, ни таймер/число повторов не превращают unknown в «не создан». Подтверждение могло ещё не закоммититься или начаться после чтения. Такой ответ **не освобождает UI для нового заказа** и не разрешает реконструировать POST. Заново входить/искать пустой список тоже не доказательство отсутствия. Lookup не резервирует, не отменяет, не погашает quote, не продлевает retention и не блокирует будущий create. Ошибка БД/повреждённые metadata даёт двуязычный503 `taxi_consent_result_unavailable`, а не unknown. SQL exceptions/значения ключа не передаются в ошибку/логи.

Нет копии тела, маршрута, адресов или контактов, нового журнала/таблицы и нового срока хранения. Выбираются только ID и существующие consent metadata; наружу не уходят request_key/quote_id/digests, owner ID, raw snapshot, география или контакты. После физического удаления metadata исчезают вместе с заказом; отличить deletion от неизвестного без отдельного tombstone нельзя. Прежний consumed ключ при этом не получает права создать второй заказ (API07).

## База и миграции

Main при старте `34b8fe2e39f5f4a3f5ba760b0d57d9ac56bfe414` не содержит API07. Выбран явно зависимый parent2ae, без импорта PWA/Android/TF10/других веток. Endpoint не меняет схему: **новой миграции нет**, опубликованная cz_taxi_initial_price_consent не редактируется; на этой ветке сохраняется одна прежняя head.

У main отдельная da_route_watch_dispatch после общего опубликованного предка. Будущее совместное объединение потребует отдельной корректной merge-head revision/интеграционного гейта обеих цепочек. Этот follow-up не выдаёт проверку своей унаследованной цепи за интеграцию свежего main; merge/deploy не разрешены.

## Отдельная вторая часть: окончательное «не создан»

Не реализована. Для неё нужен явно вызываемый механизм, который линеаризуется с подтверждением на том же owner/key lock и уникальной записи: только один исход committed или permanently-not-created. Если confirm выиграл, освобождение не отменяет его и возвращает исходный ID; если отрицательный исход выиграл, любое запоздалое confirm обязано отказать до эффектов. Replay уже созданного сохраняется раньше expiry.

Нужны отдельные решения о долговечной записи и ограниченной retention. Удалить tombstone по таймеру недостаточно: прежний ключ/запоздалый create не должен воскреснуть после GC. Потребуется серверно проверяемый предел допустимости/retired generation или другой доказанный протокол, согласованный с Redis expiry/loss, SQL и cleanup. Не добавлять частичный tombstone и не переименовывать unknown в отрицание. Отдельно проверить оба порядка гонки, rollback/crash, replay и GC. Это самостоятельный контракт/миграция/приёмка, не скрытый scope текущего чтения.

## Передача клиентам

После будущего отдельного внедрения клиент с сохранённым непрозрачным ключом и актуальной авторизацией сможет найти положительный committed результат без тела и перейти к существующей карточке. Текущие клиенты не изменены и не включены. Хранение ключа/привязка к owner/session/environment, отсутствие автоматического POST и UX unknown остаются отдельной проверкой. Положительный lookup сам по себе не устраняет блокер безопасного конечного освобождения UI.

Отдельный последующий серверный контракт [явного завершения попытки](09-price-consent-close-api.md) добавляет обязательный SQL admission для новых пар и отдельное закрытие. Он не меняет read-only lookup, не включает клиентов и не называет неизвестную после GC историю доказанным отсутствием.
