# Проверка только положительного исхода защищённого заказа «сейчас»

По сохранённому ключу пассажир может узнать, успел ли сервер сохранить заказ после потери ответа. Клиентам достаточно действующей сессии и ключа из [выданной оценки](07-initial-price-consent-api.md).

## Минимальный read-only контракт

Авторизованный `POST /instant/orders/result/v1` принимает строго `{"request_key":"<server UUID>"}`. Ключ — коррелятор, не bearer credential; его нельзя помещать в path/query/логи. Актуальный current_user проверяет сессию, SQL выбирает только запись с текущим passenger_id и этим ключом среди всех статусов. Нужны существующие consent metadata из API07. Дополнительные поля запрещены; стандартный validation handler не возвращает входные значения. Успешные ответы и 503 имеют `Cache-Control: no-store`.

Положительный ответ 200:

```json
{"schema":"taxi-consent-result-v1","state":"committed","order_id":77,"initial_payable_kop":45000,"next":"fetch_order"}
```

ID — синтетический пример. Сумма берётся из `consent.accepted.payable_kop`, проверяется целостность структурных денежных инвариантов. Это **первоначально принятая сумма**, не обещание текущей суммы terminal/изменённого заказа. Следующий шаг — существующий авторизованный `GET /instant/orders/{order_id}`: только он даёт актуальные статус, сумму и доступ. Lookup не объявляет поездку активной и не запускает reconcile/matcher. Заказ может быть удалён между чтением и следующим GET.

Для незнакомого, чужого, выданного но ещё не использованного, не закоммиченного или уже удалённого ключа один ответ 200:

```json
{"schema":"taxi-consent-result-v1","state":"unknown"}
```

Ни пустой SELECT, ни expiry, ни потеря Redis, ни таймер/число повторов не превращают unknown в «не создан». Подтверждение могло ещё не закоммититься или начаться после чтения. Такой ответ **не освобождает UI для нового заказа** и не разрешает реконструировать POST. Заново входить/искать пустой список тоже не доказательство отсутствия. Lookup не резервирует, не отменяет, не погашает quote, не продлевает retention и не блокирует будущий create. Ошибка БД/повреждённые metadata даёт двуязычный 503 `taxi_consent_result_unavailable`, а не unknown. SQL exceptions/значения ключа не передаются в ошибку/логи.

Нет копии тела, маршрута, адресов или контактов, нового журнала/таблицы и нового срока хранения. Выбираются только ID и существующие consent metadata; наружу не уходят request_key/quote_id/digests, owner ID, raw snapshot, география или контакты. После физического удаления metadata исчезают вместе с заказом; отличить deletion от неизвестного без отдельного tombstone нельзя. Прежний consumed ключ при этом не получает права создать второй заказ (API07).

## Хранение и действия клиента

Операция читает существующие поля заказа из ревизии `cz_taxi_initial_price_consent`. Отдельная миграция для чтения не требуется.

При `committed` клиент открывает карточку заказа по ID. При `unknown` исход остаётся неопределённым. Для явного закрытия используется [контракт завершения попытки](09-price-consent-close-api.md). Он возвращает `closed/not_created` только после того, как сервер под блокировкой подтвердил, что эта попытка не создала заказ, и сохранил запрет на её дальнейшее подтверждение. Клиент не повторяет отправку заказа автоматически.
