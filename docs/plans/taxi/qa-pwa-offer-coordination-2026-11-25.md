# Такси PWA: проверка одного входящего заказа в двух вкладках

## Ветка и ограничения

- База: `95ffe0a24d453553e6c7786bc60981c5ae6f3d3b`. Таймер закрывает карточку локально: окончанием окна управляет сервер. Бэкенд и Android в этой ветке не меняются.
- Ветка с закрытием по таймеру проверена: 169 наборов (3096 проверок), сборка PWA, два серверных теста с SQLite (тайм-аут и явный отказ). Смоделированы кнопка и таймер настоящего компонента; реальный браузер не запускался.
- Новый кандидат хранит один маркер принятия в IndexedDB на один вход. Проверка актуального входа и сохранение или точное удаление маркера выполняются в той же транзакции, что и доступ к записи входа. Выход удаляет маркер; обновление токена в том же входе его сохраняет. Запись содержит только API, ID водителя, ID заказа и ID попытки. Токены, телефон и маршрут в маркере не хранятся.
- Без Web Locks две одновременные попытки проходят через одну транзакционную запись; при сбое записи кнопка не отправляет запрос. Нет автоматического повтора Accept; при неизвестном ответе выполняется только чтение.
- Не запускать этот кандидат на одном origin с прежней тестовой сборкой, использующей localStorage для ещё не завершённых попыток. Эти два механизма не координируются. Предварительные ветки в main не влиты.
- Не обещаем поддержку старых Safari целиком: iOS-версия и доступность IndexedDB, безопасного контекста и уже используемого в авторизации `crypto.randomUUID` влияют на работу. Web Push от iOS 16.4 относится только к push, а не устанавливает общий минимум браузера. [WebKit о Web Locks в Safari 15.4](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/); [порядок транзакций IndexedDB](https://www.w3.org/TR/IndexedDB-2/#transaction-scheduling).

## До приёмки

1. На точном SHA в двух реальных вкладках прогнать одновременный Accept, истечение второй вкладки, сбой IndexedDB, выход/повторный вход и холодный перезапуск при потерянном ответе. Записывать число POST и итог команды на синтетическом сервере.
2. Отдельно проверить явный «Пропустить» против «Взять» и повторное ручное действие после подтверждённого результата. Непосредственно перед явным отказом клиент читает текущий маркер, но чтение и отправка отказа не образуют общей транзакции с Accept.
3. Перед приёмкой полного набора отдельно совместить с доходом завершённой поездки `26dc441c5286be32e6bcd90e9a7da3f2e596a1c7`: его тесты относятся к другому дереву. Не сливать в main и не развёртывать без отдельного разрешения.

## Кандидат: «Взять» и «Пропустить» в разных вкладках

На базе `ac19004a38c644da71e4bd7faa7827ca76b34290` тест с двумя экземплярами экрана воспроизвёл по одному POST каждого вида при одновременном выборе. В новом кандидате первое успешно сохранённое действие занимает общий слот входа до подтверждения. Вторая вкладка только читает статус. При неизвестном ответе запрос не повторяется; после подтверждения идентификатор закрытого предложения остаётся защищён до исходного дедлайна. После выхода записи удаляются существующей транзакцией отзыва сессии.

Проверено на двух экземплярах настоящих экранов с имитацией IndexedDB и сервера: «Пропустить» первым, «Взять» первым, повторные клики со старой карточки и потерянный ответ на «Пропустить». Проверка в двух реальных вкладках остаётся обязательной. Этот патч не координирует отдельные браузерные профили, разные устройства или старую PWA-вкладку той же тестовой сборки после обновления; для приёмки используйте один точный SHA и чистый профиль. Сервер, Android и ветка дохода не менялись. Отдельный Android-кандидат тайм-аута `efba835a` не включён.
