## 2. Основной принцип

Повышать цену не «потому что можно», а по понятной причине с ограничением и измеренной целью: покрыть обоснованные затраты и помочь получить доступную машину. Нельзя обещать, что любое повышение добавит водителей или обеспечит прибыль.

Предлагаются три независимых слоя:

1. **Базовый сезонный профиль.** Проверяемые долгосрочные затраты класса/территории: зимний расход, шины, обслуживание, время работы. Если утверждён, публикуется заранее как новая версия базового тарифа с датами. Это не ежедневная доплата за календарную зиму и не компенсация любого расхода водителя.
2. **Время дороги.** Прогноз длительности по доступным дорогам с учётом пробок; источник, время прогноза и качество сохраняются. Уже учтённые в длительности задержки дождя/снега второй раз не оплачиваются отдельной «погодной минутой».
3. **Одна ограниченная динамическая доплата за подтверждённый дефицит.** Дождь, концерт, час пик, праздник, ночь могут объяснять дефицит, но не умножаются друг на друга. Дождь без дефицита не включает этот слой. Погода и календарь помогают прогнозировать/проверять спрос, а не служат доказательством дефицита сами по себе.

Отдельную краткосрочную погодную компенсацию затрат пока НЕ вводить: сначала доказать остаточный расход, не покрытый базой, временем и динамической доплатой. Если такая политика позднее нужна, она требует новой схемы/независимой проверки пересечений, а не ещё одного множителя в редакторе.

## 3. Предлагаемый расчёт и объяснение

Схема для проектирования, не готовая функция и не разрешение изменить существующий расчёт:

```text
B = согласованный базовый расчёт выбранного класса/зоны/сезонной версии
    с минимумом, включёнными км/минутами и прогнозом дороги
A = min(округление(B × r), абсолютный_потолок_доплаты)
    где 0 ≤ r ≤ относительный_потолок; все значения конфигурируются
P = B + A + отдельно согласованные услуги/сборы − допустимое промо
```

Здесь B уже включает минимум; A не умножает ожидание, чаевые, компенсации, долги, платную дорогу, подачу и сторонние сборы. Их место и ограничения задаёт06. Если базовая модель не может отделить эти суммы, динамику не подключать до разделения. Это предложение новой схемы, а не утверждение о текущем runtime. Округление A только один раз; копейки, фиксированная точность ставок, не float. Порядок минимума/промо/финального округления явно фиксируется в версии и golden-примерах. Промо не даёт отрицательного итога и не скрывает исходную доплату.

Потолки нужны одновременно в процентах и рублях для класса/территории; крупная базовая цена не должна скрывать чрезмерную надбавку. Сезонная база, длинная подача и дорожные сборы показываются отдельно, чтобы лимит A не выдавался за ограничение всей стоимости. Предельная итоговая цена/ручная проверка необычного маршрута также задаётся до запуска. Нельзя молча обрезать итог ниже договорной выплаты водителю: предложить утверждённую субсидию с бюджетом либо честно недоступную услугу.

Пассажир до заказа видит итог, причину и сумму доплаты, срок предложения, класс, условия платного ожидания/изменения маршрута. Формулировка «мало свободных машин» допустима только при качественных данных. Не обещать «цена снизится через N минут» без надёжного основания. Альтернатива: ждать без гарантии снижения, выбрать другой доступный класс с явным согласием или отменить оформление.

Водителю до принятия видны валовая сумма, динамическая часть, комиссия и понятная ожидаемая выплата с условиями корректировки. Доля A водителю и база комиссии должны быть утверждены отдельно; скрыто увеличивать процент комиссии в пик нельзя. Отклонение небезопасного заказа не превращается автоматически в штраф. Не стимулировать скорость, переработку или выезд на закрытую дорогу.

## 4. Условия и четыре класса

| Условие | Предлагаемое поведение для всех классов | Особые ограничения |
|---|---|---|
| Обычная зима, сухая дорога | Только заранее утверждённый сезонный профиль; A=0 без дефицита | Не брать повторно стоимость шин/аренды, уже включённую в базу |
| Дождь, снегопад, мороз, жара | Обновить прогноз дороги и проверить реальную доступность; A только по достоверному дефициту | Температура сама не доказывает нехватку, расход или безопасность |
| Гололёд, метель, подтопление, закрытие дороги | Сначала безопасность/достижимость; ограничить или остановить новые заказы | Цена не делает опасный маршрут допустимым; неопределённость не считать безопасностью |
| Час пик, конец мероприятия, праздник | Объединить причины в один сигнал дефицита; сгладить, ограничить A | Не умножать «праздник × ночь × дождь × спрос» |
| Ночь без дефицита | Не включать A только по часам | Если нужен плановый ночной базовый профиль, отдельное согласование затрат и пересечений; по умолчанию не включён |
| Долгая подача/пустой возврат в район | Отдельная прозрачная политика06, известная до согласия | Не маскировать под дождь/спрос; не брать пустой возврат повторно |
| Пробка возникла после заказа | Сохранить принятый договор, не начислять новый surge | Компенсация реального перерасхода водителю требует источника финансирования, не скрытой доплаты пассажиру |
| Нет ни одной подходящей машины | Показать недоступность/ограниченный поиск, не «гарантированную подачу за высокую цену» | Для предзаказа отделить заявку, подтверждение наличия и гарантию |

| Класс | Уфа | Районы/межгород | Что не менять из-за пика |
|---|---|---|---|
| Эконом | Самостоятельные профиль затрат, пороги, потолки A; оценивать доступность для регулярных поездок | Малая выборка требует более устойчивого окна/запрета автоматической динамики при недостатке данных | Бесплатные accessibility-опции; верхний класс приехал вместо нижнего не означает доплату |
| Комфорт | Отдельная фактическая доступность и экономика, не копия множителя Эконома | Класс доступен только при подходящем подтверждённом парке | Обещанные характеристики и качество не снижаются молча |
| Бизнес | Те же прозрачность/потолки и права, без персональной оценки платёжеспособности | Нет класса: недоступность либо явное предложение другого класса | Высокая цена не разрешает снять проверку допуска автомобиля |
| Минивэн | Считать подходящие машины с нужным числом мест, не общее supply города | Нулевая/редкая доступность не даёт бесконечную доплату; предзаказ отдельно | Места/багаж/детские кресла и спецоборудование не взаимозаменяемы |

Цена зависит от услуги, а не от владения автомобилем: частная машина и наш арендный парк в одинаковых условиях имеют одинаковое пассажирское правило. Договор аренды, смена водителя и выплаты ведутся отдельно по07. Нельзя повышать цену пассажиру галочкой «арендная» или давать своему парку скрытый приоритет.

## 5. Данные, защита и границы

- Supply: уникальные допущенные свободные водитель+машина с свежим присутствием, подходящим классом/местами/опциями и достижимой подачей. Не считать занятых, отозванных, устаревшие координаты, несколько телефонов одного водителя как разные машины.
- Demand: дедуплицированные реальные намерения/заказы по выбранному окну, а не каждый refresh quote. Учесть отменённые, повторные и подозрительные запросы. Формальное определение счётчика, знаменателя и границ окна утвердить до алгоритма.
- Quality: источник, observed_at/received_at, область покрытия, версия прогноза, единицы, полнота, лимит возраста, минимальная выборка, clock skew. Ноль, неизвестно и timeout различаются. Ошибка Redis/GEO не означает supply=0 и максимальную цену.
- При устаревшей/неполной телеметрии A не повышать: утверждённый короткий срок последнего достоверного значения, затем A=0 либо закрыть новые предложения, если нельзя гарантировать расчёт/безопасность. Конкретный вариант и TTL фиксируются до запуска. Safety-сигналы имеют отдельную свежесть: A=0 не означает, что поездка разрешена.
- Weather provider/аварийные уведомления: источник/лицензия/квоты/бюджет и территориальное покрытие отдельно; конфликтующие/поздние данные не смешивать. Прогноз не подтверждает фактическое состояние дороги. Подтверждение безопасности не возлагается на пассажира кнопкой согласия.
- Территория цен: детерминированное правило по месту подачи, версии геозон и заявленному маршруту; пересечение зон не меняет принятый заказ. Полигональные границы/перекрытия, отсутствие зоны и аэропорт имеют явный приоритет. Пограничный GPS не должен переключать цену туда-сюда.
- Время: хранить UTC, применять утверждённую IANA timezone территории, не телефона и не сервера. Тестировать полночь, сезонные интервалы, календарь праздников и будущие зоны с переводом часов; начало включено, конец исключён. Предзаказ использует согласованное время услуги, а не случайное время фонового запуска.
- Пороги входа/выхода разные, минимальная длительность подтверждения, ограничение скорости роста/снижения, максимум времени действия, автоматический expiry и ручное отключение. Каждая величина остаётся policy-pending, отсутствие конфигурации запрещает включение A.
- Защита от накрутки спроса, сговора временно ушедших offline водителей, GPS spoofing, повторного счёта и повторов событий. Подозрение не даёт автоматического штрафа/бана; действие ограничивает влияние плохих данных, решение и обжалование отдельно.
- Не использовать баланс телефона, модель устройства, личные поездки/профиль, инвалидность или предполагаемую готовность платить для повышения цены. Агрегаты не должны раскрывать положение единственного водителя/пассажира в селе. Минимизировать сырые координаты и сроки хранения; replay доступен только по роли.

## 6. Конфигурация, quote и безопасное управление

В схему06 добавить: class/zone; season_profile/version; IANA timezone; effective interval; определения signal/window; quality gates/TTL; hysteresis/ramp/expiry; relative+absolute cap; breakdown/reason codes; правила комиссии/доли водителя; fallback/safety state; budget guard; schema+policy version. Без произвольного исполняемого кода. Серверные allowlist/права/усиленная авторизация, журнал автора/основания и compare-and-swap остаются обязательными.

Состояния отдельно: normal, scarcity, telemetry-degraded, service-restricted. Ограничение новых заказов не отключает поддержку/историю/безопасное завершение активных. Оператор не может обойти safety ростом цены. При чрезвычайных/опасных событиях предлагается отключать дефицитную доплату в затронутой зоне и решать доступность отдельно; конкретный emergency override и обязанности дежурного утверждаются до выпуска. Никаких автоматических обещаний эвакуации/помощи.

В quote неизменно сохраняются расчёт, B/A/итог, причины и применённые потолки, тарифная и сигнальная версии, качество/время входов, TTL и полный fingerprint намерения. Сырой provider payload/PII не хранить автоматически. Сервер атомарно проверяет владение, актуальность и неизменность условий при принятии.

Действующий quote нельзя повышать; снижение обрабатывается целостным меньшим предложением по06, без смеси старой базы и новой комиссии. Истёкший/утраченный quote требует нового согласия. Зафиксированный заказ не меняется при дожде, росте спроса, смене сезона, перезапуске, переназначении или откате конфигурации. Изменение маршрута пассажиром требует отдельного согласованного расчёта. Предзаказ следует выбранной модели06/08, не превращается молча из фиксированного в оценочный.

Публикация: черновик → валидатор → сравнение на эталонных маршрутах всех классов/территорий → независимое ревью → разрешённый rollout. Атомарное переключение версии и проверка всех экземпляров. Откат действует только на новые предложения; старые снимки и финансовые обязанности сохраняются. Неизвестный исход публикации сначала сверить по idempotency/revision, не повторять как новую операцию. Отмена будущего расписания тоже журналируется.

## 7. Экономика до утверждения значений

Раздельно считать водительскую экономику собственной/арендной машины и экономику платформы/парка. Не суммировать одновременно полную амортизацию владельца и аренду за тот же актив. Зимний расход изучать по классу/топливу/температуре/реальному пробегу, включая подачу и порожняк; не выдавать одну среднюю цифру за всех.

Платформа: комиссия и её налоговая база; эквайринг/выплаты, карты/матрицы/погода, SMS/связь, серверы, поддержка, возвраты/споры/мошенничество, бонусы/гарантии/промо, привлечение, постоянные расходы, налоги и кассовый разрыв. У парка отдельно аренда, простой/ремонт/страхование и риск невыплаты. Валовая аренда не прибыль. Часть затрат на неуспешные поиски распределяется на завершённые заказы, а не исчезает из отчёта.

Проверить обычный/пиковый/зимний день, малая районная выборка, падение конверсии из-за цены, рост отмен, отсутствие реакции supply, дорогой API, длительная пробка после фиксированной цены, субсидия при cap, двойной всплеск события/погоды. Для каждого: маржа поездки и дня, доход водителя после затрат/час и на полный пробег, нагрузка поддержки, бюджет и денежный поток. Среднее положительное не скрывает убыточный класс/район. До запуска нужны согласованные пороги stop-loss, ответственный и источник покрытия гарантированных выплат; этот документ не гарантирует безубыточность.

|---|---|
| SP01: каждый из 4 классов × Уфа/район × сухо/дождь/снег/мороз × достаточно машин | Погода не создаёт A сама; выбран правильный профиль и детализированный итог |
| SP02: те же классы/территории, дефицит+ночь+праздник+погода | Одна A с обоими caps; нет произведения надбавок или повторной оплаты погодных минут |
| SP03: одинаковый маршрут, время прогноза выросло из-за пробки | Обновлённый прогноз применяется к новому предложению; действующий quote в пределах TTL не повышается; после принятия действует snapshot |
| SP04: минимальный/нулевой/дальний путь, дробные единицы, граничная копейка, промо выше суммы | Golden oracle, неотрицательный итог, точное округление, minimum/cap/commission без потери денег |
| SP05: NaN/Infinity/минус/переполнение, неверная валюта/схема/единицы, caps отсутствуют | Валидация отвергает публикацию/расчёт; нет fallback на случайный тариф |
| SP06: 0 supply против unknown/timeout/stale, мало выборки, ложный forecast | Достоверный ноль отличим от сбоя; плохие данные не повышают A; safety отдельно |
| SP07: полночь, граница сезона/зоны, GPS jitter, перекрытие, часовой пояс телефона другой | Детерминированный профиль; принятый заказ не пересчитывается |
| SP08: всплеск/спад у порога, поздний event, массовые retry/боты/offline сговор | Сглаживание/expiry, дедупликация, ограниченное влияние; нет автоматического наказания |
| SP09: quote одновременно принимают/обновляют/публикуют/откатывают/истекает | Один согласованный snapshot и заказ либо явный отказ/новое согласие, никогда смешанный расчёт |
| SP10: ответ create потерян после commit, Redis очищен, DB failover, два устройства | Повтор не создаёт дубль; неизвестное сверяется; нельзя восстановить цену из новых правил |
| SP11: назначение/переназначение/отмена/неявка/частичное завершение/смена маршрута в пик | Комиссия, удержание, возврат и выплата по соответствующему договору/снимку, без новой A задним числом |
| SP12: наличные/безналичные, webhook duplicate/out-of-order, частичный возврат | Единая сверка ledger; не списывать/начислять дважды, причины сумм доступны сторонам |
| SP13: предзаказ через сезон/ночь/рост спроса и отсутствие машины | Применена явно выбранная модель; заявка не названа гарантией; изменения согласованы |
| SP14: закрытая дорога, угроза, emergency override, устаревший safety feed | Цена не обходит запрет; новые заказы ограничены по политике, активные не брошены |
| SP15: все классы, отсутствие/смена класса, собственная/арендная машина и смена водителя | Нет скрытого downgrade/надбавки за аренду, места и допуск соблюдены, выплата адресована верному исполнителю |
| SP16: Android↔PWA, старый клиент, RU/BA, TalkBack/крупный текст/нет карты/слабая сеть | Итог/причина/TTL доступны, новое согласие достижимо; старый клиент не принимает непонятную схему |
| SP17: оператор без роли/отозванная сессия, два редактора, частичный rollout/rollback | Нет неавторизованной цены; конфликт явный; снимки и журнал сохраняются |
| SP18: высокая quote-нагрузка, API quota/cost limit, горячая зона, восстановление | Измеренные latency/throughput и bounded queues; отказ не считается поездкой; safety/активные приоритетны |
| SP19: caps ограничили доход, гарантии/промо/длительная поездка дали убыток | Сработал согласованный бюджетный guard для новых предложений; уже принятые обязательства сохранены |

Денежные и safety варианты обязательно прогнать по всем классам/территориям и критическим пересечениям, не заменить только pairwise. Конкуренцию подтвердить PostgreSQL-барьерами; SQLite и unit недостаточны. Проверки платёжных/погодных аварий имитируются в изолированном стенде, без живых денег/экстренных вызовов. Полные repo gates и независимая продуктовая приёмка на точном SHA обязательны перед кодовым выпуском; документ не доказывает ни одного runtime PASS.

1. Независимо проверить редакционную совместимость с06/08. Значения, права и безопасность не утверждаются ревью текста.
