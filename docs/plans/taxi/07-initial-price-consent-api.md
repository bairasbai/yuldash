# Подтверждение первоначальной цены такси «сейчас», API v1

Это отдельный opt-in серверный контракт. Старые `/instant/estimate`, `/instant/orders`, предзаказы, курьер и попутка сохраняют прежнюю семантику и **не получают эту защиту**. PWA/Android пока не подключены. Этот этап не реализует опубликованные версии тарифов, заморозку ожидания/отмены/комиссии и изменений маршрута в поездке; тарифные правила не меняются.

## Оценка и явное подтверждение

`POST /instant/quotes/v1` принимает существующие поля маршрута EstimateIn, но только `scheduled_at=null`, известные options и без дополнительных полей. Авторизация обязательна. Сервер сам рассчитывает цену и выдаёт независимую неизменяемую пару UUID `quote_id` + `request_key`, `schema=taxi-initial-consent-v1`, `snapshot_digest`, `pricing_inputs_digest`, `expires_at`, `price_kop`, `promo_discount_kop`, `payable_kop`, `breakdown`, расстояние, ETA и round_trip. Все деньги этой новой оценки — целые копейки. Сумма breakdown (ride_price/pickup_fee/options_fee/weather_fee с суффиксом `_kop`) равна price_kop; payable_kop=price_kop−promo_discount_kop. Digest — идентичность снимка/его входов, **не опубликованная версия тарифных правил**.

Владелец, точные конечные координаты, упорядоченные координаты остановок, класс, нормализованные options, round_trip и return_wait_min связаны с оценкой. Подписи точек не меняют цену. В кэше только их salted hash, без второй копии координат/адресов/телефона/получателя. Две вкладки получают разные пары и не заменяют снимки друг друга. Срок берётся из существующего price_freeze_sec; потеря Redis не превращается в незаметный пересчёт с созданием.

Если подача ещё не известна (`pickup_pending`), новый API отказывает `409 taxi_quote_price_pending`: нельзя обещать полный итог, который существующий matcher позже увеличит. Старый режим неизвестной подачи не меняется. При подтверждении известный полный снимок не заменяется свежим снимком с неизвестной подачей.

`POST /instant/orders/confirmed/v1` принимает полный OrderIn и выданную сервером пару UUID. Клиентская сумма не принимается. Неизвестные верхние поля дают422, предзаказ или неизвестная опция —422 taxi_quote_request_invalid. Выбранный закрытый способ оплаты отклоняется422 taxi_quote_payment_unavailable; после успешного создания replay проверяется раньше текущих флагов оплаты.

Перед новым созданием проверяются владелец/пара/срок/маршрут/снимок/промо. Из двух полных расчётов берётся меньшая цена: действующий снимок или новый расчёт с известной подачей. Компоненты не смешиваются. Потеря/изменение ресурса промо или показанного размера скидки требует новой оценки, включая случай уменьшения скидки из-за нового потолка при более дешёвой поездке. Изменение с нулевой скидки на новую тоже требует отдельного подтверждения. Применимое промо проверяется повторно атомарно; проигравший CAS не создаёт заказ без скидки.

409 taxi_quote_refresh_required означает: получить новую оценку, показать итог и ждать нового явного действия. Отказ не возвращает автоматически созданный заказ или автоматическое подтверждение другой цены. Сбой сохранения кэша/его транзакции —503 taxi_quote_unavailable. Запрещён тихий fallback на legacy POST. Ошибки содержат code и RU/BA detail.

Успех200 возвращает `{order, consent:{quote, accepted}}`. `order` — существующий формат заказа с прежней размерностью старых полей (например, price_estimate в рублях); новые *_kop внутри consent однозначно в копейках. quote хранит исходный показанный состав, accepted — выбранный целый состав по той же или меньшей цене и собственный digest. Это первоначальный снимок: terminal cancelled/expired штатно освобождает промо, текущий terminal payload не объявляется обещанием сохранить потраченную скидку.

## Повтор, транзакция и срок хранения

Для блокировки переиспользуется существующий lock_refresh_user без изменений auth-кода: PostgreSQL FOR UPDATE, SQLite no-op UPDATE для writer-lock без изменения last_seen_at. Под блокировкой пассажира сначала ищется `(owner,request_key)` среди **всех** статусов, до Redis/TTL/нового расчёта и feature/payment gates. Тот же полный существенный запрос возвращает тот же заказ с текущим состоянием и исходным consent, в том числе после terminal/потери ответа/истечения оценки. Изменение тела (включая quote_id, подписи, комментарий, получателя/телефон, оплату и women_only) даёт409 taxi_consent_key_conflict. Хеш детерминирован по запросу, не по текущим флагам/цене/часам. Чужой ключ не раскрывает чужого заказа.

Новый несвязанный live-заказ блокирует создание409 taxi_consent_active_order. WATCH устанавливается до чтения кэша; только проверенная неизменившаяся пара удаляется MULTI/EXEC. Затем order, metadata повтора, полный финансовый снимок, CAS промо и допустимое закрытие прежнего expired.wait_until (cancelled, без штрафа/нового списания) коммитятся одной SQL-транзакцией. Закрытый терминальный статус не позволяет уже выбранному worker заново поднять старую очередь. Если worker успел активировать её до блокировки строки, повторная LIVE-проверка перед commit даёт409 и откатывает новый заказ. Телеметрия retry worker отдельно не исправляется. Ошибка/CAS-loss откатывает всё; прежний consume с его commit/fallback для старых клиентов и предзаказов не меняется. Matcher/воронка/модерация вызываются после коммита, replay их не вызывает повторно.

Все четыре consent_* поля nullable и скрыты из обычной сериализации модели. Ограничения unique(owner,key) и unique(quote_id) усиливают транзакционную защиту. Миграция cz_taxi_initial_price_consent после cz_rideshare_recipient_setup добавляет только opt-in metadata; нет копии PII/маршрута и нового журнала хранения. Metadata живёт с самим заказом по существующим cleanup/account. Terminal сам по себе её не удаляет. После фактического удаления заказа вернуть его невозможно: старая пара уже consumed/missing => safe409; новая оценка всегда имеет новый серверный ключ, старый ключ к ней не подходит. Отсутствие metadata не становится разрешением заново принять старую пару.

## Передача PWA/Android отдельным этапом

Read-only API проверки результата только по непрозрачному ключу **в этом контракте нет**. Для replay сейчас нужно точное исходное тело с парой. Нельзя обещать восстановление после перезапуска, если сохранён лишь ключ. Безопасный owner-scoped lookup — отдельная задача; хранение полного тела на клиенте требует отдельной приёмки приватности/сессии/очистки.

Клиентское внедрение должно свести одни и те же options/route inputs при оценке и создании, связать запрос с сессией и текущей формой, сохранять пару только по принятой политике и ждать нового явного действия при409/изменении цены. На Android статически обнаружено отсутствие orderOptions в ключе/входе прежней оценки; это остаётся задачей клиентского этапа. TF09-B и TF10 не считаются частью main и не включены сюда.

Нужны отдельные реальные клиентские проверки двух вкладок, expiry/resume, смены пользователя, stale responses, double tap и восстановления после потери ответа. Этот серверный пакет не является общей E2E-приёмкой такси и не разрешает merge/deploy. Перед будущим выпуском требуется миграция и интеграционная приёмка на актуальной базе.
