# Планы реализации (ТЗ для агентов Codex и Claude)

Здесь лежат пошаговые планы: что сделать, чтобы режим заработал полностью. Один файл — одна функция.
Очередь режимов (решение Александра 24.10.2026): **попутка полностью → курьер → такси**.
По отдельному поручению Александра 25.10.2026 подробный план курьера как второго этапа подготовлен заранее.
Это разрешение на документацию, не приёмка попутки и не запуск курьера. Реализация курьера начинается после
приёмки попутки либо отдельного явного решения владельца о смене очереди. План такси остаётся следующим этапом.

| Папка | Режим | Список планов |
|---|---|---|
| [rideshare/](rideshare/00-index.md) | Попутка | RS-01 … RS-16 |
| [courier/](courier/00-index.md) | Курьер, второй этап | CP-01 … CP-24; подготовлен план, реализация не принята |

Источник требований: исследование Яндекс Go / Яндекс Про / BlaBlaCar (ветка `research/app-audit-snapshot`,
`docs/research/apps/`) — оно описывает чужие приложения и предлагает требования, но **ничего в Юлдаше
не проверяло**. План берёт из него идеи и поведение, не чужой код и не тексты. Ветку ChatGPT перезаписывает
каждой выгрузкой, поэтому ссылки на исследование даются с коммитом (`c5be55a:docs/research/apps/master/part-001.md`).
Решения Александра 24.10.2026 (Q1–Q19) и общие решения после приёмки планов записаны в `docs/decisions.md`.
Решения, которые расходятся с буквой `AGENTS.md`, действуют после строки в `AGENTS.md` (раздел «Исключения» ниже).
Общие механизмы (ошибка с кодом, выключатели владельца, ключ повтора, места по участкам), порядок миграций
и очередь по общим файлам — в [индексе попутки](rideshare/00-index.md).

## Порядок работы агента по плану

1. **Свежий код.** `git fetch origin` и работа от свежего `origin/main`, а не от старой копии:
   Александр пишет и локально, и в облаке. Перед выкладкой своей ветки — снова влей свежий `main`.
2. **Не сделано ли уже.** Открой план и его строку в [индексе](rideshare/00-index.md). Проверь, что пункт
   не сделан и не занят: открытые PR с `[RS-XX]` в названии, `git log origin/main --grep "RS-XX"`, поиск по коду
   из раздела «Что уже есть». Сделано — обнови статус плана (шаг 8) и не делай второй раз.
3. **Занять пункт.** Своя ветка `<claude|codex>/rs-XX-<коротко>` → строка «в работе» в разделе 10 плана →
   push → черновой PR с `[RS-XX]` в начале названия (крупный план — тег части `[RS-02А]`, `[RS-04А1]`; деление —
   в шапке). Push своей ветки и черновой PR разрешены решениями Александра Q3 а и Q4 в, но действуют после строки
   в `AGENTS.md` §8 (раздел «Исключения» ниже). Пока её нет, **любой** агент спрашивает «да» на push; без «да»
   работа остаётся локальной: сообщи Александру зону файлов и статус — локальную отметку другие окружения не видят.
   Открытый PR и есть «замок»: его видят и облачные агенты, и агенты на компьютере
   (файл `%LOCALAPPDATA%\yuldash\locks.md` облаку не виден). Чужой открытый `[RS-XX]` — бери другой пункт.
4. **Параллельно — только без пересечений.** У каждого плана есть «Зона файлов». Пункты с общей зоной —
   по очереди. Общие файлы (`MainActivity.kt`, `YuldashApp.kt`, `ApiClient.kt`, `models.py`, `*.gradle.kts`)
   — правило «один файл — один агент» (`AGENTS.md` §11–§12).
5. **Сделать по шагам плана** и по правилам `AGENTS.md`: два языка, `Canon*`, состояния загрузка/пусто/ошибка,
   деньги — по D7, геолокация после подтверждения. Порядок: прямое поручение Александра в текущей задаче →
   `AGENTS.md` → этот README → план. План не разрешает нарушать правила; нашёл противоречие — останови зависимую
   часть, продолжай независимую и опиши блокер в PR (или в отчёте Александру, если PR ещё нет).
6. **Проверки.** `/gotovo` (Claude) или те же команды из `.claude/skills/gotovo/SKILL.md` (Codex) — с выводом.
   Эмулятор — только на компьютере Александра. Сборку и unit-тесты Android облачный агент делает сам, если
   в его сессии открыт `dl.google.com` (Александр разрешил 24.10, Q19 а; правило сети действует для сессий,
   запущенных после изменения — проверь `curl -sI https://dl.google.com`). Иначе облачный агент делает сервер
   и сайт, а Android-шаги передаёт агенту на компьютере через тот же план (отдельный PR с тегом части).
   Проверка цепочек `tools/audit_traceability/check.py` требует git ≥ 2.44 — запускается на компьютере.
7. **Приёмка — агентом другой «семьи».** Сделал Codex — принимает свежий Claude Opus 5.5; сделал Claude —
   свежий Codex `gpt-6.1-sol` (решение Q9). Принимающий не автор плана, по умолчанию «не принято»,
   сверяет результат с разделом 8 плана и правилами. Вердикт — комментарием в PR с проверенным SHA (если поручение
   запрещает комментарии — в отчёте Александру). Приёмка той же «семьи» приёмкой не считается. Доработка текста
   плана не принимает реализацию и не закрывает реестр аудита.
8. **Отметки.** Раздел 10 плана и строка в индексе: `не начато` → `в работе (PR #N)` → `сделано в коде (PR #N, коммит)`.
   «**Принято**» ставится **только** в [едином реестре](../audit-blocks.md) после настоящей приёмки
   (`AGENTS.md` §13, `/audit-traceability`) — план лишь ссылается на него.
9. **Слияние.** Код в `main` — только после «да» Александра. PR, где меняются **только** файлы `docs/plans/`
   (отметки, уточнения), агент сливает сам при зелёных проверках (решение Q4 в) — после строки-исключения
   в `AGENTS.md` §8; до неё и такой PR ждёт «да».
   Выкладка на сервер, изменение рабочей базы, деньги и тарифы — только после «да» Александра (`AGENTS.md` §8).

## Что такое «Ждёт «да»» в плане

Пункт помечен, если затрагивает деньги или тарифы, рабочую базу данных (миграции), удаление данных, платные
сервисы и договоры, тексты соглашения и политики, класс такси. Код такого пункта можно сделать и принять в ветке;
влить и выложить — только после «да». Выкладка сервера и сайта ждёт «да» всегда и в планах отдельно не пишется.
Для пунктов из этого списка исполнитель до кода показывает уточнённый план принимающему (`AGENTS.md` ⭐ п.8).

## Общие правила кода во всех планах

- Ошибка сервера — только `herr(status, ru, ba, *, code=…)` (вводит RS-01); клиенты ветвят по `code`.
- Миграция — имя без жёсткого префикса: `down_revision` = голова свежего `main` на момент слияния (порядок — индекс).
- Новая таблица или поле с личными данными — срок хранения (`cleanup.py` / `KEEP_FOREVER` с причиной) и поведение
  при удалении аккаунта (`account.py`), иначе покраснеют `test_nothing_grows_forever.py`, `test_account_deletion.py`.
- Единицы денег попутки — целые рубли (D7), в копейки только при показе; суммы в базе на 100 не умножать,
  единицы в одной поездке не смешивать. Перевод — одна функция на платформу, с тестом.

## Исключения из `AGENTS.md` (ждут строку от Александра)

Решения Александра 24.10 (`docs/decisions.md`) расходятся с буквой `AGENTS.md` §8. Правила агентов агент себе
не расширяет: строку вносит сам Александр. Пока её нет, действует `AGENTS.md`: push, черновой PR и любое слияние —
после «да»; пункт с новым денежным полем или пересчётом сумм (RS-02 Б, RS-15) делается только в ветке, с diff
и риском, и вливается после «да» (`AGENTS.md` §8). Предлагаемая строка в `AGENTS.md` §8, в список «Ждёт «да»»:

> Исключения (решения Александра 24.10.2026, `docs/decisions.md`): агент пушит свою ветку и открывает черновой PR
> по плану из `docs/plans/`; PR, где меняются только файлы `docs/plans/`, сливает сам при зелёных проверках.
> Суммы попутки (`Ride.price`, `Booking.price`, `pay_amount`, цены остановок) — целые рубли; в копейки — только при показе.

Исключение D7 не включает банк: RS-08 сохраняет замок онлайн-оплаты из RS-01; такси и доставка — по общему правилу.

## Общие контракты D1–D11 (24.10.2026)

В планах «D1»…«D11» — это пункты ниже (не путать с D-номерами в других документах `docs/`).
Тексты уточнены по [полному обзору B1–B20/N1–N8](https://github.com/bairasbai/yuldash/pull/211#issuecomment-6385928475).
Основа кода — `main` `0ef03f4`. Все продуктовые тесты и миграции ниже — **NOT_EXECUTED**, пока к конкретному
сценарию не приложен реальный вывод. Правки Codex (`101e060`) проверил свежий Claude; его находки исправлены
следующим коммитом — вердикт и SHA в PR #211.

D1. Один механизм «настройки владельца с журналом» вводит RS-04 А1: `backend/app/owner_switches.py`, `appsetting` (`key` PK, `value`, `updated_at`, `updated_by` FK nullable SET NULL), `appsettingchange` (`key`, `old_value`, `new_value`, `admin_id` nullable SET NULL, `created_at`, `note`). Реестр: значения, default, blocker и группа ключей. Запись: все строки группы заведены миграцией, `FOR UPDATE` в порядке ключей, no-op без лишней записи журнала; `admin_action`. Журнал KEEP_FOREVER с причиной, при удалении админа SET NULL. Ключи `login.sms|telegram|vk|whatsapp`, затем `rideshare_card_payments`. Telegram нельзя выключить, пока это единственный путь администратора D8. Кеш ≤10 с допустим только для отображения/config; **авторизация, резерв платного кода и денежный gate читают БД авторитетно под нужными замками**, не кеш. Off линеаризуется commit записи под теми же замками, что выдача разрешения; тест off↔операция обязателен. RS-08 всегда `effective=false`, blocker `bank_project_unaccepted`, hard lock не связан со stored. В dev/тестах SMS может быть default-on; платный провайдер не вызывается. Один экран «Выключатели» Android/PWA создаёт RS-04; RS-08 добавляет раздел. Ответ `{stored,effective,blockers,updated_at,updated_by_name,history[50]}`, доступ по D8 (выключить `rideshare_card_payments` может любой администратор, RS-08).

D2. Единый договор ошибок вводит RS-01 (первым): `herr(status, ru, ba, *, code=None, **extra)` в `backend/app/errors.py` → ответ `{"ru","ba","code",…}` как у `_pickup_refusal` (`bookings.py:302`); сайт — поле `code` в `ApiError` (`webapp/src/api/client.ts`); Android — `detailCode`. Клиенты ветвят по `code`, а не по HTTP-статусу. Все планы используют только это (никаких ручных `HTTPException(detail={…})`), а пункты «если `code` в `ApiError` нет — добавить» заменить ссылкой на RS-01.

D3. Миграции: `down_revision` = голова свежего разрешённого основания; имя `<префикс>_<суть>_<дата>`, префикс по индексу. Одна голова, up→down→up на SQLite/PostgreSQL, сторожа `test_migrations_reach_production.py`, `test_migrations_match_the_models.py`. Кроме чистой БД — точная схема предыдущего main со старыми синтетическими строками → target, сохранность значений/смысл backfill, согласованный rollback каждой миграции. `create_all` новых моделей не заменяет старую схему. Линейная очередь и возможные потери при downgrade — в индексе; рабочая БД/её копия в этих тестах не используется.

D4. Каждый крупный план делится на PR с тегами в названии: `[RS-XXА]`, `[RS-XXБ]`… (замок — по тегу части). Обычное деление: сервер (облачный агент) → сайт → Android (агент на компьютере Александра; облачный тоже, когда откроется `dl.google.com`). Деление записать в шапку плана строкой «Деление на PR».

D5. В шапку каждого плана добавить строки: «Не параллельно с» (по индексу), «Деление на PR», «Проверка `yuldash-security-privacy`: да/нет». В §4 — обязательная строка «Срок хранения (`cleanup`/`KEEP_FOREVER`) и удаление аккаунта (`account.py`)» для каждой новой таблицы/поля с личными данными. Новый раздел в конце §8 или §10: «Мозг» — что дописать в `docs/architecture.md`, `decisions.md`, `tasks.md`, `lessons.md` (⭐ п.6).

D6. RS-01: вкладки «Такси» и «Курьер» НЕ скрывать — сохраняется «Скоро в Юлдаше», лист ожидания и предварительная запись. Направление сверки кода посадки НЕ менять (Q14 а); тексты не обещают серверной проверки. Hard lock RS-01 «оплата брони card/sbp → всегда 503, до создания Payment/вызова провайдера» сохраняется в RS-08. Снять его может только отдельный принятый банковский проект с новым разрешением владельца; флаги, ключи, договор и выбор водителя его не снимают.

D7. Единицы денег попутки — **РЕШЕНО 24.10: вариант А** (Александр поручил решить: «сделай как правильно и считаешь нужным»). `Ride.price`, `Booking.price`, `pay_amount`, входные цены остановок, их JSON-хранение и ответы — целые рубли; это осознанное исключение из `AGENTS.md` §8 (строка — раздел «Исключения»). Ни миграция, ни перенос данных суммы на 100 не умножают. На Android и сайте — по одной функции перевода для показа (`rub → kop → kopToRub`), с тестами туда-обратно, границ и переполнения; внутри одной поездки единицы не смешиваются. Такси, доставка и банк в исключение не входят. Денежная часть делается в ветке, с diff и риском; вливается после «да» Александра (`AGENTS.md` §8).

D8. RS-04: роль сама по себе не даёт привилегии сессии. Все admin/switches/денежные двери требуют `require_telegram_admin`: role=admin **и** проверенный сервером `amr=telegram`. Исключение — выключение оплаты картой (RS-08): безопасное направление, достаточно `role=admin` в любой действующей сессии (решение Александра 24.10). User и RefreshToken хранят `auth_epoch` (BIGINT default0), RefreshToken — `auth_method`, `auth_time`; JWT получает epoch/amr/auth_time после проверенного входа, refresh переносит из БД без усиления по текущей роли. При Telegram-повышении под `lock_refresh_user` (User→RefreshToken) одной транзакцией увеличить auth_epoch, сдвинуть `tokens_valid_from`, отозвать ВСЕ прежние refresh, обновить роль; новая Telegram-пара выдаётся строго после границы. Access (включая optional/WS), refresh и recovery-child требуют token epoch==User.auth_epoch, отсутствие поля=0; старые пары закрыты даже при одинаковом времени iat. Миграция помечает прежние сессии legacy; существующим admin отзывает сессии для нового Telegram-входа. JWT без amr не привилегирован. Тесты: SMS access+refresh до повышения → обе недействительны после; Telegram и её refresh сохраняют assurance; SMS с ADMIN_PHONES не получает admin-доступ.

D9. RS-03: один явный allowlist DTO по actor/роли/фазе для **всех** поверхностей: details, списки, ответы confirm/cancel/decline/no-show/driver-status, `_booking_out`, `response_model`, события, export/share/SOS и replay квитанций. Точку, note и proposal водитель видит только при `confirmed`/`onboard`; после terminal — только признак «место было указано». Посторонний не получает личных точек; собственные данные пассажира и аварийный доступ — по отдельной серверной политике. Сохранённый ответ команды не обходит актуальные права/фазу: хранить ссылку на результат, сериализовать заново, не возвращать сырой Booking/старый JSON. Срок зачистки — от `ride.depart_at`, детали в RS-03.

D10. Выкладка сервера и сайта всегда ждёт «да» (§8) и в столбце «Ждёт «да»» не повторяется; столбец — деньги и тарифы, миграции рабочей базы, удаление данных, платные сервисы/договоры, тексты соглашения и политики, класс такси.

D11. Ключ повтора (`Idempotency-Key`) RS-05: `[A-Za-z0-9_-]{16,128}`; серия RS-09 — базовый ≤115 знаков + `-YYYYMMDDhhmm` (UTC до минуты, 13 знаков). Unresolved-intent сохраняет ключ/хеш через 15 минут/24 часа/рестарт; повтор посылает только неизменный исходный payload, а при его утрате делает GET/close, TTL не создаёт новое намерение. После окна полного ответа остаётся tombstone с результатом/ссылкой до удаления аккаунта; повтор старого ключа не исполняет эффект снова. Сверка `GET /command-intents/{key}` различает подтверждённый исход и неизвестный результат. Новое намерение требует явного отдельного действия после сверки, даже если первая бронь уже отклонена. Повтор серии всегда `/rides/series`, включая подмножество из одной даты.

## Как устроен план

Шаблон — [TEMPLATE.md](TEMPLATE.md). Разделы: что получит человек → что уже есть в коде → шаги для сервера,
Android и сайта → база данных → надписи → состояния экрана → тесты → приёмка → риски → журнал статуса.
Ссылки «файл:строка» даны на `main` того дня, что указан в плане; номера строк уезжают — ищи по имени.

## Кто следит за актуальностью

Плановая сверка Claude (дважды в день, решение Q6 а) сравнивает планы с `main` и открытыми PR и обновляет отметки
отдельным PR только по `docs/plans/`, сохраняя чужие изменения. Сама сливает его только после строки-исключения
в `AGENTS.md` §8; до неё — оставляет PR и пишет Александру.
