# Планы реализации (ТЗ для агентов Codex и Claude)

Здесь лежат пошаговые планы: что сделать, чтобы режим заработал полностью. Один файл — одна функция.
Очередь режимов (решение Александра 24.10.2026): **попутка полностью → курьер → такси**.
Планы курьера и такси пишутся только после приёмки попутки.

| Папка | Режим | Список планов |
|---|---|---|
| [rideshare/](rideshare/00-index.md) | Попутка | RS-01 … RS-16 |

Источник требований: исследование Яндекс Go / Яндекс Про / BlaBlaCar (ветка `research/app-audit-snapshot`,
`docs/research/apps/`) — оно описывает чужие приложения и предлагает требования, но **ничего в Юлдаше
не проверяло**. План берёт из него идеи и поведение, не чужой код и не тексты. Ветку ChatGPT перезаписывает
каждой выгрузкой, поэтому ссылки на исследование даются с коммитом (`c5be55a:docs/research/apps/master/part-001.md`).
Решения Александра 24.10.2026 (Q1–Q19) и общие решения после приёмки планов записаны в `docs/decisions.md`.
Общие механизмы (ошибка с кодом, выключатели владельца, ключ повтора, места по участкам), порядок миграций
и очередь по общим файлам — в [индексе попутки](rideshare/00-index.md).

## Порядок работы агента по плану

1. **Свежий код.** `git fetch origin` и работа от свежего `origin/main`, а не от старой копии:
   Александр пишет и локально, и в облаке. Перед выкладкой своей ветки — снова влей свежий `main`.
2. **Не сделано ли уже.** Открой план и его строку в [индексе](rideshare/00-index.md). Проверь, что пункт
   не сделан и не занят: открытые PR с `[RS-XX]` в названии, `git log origin/main --grep "RS-XX"`, поиск по коду
   из раздела «Что уже есть». Сделано — обнови статус плана (шаг 8) и не делай второй раз.
3. **Занять пункт.** Своя ветка `<claude|codex>/rs-XX-<коротко>` → первый коммит: строка «в работе»
   в разделе 10 плана → push → **черновой PR с `[RS-XX]` в начале названия** (крупный план — тег части:
   `[RS-02А]`, `[RS-04А1]`; деление — в шапке плана). Push своей ветки и черновой PR — по решениям
   Александра Q3 а и Q4 в от 24.10 (`docs/decisions.md`). `AGENTS.md` §8 пока говорит «push — после «да»»:
   строку-исключение туда вносит сам Александр; до этого Codex, читающий только `AGENTS.md`, спрашивает «да».
   Открытый PR и есть «замок»: его видят и облачные агенты, и агенты на компьютере
   (файл `%LOCALAPPDATA%\yuldash\locks.md` облаку не виден). Чужой открытый `[RS-XX]` — бери другой пункт.
4. **Параллельно — только без пересечений.** У каждого плана есть «Зона файлов». Пункты с общей зоной —
   по очереди. Общие файлы (`MainActivity.kt`, `YuldashApp.kt`, `ApiClient.kt`, `models.py`, `*.gradle.kts`)
   — правило «один файл — один агент» (`AGENTS.md` §11–§12).
5. **Сделать по шагам плана** и по правилам `AGENTS.md`: два языка, `Canon*`, состояния загрузка/пусто/ошибка,
   деньги в копейках, геолокация после подтверждения. План не разрешает нарушать правила; нашёл противоречие —
   остановись и опиши его в PR.
6. **Проверки.** `/gotovo` (Claude) или те же команды из `.claude/skills/gotovo/SKILL.md` (Codex) — с выводом.
   Эмулятор — только на компьютере Александра. Сборку и unit-тесты Android облачный агент делает сам, если
   в его сессии открыт `dl.google.com` (Александр разрешил 24.10, Q19 а; правило сети действует для сессий,
   запущенных после изменения — проверь `curl -sI https://dl.google.com`). Иначе облачный агент делает сервер
   и сайт, а Android-шаги передаёт агенту на компьютере через тот же план (отдельный PR с тегом части).
   Проверка цепочек `tools/audit_traceability/check.py` требует git ≥ 2.44 — запускается на компьютере.
7. **Приёмка — агентом другой «семьи».** Сделал Codex — принимает свежий Claude Opus 5.5; сделал Claude —
   свежий Codex `gpt-6.1-sol` (решение Q9). Принимающий не автор плана, по умолчанию «не принято»,
   сверяет результат с разделом 8 плана и правилами. Вердикт — комментарием в PR.
8. **Отметки.** Раздел 10 плана и строка в индексе: `не начато` → `в работе (PR #N)` → `сделано в коде (PR #N, коммит)`.
   «**Принято**» ставится **только** в [едином реестре](../audit-blocks.md) после настоящей приёмки
   (`AGENTS.md` §13, `/audit-traceability`) — план лишь ссылается на него.
9. **Слияние.** Код в `main` — только после «да» Александра. PR, где меняются **только** файлы `docs/plans/`
   (отметки, уточнения), агент сливает сам при зелёных проверках (решение Q4).
   Выкладка на сервер, изменение рабочей базы, деньги и тарифы — только после «да» Александра (`AGENTS.md` §8).

## Что такое «Ждёт «да»» в плане

Пункт помечен, если затрагивает деньги или тарифы, рабочую базу данных (миграции), удаление данных, платные
сервисы и договоры, тексты соглашения и политики, класс такси. Код такого пункта можно сделать и принять в ветке;
влить и выложить — только после «да». Выкладка сервера и сайта ждёт «да» всегда и в планах отдельно не пишется.
Для пунктов из этого списка исполнитель до кода показывает уточнённый план принимающему (`AGENTS.md` ⭐ п.8).

## Общие правила кода во всех планах

- Ошибка сервера — только `herr(status, ru, ba, *, code=…)` (вводит RS-01); клиенты ветвят по `code`.
- Миграция — имя без жёсткого префикса: `down_revision` = голова свежего `main` на момент слияния (порядок — индекс).
- Новая таблица или поле с личными данными — срок хранения (`cleanup.py` / `KEEP_FOREVER` с причиной) и поведение
  при удалении аккаунта (`account.py`), иначе покраснеют `test_nothing_grows_forever.py`, `test_account_deletion.py`.
- Единицы денег попутки (`Ride.price` сейчас — целые рубли, а §8 требует копейки) — ждут решения Александра;
  до решения новые денежные поля не реализуются (см. RS-02).

## Общие решения D1–D11 (24.10.2026, после независимой приёмки планов)

В планах «D1»…«D11» — это пункты ниже (не путать с D-номерами в других документах `docs/`).
Открытые вопросы Александру — единицы цен (D7) и замок «Telegram нельзя выключить» (следствие D8) —
перечислены в верхней записи `docs/decisions.md` от 24.10.

D1. ОДИН механизм «настройки владельца с журналом». Вводит RS-04 часть А1 (этап 2): модуль `backend/app/owner_switches.py`, таблицы `appsetting` (`key` PK, `value`, `updated_at`, `updated_by` FK nullable ON DELETE SET NULL) и `appsettingchange` (`key`, `old_value`, `new_value`, `admin_id` nullable SET NULL, `created_at`, `note`). Реестр ключей в коде: допустимые значения, значение по умолчанию, функция-блокер (почему нельзя включить), правило группы (например «нельзя выключить последний способ входа»). Запись — строки заведены миграцией, `FOR UPDATE` по всем ключам группы в порядке ключей; то же значение — 200 без строки журнала; `admin_action`. Журнал — бессрочно (`cleanup.KEEP_FOREVER` с причиной); удаление аккаунта админа — SET NULL (`account.py`). Кеш чтения ≤10 с. Ключи: `login.sms|telegram|vk|whatsapp` (RS-04), `rideshare_card_payments` (RS-08). Вне прода (dev/тесты) способ `login.sms` по умолчанию включён (17 тестов ходят через `/auth/request-code`). Один экран админки «Выключатели» (Android + сайт) создаёт RS-04 (⭐ п.4), RS-08 добавляет в него раздел. `LoginMethodSwitch` больше нет. Ответ ручек админки: `{stored, effective, blockers, updated_at, updated_by_name, history[50]}`.

D2. Единый договор ошибок вводит RS-01 (первым): `herr(status, ru, ba, *, code=None, **extra)` в `backend/app/errors.py` → ответ `{"ru","ba","code",…}` как у `_pickup_refusal` (`bookings.py:302`); сайт — поле `code` в `ApiError` (`webapp/src/api/client.ts`); Android — `detailCode`. Клиенты ветвят по `code`, а не по HTTP-статусу. Все планы используют только это (никаких ручных `HTTPException(detail={…})`), а пункты «если `code` в `ApiError` нет — добавить» заменить ссылкой на RS-01.

D3. Миграции: имён с жёстким префиксом в планах не задавать. Правило: перед слиянием свежий `origin/main`, `alembic heads` → `down_revision` = эта голова, префикс — следующая свободная буква; одна голова; up→down→up на SQLite и PostgreSQL; сторожа `test_migrations_reach_production.py`, `test_migrations_match_the_models.py`. Порядок по умолчанию — в индексе (раздел «Порядок миграций»). В §4 плана — «имя: `<префикс>_<суть>_<дата>`, префикс по индексу».

D4. Каждый крупный план делится на PR с тегами в названии: `[RS-XXА]`, `[RS-XXБ]`… (замок — по тегу части). Обычное деление: сервер (облачный агент) → сайт → Android (агент на компьютере Александра; облачный тоже, когда откроется `dl.google.com`). Деление записать в шапку плана строкой «Деление на PR».

D5. В шапку каждого плана добавить строки: «Не параллельно с» (по индексу), «Деление на PR», «Проверка `yuldash-security-privacy`: да/нет». В §4 — обязательная строка «Срок хранения (`cleanup`/`KEEP_FOREVER`) и удаление аккаунта (`account.py`)» для каждой новой таблицы/поля с личными данными. Новый раздел в конце §8 или §10: «Мозг» — что дописать в `docs/architecture.md`, `decisions.md`, `tasks.md`, `lessons.md` (⭐ п.6).

D6. RS-01: вкладки «Такси» и «Курьер» НЕ скрывать — действует прежнее решение «Скоро в Юлдаше» с листом ожидания такси и «Стать курьером заранее» (`docs/decisions.md` ~6930); пункт убрать из плана. Направление сверки кода посадки НЕ менять (Q14 а: оставить как есть) — только честные формулировки без слов-гарантий. Серверный замок «оплата брони картой/онлайн → всегда 503» (пока нет RS-08) переносится в RS-01 — это деньги, «Ждёт «да»: деньги (замок онлайн-оплаты брони), текст соглашения».

D7. Единицы денег попутки — ВОПРОС АЛЕКСАНДРУ (ещё не решён). Сейчас `Ride.price`, `Booking.price`, `pay_amount` — целые рубли, а `AGENTS.md` §8 требует копейки. В RS-02 и всех планах с новыми денежными полями (RS-02, RS-07, RS-09, RS-12) записать: «Единицы — по решению Александра (вопрос от 24.10): вариант А — осознанное исключение «цены попутки — целые рубли», в копейки только на границе показа (`kopToRub(rub*100)`), смешивать единицы в одной поездке нельзя, серверный тест на единицу; вариант Б — перевод попутки в копейки отдельной миграцией до RS-02. До решения денежную часть не реализовывать.» Не выбирайте за Александра.

D8. Безопасность входа (RS-04): роль администратора НИКОГДА не выдаётся входом по СМС/VK/WhatsApp — только входом через Telegram владельца (`admin_telegram_chat_id`) или с подтверждением в Telegram; тест «вход по СМС с номером из `ADMIN_PHONES` → не админ».

D9. RS-03: точную точку и пояснение водитель видит только при статусе брони `confirmed`/`onboard`; после `done` — только «место было указано»; срок зачистки — от `ride.depart_at`.

D10. Выкладка сервера и сайта всегда ждёт «да» (§8) и в столбце «Ждёт «да»» не повторяется; столбец — деньги и тарифы, миграции рабочей базы, удаление данных, платные сервисы/договоры, тексты соглашения и политики, класс такси.

D11. Отметки и повтор: формат ключа повтора (`Idempotency-Key`) фиксирует RS-05: `[A-Za-z0-9_-]{16,128}`; производные ключи (RS-09 серия) — базовый ≤115 знаков + суффикс; при повторе части серии — тот же базовый ключ.

## Как устроен план

Шаблон — [TEMPLATE.md](TEMPLATE.md). Разделы: что получит человек → что уже есть в коде → шаги для сервера,
Android и сайта → база данных → надписи → состояния экрана → тесты → приёмка → риски → журнал статуса.
Ссылки «файл:строка» даны на `main` того дня, что указан в плане; номера строк уезжают — ищи по имени.
