## Что такое «Ждёт «да»» в плане

Пункт помечен, если затрагивает деньги или тарифы, рабочую базу данных (миграции), удаление данных, платные
сервисы и договоры, тексты соглашения и политики, класс такси. Код такого пункта можно сделать и принять в ветке;
влить и выложить — только после «да». Выкладка сервера и сайта ждёт «да» всегда и в планах отдельно не пишется.
Для пунктов из этого списка исполнитель до кода показывает уточнённый план принимающему (`AGENTS.md` ⭐ п.8).

## Общие правила кода во всех планах

- Ошибка сервера — только `herr(status, ru, ba, *, code=…)` (вводит RS-01); клиенты ветвят по `code`.
- Миграция — имя без жёсткого префикса: `down_revision` = голова свежего `main` на момент слияния (порядок — индекс).
- Новая таблица или поле с личными данными — срок хранения (`cleanup.py` / `KEEP_FOREVER` с причиной) и поведение
  при удалении аккаунта (`account.py`), иначе покраснеют `test_nothing_grows_forever.py`, `test_account_deletion.py`.
- Существующие суммы попутки сохраняются как legacy-рубли; автоматической миграции ×100 нет. Целевой контракт
  D7 описан для проверки, но его реализация ждёт согласованного владельцем ограниченного исключения из §8.

## Разрешения и денежный gate (B5)

`AGENTS.md` §8 требует копейки; действующий код попутки хранит рубли. Лучший технический вариант — сохранить
эти единицы с узким исключением, а не менять значения в рабочей базе. **До явного согласования владельцем
исключения и его фиксации в `AGENTS.md` новые денежные поля, пересчёт цены и изменённые денежные API закрыты**
(RS-02 Б, денежные шаги RS-07/09/12/14/15). Разрешены документация, чтение и независимые неденежные части.
Авторский текст PR, Q-запись или рекомендация ревью не являются таким согласованием. Агент `AGENTS.md` не меняет.

Предмет согласования: только `Ride.price`, `Booking.price`, `pay_amount`, цены остановок и их DTO попутки — целые
рубли; taxi/courier и банковский учёт не меняются. Форматирование через один проверяемый адаптер на каждой
платформе (`rub → kop → kopToRub`), без разбросанных ×100. Отдельно всё ещё нужны «да» на push, merge,
миграцию рабочей базы и выкладку. Разрешение на D7 не включает банк: RS-08 сохраняет hard lock RS-01.

## Общие контракты D1–D11 (24.10.2026, до новой независимой проверки)

В планах «D1»…«D11» — это пункты ниже (не путать с D-номерами в других документах `docs/`).
Тексты уточнены по [полному обзору B1–B20/N1–N8](https://github.com/bairasbai/yuldash/pull/211#issuecomment-6385928475).
Основа кода — `0ef03f4194012431e0996be4d8e748d37e34d63d`, сохранены новые изменения автора до
`7e532d0e3274c2bc4988f6bf4d4507fbaae753dc`. Все продуктовые тесты и миграции ниже — **NOT_EXECUTED**,
пока к конкретному сценарию не приложен реальный вывод. Независимая проверка нового SHA ещё впереди.

D1. Один механизм «настройки владельца с журналом» вводит RS-04 А1: `backend/app/owner_switches.py`, `appsetting` (`key` PK, `value`, `updated_at`, `updated_by` FK nullable SET NULL), `appsettingchange` (`key`, `old_value`, `new_value`, `admin_id` nullable SET NULL, `created_at`, `note`). Реестр: значения, default, blocker и группа ключей. Запись: все строки группы заведены миграцией, `FOR UPDATE` в порядке ключей, no-op без лишней записи журнала; `admin_action`. Журнал KEEP_FOREVER с причиной, при удалении админа SET NULL. Ключи `login.sms|telegram|vk|whatsapp`, затем `rideshare_card_payments`. Telegram нельзя выключить, пока это единственный путь администратора D8. Кеш ≤10 с допустим только для отображения/config; **авторизация, резерв платного кода и денежный gate читают БД авторитетно под нужными замками**, не кеш. Off линеаризуется commit записи под теми же замками, что выдача разрешения; тест off↔операция обязателен. RS-08 всегда `effective=false`, blocker `bank_project_unaccepted`, hard lock не связан со stored. В dev/тестах SMS может быть default-on; платный провайдер не вызывается. Один экран «Выключатели» Android/PWA создаёт RS-04; RS-08 добавляет раздел. Ответ `{stored,effective,blockers,updated_at,updated_by_name,history[50]}`, доступ только по D8.

D2. Единый договор ошибок вводит RS-01 (первым): `herr(status, ru, ba, *, code=None, **extra)` в `backend/app/errors.py` → ответ `{"ru","ba","code",…}` как у `_pickup_refusal` (`bookings.py:302`); сайт — поле `code` в `ApiError` (`webapp/src/api/client.ts`); Android — `detailCode`. Клиенты ветвят по `code`, а не по HTTP-статусу. Все планы используют только это (никаких ручных `HTTPException(detail={…})`), а пункты «если `code` в `ApiError` нет — добавить» заменить ссылкой на RS-01.

D3. Миграции: `down_revision` = голова свежего разрешённого основания; имя `<префикс>_<суть>_<дата>`, префикс по индексу. Одна голова, up→down→up на SQLite/PostgreSQL, сторожа `test_migrations_reach_production.py`, `test_migrations_match_the_models.py`. Кроме чистой БД — точная схема предыдущего main со старыми синтетическими строками → target, сохранность значений/смысл backfill, согласованный rollback каждой миграции. `create_all` новых моделей не заменяет старую схему. Линейная очередь и возможные потери при downgrade — в индексе; рабочая БД/её копия в этих тестах не используется.

D4. Каждый крупный план делится на PR с тегами в названии: `[RS-XXА]`, `[RS-XXБ]`… (замок — по тегу части). Обычное деление: сервер (облачный агент) → сайт → Android (агент на компьютере Александра; облачный тоже, когда откроется `dl.google.com`). Деление записать в шапку плана строкой «Деление на PR».

D5. В шапку каждого плана добавить строки: «Не параллельно с» (по индексу), «Деление на PR», «Проверка `yuldash-security-privacy`: да/нет». В §4 — обязательная строка «Срок хранения (`cleanup`/`KEEP_FOREVER`) и удаление аккаунта (`account.py`)» для каждой новой таблицы/поля с личными данными. Новый раздел в конце §8 или §10: «Мозг» — что дописать в `docs/architecture.md`, `decisions.md`, `tasks.md`, `lessons.md` (⭐ п.6).

D6. RS-01: вкладки «Такси» и «Курьер» НЕ скрывать — сохраняется «Скоро в Юлдаше», лист ожидания и предварительная запись. Направление сверки кода посадки НЕ менять (Q14 а); тексты не обещают серверной проверки. Hard lock RS-01 «оплата брони card/sbp → всегда 503, до создания Payment/вызова провайдера» сохраняется в RS-08. Снять его может только отдельный принятый банковский проект с новым разрешением владельца; флаги, ключи, договор и выбор водителя его не снимают.

D7. **Рекомендация, gate закрыт до согласованного владельцем исключения из `AGENTS.md` §8.** Сохранить legacy-рубли попутки: `Ride.price`, `Booking.price`, `pay_amount`, входные цены остановок, JSON-хранение и выходные DTO — целые рубли. Ни миграция, ни backfill не умножает суммы на 100. После согласования реализовать по одному адаптеру отображения на Android/PWA, тесты round-trip/границ/переполнения; только на этой границе переводить в копейки для существующего форматтера. Внутри одной поездки единицы не смешиваются. Taxi/courier/банк вне исключения. До согласования разрешено исправлять эти планы, но не вводить изменённый денежный контракт. Отдельные «да» на push, merge, миграцию/выкладку сохраняются.

D8. RS-04: роль сама по себе не даёт привилегии сессии. Все admin/switches/денежные двери требуют `require_telegram_admin`: role=admin **и** проверенный сервером `amr=telegram`. User и RefreshToken хранят `auth_epoch` (BIGINT default0), RefreshToken — `auth_method`, `auth_time`; JWT получает epoch/amr/auth_time после проверенного входа, refresh переносит из БД без усиления по текущей роли. При Telegram-повышении под `lock_refresh_user` (User→RefreshToken) одной транзакцией увеличить auth_epoch, сдвинуть `tokens_valid_from`, отозвать ВСЕ прежние refresh, обновить роль; новая Telegram-пара выдаётся строго после границы. Access (включая optional/WS), refresh и recovery-child требуют token epoch==User.auth_epoch, отсутствие поля=0; старые пары закрыты даже при одинаковом времени iat. Миграция помечает прежние сессии legacy; существующим admin отзывает сессии для нового Telegram-входа. JWT без amr не привилегирован. Тесты: SMS access+refresh до повышения → обе недействительны после; Telegram и её refresh сохраняют assurance; SMS с ADMIN_PHONES не получает admin-доступ.

D9. RS-03: один явный allowlist DTO по actor/роли/фазе для **всех** поверхностей: details, списки, ответы confirm/cancel/decline/no-show/driver-status, `_booking_out`, `response_model`, события, export/share/SOS и replay квитанций. Точку, note и proposal водитель видит только при `confirmed`/`onboard`; после terminal — только признак «место было указано». Посторонний не получает личных точек; собственные данные пассажира и аварийный доступ — по отдельной серверной политике. Сохранённый ответ команды не обходит актуальные права/фазу: хранить ссылку на результат, сериализовать заново, не возвращать сырой Booking/старый JSON. Срок зачистки — от `ride.depart_at`, детали в RS-03.

D10. Выкладка сервера и сайта всегда ждёт «да» (§8) и в столбце «Ждёт «да»» не повторяется; столбец — деньги и тарифы, миграции рабочей базы, удаление данных, платные сервисы/договоры, тексты соглашения и политики, класс такси.

D11. Ключ повтора (`Idempotency-Key`) RS-05: `[A-Za-z0-9_-]{16,128}`; серия RS-09 — базовый ≤115 знаков + `-YYYYMMDDhhmm` (UTC до минуты, 13 знаков). Unresolved-intent сохраняет ключ/хеш через 15 минут/24 часа/рестарт; повтор посылает только неизменный исходный payload, а при его утрате делает GET/close, TTL не создаёт новое намерение. После окна полного ответа остаётся tombstone с результатом/ссылкой до удаления аккаунта; повтор старого ключа не исполняет эффект снова. Сверка `GET /command-intents/{key}` различает подтверждённый исход и неизвестный результат. Новое намерение требует явного отдельного действия после сверки, даже если первая бронь уже отклонена. Повтор серии всегда `/rides/series`, включая подмножество из одной даты.

## Кто следит за актуальностью

Упомянутая в истории Q6 плановая сверка не создаётся этим документом. При отдельно порученной сверке сравнить
свежие main/head, сохранить чужие изменения, обновить локальные отметки; push/PR/merge — в пределах явного
разрешения владельца. При паузе передать координатору статус и очередь файлов, не публиковать сообщения автоматически.
