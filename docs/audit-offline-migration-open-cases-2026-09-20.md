# Следующие проверки офлайн-хранилища — 20.09.2026

Это реестр отдельных границ и их статусов. Не каждый пункт остаётся открытым: ниже указаны ссылки на последующие проверки. Исходники: TripPass.kt, OfflineStoreReset.kt, OfflineWrites.kt. Исправление отказа копирования описано отдельно в audit-migration-and-taxi-docs-2026-09-20.md.

## Удаление исходника после удачного копирования — исправление проверено отдельно

Код до этой группы удалял plain через apply после подтверждённой secure-копии. Если удаление не попадёт на диск, следующий init может снова перенести устаревший источник поверх обновлённого secure. Нужен отдельный тест с раздельными памятью/диском и настоящим повторным запуском.

Простой вариант «если удаление не удалось, восстановить plain и продолжать писать туда» **недостаточен**: скопировать pass7 → отказ удаления исходника → восстановить plain7 → удалить plain7 → новый init видит пустой plain и выбирает прежнюю secure7. Промежуточная копия воскреснет. Нельзя безусловно clear всего secure: там могут быть действующие паспорта, отсутствующие в fallback.

Предложение для отдельной реализации: подтверждённый журнал повторяемого переноса в plain, затем подтверждённая запись только перечисленных ключей в secure, затем одним plain commit удалить исходники и журнал. До завершения запретить изменения/flush и честно возвращать отказ сохранения. При commit(false), изменившем память, удерживать pending-журнал в объекте до подтверждённого завершения. Выход должен согласованно отменять его только после сохранения требования очистить secure. Реализован журнал и временный запрет изменений; доказательства и точные ограничения — [новый отчёт](audit-offline-migration-journal-2026-09-20.md). Непрерывный приём новых офлайн-действий во время такого отказа по-прежнему потребует более сложного журнала операций с отметками удаления.

## Удаление отметки secure_clear_pending — исправлено

OfflineStoreReset.finish удаляет PENDING через commit. Если false уже изменил память, следующий init в том же процессе может не увидеть требование очистки, хотя оно осталось на диске. Нужен тест: false меняет память → повторный init → новые данные → настоящий перезапуск. Последующая группа добавила модель с отдельными памятью/диском, воспроизвела и исправила этот случай: [отчёт](audit-android-reset-marker-2026-09-20.md). Отказ самой первой записи маркера выхода после перезапуска остаётся отдельной открытой границей.

## Другие отдельные границы

- Старая secure-очередь и новая fallback-очередь без выхода: простая замена теряет прежние действия, а простой merge может воскресить уже отправленные. Нужны устойчивые идентификаторы и подтверждения удаления.
- Возврат отдельно удалённого паспорта из недоступного secure и старого журнала воспроизведён и исправлен устойчивой отметкой удаления: [новый отчёт](audit-trip-pass-deletion-2026-09-20.md). Первая неподтверждённая запись и её показ в UI остаются явной границей.
- TripPassStore теперь сериализует init/save/remove/update/clear одним монитором. Это не заменяет проверку всех пользовательских сценариев конкуренции.

Эти пункты пока нельзя считать закрытыми по зелёной сборке или тестам успешного переноса.

- Отказ фонового saveTripPass в BookingScreen теперь отображается с повтором; прицельные проверки прошли, см. [отчёт](audit-booking-offline-save-2026-09-20.md). Вызовы remove и updateBoardingCode на экране активной поездки пока не учитывают результат. Подтверждённый серверный статус не означает, что локальная очистка завершилась.

Проверка настоящего ApiClient с локальным сервером и моделью раздельных памяти/диска воспроизвела возврат паспорта и очереди A после входа B: до исправления упали два из трёх тестов. Теперь перед сохранением новой авторизации оба хранилища повторяют неподтверждённую очистку; при продолжающемся отказе запись нового входа запрещена. После восстановления диска следующий вход проходит. Расширенный профиль — 107/107 и успешная сборка; полный повтор ведётся отдельно. [Сценарий, доказательства и ограничения](audit-login-offline-reset-2026-09-20.md).

Не доказаны показ чужого паспорта обычным экраном, принятие чужих действий сервером и повтор настоящего одноразового кода. Уже существующее на диске смешение токена B и данных A от прежней версии эта защита не распознаёт. Поэтому общий случай всех отказов выхода и всех прежних повреждений не закрыт.

### Предыдущая статическая проверка и её последующее уточнение

Пункт saveTripPass ниже уже воспроизведён и исправлен следующей группой: 93/93 прицельных проверок и успешная сборка, [доказательства](audit-booking-offline-save-2026-09-20.md). Описания updateBoardingCode/remove остаются открытыми; текст исходного разбора сохранён для истории.

Все рабочие вызовы находятся в BookingActiveTripScreen.kt: помощник saveTripPass (около строки 291) отбрасывает Boolean; загрузка BookingScreen (около 364) не сообщает о несохранённом паспорте. При следующем открытии без сети отсутствующая копия не даст показать офлайн-карточку. updateBoardingCode в TripPass.kt тоже отбрасывает результат save; обработчик экрана около 1448–1451 показывает сетевой код и перечитывает старый паспорт. Вызовы remove около 1605, 1640, 2140 продолжают завершение/отмену, не проверяя локальную очистку. Номера указаны для рабочей копии на момент чтения, искать также по именам методов.

Сверка main 527dbb0: места вызовов уже есть, но старые операции хранилища были Unit/apply. Конкретное новое поведение при незавершённом журнале относится к совместной рабочей ветке. UI-воспроизведение этих трёх последствий ещё не запускалось, поэтому это не три новых подтверждённых тестами бага.

Следующая малая группа: Compose v2 + настоящий BookingScreen + локальный HTTP; при отказе очистки источника новая бронь должна остаться видимой, новый паспорт отсутствовать, предупреждение — присутствовать. После восстановления записи повтор должен действительно повторить перенос и сохранить паспорт. Не объявлять серверную бронь неуспешной из-за локального кеша. Для удаления одного предупреждения недостаточно: требуется сохраняемое намерение удаления и повтор после восстановления хранилища. Отдельно вернуть результат updateBoardingCode и убрать синхронную запись с UI-потока. Нет новых правок продукта в рамках этого read-only разбора.

## Следующая группа удаления: уточнение по коду после исправления BookingScreen

Обновление: протокол удаления и запрет нового сохранения done/cancelled уже реализованы, пять начальных RED воспроизведены; профиль 131/131 и 17 этапов эмулятора прошли. [Доказательства](audit-trip-pass-deletion-2026-09-20.md). Ниже сохранён первоначальный план; полный набор восьми предложенных сценариев и все UI-обработчики отказа пока не закрыты.

1. TripPassStore.remove удаляет только ключ из выбранного хранилища. Если secure с pass_7 временно недоступен, выбранный plain пуст; remove может вернуть true, удалив отсутствующий ключ. Когда secure вернётся, pass_7 снова доступен. Подобный выбор одного источника есть и в main (там apply/Unit).
2. Три вызова remove в BookingActiveTripScreen после завершения/отмены игнорируют false при pending migration. Намерение удаления не сохраняется. Кроме диска, ActiveTripScreen держит собственный tripPass в Compose-состоянии — его очистку тоже надо проверить.
3. BookingScreen сохраняет паспорт по одному contactUnlocked. Серверный booking_details вызывает booking_contacts_open (backend/app/visibility.py), который может оставить контакты открытыми для done в окне общения/поиска забытой вещи. boarding-code не запрещает done. Повторное открытие завершённой брони поэтому может сохранить удалённый паспорт заново. Условие есть и в main. Нужен UI-тест, а не только вывод по коду.

Предложение для следующей проверяемой реализации: сначала подтвердить отдельную отметку удаления по bookingId в plain (префикс не pass_), затем стирать доступные копии. Отметка должна перекрывать load/save/update и переживать недоступность secure и повтор старого migration journal. После восстановления удалять только соответствующий ключ, не весь store. Самый простой срок жизни отметки — до общего logout reset с secure_clear_pending. Метаданные надо классифицировать как управляемые собственным протоколом, чтобы общий apply-цикл не удалил их раньше очистки. Это план, не уже реализованная гарантия.

Нужные тесты: недоступный secure → remove → restart; pending journal → remove → recovery; commit удаления меняет память, но не диск; отказ первой записи отметки; поздний save после удаления; сохранность другого паспорта; logout/login B с отложенной очисткой; открытие done с contact_unlocked=true; поздняя confirmed-загрузка после удаления. Если первый commit намерения совсем не записался, отсутствие возврата после смерти процесса гарантировать нельзя — интерфейс должен отличать такой отказ от надёжно отложенной очистки и физического удаления.
