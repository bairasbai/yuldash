- 2026-06-28 — **Ревокация JWT по времени: дробный `iat` НЕ спасает от гонки — часы грубые.** Флаки-тест `test_logout_revokes_token`: `login→/me→logout` укладываются в один тик часов, поэтому `iat == tokens_valid_from` (замер: 99.7% соседних `utcnow()` возвращают ОДИНАКОВОЕ значение, особенно на Windows). Строгое `iat < tokens_valid_from` → токен, выпущенный в тот же тик что logout, НЕ гасится → ассерт 401 падал через раз (предыдущий урок про «дробный iz решает» был неверен — точность iat бессмысленна, если часы дают одно значение дважды). Чистым сравнением не починить: при коллизии `login1==logout==relogin` старый и новый токен по времени неразличимы. Фикс из двух частей: (1) `_token_revoked` → нестрогое `<=` (токен «в момент logout» тоже отозван — это корректно); (2) `issue_tokens` сбрасывает `tokens_valid_from=None` при выдаче (свежий вход = валидная сессия, метка больше не душит новый токен). Тогда детерминированно: token1 `iat<=marker`→отозван; relogin token2 при `marker=None`→жив. Оба login-пути (SMS + Telegram) идут через `issue_tokens` — один шов. Минорный трейд-офф: сброс метки при входе может «воскресить» непротухший access другого устройства после logout-all, но refresh там уже отозван (revoke_all_refresh) → окно = короткий TTL access. Урок: ревокацию по wall-clock проверять под ГРУБЫМИ часами (`utcnow()` много раз подряд) — sub-ms точность в реальности не гарантирована.

- 2026-06-28 — Security-аудит: WebSocket-аутентификация писалась раньше REST и НЕ получила тех же проверок. `verify_token()` для WS только декодировал JWT — игнорировал ревокацию (`tokens_valid_from`/logout) и блокировки. Итог: после logout токен открывал чат до 7 дней; заблокированный слал сообщения мимо `is_blocked`. Плюс `next(get_session())` на каждое сообщение = утечка коннектов (DoS пула). Правило: ЛЮБОЙ новый канал (WS/SSE/cron/webhook), работающий с токеном или ресурсом, обязан переиспользовать те же проверки, что REST `current_user` (существование+ревокация) и те же бизнес-гарды (блок, owner-check). Не дублировать «упрощённый» декод. Сессию БД всегда через `with Session(engine)`, никогда `next(get_session())` вне Depends. Регресс-тест на ревокацию в WS — обязателен.
