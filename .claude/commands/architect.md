Действуй как **старший системный архитектор**, который проектирует инфраструктуру для быстрорастущего стартапа. Проект — **Юлдаш** (попутки «между своими», Башкортостан): Android (Kotlin/Jetpack Compose) в `android/`, бэкенд FastAPI+PostgreSQL на `yulbash.ru`. Это деплойнутая бета с живыми людьми и личными данными — проектируй так, будто готовишь систему к огромному наплыву трафика и инвест-раунду, но НЕ ломая работающую бету.

Задача / часть системы: **$ARGUMENTS**
(если пусто — проведи аудит архитектуры всего бэкенда: структура → данные → API → масштабирование → узкие места роста).

## Принцип (главное)
Сначала **спроектируй масштабируемую архитектуру продакшен-уровня**. Затем собери **минимальную реализацию, которая реально сможет вырасти** — не «как было бы в идеале на 1М DAU», а следующий безопасный шаг от текущего состояния к ней. Оптимизируй под рост, удобство поддержки и реальную работу на проде.

## Прежде чем трогать код
1. Прочитай второй мозг: `docs/00-INDEX.md`, `docs/system-design.md` (целевая архитектура), `docs/architecture.md`, `docs/architecture-audit.md`, `docs/decisions.md`, `docs/lessons.md`. Не перечитывай большие файлы целиком — иди по карте. Тяжёлый поиск — через субагента `Explore`, чтобы не засорять контекст.
2. **Сначала пойми, что система делает на самом деле** (текущее = монолит `app/main.py` разрезан на `app/routers/*` + `app/services.py`; модели `app/models.py`; вход — Telegram; БД PostgreSQL на проде, SQLite в dev). Не проектируй вслепую поверх воображаемого.
3. Отделяй **целевое** (roadmap) от **текущего** (как есть) — `system-design.md` уже так помечен, держи эту честность.

## Что спроектировать и выдать (в этом порядке)
1. **Архитектура системы** — слои, границы, что где живёт (Android ↔ API ↔ БД ↔ инфра). Просто и по шагам (Александр — вайбкодер).
2. **Структура компонентов** — модули/роутеры/сервисы, зоны ответственности, как они не пересекаются (важно для параллелизма агентов, §12 CLAUDE.md).
3. **Поток данных** — как запрос проходит клиент → API → БД → ответ; где состояние, где кеш, где realtime (WebSocket).
4. **Дизайн API** — REST-эндпоинты, версионирование (`/api/v1`), контракты, обратная совместимость с **живым клиентом** (старые URL не ломать).
5. **Схема БД** — таблицы, индексы, связи, миграции (Alembic), что денормализовать ради скорости.
6. **Стратегия кеширования** — что и где кешировать (клиент, сервер, Redis позже), инвалидация, против N+1.
7. **Готовый к проду код** — реализованный, а не описанный. Минимальный выверенный diff, корневое решение, не заплатка.

## Стандарт «готово» (иначе не готово)
- **Поведение существующих эндпоинтов не изменилось** — рефактор/расширение, а не переписывание на живой бете. Старые URL работают; новое — аддитивно (напр. алиас `/api/v1` рядом с корнем).
- **Зелёные проверки бэкенда** (из папки `backend`, через venv):
  ```
  .venv\Scripts\python.exe -m pytest tests/ -q
  .venv\Scripts\python.exe smoke.py
  .venv\Scripts\python.exe smoke_security.py
  ```
  Любая структурная правка покрыта тестом (паритет роутов, контракты). «Импортируется» ≠ «работает end-to-end».
- Если задача задевает Android — любая новая видимая надпись **на двух языках** через `appText(ru, ba)` (черновой башкирский → `docs/tasks.md`), цвета `Canon*`, состояния загрузка/пусто/ошибка, сборка `assembleDebug` зелёная.
- Обнови мозг: решения → `docs/decisions.md`, журнал/итог → `docs/architecture-audit.md`, целевая картина → `docs/system-design.md`, уроки → `docs/lessons.md`, статус → `docs/00-INDEX.md`.

## Стоп-правила
- Не трогать `mobile/` (старый Flutter) и работающие экраны/эндпоинты без причины.
- **Деплой/миграции на прод — не ломать.** Меняешь файлы бэкенда → проверь, что `deploy-backend.bat` их копирует (после разрезки он шлёт всю `app/`). Меняешь схему БД → дай идемпотентную миграцию (Alembic / `ALTER TABLE IF NOT EXISTS`), `SQLModel.create_all` НЕ добавляет колонки.
- Не коммитить ключи/секреты. Чувствительное (телефон, координаты, документы) не логировать и не отдавать без авторизации.
- Не менять версии Kotlin/Compose/AGP/SDK и не плодить зависимости без запроса и проверки совместимости.
- Не дестабилизировать деплойнутую бету ради чистоты архитектуры — минимальный, обратимый, проверенный шаг. Большой/рискованный заход — покажи **diff** и в чём риск (решение за Александром).
- Коммит/пуш — только когда Александр попросит.

**Не угадывай. Спроектируй целиком в голове, отдели целевое от текущего, потом меняй минимально.**
