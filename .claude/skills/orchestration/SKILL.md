# Оркестрация: несколько агентов одновременно

**Зачем:** ускорить — пустить агентов параллельно.
**Главная опасность — конфликты.** Экраны давно разнесены по своим файлам (67 файлов `*Screen*.kt`, ~96 экранов), но общие файлы остались. Если два агента правят один файл разом, последний затирает правки первого (уже ловили вживую: файл «уехал» на 350 строк за минуту, сборка краснеет, эмулятор уходит в ANR).

**Горячие общие файлы** — их трогают почти все задачи, правка только по одному:
- навигация: `enum Screen` в `MainActivity.kt`, ветки экранов — в `YuldashApp.kt` (`when (scr)`) и `AppNavHome.kt` / `AppNavOrders.kt` / `AppNavAdmin.kt` — новый экран задевает их всегда;
- общее ядро `MainActivity.kt` (в нём же `enum Screen`), шкалы `CanonTokens.kt`, тема `ui/theme/`;
- сеть `data/ApiClient.kt` (~8 000 строк);
- экраны-гиганты: `InstantOrderScreen.kt` (такси, ~8 300 строк), `ProfileScreen.kt` (~4 800), `BookingActiveTripScreen.kt` (~4 000).

## 🥇 Золотое правило
**Один файл — один агент в один момент.** Параллелить можно только то, что НЕ пересекается по файлам и общим ресурсам (эмулятор, сборка).

> Это правило продублировано в §11 «Стоп-правила» файла `AGENTS.md` — там оно всегда в контексте, даже если этот скилл не загружен.

## A. Зоны ответственности (lanes)
Делим проект на непересекающиеся зоны. Один агент = одна зона → их файлы не пересекаются → конфликтов нет.

| Зона | Файлы | Можно параллельно? |
|---|---|---|
| 🎨 **Экран** | свой файл экрана (`ProfileScreen.kt`, `MapScreen.kt`…) | да — **один агент на файл экрана** |
| 🧭 **Общий UI** | горячие общие файлы (выше) | **по одному**: кто правит — держит замок |
| 🔌 Backend | `backend/` | да |
| 🖼 Ресурсы | `android/.../res/`, иконки, ассеты | да |
| 🧠 Мозг | `docs/` | да, но **один писатель на файл** |
| ⚙️ Конфиг/сборка | `*.gradle.kts`, `AndroidManifest.xml` | **ни с кем** (влияет на всех). Файлы с ключами агенты не трогают вовсе (§11) |

→ Разные экраны — разным агентам. Если два агента добавляют новые экраны, оба полезут в `enum Screen`/`when` — делайте по очереди или пусть навигацию допишет лид в конце. Backend / ресурсы / доки можно вести параллельно с UI — это разные файлы.

## B. Общие ресурсы — строго по очереди
- **Эмулятор один.** `install` / `launch` / `screencap` / `uiautomator` / тапы делает **только один агент** — тот, кому его отдали («эмулятор твой»). Два агента на одном эмуляторе = ANR и мусорные касания.
- **Сборка одна на компьютер.** В одном чекауте две сборки пишут в общий `app/build/` и ломают друг друга; в разных worktree мешают уже памятью (16 ГБ на Gradle, Kotlin-демон, тесты, Studio и эмулятор). Собирает один агент за раз.
- **Android Studio тоже участник очереди.** Открытая Студия на той же папке держит файлы сборки: прогон тестов падает с `FileSystemException: файл занят другим процессом`. Либо закрыть Студию, либо собирать с `-x bundleDebugClassesToRuntimeJar`.

## C. Правильная изоляция — git worktree
По-настоящему без конфликтов — когда у каждого агента своя копия репозитория (worktree): правки не пересекаются, в конце сводим (merge).
- **Предусловие:** проект — git-репозиторий. ✓ Сделано: ветка `main`, первый коммит, `.gitignore` без секретов (`local.properties`, `*.jks`, backend `.env`/`.db`/`.venv`) и без QA-артефактов. Worktree-изоляция доступна.
- Внутри одной сессии Claude Code: запускай субагентов с изоляцией `worktree` (инструменты Agent / Workflow). Каждый получает свою копию, лид сводит результат. Это **родной механизм Claude Code — предпочитай его «двум окнам вручную».**
- **Осторожно с деплой-скриптами.** `backend/deploy-backend.bat` копирует файлы из основного чекаута `C:\Users\Bayra\Yuldash\backend`, а НЕ из worktree. Работая в worktree, сначала слей ветку в основной чекаут — иначе выкатишь старый код. Слияние в `main` и выкладка — только после «да» Александра (§8 `AGENTS.md`).

## D. Если worktree пока нет (две сессии руками) — протокол «замок»
Минимум, чтобы не затирать:
1. Действующие замки — в одном файле на весь компьютер `%LOCALAPPDATA%\yuldash\locks.md` (вне git: виден из всех worktree, не попадает в коммиты; порядок — `docs/locks.md`). Старые разделы «🔒 Замки» в `docs/tasks.md` — история.
2. Перед работой агент пишет туда строку-замок: `🔒 ProfileScreen.kt — занят, <кто>, <время>`.
3. Другой агент видит замок → этот файл НЕ трогает, берёт свободную зону.
4. Закончил → удаляет свою строку из файла замков и отчитывается лиду.
5. **Перед стартом всегда:** прочитать файл замков (`%LOCALAPPDATA%\yuldash\locks.md`) и перегрепнуть свой файл — если номера строк «уезжают», кто-то пишет параллельно, остановись.

## E. Роли
- **Лид (оркестратор):** режет задачу на непересекающиеся куски, раздаёт зоны, следит за замками, в конце сводит и собирает **один раз**. Сам в общие файлы не лезет, пока заняты воркеры.
- **Воркеры:** строго своя зона, за границы не выходят, эмулятор не трогают без права, отчитываются лиду.
- **Модели (Claude 5.5, таблица — `CLAUDE.md`):** лид — Opus 5.5; воркеры по готовому плану — Sonnet 5.5; массовые однотипные куски — Haiku 5.5; приёмка — отдельный свежий Opus 5.5 (⭐ п.8 `AGENTS.md`, `/gotovo` шаг 4); Fable 5.1 — только по команде Александра.

## G. ruflo (MCP-оркестрация) — ВЫКЛЮЧЕН, и это правильно
- MCP-сервер `ruflo` (`mcp__ruflo__*`) — тяжёлый фреймворк координации/консенсуса/общей памяти между агентами.
- **Отключён 2026-08-03** при уборке: за 30 дней ни одного обращения. Понадобится — включается обратно через `/mcp enable ruflo`.
- **Когда вообще брать ruflo:** только если задача правда требует роя с консенсусом/общей памятью между многими агентами. Иначе — лишняя сложность.
- **По умолчанию — НАТИВНЫЕ инструменты Claude Code:** `Agent` (сабагент, поддерживает `isolation: "worktree"`) и `Workflow` (детерминированный фан-аут). Они реально правят файлы и собирают. ruflo — слой поверх; для обычной работы по Юлдашу не нужен.
- **ruflo НЕ отменяет золотое правило.** Рой из 10 агентов в одном файле (хоть `InstantOrderScreen.kt`) всё равно затирает сам себя. Топология роя не меняет физику: один файл — один писатель.

## H. Как реально ускорить разработку (приоритет сверху вниз)
1. **Разные экраны → разные агенты.** Это уже работает: экраны в своих файлах. Узкие места — горячие общие файлы и гиганты: правки в них по одному, гиганты резать дальше (F).
2. Параллелить только непересекающиеся зоны (экран ↔ экран ↔ `backend/` ↔ `docs/` ↔ `res/`), каждую своему сабагенту с `isolation: "worktree"`.
3. Лид сводит (merge) и собирает/тестит **один раз** в конце — сборка и эмулятор общие, их нельзя делить.
4. Тяжёлый ресёрч/аудит (не правка файлов) — в фоновые сабагенты, чтобы основной контекст был чистым.
